让「改坏了」在合并前就红

代码是 AI 写的，所以门禁不能靠自觉

研发流程 CI 门禁 测试分层 15 项审计 资源分发 AI 协作

WORKFLOW

一条改动的完整路径

从 issue 到 master，中间只有一道门，但那道门必须绿

01

先有 issue

要解决什么、验收标准是什么，写在 GitHub issue 里。改完 PR 描述带上关联 issue 号；如果这次改动真的关闭了它，就写 Closes #n。

写清「关联」和「关闭」的区别——项目里曾经有一批已经合并的 issue 因为只写了「关联」，在列表里挂了很久。

02

分支名带类型和 issue 号

fix/670-ai-drop-dead-target、feat/722-soak-point-server。 从 master 拉出，一个分支只做一件事；跨端的改动也放同一个分支，避免「服务端进了、客户端没进」的中间态。

03

本地先跑定向回归

make test-changed 只跑这次改动碰到的模块对应的测试 —— 比全量快一个数量级，够用来判断「有没有当场改坏」。

make checkmake test-changed
04

PR 触发全套 CI

静态半边 + 38 套 e2e 分 4 片并行。只跑一次：PR 的 CI 跑的是 refs/pull/N/merge（master + 本次改动），squash 之后 master 的树与它完全相同，再跑一遍测不到新东西。

所以直接 push master 是不受门禁保护的 —— 规则是「别那么干」。

05

绿了再 squash

合并方式固定 squash：master 上一条改动一个提交，回滚就是 revert 一条。合并后不再跑 CI，直接进发布流程。

为什么分支模型这么轻？没有 develop、没有 release 分支、不做 code review 轮次 —— 因为这里的「另一位开发者」是 AI，评审的价值低于自动化检查。省下的流程成本全部投到门禁上。

分片清单不写在 CI 文件里

套件清单派生自 server/package.json 的 test:e2e* 脚本，新增一套 e2e 自动进 CI。 之前是手写清单，漏了三套（管理端邮件、邮件过期、UI 特效），谁都没发现 —— 漏跑不会红，只会让「以为测过了」变成事实。

哪些路径不触发 CI

纯文档、记忆、设计稿、官网改动走 paths-ignore 直接不跑： 改 .md 不可能让代码变坏，让它在队列里排十分钟没有意义。

为什么客户端单测不上 CI

有几套客户端测试断言 assets/resources/ 下的真实素材（图集、帧序列、怪物帧 .meta）。 素材体积大、有意不入库，干净 clone 上这些断言不可能成立。 所以客户端单测是本地专属；CI 上只跑客户端类型检查（Cocos 的 cc.d.ts 已 vendoring 进仓库，不需要编辑器）。

门禁清单只有一份。CI 文件只调三个 make 目标（ci-static / server-install-ci / server-e2e-shard）， 顺序和内容写在 Makefile 里 —— 本机 make ci 跑的是同一套串行版，两边不会漂。

TESTING

五层，各管一段

越往下越慢，越往下越接近真实运行

层跑什么规模拦得住什么
类型检查 make client-check · admin build · server build 三端全量 契约改了没跟着改、字段名拼错
静态审计 make audit（15 个脚本） 全仓扫描 越界引用、手改生成物、硬编码、路径不存在
客户端单测 make client-test（本地专属） 纯函数为主 背包整理、伤害公式、坐标换算
服务端 e2e make server-verify 29 套，每套起真服务 + 真库 接口行为、权限、并发、存档一致性
人工验收 跑起来看 — 动画、位置、手感、观感

e2e 不是 mock 出来的：每套都真的 spawn 一个服务端进程、真的建一个临时 SQLite 库、真的发 HTTP / WS 请求。 代价是慢（所以分片），收益是「跑过就是真的跑过」。

测试锁什么

  • 字段格式：类型、长度、取值范围
  • 行为：调这个接口会发生什么
  • 权限：谁能调、谁不能
  • 幂等：同一个请求发两次

测试不锁什么

  • 具体数值：运营随时会改
  • 动画帧率、尺寸、坐标、颜色
  • 界面元素的位置与层级
  • 文案措辞
「显示效果不写断言」是一条明确的纪律。这类断言只会因为正常调配置而红， 真出错（错位、太小、没播）反而抓不到。可留的只有三样：素材存在性（缺文件 = 静默不播）、 代码执行顺序（帧装载完再藏站立帧）、结构接线（按钮有没有绑事件）。

AUDITS

15 个守点

每一条都对应一次真实踩过的坑

契约与权威

7 项
  • 生成物一致性 —— 接口文件必须是生成的，手改或忘生成都红
  • 接口地址硬编码 —— 地址与请求各有唯一出口
  • 快照契约 —— 客户端「要什么」与「发什么」是同一张清单，缺段抛错而非静默跳过
  • 数据权威 —— 代码里不允许存在第二份数据
  • 世界权威 —— 怪物生成与掉落只认服务端
  • 角色存档边界 —— 服务端独占字段，客户端推整份存档也改不动
  • 服务端内部边界 —— 跨模块 import 只走白名单边

口径与一致性

5 项
  • 地图原点 —— 世界坐标与 TMX 坐标只差一次 y 取反，错一处 NPC 全体偏半张图
  • 资源引用 —— 代码里写的每个资源路径都要在磁盘上真存在
  • 装备对齐清单 —— 管理端派生的 JSON 与客户端配置一致
  • 配置外泄 —— 位置、颜色、时长、概率、文案不许写进逻辑
  • 部署接线 —— nginx 上游名 = compose 服务名；DB_PATH 必须落在卷里

表现与构建

3 项
  • UI 点击穿透 —— touch 通道与 mouse 通道的命中归属不能互相挡
  • 管理端界面一致性 —— 页头、弹窗、卡片、字段标签不许各写一份
  • 迭代器展开 —— babel loose 下 [...map.values()] 会被吞掉
为什么用静态扫描而不是写更多测试？这些问题的共同点是「能出图、能跑、不报错」—— 地图偏半张、资源静默空白、生成物被手改，全都不会让任何测试变红。 静态扫描比测试便宜，而且能一次性覆盖全仓，适合守这种「约定类」的错误。

ASSETS

素材不进版本库，但要能锁住

清单 + Release 分卷，多人多机保持一致

client/assets/resources/ 体积大，有意不进 Git。但「不进库」不等于「不管」—— 仓库里提交一份 resources.manifest.json，记录每个文件的 sha1 + 大小， 连 .meta 一起记（Cocos 的 uuid 绑在 meta 上，漏了 meta 等于素材全断链）。

make resources-verify # 拉代码后先跑：本地资源 vs 清单 make resources-download VERSION=x # 不一致或新机器：下载分卷、解压、自动校验 # 改完素材的人发布： make resources-manifest → make resources-pack → make resources-upload

约定是先合并带新清单的 PR，再上传 Release。反过来的话，别人拉到的清单指向一个还不存在的包。

AI COLLABORATION

AI 写代码，人只提需求与验收

这是前提，也是所有工程约束的由来

仓库里每一行代码都是 AI 写的。人做的事只有三件：提需求、看效果、说不。 这个前提直接决定了两件事 —— 门禁必须自动化，知识必须写下来。

知识沉淀跟着仓库走

项目里有三处长期记忆，全部随代码提交：

  • .workbuddy/skills/ —— 分端技能：服务端架构约定、管理端接口规范、客户端引擎坑、部署流程、地图制作。新会话读一遍就知道边界在哪。
  • .workbuddy/memory/ —— 按日的工作日志与长期索引。记的是「为什么这么做」和「上次这么改踩了什么」，不是「改了什么文件」。
  • 各端 README.md / FAQ.md —— 面向人的说明，也是 AI 每次改动的输入。

这三处的分工是刻意的：技能写「怎么做」，日志写「为什么」，README 写「是什么」。 混在一起会变成没人读的长文档。

几条被写死的纪律

R-01

测试锁字段格式与行为，不锁数值

为什么

运营随时在管理端调数值。断言里写死「攻击力 = 137」，下一次调平衡就红一片。

改成什么

断言「是正整数」「在范围内」「改了之后读回来一致」。数值本身交给运营。

代价

数值算错（比如倍率接反）测不出来，得靠人眼看。

R-02

显示效果一律人眼看，不写断言

为什么

动画位置、尺寸、帧率、层级全是会正常变化的调参项。断言它们等于给自己埋雷。

保留什么

只剩素材存在性、代码执行顺序、结构接线。曾据此删掉 4 个纯几何测试文件。

代价

错位、太小、没播这类问题只能靠截图和实机发现，回归靠人。

R-03

假绿比漏检更可怕

为什么

一条永远通过的断言，会让所有人误以为这块有人看着。比没测更危险。

怎么做

审计断言扫到的模块数；错误必须精确匹配文案；缓存 TTL 压到 0 让测试真的走链路。

代价

测试更脆，改动时常要一起改断言；但每次红都指向真问题。

R-04

新增一张表要登记四处

为什么

配置表要进快照、进 API 文档、进边界白名单、进快照契约。漏一处不会报错，只会「管理端看不到新行」。

怎么做

清单写进技能文档，加表时照着勾；漏了由审计脚本红。

代价

加表比「只写 DDL」麻烦，但省掉了线上静默少数据的排查。

一句话总结这套工程管理：不假设执行者会记得任何事。 能写成脚本的就写成脚本，写不成脚本的就写进技能文档，两者都做不到的才留给人眼。
