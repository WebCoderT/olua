ARCHITECTURE · 架构与数据流

数据是怎么走的

一次攻击、一件装备、一条配置改动 —— 各自的完整路径

拓扑 五条主链路 契约管线 数据分层 双进程与库

TOPOLOGY

四个运行单元

两个前端、两个服务端进程、一个数据库文件

CLIENT

客户端 · Cocos Creator 3.8.7

登录、选角、战斗、背包、商城、社交。只负责输入与表现：本地存档仅作缓存，任何数值以服务端回包为准。

assets/configs/ 收全部可调项（布局、配色、时长、资源路径），逻辑里不写死数值。

▲ HTTP / WebSocket ▼
AUTH+SAVE

存档进程 · :3100

账号与角色、管理端接口、邮件与公告、排行榜、备份。唯一手写接口的地方，Swagger 文档从这里生成。

写入：accounts / roles / role_mails / audit_logs …

REALTIME

实时进程 · :3101

WS 通道、取票接口、世界权威（怪物实例）、伤害结算。与存档进程同一个镜像、同一份代码，只装实时那一侧的依赖图。

写入：world_monsters（5 秒批量）与结算血量；不挂 Swagger，避免出现第二份契约源。

ADMIN

管理端 · React 19 + Vite

50 个页面覆盖账号、角色、地图、刷怪区、NPC、碰撞盒、掉落表、装备体系、特效、权限与操作日志。

接口文件由服务端生成，不手写任何一个请求类型。

▲ ▼ prepared statements
STORAGE

SQLite 单库 · WAL

59 张表，两个进程共享同一个文件。各写各的表（存档进程写账号角色，实时进程写世界怪物），低频并发交给 WAL + busy_timeout。

没有 Postgres、没有 Redis、没有消息队列 —— 一个文件就是全部状态，拷走即可迁移。

为什么只有两个进程？战斗需要每秒多次广播，而登录 / 后台 / 邮件是低频长事务；混在一起会让一次后台导出卡住整张地图。 拆开之后，实时进程只装它需要的模块，挂机也不影响后台；代价是两个进程必须约定「谁写哪些表」，写重了 WAL 也救不回来。

DATA FLOW

五条主链路

从点下登录，到一件装备落进背包

① 登录与进服

01

口令校验在服务端

账号与密码发到存档进程，scrypt 加盐摘要比对，通过后签发 7 天有效的 JWT。

同一用户名与来源 IP 两个维度各自限流，超限直接拒绝。

POST /api/auth/login→ JWT
02

角色列表与建号

角色数据全在服务端，每账号最多 3 个。第一个注册的管理员自动成为超管（仅在管理端侧）。

GET /api/rolesPOST /api/roles
03

取票后建 WS 连接

先向实时进程要一张短期票，再用票建 WebSocket。客户端零改动：取票与建连同属 /api/realtime* 前缀，nginx 按路径反代。

一账号只保留一条实时连接，顶号即踢。

POST /api/realtime/ticketWS upgrade

② 进图与世界加载

01

地图文件只是「一张图」

TMX 里只有瓦片与图层，没有对象组。刷怪区、NPC、复活点、碰撞盒全部在管理端配置、由服务端下发。

这样换一张底图不需要重新导出一堆对象坐标，也不会出现「图和碰撞对不上」。

TMX：ground + wall无 objectgroup
02

服务端下发场景配置

进图时拿到该图的复活点、矩形刷怪区、NPC 点位、碰撞盒。客户端只登记，不自己刷怪。

map_spawn_areasmap_npcsmap_collisions
03

世界权威生成怪物实例

怪物实例由服务端持有并跨账号共享，状态落盘、跨重启恢复。客户端进图只做一件事：把服务端告诉它的怪物摆到位置上。

所以两个人看到的同一只怪，血量和位置永远一致。

world_monsters5s 批量落盘

③ 一次攻击的结算

01

客户端先演，不等回包

点怪立即播挥砍动画，手感不依赖网络。同时发一条 intent：攻击对象 + 本次操作的 castId。

WS → attack{castId, targetId}
02

实时进程按共享快照算伤害

攻防区间、技能倍率、暴击、状态加成全部在服务端算。同一条 castId重复到达只结算一次（幂等），掉线重连也不会打出双倍伤害。

技能还要先过冷却、耗蓝、距离三道校验 —— 校验不过直接丢弃，不扣冷却。

config snapshotcastId 幂等
03

广播命中帧

结果回给操作者，同时广播给同图其他玩家：伤害数字、目标剩余血量、出手动作。主播和观众看到的是同一条帧。

客户端收到后只做一件事：把数字飘出来。

hit{damage, hpLeft, castId}

④ 掉落到入包

01

抽奖发生在服务端

击杀结算后，按这只怪自己那份掉落表（每只怪一份，条目逐条配权重 / 概率 / 数量）抽。抽到什么，在发出广播之前就已经定好。

monster_dropsdrop_tables
02

直接入包，不经过客户端

物品写进角色背包后才广播「拾取帧」。客户端拿到的是结果，不是「你可以捡了」—— 改客户端内存改不出装备。

picked{itemId, count}
03

客户端只负责好看

同心环散落、品质光柱（普通 → 超神五档）、拾取吸附动画，全是纯表现。光柱的摆位、缩放、时长、开关还能在管理端「特效管理」里调。

背包开着时同时刷新背包 —— 这一条曾经漏过，拾到东西要关掉重开才看得见。

light_1…light_6ui_effects

⑤ 管理端改一条数据

01

写库，带乐观锁

管理端 PATCH 某条配置，带上读到的 revision。版本对不上直接 409，不会「最后写入者覆盖」。

写操作自动留痕到 audit_logs，口令类字段落库前打码。

PATCH /admin/*revision → 409
02

快照段重建

库表是权威，服务端把它拼成一份 JSON 快照（怪物、装备、地图、掉落、特效…）。这是客户端唯一的数据来源。

config snapshot整表重建 → 派生 Map 重建
03

两端各自生效

客户端下次拉快照生效；实时进程按固定间隔（默认 10 秒）重装配置 —— 否则会出现「管理端改完，只有存档进程知道」，表现为战斗力来回抖。

REALTIME_CONFIG_REFRESH_MS
五条链路是同一条原则的不同侧面：客户端能算的只有「怎么画」，不能算「是什么结果」。 位置、血量、伤害、掉落、能不能进图 —— 全在服务端定，客户端拿到的是既成事实。

CONTRACT

接口契约单向生成

只有服务端手写，另外两端是产物

server/src 控制器 + DTO + 装饰器
唯一手写处
→
openapi.json swagger:emit
提交进仓库
→
gen-api.cjs 按模型生成
路径 / 类型 / 调用
→
client · Api*.ts 路径 / 模型 / 客户端
＋
admin · api/*.ts routes / models / endpoints

这不是为了少写几行代码，而是为了让忘记改另一边变成编译错误。 服务端把一个字段从 level 改成 roleLevel，跑一遍 npm run gen:api， 两端 tsc 立刻报错——而不是等到线上某天冒出 undefined。

配套的 audit-api-generated.cjs 盯着生成物：手改了、或者忘了重新生成，门禁直接红。 所以「生成物禁止手改」不是一句约定，是一条会拦住你的检查。

做对了会怎样

  • 改一个 DTO，两端签名同时变
  • 接口不兼容 = 本地 tsc 就红
  • 新增接口自动出现在两端
  • Swagger 页面永远和代码同步

手写会怎样

  • 三份接口定义慢慢漂移
  • 字段名不一致只能靠运行时发现
  • 改完忘了通知另一边
  • 文档写着上一版的参数

DATA LAYERS

数据分四层，每层只有一个来源

同一份数值不允许在两处都能改

L1 权威

SQLite 库表 · 59 张

运营在管理端改的所有东西都在这里。运行时的每一次读都走库或库生成的快照，代码里没有任何数值副本。

L2 出厂

config-sync.sql

出厂快照，只在空库上灌一次。判据是 marker 表没有记录且哨兵表为空 —— 两条缺一不可，存量库升级绝不整表替换（那会把运营改过的东西冲掉，且毫无提示）。

所以新机器 make dev 起来就是同一套数据。

L3 下发

运行时快照段

服务端把库表拼成 JSON 下发给客户端。整表重建之后，所有派生 Map 必须跟着重建 —— 漏一处就会读到旧值。

L4 客户端

assets/configs

只放纯表现参数：布局、配色、时长、资源路径、帧率。所有业务数值初始为 0 / 空 / false，没有本地兜底。

没有兜底听起来危险，实际相反：兜底会把「服务端没下发」变成「看起来正常但数值是旧的」，这种 bug 比白屏难查十倍。

唯一来源的代价是启动顺序变严格了。客户端必须等快照到了才能显示真实数值（加载期显示 0/空）， 服务端必须先建表再灌快照、先灌快照再补标量行。顺序错了不会崩，只会静默少一块数据 —— 所以每一步都有对应的守卫。

PROCESSES

两个进程，一个数据库文件

没有中间件，靠约定划清写入边界

存档进程 :3100
账号、角色、背包、邮件、公告、排行榜、管理端全部接口、备份。低频、事务长、要求强一致。
实时进程 :3101
WS 通道、取票、世界怪物、伤害结算。高频、短事务、可容忍 5 秒落盘延迟。
共享方式
同一个 SQLite 文件，WAL 模式 + busy_timeout。各写各的表，跨进程不写同一行。
为什么不用 Postgres
单人 / 小团队运维，一个文件拷走就能迁移、备份就是 cp。代价是并发上限低，所以必须靠「不写同一行」来绕开竞争。
重启恢复
怪物实例定期落盘，重启后按最后状态重建；玩家数据每次变更即落库，不依赖内存。
反向代理
nginx 按 /api/realtime* 前缀把实时流量分给 3101，其余进 3100。客户端只认一个域名。
这套结构最适合「一台机器、一个人维护」。要横向扩到多台时，WAL 单文件会成为瓶颈 —— 那时候该换的是存储而不是打补丁。项目在这一点上不做提前抽象。
