  6. **交付缺口**：无 Dockerfile / docker-compose、无备份脚本、日志非结构化。

## 14:27 新增根 `Makefile`（三端开发命令收在一处）

**目标**：把散在三个子工程里的命令收敛成 `make <目标>`，并在文档里做成索引。

**关键设计**（都踩过点才发现必须这么写）：
- `RUN_ENV ?= env -u NODE_OPTIONS`，`NODE := $(RUN_ENV) node` / `NPM := $(RUN_ENV) npm` —— 本机注入的 `NODE_OPTIONS` 垫片会让服务端**静默起不来**（e2e = 「等待服务启动超时」），统一在 Makefile 里清掉，开发者就再也不用记这个前缀。**普通终端下 `env -u` 对未设置的变量是无害 no-op**，所以可以无条件带上；想用原始环境 `make RUN_ENV= <目标>`（命令行的 `?=` 覆盖）。
- `.NOTPARALLEL:` —— e2e 真实起服务、真实占端口，`make -j verify` 只会互相打架。
- `dev` 目标**不能用 `kill 0` 收尾**：第一次这么写，测试时把调用方所在的进程组一起打死了（`kill 0` 只在该目标独占进程组时才安全）。改成 `set -m`（每个后台任务自成进程组）+ `trap 'kill -TERM -$srv -$adm'`，只杀自己的两棵进程树。实测：模拟 Ctrl-C 后**服务端与自己的 vite 都退了，别人的 vite 不动**。
- `help` 用 `## ` 注释自动生成（`grep -hE '^[a-zA-Z0-9_-]+:.*## ' $(MAKEFILE_LIST)` + awk 定宽）；补 `info` 目标打印工具链与关键路径（`node/npm/tsc` 版本、四目录是否存在、`.env` 与 `node_modules` 是否就绪）。
- 目标命名 `端-动作`：`client-check|test|test-one|gen-monster|gen-drops|clean-frames[-apply]|open`、`server-dev|build|start|e2e|e2e-roles|e2e-guard|verify`、`admin-dev|build|typecheck|preview`、跨端 `gen-api` `audit[-generated|-hardcode|-config|-click]`；组合门禁 `check`（静态）/ `test`（全部测试）/ `verify`（check + 三端构建 + 全部测试）。
- `client-test` 逐套跑、逐套打 PASS/FAIL 并汇总「N 通过 / M 失败」，失败日志落 `/tmp/olua-*.log`；`client-test-one T=test-bag-tidy` 单跑，参数错就列出全部可选脚本。

## 后台补全第 1 块：账号封禁闭环（#173 → b689b0f，24 文件 +844/-50）

用户拍板「六块全做」（除「运营触达」需客户端配合），按「逐块串行落地、每块独立提交」推进。

**关键设计**：
- 状态机**仍只有两态**（`active`/`disabled`），「临时封禁」用 `ban_until`（毫秒）表达；判据是纯函数 `common/utils/ban.util.isBanExpired/isBanned`。于是**「到期自动解封」是判定结果而不是某个动作** —— 登录与守卫每次请求按时间算，定时器（`BanSchedulerService`，`setInterval(60s)` + `timer.unref()`）只负责把库里的 status 扫回 `active`，两者互不依赖，服务端停过一段时间再起来也不会漏掉解封；e2e 直接调 `sweep(now)` 注入时间，不必等一分钟。
- **`ban_until = null` 的两种含义必须靠 status 区分**：`active` = 从没封过，`disabled` = 永久封禁。所以判据只能是「disabled **且** 有结束时间 **且** 已到期」三者同时成立 —— 只看时间会把正常账号误判成「已解封」。e2e 钉了一条 `isBanExpired({status:"active", ban_until: now-1}) === false`。
- 到期后库里 status 可能仍是 `disabled`（定时器最多晚一分钟）：守卫**读判不放行、不回写库**（每次请求写一次太重），回写放在登录（低频）与定时器里；管理端用与后端同源的 `banStateOf()` 显示三态（红「封禁中·剩余 X」/ 琥珀「封禁已到期」/ 绿「正常」），否则会把一个能玩的号显示成封着。
- 系统自动解封**有意不写操作日志**：`audit_logs` 记「谁改了什么」，actor 为空只会让「按操作人筛」多出一堆查不到人的记录。
- 封禁时长上限一年 `BAN_DURATION_MAX_HOURS = 24*365`：再长在运营上等价于永久，限制住可避免「填错一个数字 → 封到 275760 年」这种看不出错的错。
- 玩家登录被拒时**只能**从提示里知道为什么（那时拿不到账号详情），所以 `describeBan` 把原因、是否永久、还剩多久都说清（`humanizeDuration` 出「2 天 2 小时」；已有「天」就不报分钟）。
- 管理端 `BanDialog`：原因必填（空则拦下）+ 时长快选（默认 24 小时，**永久要显式选**）+ 自定义小时数。

## 后台补全第 2 块：运营看板（#174 → 3609dce，18 文件 +1365/-53）

**关键设计**：
- **按天聚合必须 `date(created_at/1000, 'unixepoch', 'localtime')`**：直接对毫秒整除得到的是 **UTC 天**，东八区会把「早上 8 点前创建的角色」算进前一天，曲线整体左移。

## #178 交付运维（拆成四块各自提交）

### ① 生产加固（f089de5）
原来「没配 `ADMIN_REGISTER_CODE` = 管理端开放注册」+「第一个注册的自动是超管」= **公网裸奔**。改成：配了注册码以注册码为准；没配必须 `ADMIN_REGISTER_OPEN=true`（默认 false）。玩家侧对称加 `PLAYER_REGISTER_OPEN`（默认 true，保持旧行为）。两条配置组合的判定抽成私有方法 `assertRegistrationAllowed`，且**先于账号查重跑**。新业务码：`10006` 玩家注册关闭 / `30012` 管理端注册关闭（与「注册码错误」30004 分开）。没有任何管理员且注册关闭时，`onModuleInit` 在启动日志里给出补救办法。

### ② 备份 / 恢复 + 优雅关闭（813150a）
**备份不能 `cp`**：库是 WAL 模式，最新提交在 `-wal` 里，`cp` 主文件会静默丢最后几次写入。改用 `VACUUM INTO`（SQLite 自己产出一致性快照，**不需停服、不需带 `-wal`/`-shm`**）并当场校验产出物。

恢复是五步：①校验备份 ②有 `-wal`/`-shm` 默认拒绝（`--force` 越过）③现库改名留档 `.before-restore-<时间戳>` ④**先清旧 `-wal`/`-shm`**（留着会按它回放 → 损坏新库）⑤写 `.restoring` 再同目录 `rename` 原子到位。

**踩的两个坑（都值得记）**：
1. 备份 e2e 一开始 7 条失败，报「数据文件旁边还有 `-wal`/`-shm`」 —— 根因是服务端**没有优雅关闭**，SIGTERM 后 SQLite 不 checkpoint。修法：`app.enableShutdownHooks()` + `DatabaseService.onApplicationShutdown`（`PRAGMA wal_checkpoint(TRUNCATE)` 后 `close()`）。
2. 测试自己的**只读** `DatabaseSync` 连接会建出空 `-wal`/`-shm` 却删不掉 → 污染「服务是否在跑」的信号。修法：`inspect()` 只擦掉**自己带出来的空文件**，非空的一律不碰。

### ③ Docker 一键起（0d759ef）
`server/Dockerfile`（node:22-alpine 两阶段、非 root）+ `admin/Dockerfile`（Vite build → nginx）+ `nginx.conf` SPA + `docker-compose.yml` 具名卷。三个要点：
- **管理端与接口同源**：nginx `/api/` 反代 → 浏览器不发跨域 → 服务端不必配 `CORS_ORIGINS`；但反代后必须 `TRUST_PROXY=true`，否则 `req.ip` 全是 nginx 容器地址，**登录限流会把所有人当同一人锁死**。
- **nginx 上游用变量 + Docker 内置 DNS**（`resolver 127.0.0.11; set $olua_api http://server:3100;`）：写死上游名时 server 未就绪会让 nginx 直接 `host not found in upstream` 启动失败。
- **`VITE_API_BASE_URL` 是构建期内联**，换地址要重新构建，不是改运行时环境变量。
- 本机没有 Docker → 守卫只能静态做：`tools/audit-deploy.cjs` 用锚点匹配审计跨文件接线（服务名↔nginx 上游、上游端口↔EXPOSE、`DB_PATH`⊂挂载点、具名卷已声明、反代前缀↔`API_PREFIX`↔`VITE_API_BASE_URL`、COPY 源存在、`.dockerignore` 排除 `.env`/`node_modules`、compose `${VAR}` 都有默认值）。用 PyYAML 手工确认 compose 语法。

### ④ CI（2caf4e7）
`.github/workflows/ci.yml` **只调 `make ci`** —— 门禁清单写在 Makefile 里，本机跑同一条即可复现，不会出现「CI 跑了什么只有 workflow 知道」的漂移。CI = 按锁文件 `npm ci` + 5 审计 + 服务端编译 + 管理端构建 + 四套 e2e。

**客户端在 CI 里跑不了，两条独立原因（都要记住）**：
1. `client-check` 要 `client/temp/declarations/cc.d.ts` —— 编辑器产物，内容是**指向本机引擎绝对路径**的 `<reference>`，而 `client/temp/` 被 gitignore；
2. 24 套客户端单测里**有 10 套直接断言 `assets/resources/` 下的真实素材**（图集 / 帧序列 / 怪物帧 `.meta`），而素材体积大、**有意不入库** → 干净 clone 上这些断言不可能成立。

第 1 条我一度想「给 `cc` 加个仓库内 any 兜底 + 严格性跟着引擎声明走」并实测可行（模拟无引擎声明时 24/24 通过），但第 2 条才是决定性的 —— 既然 CI 根本不跑客户端单测，那套宽松化就是**死代码**，按纪律回退了。教训：**先验证目标能不能达成，再决定要不要造配套机制**。

**issue↔分支/提交联动机制（记准，写代码时要用）**：
- `gh issue develop <N> --checkout` = 唯一能建**结构性关联**分支的方式（会出现在 issue 侧栏 Development 区）；纯 git 建分支做不到。
- commit message / PR 正文里的 `closes #N` / `fixes #N` → **PR 合入默认分支时**才自动关单；推到 feature 分支上不触发。正文里写 `#N` 会自动生成双向引用。

**⚠️ 新发现的坑：命令会被重复执行一次**。做「零残留分支验证」时，用 `BR="chore/gh-smoke-$(date +%H%M%S)"` 建→推→删，结果磁盘上多出两个我**没建过**的残留分支 `chore/gh-smoke-test` 与 `chore/gh-smoke-165140`（都是 master 同点、无独有提交、远端不存在）。回推时间戳才明白：命令被跑了两次，第一次中途被回收，只留下「建了本地分支」这半截状态（第二次再用同名就报 `already exists`）。**与既有那条「工具输出会串扰」是同一类风险的延伸**：不止「报了成功却没落盘」，还会「执行两遍」。→ 写一次性验证时**用带时间戳的名字**、并**收尾核对是否有同族残留**；判断分支是否可删先看 `git log master..<b>` 是否为空、远端是否无对应分支。

### 闭环的六个动作（实测可用）
1. `gh issue create --body-file` 建 issue（**#2**），正文写清范围 + 排除项 + 验收清单；
2. **`gh issue develop 2 --base master --name feat/2-announcement-system --checkout`** —— 这是**唯一**能建「结构性关联分支」的方式（`gh issue develop 2 --list` 认得它；纯 `git branch` 建的名字再像也没有这层关联），顺带把分支推上远端；
3. 在分支上开发 → `make verify` 全绿 → **一个功能一个提交**（`e5ddcea`，32 文件）+2783/-108；
4. `gh pr create --body-file`（正文里写 **`Closes #2`**）→ PR **#3**；
5. `gh pr checks 3 --watch` 盯 CI（**47 秒 pass**）；
6. `gh pr merge 3 --squash --delete-branch --subject ... --body "…Closes #2"` 合并。

**自动关单确认生效**：issue #2 时间线依次是 `labeled → referenced（推分支）→ connected + cross-referenced（开 PR）→ closed（合并后 2 秒）`，`stateReason=COMPLETED`。
**收尾**：远端分支 `--delete-branch` **在「已合并」判定下被跳过**了（gh 打印 `already merged`），要手动 `git push origin --delete <branch>` 补删；本地 `git pull --ff-only` 同步 squash 提交（`f03eb9d`）。master 上的 CI 也绿。

### 两处偏差与两处踩坑（都值得记）
- **与 issue 的偏差**：issue 写的是 `PUT`（全量覆盖），实现改成 **`PATCH`（部分更新）**。理由：列表上的启停按钮若走全量覆盖，会把运营正在编辑的正文覆盖回旧值。偏差写进了 PR 描述 —— 「issue 是计划，PR 解释 delta」。
- **跨字段校验要按「合并后的结果」做**：只传 `endsAt` 时也得能发现它早于库里已有的 `startsAt`。逐字段校验抓不到这种「各自合法、组合不合法」。
- **⚠️ 新坑（高价值）：`enableImplicitConversion: true` 下 class-transformer 会把 DTO 的\*\*所有声明字段\*\*都变成 own property**（没传的那些值是 `undefined`）→ 我用 `hasOwnProperty` 区分「没传」与「显式传 null」，**恒为 true**，于是「结束时间早于开始」的校验被静默跳过、返回 200。**正确判据是 `=== undefined`**。这个坑是 e2e 抓出来的（`PATCH` 期望 400 实际 200）。
- **审计拦截器在守卫之后跑**：`PermissionGuard` 抛 403 时 `AuditInterceptor` 根本不会执行 → **越权尝试不会有审计记录**。所以我原先断言「某条审计的 targetName 等于某公告名」失败（那条路径只有 403，没有审计）。改成断言成功路径，并补了「目标已删 → targetName 为 null 但 targetId 仍在」。
- **断言要按发生顺序写**：审计是写操作的**结果**，我把「删除」写在审计查询之后，自然查不到 —— 调整顺序即可（不是代码问题）。
