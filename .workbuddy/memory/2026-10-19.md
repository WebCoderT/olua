## 修复：编辑器预览 baseUrl 被误判为同源 `/api`（#137 / PR #138）

**现象**：Cocos 编辑器预览里所有请求失败；用户抓到的**已解析**请求是
`url: '/api/auth/login'`（没有主机端口）—— 请求打到预览服务器自己 `:7456`，拿回 HTML，
解析不出 `{code,message,data}` 包裹，报「请求失败」。

**用户最初的判断是错的**（以为 `path: '/auth/login'` 没有拼地址）：他打印的是
`HttpClient.send()` 里的 `options`（`RequestOptions`），那时还没 `resolve()`；同一段真实代码
用假 XHR 跑出来是 `http://localhost:3100/api/auth/login`。**「日志里只有 path」不构成 bug，
要看 `url` 字段**。这个区分方法是本次最有复用价值的一条：想判断请求打到哪，必须看
`ResolvedRequest.url`，不能看入参。

**根因**：`resolveBaseUrl()` 只按 hostname 判本地/线上。Cocos 预览地址按网卡生成 ——
带方括号的 IPv6（`[fe80::…]` / ULA）、`0.0.0.0`、甚至长得像公网的地址 —— 白名单必然漏，
一漏就落到「线上部署」支（`/api`）。

**修法**：判据改成**预览端口优先**（`PREVIEW_PORTS = ["7456"]`，Cocos 预览服务默认端口）；
预览页永远由预览服务提供，这条与 host 形态无关。`LOCAL_HOSTS` 补 `0.0.0.0`。
WS 地址由同一个 `baseUrl` 推导，实时通道一并受益。

**验证手法**（可复用）：
- 单测帮助函数 `resolveBaseUrlWith(hostname, port)` 扩出 port；7 种预览 host + 7456 → 本机，
  公网域名 + 8080/80 → 仍 `/api`（防端口判据误伤部署站）
- **反向验证**：清空 `PREVIEW_PORTS` 后 4 项转红、退出码 1 —— 新判据真的被咬住
- 端到端模拟：`globalThis.location = { hostname: "[fe80::…]", port: "7456" }` 再 `prepareNet`，
  打印实际请求 URL

**顺带确认的环境事实**：服务端 node 监听 `*:3100`（IPv6 双栈），`127.0.0.1` 与 `localhost` 都通；
CORS 回显任意 Origin（含 `null`）；`1/1` 这种账号返回 401 `code=10003 账号或密码错误`（业务失败，
`kind=business`，与「发不出去」是两回事）。

**文档**：`client/README(_en)` 的「连哪个服务端」补预览端口；`client/FAQ(_en)` 新增
「编辑器预览里接口请求全都失败？」（含 `kind=network` vs `kind=business` 的判别）。
`audit-docs-en` 的数字 multiset 对得上（两版都写了 7456 / 3100 同样的次数）。

**留下的调试行**：用户自己在 `HttpClient.ts:115` 加了 `console.log(options)`，未提交，
本次提交刻意不含它。

## 续修：编辑器内预览（`packages://scene`）仍落同源（#140 / PR #141）

**#137 只堵住了一半**：那条修法按「预览端口 7456」识别，但 **编辑器内预览没有端口** ——
用户实测 `origin=packages://scene`、`url=/api/auth/login`、`kind=network status=0`。
也就是说 #137 的三条判据（端口 / host / 回环）在这里全落空。

**关键认知（写进 skill 级结论）**：**「同源相对地址」只在 http(s) 页面上成立**。
`packages://scene` 上的 `/api/...` 会解析成 `packages://scene/api/...`（非法 HTTP 地址），
`xhr.open()` 当场失败 → 表现成 `status=0 / code=-1 / kind=network`，很容易被误诊成
「服务端没起」。判据该选在**协议**这一层，而不是 host / port。

**修法**：`resolveBaseUrl()` 最前面加 `WEB_PROTOCOLS = ["http:", "https:"]`，
非 http(s)（`packages:` / `file:` / `chrome-extension:`）一律走 `DEV_BASE_URL`；
`protocol` 缺失时（老宿主 / 单测垫片）不作判据，继续按 port → host 判。

**诊断信息固化**（这次定位全靠它，值得长期保留）：
- `ApiError.url`：`HttpClient` 四条失败路径（parse / business / network / timeout）都填
- `NetworkSetup` 失败日志：`kind=… url=… code=… status=… origin=…`
- 请求层的 `console.log` 已删；单测加了源码判据防它回来

**坑：明细审计规则 `cn`（中文文案硬编码）会放行「含 `console.` 的行」**（视作开发期日志）。
把 `console.warn(` 和模板串拆成两行后，模板串那行不含 `console.` → 被判外泄、`make audit` 变红。
**修法是把调用与文案保持同一行**，并在注释里写明原因（否则下一个人格式化一下又踩）。

**单测**：`resolveBaseUrlWith(hostname, port, protocol)`，新增 3 条非 http + 3 条 http(s) 反向；
另加 3 条源码判据（协议判据必须在端口判据**之前**、请求层不残留 `console.log`、
失败日志必须带 `url` 与 `origin`）。反向验证删掉协议判据 → 2 红 / 退出码 1。
实测 `{protocol:"packages:",hostname:"scene",port:""}` → `http://localhost:3100/api/auth/login`。
服务端对 `Origin: packages://scene` 预检回显该 origin，跨域不拦。

`git commit --amend --author=…` 对齐，否则 GitHub 上认不到贡献者。
