## #768 同步延迟第二步：10Hz + 帧瘦身 + 序列化缓存（PR #945 / `9202366c`，issue 已关）

**落地**：三个默认值 200→100（服务端两键 + 客户端 `POSITION_INTERVAL`）· monster-ai/players 两帧字段缩写
（world 帧原名，协议同批发）· `sendToViewers()` 一帧只 stringify 一次 + players 出口共用 JSON 快路径。
**实测**（6 人同图 15s）：players -27.5% 字节、stringify 6→1、轮间隔 478→102ms；monster-ai -31.4%、
stringify 5.96→1、轮间隔 329→153ms。数字与回退说明进 `server/FAQ.md`。

**新增门禁 `e2e-protocol-slim`**：源码级双侧接口逐字段比对（stripComments + 花括号配对，允许注释漂移）+
钉 10Hz 默认值 + world 帧保持原名。比 grep 单串强——一次就抓出客户端三处可选性没跟上。

**三个坑（全是「改字段名」的连带，不是功能 bug）**：
1. `e2e-status` 的 `latestAi()` 内部还写 `mob.instanceId === id`（条目已缩成 `i`）→ 恒 null，连带灼烧「掉 0」、
   血量 null、眩晕「没取到 BOSS 坐标」5 条红；`e2e-status-player` 格挡断言读 `hit.damage`（应为 `hit.d`）。
   **改帧字段要按「函数体内读点」扫，不能只 grep 字面**；且「本地绿」是会过期的结论——那轮 status 根本没跑。
2. `e2e-event-log`：拾取后人物停在怪倒下处，quest 距离闸读 `role_positions`，落库是 `flushPositions` 按
   **每角色 1 秒**节流（`rolePositionPersistMs` 默认 1000 / 下限 200）。旧 200ms 广播节拍下接取抢在落库前
   才绿。修法 = 接取前补报一帧 NPC 旁 pos，再**轮询 `role_positions` 直到坐标到位**；固定 sleep 会撞节流窗口，
   直接改库会被服务端内存位置下一轮 flush 覆盖回去。
3. CI 上同一套件连续 3 轮同断言红才敢确认不是抖动 —— 前两轮我按「负载抖动」rerun 了两次，纯浪费。
   **判据：本地能精确复现 = 代码/测试问题；只有本地绿而 CI 红才考虑分片负载**。

**收尾动作**：本地完整 verify（72 套）exit 0 → 推 → CI 四分片+静态全绿 → squash → 手动 `gh issue close 768`
