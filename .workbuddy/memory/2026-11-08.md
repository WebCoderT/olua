## docs/17 物品掉落流程（#796 / PR #797，合并 31e8b9cb）

用户要求「详细写物品掉落：怎么配置 / 怎么掉落 / 掉在地图上 / 捡起来 / 不捡怎么办 / 刷新后去哪了」。
新增 `docs/17-物品掉落流程.md`（986 行），九节 + 两附录。README 篇数改 17 篇 / 约 6600 行。

**全篇支点是「三份真相」（以后回答任何掉落问题先对这张表）**：
- 配置真相 = 库（`monster_drops` / `drop_tables` / `runtime_params.drop_params`），永久；
- 内容真相 = 实时进程内存 `dropLedgers`（`Map<accountId, Map<castId, entry[]>>`），**会话级**；
- 实体真相 = 客户端 `DropManager.dropMap`（`Map<Node, DropItem>`），**场景级**。
- **存档里没有掉落物**（`roles.data.bag` 只有已拾的格子），**世界状态里也没有**。
  三者错位 = 所有掉落 bug 的根源（「东西在地上捡不起来」= 节点在、账本不在）。

**最关键的两个答案**：
1. **不捡 = 永远不消失**。`DropManager` **没有任何 TTL**，`dropMap` 只在「拾取成功 / 换图 reset /
   节点被别处销毁后清残留」三处删条目。东西会一直留在原地，直到换图或关客户端。
2. **刷新分五种，结果不同**：
   - ①换图再回来 → 客户端 `DropManager.reset()` + 服务端 `targetsReset` 清账本 → **干净永久消失**
   - ②刷新网页 / 重开客户端 → WS 断开 `dropAccount` + 进程重启 → **干净永久消失**
   - ③**掉线重连 → 残留不可拾**（服务端断开即清账本，客户端**没有断开清理钩子**；
     重连重发 `worldJoin` 而 `world.join()` **不清账本**、也不重建 `GameMap` → 节点在、账本没了）
   - ④服务端重启 → 同 ③
   - ⑤击杀超过 256 次 → `CAST_DEDUPE_CAPACITY=256` 挤掉最旧的那次 → 那几堆变幽灵

**幽灵掉落物的具体表现**（真实行为，值得记）：点它 → `pick` → 服务端 `unknown_drop` →
客户端 `applyPickedFrame` 只在 `bag_full` 弹提示，其他**只 `console.warn` 且不删节点** →
`pendingPicks` 已清 → 5s 后 `autoPickup` 再试 → 无限循环（每 5 秒一条 warn）。解法：换一次图。

**实算数字（以后别再估）**：`monster_key='2'` 的 `entries` 是 **112 条**，权重和 **261.640**；
`drug_hp_1` 11.47%、`weapon_1` 2.40%、`weapon_1_p4s2` **0.065%** → 3 次内至少一次 0.19%（约 520 只怪），
乘 90% 未绑定 ≈ 580 只。**「打了半天没有」是正常的：分母是权重总和，不是条目数。**

**四个缺口（已记录，未修）**：
1. 无 TTL → 别人击杀的 `spawnRemoteDrops` 节点不可拾且永不消失，多人场景地面只增不减；
2. 断线重连残留（见上）；
3. 无条目级绑定（`DropEntryDto` 只有 goodId/weight/chance/count）；
4. `bindChance` 本地库曾缺键（已补 10）。

- `combat-settlement.service.ts` 头注释说「断线重连 / 换图后清掉旧账**重新计数**」——
  实际 `CombatChannel.castSeq` 是 `private static castSeq = 0` 只在 `sendCast` `+= 1`，**从不清零**；
  服务端靠 `targetsReset` 清账本兜住归属。`realtime.service.ts:425` 的 close 注释也重复了这个过期说法。
