## 动画节点销毁后状态残留（#560，fix/560-animation-destroy）

- **现象**：进游戏后控制台每帧一条 `[PreviewInEditor] Cannot read properties of null (reading '_uiProps')`，
  栈 `AnimationState._sampleCurves → TrackEvalStatus.evaluate → Sprite.set spriteFrame → _applySpriteSize`；
  用户复现路径 = **打掉一只怪 → 传送两次地图** 之后开始刷，重启才停。
- **原因**（Cocos 3.8.7 的坑，官方论坛 `forum.cocos.org/t/topic/169283` 有一模一样的栈）：
  带循环片段的节点 `destroy()` 后引擎不保证把 `AnimationState` 从**全局** `AnimationManager` 摘干净 ——
  `Animation.onDestroy → AnimationState.destroy()` 只在「正在播」时才 `removeAnimation`；组件没过 `onLoad`
  连 `onDestroy` 都不走。残留状态每帧往已销毁的 Sprite 写 `spriteFrame`，`self.node` 为 null → 炸 `_uiProps`。
- **改法**（`ui/helpers/AnimationHelper.ts`）：
  ① `useAnimation` 顺手 `guardDestroy(node)`，在 `NODE_DESTROYED`（引擎**先**发事件、**再**销毁子节点与组件）
  上挂一次性钩子 → `stopTree` 递归 `getComponentsInChildren(Animation)` → **逐个 `state.stop()`**
  （`animate.stop()` 只停 cross-fade 权重，状态还留在全局管理器里 —— 这正是论坛里「先 stop 了还照样崩」的原因）；
  ② 播放入口一律先过 `animatable(node)` = `isValid(node, true)`：`destroy()` 同帧内 `isValid(node)` 仍是 true
  （只进了 `ToDestroy` 队列），不拦就会在将死节点上起一个没人停的状态；
  ③ 一次性播放的 `animate.on(FINISHED)` 改 `once(..., node)`，避免监听堆在复用组件上误销毁节点。
- **守点**：`client/tools/test-animation-destroy.cjs`（最小 cc 垫片照抄引擎语义，`Animation.stop()` 故意不动状态，
  判据 = 全局管理器里还剩几个在播的状态）。**已实测不是假绿**：摘掉 `guardDestroy` 立刻红 5 条。
- 顺带修上一刀（#557）留下的两处：
  - `test-equipment-upgrade-hint.cjs` 的静态断言还按 `static equipBetterFromBag` 老签名匹配 → 恒红（`client-test` 不在 CI 里，漏了）；
  - `Makefile` 缺 `server-e2e-bag` 目标（`make test` 声称「全部测试」却不跑背包 e2e），已补目标 + PHONY + test 列表。
- 基线更新：客户端 58 → **59 套**（54 过 / 5 红，红全是素材未入库）；`server/README` 的 25 套 e2e 不变。

## 地图原点改为左上角（#566，feat/566-map-origin-topleft）

- **需求**（用户）：「将客户端地图改为左上角为原点，这样 tmx 地图就可以直接使用，客户端位置也不需要计算偏移量了」。
  动机不是审美：旧口径每接一张新 TMX 都要在脑子里「减半个宽、翻半个高」，而服务端导入工具、小地图、
  预览图、寻路网格各写过一遍同一套算式，任何一处写反都是「NPC 全体偏半张图」这种只能靠眼睛发现的错。
- **做法（读 3.8.7 引擎源码定的，不是猜）**：`tiled-map.ts` 的 `_buildLayerAndGroup()` 建完图层把节点
  contentSize 设成地图像素尺寸后调 `_syncAnchorPoint()`，把**图层节点锚点同步成地图锚点**；
  `assembler/simple.ts` 再按 `left = col*tw - w*anchorX`、`bottom = rowY - h*anchorY` 平移顶点。
  → 锚点 (0.5,0.5) 时瓦片铺在 `[-W/2,W/2]×[-H/2,H/2]`（原点=中心）；锚点 **(0,1)** 时铺在 `[0,W]×[-H,0]`（原点=左上角）。
  于是换算只剩 `(x, y) → (x, -y)`，`MapPointMath.getMapPointPosition` 一行搞定。
- **最关键的坑：锚点必须在 `tmxAsset` 赋值之前设**。`set tmxAsset` → `_applyFile()` → `_buildWithMapInfo()`
  → `_buildLayerAndGroup()` 全同步，图层锚点与顶点平移量在那一刻就算好了；赋值后再 `setAnchorPoint`
  只改地图节点自身，图层照旧 → 地图整体偏半张图（不报错、不崩）。锚点设在赋值前 → 建图时天然按新锚点走。
- **世界坐标整体平移了** `(W/2, -H/2)`（8192 的图就是 +4096 / -4096）。所以：
  - `tools/import-spawn-areas.cjs` 公式改成 `cx = x + w/2`、`cy = -(y + h/2)`，重生成 62 个区域；
    逐项核对过「新 = 旧 + (4096, -4096)，名称/key/min/max/尺寸一个没动」。
  - 新增 `server/src/shared/map-sizes.generated.ts`（同一工具从 TMX 头产出，11 张图均 64×64×128=8192²）。
  - 存量库一次性平移：`database.service.migrateMapCoordinateOrigin()` 按图各平移 `map_spawn_areas.cx/cy` 与
    `world_monsters.x/y`，用 `world_meta.coord_origin`（新库建表默认 'topleft'、存量库补列默认 'center'）打标记。
    **平移不可重复执行**（再来一次就整体偏半张图），所以判据只能是标记值，不能用「范围」猜。
    实测：拿 `server/data/olua.db` 的副本起服务 → 62 区域 + 173 只怪座标全部平移、日志一条、标记置 topleft；
    再起一次 → 数值不变、日志 0 条（幂等）。
- **同一套「中心」算式收敛到一处**：新增 `getMapWorldRect(map)`（x/y 是左下角 = 原点 - H），小地图底图
  （`SmallMap`）、地图预览（`MapPreviewDialog` 正反两个方向）、寻路网格（`AutoBattle.ensureGrid`）全部改吃它，
  `getMapPixelSize` 从此只在 `MapPointMath` 内部用。
- **顺手修的顺序坑**：NPC / 碰撞区原来是 `setWorldPosition` 再 `addToMapLayer` —— 无父节点时写进去的是本地坐标，
  以前能对只是因为地图层恰好在世界原点。改成先入层再定位。
- **守点 `tools/audit-map-origin.cjs`**（5 条）：① `GameMap` 必须 `setAnchorPoint(0, 1)` 且在 `tmxAsset` 之前；
  ② `getMapPointPosition` 函数体必须是 `(x, y) -> (x, -y)`；③ 导入工具代码里不许有 `- mapW / 2`；
  ④ 生成的刷怪区矩形必须整体落在图内（旧口径的值会越界，这条不需要跑客户端就能发现）；⑤ 客户端不许再有 `mapCenter`。
  负向验证：三条同时改坏 → 报 59 处 exit 1；恢复回绿。审计数 14 → 15（README/README.en/olua-server SKILL 同步）。

  「地图坐标为什么不用再减半个地图了」。

## 进图黑屏：图层没跟上锚点（#568，fix/568-layer-anchor-resync）

- **用户报的现象**：地图锚点确实是 (0,1)，但**进游戏整屏黑**；手动改一下 anchorPoint 就能看到地图。
- **根因（读引擎源码定的）**：`TiledLayer` 的顶点平移量 `leftDownToCenterX/Y = w*anchorX / h*anchorY` 只在
  `init` 时算一次、以及收到 `ANCHOR_CHANGED` 时重算；而那个监听是 **`onEnable` 里才注册**的（`tiled-layer.ts:453`）。
  本工程「先建图、后入场景」（`addToMapLayer` 在 `tmxAsset` 之后）→ 建图那一刻图层**未启用** → 地图的
  `_syncAnchorPoint()` 把图层锚点改成 (0,1) 时**没人接事件** → `leftDownToCenter` 停在按默认锚点 0.5 算的
  `(W/2,H/2)`。`onEnable` 只补注册监听 + mark dirty，**不补算**。
- **为什么表现为「全黑」而不是「偏半张图」**：瓦片照旧铺在中心（`[-4096,4096]²`），而坐标换算已按左上角把角色
  送到 `(4100,-4736)` —— 轴对齐的 8192 图里这个点**恰好在旧位置的图之外**（x>4096、y<-4096）→ 视野里一格瓦片都没有。
- **为什么手动改锚点能看见**：那时图层已启用、事件被接住，重算一次就对了 —— 等于人手替引擎补了那一步。
  这条正是本次定位的关键证据：**症状「改一下反而好了」指向的是「某次重算被漏掉」，不是「值算错」**。
- **修法**：`GameMap.loadMap` 在 `tmxAsset` 赋值后 `for (const layer of tiledMap.getLayers()) layer._syncAnchorPoint()`。
  `_syncAnchorPoint` 是 TiledLayer 的 protected 引擎内部方法（无公开替代），重算 `leftDownToCenter` +
  mark render data dirty，顶点随之重排；重复调用无副作用。
- **守点**：`tools/audit-map-origin.cjs` 新增第 2 条 —— `tmxAsset` 赋值后必须出现 `_syncAnchorPoint()` 调用，且在赋值之后。
  负向验证：删掉循环 → 报 1 处 exit 1；恢复回绿。审计总数不变（15），只是规则数 5 → 6。
- **两个坑的判据分清了**（写进技能，避免下次又混）：
