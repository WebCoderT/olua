## #631 CI 精简：三遍全量 → 一遍

用户问「为什么本地跑一次 CI，远程还跑一次，合并前后都跑，不就跑了 3 次？写记忆也单独跑，很慢」。

**实测基线**（不是印象）：本机 `make ci` **186s**（其中 e2e 171s、静态半边 15s）；PR CI **4m33s**（run 41498688071）；
合并后 master CI **4m23s**（run 41499456170）；纯文档 PR（#628/#629/#630）也各跑满 4 分钟。

**三个结论**：
1. 合并后那遍是纯重复 —— PR CI 跑 `refs/pull/N/merge`（master + 本次改动），squash 后树的哈希序列与之一致。
2. 本机全量既慢又不稳（负载高时红在 e2e 等待超时，同一份代码 CI 连续三次全绿）→ 本机不该当硬门禁。
3. **门禁清单漂了**：`server/package.json` 29 个 `test:e2e*`，`make ci` 手写清单只覆盖 26 个 ——
   `admin-mail`(30 条) / `mail-expiry`(15 条) / `ui-effect`(27 条) **从未在 CI 跑过**（本地单跑全绿）。

**改法**：
- `ci.yml`：只留 `pull_request`（`paths-ignore`: `**/*.md` / `.workbuddy/**` / `design/**` / `website/**`）+ `workflow_dispatch`；
  两个 job 并行 —— `static`（`make ci-static`）与 `e2e × 4`（`make server-e2e-shard I=${{matrix.shard}} N=${{strategy.job-total}}`）。
- 新 `tools/run-e2e.cjs`：清单**派生自 package.json**，按 `WEIGHT`（本机实测档位：backup 7 / guard 6 / mail 5 / combat 5 / party 4 / realtime 4 / 其余 1~2）
  贪心装箱（重的先放、丢给最轻的一片）；实测 4 片各 15 权重（7~8 套），29 套无重叠无遗漏；
  扫 0 套直接报错（防假绿）；失败 fail-fast 并列出「未跑」（重跑自然会跑到）；`--list` 只打印不执行。
- Makefile：`ci-static` / `ci`（=ci-static + e2e-all）/ `e2e-all` / `server-e2e-shard` / `server-install-ci`；
  `test` 与 `ci` 不再手写 26 个 target；`INSTALL ?= install-ci`（本机可 `INSTALL=install` 省时间）。
- 文档：根 FAQ 中英文各加「一次改动跑几遍门禁」；MEMORY.md 纪律改成 `test-changed` + PR CI 为准。

**验证**：`make ci-static` 15.2s（3 个 npm ci + client-check 0 错 + 15 审计 PASS + 两端构建）；
`make server-e2e-shard I=3 N=4` 26.6s（7 套全过）；切片并集 8+7+7+7=29 无重叠无遗漏。

### 合并与实测（PR #632 → master `cce9076`）

| 运行 | 形态 | 墙钟 |
|---|---|---|
| 41498688071（旧） | 单 job 串行 26 套 | 4m33s |
| 41504017895 | 首轮分片（取模切） | 4m05s（静态 job 有 3.5 分钟**无法解释的收尾尾巴**：步骤 18:48:54 就结束，job 到 18:52:24 才完） |
| 41504864574 | 同上，手动重跑 | 2m26s（尾巴没复现 —— 首轮那次是 runner 侧异常，不是 yml 问题） |
| 41507058725 | 按耗时装箱后 | **2m00s**（静态 48s；分片 1m07~1m46） |

- 合并后**没有任何 CI 运行**（`push: master` 已删）：`gh run list` 里最新一条还是 PR 的。
- 分片均衡的判据：`WEIGHT` 装箱后 4 片各 15 档；`backup` 单独 52s 是分片墙钟的地板（再想快只能拆 backup 或加到 8 片）。
- 教训：**「按个数均分」在耗时差一个数量级时等于没并行**（片 0 118s / 片 1 47s）。
- 另一条：CI 上每个 job 的 reported 时长可能远大于其步骤总和（收尾尾巴），**排查性能要看 steps 的 started_at/completed_at，不要看 job 时长**。

## #634 掉落光效纳入管理端特效管理（分支 feat/634-drop-light-ui-effect）

**诉求**：装备落地的品质光柱原来参数全写死在客户端（前缀→光柱在 `configs/light.ts`、400×400 + 帧率 10 在 `configs/layout/lights.ts`），改一个数要重打 3G 包。搬到 `ui_effects`，与升级特效同一套调试能力（实时预览 / 一 key 一页签 / 保存即生效 / 无新建删除）。

**关键决策**
- **key 即素材名** `light_1`…`light_6`（不合成 `dropLight` 再套子字段）：客户端 `getEquipmentLightKey()` 返回的就是它，两端省掉翻译表，六份美术各自可调。
- **「取哪张光柱」留在客户端**：前缀表 + 特殊装备自定义表是美术分配，塞不进扁平的表现参数表。
- **挂点不同**：升级特效偏移相对 UI 层锚点；掉落光效相对掉落物图标中心（`new Vec2(config.offsetX, dropItemLayout.iconOffsetY + config.offsetY)`，故 (0,0) = 与图标同心 = #634 之前的行为）。
- **时长口径统一成「一轮总时长」**：光柱从 `playLoopAtlas(frameRate=10)` 改 `playLoopAtlasWithDuration(durationMs/1000)`；出厂 = 帧数 × 100ms（1 号 14 帧 1400，2~6 号各 15 帧 1500）。
- **列表改 `ORDER BY rowid`**（= `UI_EFFECT_KEYS` 登记顺序）：字典序会把 `light_*` 顶到 `upgrade` 前面，管理端第一个页签就变了。e2e 用 `allRows[0].key === "upgrade"` 钉住。
- 管理端预览分两族（`previewKindOf`）：`role` 拉裸模；`dropItem` 画 40×40 虚线图标占位框 + 地面线，光柱先画（下层），与客户端层级一致。

**踩坑**
- **改 DTO 描述必须重跑 `swagger:emit` + `gen-api`**：`audit-api-generated` 的 A 段是「现算一遍逐字节比对」，漏了直接 FAIL（本次差点漏）。
- 改 DTO 时我在现场又发现 offsetY 描述写成「同上口径」，生成到 API 文档里没有上下文 → 改成「相对挂点同 X」。
- **用户「管理页面没有看到」= 服务端 seed 只在启动时跑**：`onModuleInit` 按 `UI_EFFECT_KEYS` 做 `INSERT OR IGNORE`，跑着的进程还是改代码之前起的 → 库里只有 `upgrade` 一行，而且列表仍是旧的 `ORDER BY effect_key`。**光重启管理端没用，得重启 3100**；页面列表只在进页面时拉一次，刷新后才多出六个页签。已 `npm run build` + `npm start` 重启，库里 7 行（`upgrade` 保留 -20/100）。

**验证**：`make client-check` 0 错 · `make admin-typecheck` 0 错 · `make client-test` 55 过 4 红（基线，红在素材未入库）· 15 个审计全 PASS · `make server-e2e-ui-effect` 34 条 · `make test-changed` 74 步全绿。

### 追加（用户看过页面后提的）：页签合并成两族，档位改下拉框

用户的判断：**六个光柱档位不该各占一个页签**。改成「一族一个页签」（升级特效 / 掉落光效），
掉落光效页签内容顶部一个 `Select` 选 1~6 档 —— 理由与落地细节：

- 七个页签会把「升级特效」挤到最右边，而它才是这个页面最初的用户；六档也只是「同一件事的六个档」。
- 页签判据复用预览那条：`tabOf(key) = previewKindOf(key) === "dropItem" ? "drop" : "upgrade"`（一处口径两处用）。
- 状态从「一个 activeKey」拆成 `activeTab` + `activeLightKey`；`forms` 本来就按 key 存，
  所以**切档 / 切族都不会丢未保存的改动** —— 但改动会跟着藏起来，于是页签上加「未保存」小圆点
  （`dirtyCountOf`，一族几条）、下拉项后缀「（未保存）」，靠这两个提示兜住。
- 页签只渲染「有行的族」（`tabs = TAB_ORDER.filter(...)`），seed 少了哪族就不出现；
  刷新后页签与档位都尽量停在原处（key 被删才回落）。
- 顺手：停用文案按族换（启用光柱 / 启用特效）、保存提示改用中文名（`掉落光效 3 号 已保存`）。
