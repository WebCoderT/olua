# 给项目设计一条成长曲线（等级 / 怪物 / 装备 / 战魂 / 药品）

适用场景：项目里的数值是「一只手一只怪地手填」出来的——`levelMap` 里 60 行手写数字、
220 只怪各自写 `maxHp / physicalAttack / ...`、37 件装备各写各的，结果是低级怪血量比高级怪多、
60 级升一级要打 11 万只怪、穿了新手装就打不动怪。目标 = **一条曲线 + 各配置只写表现，数值全部派生**。

## 一、先问清三个数（不问就先别动手）

设计曲线前必须和用户确认这三件事，否则几十只怪白配：

| 问题 | 为什么要问 | 典型选项 |
|---|---|---|
| 曲线形态 | 决定后期数值膨胀速度与「好不好手调」 | 分段线性（每 N 级一档，档内固定增量）／整条线性／指数或二次 |
| 怪物等级怎么定 | 决定「等级是数据还是从 id 推出来的」 | 每条怪显式写 `level`（推荐）／按编号铺一次天梯再冻结成明文／只配地图里用到的 |
| 同级 1v1 打怪节奏 | 决定「怪血 / 角色输出」的比例，是整条曲线的定标锚点 | 约 2~3 秒／5~6 秒／10~12 秒 |
| 装备占多大分量 | 决定要不要同时重新定标怪物（见第六节的锚点冲突） | 同级裸属性的 ~30%／~60%／~200% |
| 「打怪节奏」锚在哪个状态 | 决定裸装能不能玩 | 锚在裸装／锚在满装／锚在半套 |

推荐默认：**分段线性 + 每条怪显式 `level` + 同级 5~6 秒 + 装备约 ~60% 且锚点仍在裸装**。
分段线性最好手调（每档只有 start 与 perLevel 两个数），5~6 秒挂机舒适；等级写成数据字段的理由见第五节；
装备超过 100% 时一定先把第六节的冲突算出来再定。

## 二、目标结构：一个 growth 文件当唯一来源

```
configs/growth.ts        ← 曲线本身 + 从曲线取值的函数（新建，别塞进 level.ts）
configs/level.ts         ← 只做「曲线 → levelMap」的搬运 + 经验换算
configs/monster.ts       ← 数据数组：每条写 { key, level, tier?, …表现字段 }，末尾统一 monsterStats(level, tier) 注入属性
configs/equipments.ts    ← 数据数组：每条写 { key, level, slot, …表现字段 }，末尾统一 buildEquipmentMap 注入属性
configs/soul.ts          ← 按「等效等级」取角色属性再打折
configs/drug.ts          ← 回复量按血量曲线定标（否则高等级药水毫无用处）
configs/types            ← MonsterTier / MonsterData / EquipmentData 等类型（configs 依赖 types，反过来不行）
```

```ts
/** 一条分段线性曲线的一档：档内按等级线性增长，档间靠 perLevel 跳档 */
export interface GrowthSegment { from: number; to: number; start: number; perLevel: number }

export function sampleGrowth(segments: GrowthSegment[], level: number): number {
  if (level <= 0) return 0;
  let last = segments[0];
  for (const segment of segments) {
    if (level <= segment.to) return segment.start + (level - segment.from) * segment.perLevel;
    last = segment;
  }
  return last.start + (level - last.from) * last.perLevel; // 超出最后一段按末尾斜率外推，方便测试填高等级
}
```

角色曲线只写三张表 + 一张节奏表：`maxHp / attack / defense / killsPerLevel`，
攻击与防御各写一列（不要写 6 列）——三项攻击同值、三项防御同值，组件侧按同一份值填六个字段。
**理由**：角色只用自己职业那一项攻击，怪也大多只有一种攻击，把三项拉开只会凭空造出职业强弱差；
职业差异应该来自装备与技能倍率。旧项目里常见 `0.10/0.08/0.06` 这种比例，基本都是占位产物。

## 三、三条设计目标（改曲线前先回来看）

1. **打怪节奏**：角色**裸属性**普攻同级普通怪 = `N` 刀（`N` 就是确认到的手感锚点）。
   普攻冷却 1 秒时，5.5 刀 ≈ 5~6 秒。全等级都应该稳定在这个值。
2. **生存节奏**：角色裸血能扛同级怪 `M` 刀（怪普攻 2 秒一次 → `2M` 秒）。
   想让「前期脆、后期肉」，就让**攻击/血量比逐档下降**（例：20% → 12.7%），而不是靠改刀数。
3. **升级节奏**：每级要打多少只同级怪（例：10 → 350 只），乘每只耗时得到全局时长（例：1→60 级 7655 只 ≈ 11.7 小时）。

把这三条写进 growth.ts 的文件头注释，否则半年后没人知道为什么是这个数。

## 四、关键机制：怪物血量不要直接拍，要反推

这是整套做法的核心，也是最容易做错的地方。**怪物血量由「角色打几刀」倒推**：

```ts
const averageFactor = (1 + attributeRange.minRate) / 2;        // 区间均匀随机的均值系数
const damagePerAttack = averageFactor * (roleAttackMax - monsterDefenseMax);  // 角色一次普攻的平均伤害
const maxHp = Math.round(damagePerAttack * monsterBalance.hitCount * tier.hp);
```

好处：以后改角色曲线（哪怕整体乘 10 倍），**怪的耐打程度自动保持同一手感**，
不会出现「改了等级曲线，结果所有怪变成豆腐」这种返工。

配套：角色与怪物都用同一个区间倍率 `attributeRange.minRate`（推荐 0.7，即 [70%, 100%]），
这样两边均值系数一致，反推公式才成立。旧项目里常见的 `[上限×0.25, 上限]` 会让伤害纯看运气，顺手改窄。

## 五、怪物：`level` 与 `tier` 都是数据字段，key 只做关联

**核心规则：等级不能从 key 推出来。** key 的职责只有「相互关联」（地图对象组的 id、掉落表、AI 引用同一只怪），
它可以是任意字符串（`"goblin_chief"` 完全合法）。一旦某处代码去 `Number(key)` 猜等级，key 改名或换成字符串就崩。
所以取属性的函数收的是**等级**，不是 id：

```ts
// growth.ts：只认等级与定位
export type MonsterTier = "normal" | "elite" | "boss";   // 类型放 types/monster（否则 types 反向依赖 configs）
export const monsterTierScale: Record<MonsterTier, { hp: number; attack: number; defense: number }> = {
  normal: { hp: 1, attack: 1,   defense: 1 },
  elite:  { hp: 3, attack: 1.3, defense: 1.3 },
  boss:   { hp: 8, attack: 1.5, defense: 1.4 },
};
export function monsterStats(level: number, tier: MonsterTier = "normal"): MonsterBaseStats { /* 见第四节反推公式 */ }
```

配置侧写成「数据数组 + 统一注入」——等级只写一次，属性一律由等级派生：

```ts
// configs/monster.ts
const monsterData: MonsterData[] = [
  { key: "1",   level: 1,  icon: "…", label: "…", moveSpeed: 2, … },        // 普通怪
  { key: "200", level: 45, tier: "boss", icon: "…", drops: "boss", … },     // 首领
];

export const monsters = new Map<string, MonsterConfig>();
for (const data of monsterData) {
  const { key, tier, ...rest } = data;                                   // key / tier 不写进最终配置
  monsters.set(key, { ...monsterStats(data.level, tier), ...rest });     // rest 里若写了属性则覆盖生成值
}
```

- **等级从哪来**：首次迁移可以先用「按编号线性插值」批量铺一遍
  （`round(fromLevel + (id-fromId)/(toId-fromId) * (toLevel-fromLevel))`），但**铺完立刻冻结成明文 `level:` 写进每条怪，
  然后把天梯函数删掉**——留着它就等于留着一个「用 key 猜数值」的入口。
- **天梯要铺满等级上限**，否则高等级玩家没有同级怪（第一版踩过：普通怪只铺到 50 级，51~60 级玩家只能打 BOSS）。
- **定位用「血 ×N 倍」表达精英/BOSS**（同级 BOSS 打 N 倍刀数），攻防小幅放大——BOSS 应该「耐打 + 打人疼」，
  不是「一刀秒人」。定位同样写在数据里（`tier`），不要靠 key 落在哪个数值区间去猜。
- **直接收益**：加新怪 = 写 `{ key, level, …表现字段 }`，不用管它在表里的位置；调强弱 = 只改那只的 `level`；
  特例（法系怪补 `magicAttack`、某只怪加血）= 在条目里写同名字段覆盖生成值。

## 六、装备：等级是「定强入口」，权重按部位分

装备和怪物同构（数据数组 + 统一注入），但有两处不同：

**① 装备的 `level` 是双重语义**——既是**穿戴需求等级**（校验会挡「需要等级 N」），又是**强度档位**。
所以排等级时问的不是「它有多强」而是「它应该在什么等级被拿到」。用户已排好名称/图标/描述时，
**按名称强弱排**是最贴合直觉的做法（"送给新手的第一件武器" = 1 级，"唯有真正的强者" = 满级）；
成对的「同一形态的觉醒版」要保证觉醒版等级更高（本次 `weapon_18 紫翼神冠刃` 排在 `weapon_14 紫翼金冠刃` 之后）。

**② 数值分「总量」与「分配」两层**，两个数分别可调：

```ts
export const equipmentGrowth = {
  /** 全套装备合计 = 同级角色裸属性的该倍数（2 = 每类属性都 +200%） */
  setPowerRate: 2,
};

/** 部位分配权重（每列合计 100）：数值 = 裸属性上限 × (权重/100) × setPowerRate */
export const equipmentSlotShare: Record<EquipmentSlotKey, { maxHp: number; attack: number; defense: number }> = {
  weapon:   { maxHp: 0,  attack: 52, defense: 8  },   // 武器只给攻击
  cloth:    { maxHp: 30, attack: 10, defense: 30 },   // 衣服是血防主源
  helmet:   { maxHp: 16, attack: 5,  defense: 15 },
  necklace: { maxHp: 12, attack: 12, defense: 9  },   // 首饰偏攻击
  // 尚未做装备的部位也把键写上、权重留 0 —— 拼错部位名才能编译报错，好过静默返回 0
};
```

- **部位键用字面量联合，不要 import 枚举**：`growth.ts` 要保持「只依赖 type 导入、能被 node 直跑」，
  而枚举要运行时加载。关键是**字符串枚举成员可以赋给字面量联合类型**（已实测），所以配置侧直接传
  `EQUIPMENT_TYPE.CLOTH` 不会报错，同时拼错部位名会编译期报错。
- **装备数值用固定值 `[v, v]`**（区间两端同数）：装备是确定性的，同名装备数值应完全一致，便于横向比较与手调；
  角色等级属性那边保留 `[上限×0.7, 上限]` 的浮动区间，随机感来自等级那一份就够了。
  顺手要把详情显示改成 `min === max ? String(min) : \`${min} - ${max}\``，否则界面会出现「攻击 120 - 120」。
- **低等级要保底 1**：`weight > 0 ? Math.max(1, Math.round(...)) : 0`。1 级裸属性只有几十点，
  小份额（9% × 2）四舍五入会变 0，导致「项链在 1 级完全不提供防御」。

### ⚠ 装备总量会直接和怪物锚点打架（动手前必须算，别只交付数值）

怪物血量是**按角色裸属性**反推的（第四节）。一旦装备给出可观属性，两个问题同时出现，而且**防御那边远大于攻击那边**：

| 等级 | 裸装 击杀/能扛 | 满装 击杀 | 满装每刀吃（原值） | 满装 能扛 |
|---|---|---|---|---|
| 30 | 5.5 刀 / 9.8 刀 | 1.26 刀 | 16（原 286） | 525 刀 |
| 60 | 5.5 刀 / 13.2 刀 | 1.26 刀 | 454（原 7462） | 653 刀 |

**根因：防御在减法公式里是非线性的。** 角色裸防御通常只有同级怪攻击的 **30%**（曲线里 `defense ≈ attack × 0.3`），
所以防御加 200% 之后（3 × 30% = 90%）**已经追平怪的攻击**，`max(0, 攻−防)` 直接把怪打成挠痒；
而攻击加 200% 只是让击杀刀数除以 3。
→ 想保留高倍率装备，就得**把防御份额显著调小**（怪的防御只有角色的 30%、怪的攻击是角色的 100%，
这个不对称决定了防御的边际收益远高于攻击）。

同时要明确**「打怪节奏」这个锚点锚在哪个状态上**，否则必然两头不讨好：

- **锚在裸装** → 装备一上身就变快，越强越快（装备 = 爽感来源）；
- **锚在满装** → 裸装会打不动怪（装备 = 必需品），实现方式是让怪物也乘 `1 + setPowerRate`；
- **锚在半套** → 折中。

三种都要给用户算出来再让他选，**不要只报「装备已生成」**。另外先确认「一套」到底包含几个部位——
本次 7 个部位里有 5 个（头盔/腰带/鞋子/项链/戒指）**各只有一件 1 级「新手X」**，
所以高等级玩家实际只拿到 血+60%/攻+146%/防+90%，而不是设计的 200%。这类「权重表已就位但内容没跟上」的缺口要显式报出来。

## 七、其他数值挂在同一条曲线上

- **经验与击杀数绑死**：`levelMap[level].exp = getLevelKills(level) × (level + 1) × expGain.expPerLevel`。
  左边来自曲线里的「每级要打几只」，右边正好是「同级怪击杀经验」的公式 → 改一个数两边同步，永远对得上。
  手写经验表最常见的问题就是高段失控（例：60 级那级要 3620 万经验 = 118,700 只同级怪）。
- **战魂 / 转生 / 天赋这类额外养成线**：不要另开一套数字，而是**映射到一个「等效角色等级」**再打折：
  `属性 = getRoleLevelAttributes(等效等级) × rate × 系列系数`。
  这样等级曲线一改它们自动跟着走，永远不会出现「战魂比角色本人还强」。
- **药品 / 药水回复量**必须按血量曲线重算，否则 1 级和 60 级共用一瓶 30 点血的药。
- **装备**见第六节（它自己就是一条完整支线：等级定档 + 部位权重 + 总量倍率，且总量会和怪物锚点打架）。

### 每只怪一份独立掉落表（把一整批物品铺进列表，而不是运行时算）

需求形如「把所有装备分到每只怪的掉落列表、每只怪独立配置、条目单独配权重」时，**别继续用函数在运行时生成表**——
用户要的是能逐条手改的数据。做法：

1. **先问清三件事**（每个都会改变生成结果）：① 每只怪只放「本等级段」的物品，还是放全部？
   ② 只有基础件，还是连前后缀变体一起？③ 药品/材料条目保不保留？本次答案：等级分段 + 基础件与全部 15 变体 + 保留。
2. **窗口口径**：每个部位取 `level ≤ 怪物等级` 且 `怪物等级 − level ≤ 10` 的最近 2 档。
   既保证稀疏部位也有货，又不让高等级怪掉 1 级垃圾；同时「每件装备都被某个等级段的怪覆盖」可被断言
   （本次 555 件零缺口）。窗口宽窄、每部位几档 = 两个旋钮，写进生成脚本头部。
3. **权重用「同一量纲预算」，别一条条拍**：先定该定位的**装备权重合计**（本次普通 44 / 精英 70 / BOSS 96，
   与药品材料的 30/18/10 同一量纲），再 `单件预算 = 预算 ÷ 窗口内基础件数`，最后乘
   前缀倍率 × 后缀倍率 × 部位倍率（本次 [1,.7,.45,.25,.12] × [1,.5,.22] × [武器/衣服 1，盔/带/鞋 .9，项链/戒指 .8]）。
   稀有度只体现在权重（最稀 ≈ 普通的 1/40），不要再叠 `chance`，否则两处调稀有度会互相掩盖。
4. **独立成文件 `configs/<域>Drops.ts`，不要塞进 220 条怪物条目里**：一只怪一份 `{ picks, entries }`，
   数组为源 + 尾部建 Map + `getXxxConfig(key)`；取值做三级链：条目内联 `drops/dropPicks` 覆盖 > 独立表 >
   原生成函数兜底（这样新增怪忘铺掉落也不会「打死没东西掉」）。
5. **这种文件会很大**（555 件 × 窗口 → 本次 1.24 MB / 19.3k 行 / 16.5k 条目，每怪 51~141 条），
   所以**用脚本产出、脚本留在 `tools/`**（Cocos 只收 `assets/`，根目录 `tools/` 不影响构建），
   README 写清「想调口径 → 改脚本参数重跑」。条目一行一条 + 行尾中文品名注释，让数据能读能改。
   同样要补 `.meta`，改完 grep + sleep 复检（大文件更怕编辑器回写）。
6. **校验要跑真产物**：每只怪都有表、条目 goodId 全部能在 items 里解析、`weight > 0`、`count` 区间不倒挂、
   每怪跑几百次抽取不崩；再断言「全量装备覆盖数 == 全量装备数」。本次 220 怪 × 200 次 = 4.4 万次抽取全 PASS。
7. **顺手把数据缺口报出来**：本次头盔/腰带/鞋/项链/戒指只有 1 级新手件 → 只出现在 ≤11 级怪的列表里，
   高等级怪掉不到这 5 个部位（与第六节「装备只有 7 部位有货」是同一个缺口，别让用户以为是掉落配错了）。
8. **「掉落数量」= 件数（抽取次数），要做成可配区间**：用户说「配掉落数量，比如 [1,10] 就掉 1~10 件，可以重复」
   指的是**每次结算的件数**，不是条目里的 `count`（那是单件物品的数量）。把 `picks` 类型升成 `number | [number, number]`：
   数字 = 固定件数，区间 = 每次随机取整（**自动纠正 min/max 顺序、负数归 0**）；抽取循环本身不变，
   靠「每次独立按权重抽」天然支持重复命中同一条目（重复的合并数量）。区间按定位给（本次普通 [1,3] / 精英 [2,6] / BOSS [3,10]），
   并在每怪注释里带上「掉落 x~y 件」便于肉眼核对。
9. **「掉落物不许堆在一个点上」要按屏幕口径算，先确认有没有隐藏缩放**：先查图层/相机有没有 scale——
   本次世界坐标没有额外缩放（正交 2D、图层无 scale），所以**世界坐标里的距离就是屏幕上看到的距离**，
   直接在世界坐标里铺点即可。做法：写纯函数 `scatterDropPositions(count, minDistance)`，以落点为圆心从内圈往外
   （半径 = 圈数 × 间距）取样，每个候选点必须与**所有已放点**距离 ≥ 间距才采用（贪心铺满内圈，确定性无随机），
   间距 = 图标宽 + 留白（本次 40+12=52）。**注意别再用「y 方向乘 0.5 压扁」凑椭圆**：那样垂直间隔只剩一半，
   40px 高的图标会互相压住。校验：对 1~40 件逐对算最近距离，断言 ≥ 间距（本次恒 52.00 PASS）。

### 建号发什么：出生物品清单（发整组品质变体，但要先算背包容量）

需求形如「建号时把 X 级的所有前后缀武器都放进背包」（用户想出生就能对比不同品质的外观 / 边框）。做法与要点：

1. **按等级取整组变体**，别按 key 手写 15 个 id：`getEquipmentsByLevel(map, level)`（内部 `map.forEach` 收集，
   理由见坑 14）。装备的「等级」既是佩戴门槛又是唯一定强入口，用等级筛既自然又跟着曲线走。
2. **清单 = 少量通用件 + 全部基础件 + 指定等级的变体**，且**基础件只发一次**：基础件（普通的·人级）已在
   「全部基础件」那一步发过，变体循环里要 `if (prefix === 普通 && suffix === 人级) return`，
   否则同一件占两格（单测断言「清单里没有重复 id」）。
3. **先算总格数**：出生物品直接写进背包二维数组，`bagRow × bagCol` 是硬上限（本次 7×11 = 77，
   出生 5 + 20 + 12 + 14 = 51）。把「清单长度 ≤ 容量」写成断言；超容量时**必须先留日志再截断**，见坑 15。
4. **配置给旋钮**：发哪个等级是常量（本次 `newRoleVariantWeaponLevel = 1`，0 = 关闭）。以后想改成
   「2 级武器 + 1 级衣服」只改常量 / 加一行 `getEquipmentsByLevel(clothes, 1)`，不动实体代码。
5. **单测要跑真实体**：不只断言 `getNewRoleEquipments` 的返回，还要 `new Role(...)` 之后检查「变体 id 一个不少
   一个不重、每格 count = 1、每格都能被物品总表解析、剩余格子为 null、两个角色的背包不是同一个数组」。
   注意**先 require 物品总表**：装备对象的 `id` 是注册表（`registerItem`）载入时补上的，顺序反了会拿到一堆
   没有 id 的条目（建号时被静默跳过，断言会以「东西没发」的形式失败）。

## 八、必踩的坑

1. **改数值前先确认「等级上限」写在哪**：项目里常有 `if (role.level >= 30) role.level = 30;` 这种硬编码调试上限，
   曲线做 1~60 而这个上限还是 30，就会出现「怎么升级都到 30」。改成引用 `growth.roleMaxLevel`。
2. **构造里别直接引用配置的区间数组**：`this.attack = levelMap.get(1).attack` 拿到的是配置对象的**同一个数组引用**，
   运行时一旦原地改动就污染配置表。写 `[...levelMap.get(1).attack]`。
3. **批量改配置时，用「逗号开头的注释」做替换会把逗号一起删掉**：本次在 220 条怪物里删了
   `, // 说明注释`，结果 `...monsterStats("1")` 后面的逗号全没了。改完**一定 grep 计数**（`grep -c '…),'` 对比块数）。
4. **解析自己写的配置做批处理时，正则不要带前导换行**：`/\nfoo\(/` 会因为上一个匹配把换行吃掉而只匹配到一半
   （本次 220 块只匹配到 110 块）。用 `re.finditer(/foo\(/)` 不带前导 `\n`。
5. **改完必须校验单调性**：曲线值在档界处最容易出问题——上一档末值可能**大于**下一档起值
   （常见于「攻击随档打折、血量随档跳档」的组合），表现是「升了一级攻击反而降低」。
   写脚本断言「每项属性逐级严格递增」，并把每档交界处单独打出来看。
6. **`import type` 是校验的前提**：想脱离引擎跑曲线做校验，配置文件里的类型 import 必须写成
   `import type { X } from "..."`（否则 node 的 `--experimental-strip-types` 会试图真去加载那个模块）。
   纯数值的曲线文件本身不要 import 任何引擎模块。
7. **怪物数量大时用脚本改，不要手改**：220 条 × 8 个字段 = 1760 行手改必错。
   写 Python：正则切块 → 过滤目标字段行 → 在块首插入展开语句 → 逆序回写（保持偏移有效）。
8. **别让 key 承担数值语义**：把 `getMonsterLevel(id)` 这类函数删掉时，`monsterStats` 的返回值里也**要把 `level` 去掉**
   ——否则「数据条目里的 level」与「函数生成的 level」成为两份值，改一处不生效、改错一处不报错。
   约定：**等级全项目只有一份（写在数据条目里）**。同理，定位不要从 key 反推。
9. **校验「真实配置的构建结果」用 tsc 编 CommonJS，别用 `--experimental-strip-types` 挑文件**：
   strip-only 模式不支持 enum 与构造函数参数属性；`--experimental-transform-types` 又要求所有混写的类型 import
   （`import { SkillConfig, ... }`）都改成 `import type`，改不动第三方/既有文件。
   最稳做法：写一个**只 include configs/types 相关文件**的 tsconfig（`module: commonjs` + `outDir:/tmp/xxx/dist` +
   ambient `declare module "cc";` 桩声明），编译后配一个 `node_modules/cc` 运行时桩（`module.exports = { Vec2, Vec3, Size }`），
   直接 `require` 真实配置跑断言（如 220 怪逐条校验 drops 数组与 goodId 合法性）。依赖链会连带 skills/ui 的文件，
   include 列表报 TS2307 时按报错逐个补桩即可，配置数据本身不碰。
10. **数据条目类型要允许属性缺省**：`MonsterData extends MonsterConfig` 会要求每条写全七项战斗属性（数据里不写）→
    用 `Omit<MonsterConfig, keyof BattleAttributes> & Partial<BattleAttributes> & { key: string; tier?: MonsterTier }`。
    装备同理：`EquipmentData = Omit<Equipment, keyof BattleAttributes> & Partial<BattleAttributes> & { key: string }`。
11. **用正则切「数组里的条目」时，别要求条目之前必须有换行**：`/\n  \{\n    key: "([^"]+)"/` 在
    `finditer` 下会因为**数组第一个元素前面没有换行**而漏掉它（`body` 是从 `([\n` 之后开始的）。
    本次装备改造因此**每个 Map 的第一条被整个吞掉**（12→11、20→19、只有一条的直接变 0 条）——
    靠「改造前后的条目数对比」才发现。修法：`finditer("\n" + body)`，或干脆不在正则里带前导 `\n`。
12. **减法公式下，「属性互加」和「属性互相克制」不是一回事**：只调一边的数值前，
    先把两边区间的**精确期望伤害**算出来（`E[max(0, X−Y)]`，X/Y 各自在自己的整数区间均匀取值），
    **不要用「均值相减」**——均值相减会在 `攻 − 防` 接近 0 时给出负数或 0，让你误判成「怪完全打不动人」
    （本次第一版校验就得出「能扛无穷刀」，改用精确期望后是「每刀 454、能扛 653 刀」，量级一样骇人但结论严谨）。
13. **用 Edit 改文件时，`old_string` 与 `new_string` 的尾随换行必须一致**：`old` 以 `\n` 结尾而 `new` 不以 `\n` 结尾，
    会把两行**直接粘连**成一行（本次在类型文件与配置文件各踩一次，且都不报错、只在读文件时能看到）。
    改完后扫一眼改动处，或直接 grep 关键行确认。
14. **`[...map.values()]` 在打包产物里会静默变成空数组**（编辑器正常、打包才复现）：Cocos 打包用 babel **loose**
    模式，把 `[...迭代器]` 降级成 `[].concat(迭代器)`，而 `Array.prototype.concat` 只展开数组、**不认 Map/Set 迭代器**
    → 得到 `[MapIterator]` 这一个元素，后面 `.filter()` 恒为空。本次「打包后新建角色背包里没有装备」就是这个：
    `getBaseEquipments(map) { return [...map.values()].filter(eq => eq.prefix === 普通 && eq.suffix === 人级) }`
    在编辑器给 20+12 件、打包后恒给 0 件（背包只剩按 key `.get()` 硬取的通用件，且**不报错**）。
    约定：**Map / Set 转数组一律 `map.forEach` 收集或 `Array.from(map.values())`**，别写 `[...map.values()]` / `[...someSet]`
    （对象/数组展开随便写，只有「展开迭代器」会被降级坏）。排查手法：在 `build/<平台>/assets/main/index.js` 里搜
    `[].concat(`，参数带 `.values()`/`.keys()`/`.entries()` 的即隐患点；用「把打包产物模块图在 node 里跑起来」的方式
    可以直接复现（用一个极简 System.register 加载器 + cc 桩，见本项目 /tmp 的校验脚本）。
15. **新手物品超容量是「静默丢弃」的**：`Role` 构造函数按 `bagRow × bagCol` 写格子，越界的条目直接丢
    （不丢就会 `Cannot set properties of undefined`）。发物品的人看不到任何提示 → 玩家只是少东西。
    约定：写格子前 `slice(0, capacity)` 截断，超量时打一条带「件数 / 容量」的 warn，并让单测断言
    「背包件数 == 清单件数（没有溢出丢弃）」——这条断言能在有人往清单里加东西时立刻炸出来。

## 九、校验脚本（每次改曲线都跑）

```bash
# 前提：growth.ts 无引擎依赖、类型 import 用 import type
node --experimental-strip-types /tmp/verify.mts
```

脚本至少输出这些：

```
角色：等级 / maxHp / maxMp / 攻击区间 / 防御区间 / 每级需击杀 / 升级需经验
同级怪 vs 角色：怪hp / 怪攻击 / 怪防御 / 击杀刀数 / 击杀秒数 / 角色能扛刀数 / 能扛秒数
BOSS 天梯：每个 BOSS 的等级 / hp / 同级要打几刀
装备：件数 / 各部位权重是否都在表里 / 每条是否都是固定值 / 等级是否越界
装备：①「全部位同级装备合计 ÷ 裸属性上限」（验口径，应 = setPowerRate）
      ②「玩家实际可及的一套（等级 ≤ 玩家等级里最高的那件）÷ 裸属性上限」（验内容有没有跟上）
      ③ 裸装 / 满装两种状态下的击杀刀数与能扛刀数（验会不会打破锚点）
掉落：每只怪独立表的条目数 min/avg/max / 装备覆盖数 vs 全量装备数 / 非法 goodId·权重·数量区间 /
      件数区间是否合法并已接到怪物配置 / 每怪几百次「件数结算 + 抽取模拟」是否越界·可解析 /
      散落位置 1~40 件逐对最近距离是否 ≥ 最小间距（不重叠）
全局节奏：升到满级总击杀数 / 总经验 / 折合小时
断言：每项属性逐级递增；击杀刀数全程落在目标区间内；天梯覆盖玩家 1~满级无缺级
```

**验收标准**：击杀刀数全程稳定（例 5.42~5.57）、能扛刀数单调上升（前期脆后期肉）、
天梯无缺级、属性逐级递增、装备两套口径都算得出来。任何一条不满足就回去改曲线，别靠肉眼盯表格。

**关键：①②必须分开算。** ①证明「公式没错」，②暴露「内容缺口」。
只算 ① 会得出「完美 200%」的结论，实际上玩家在高等级只拿到 60%——因为一半部位只有 1 级装备。

**重构「取值方式」时的额外一步（强烈建议）**：改之前先把**旧实现**跑一遍，导出「每只怪的 等级 / 定位 / 七项属性」
成基线 JSON；改完用新实现重算并逐条比对（本次 220/220 零差异，含 21 只 BOSS 的倍率没丢）。
这样能证明「只换了取值方式、数值一个字没变」，比抽查几条靠谱得多；再顺手核对最终 Map 里
`key` / `tier` 没有泄漏进配置对象、必填字段无缺失。

## 十、实施顺序

1. 建 `growth.ts`（曲线 + 取值函数 + 设计目标注释）→ 写校验脚本，先确认曲线本身好看好用；
2. 改 `level.ts` 由曲线生成（这一步跑通后角色数值就位）；
3. 脚本批量改 `monster.ts`（切块 → 换展开 → 逆序回写），改完 grep 计数 + 抽查 2~3 条；
4. 装备：先确认「等级怎么排 / 全套占裸属性多少 / 部位怎么分 / 固定值还是区间」，再**先把锚点冲突算给用户看**
   （满装 vs 裸装的击杀刀数与能扛刀数），得到确认后再动 `equipments.ts`；
5. 挂其他养成线（战魂/药品/…），确认单调；
6. `tsc` + 项目自带检查 + 校验脚本全跑一遍；
7. 把「已知会出问题但现在不改的」列成清单交回用户（例：某张地图的怪等级跨度太大、经济线没做、
   某些部位只有低等级装备导致吃不满权重）。
