# 18 · 掉落系统重构设计（v2 · 已定稿）

> **状态**：**已定稿（2026-11-08 用户逐项拍板）**，按 #801 拆四批实施：世界级实体 → 流水 → 客户端 → 管理端。
>
> **一句话**：把掉落物从「击杀者的私人账本」升级成「世界里的实体」—— 所有人看得见、
> 归属者与队友先捡、30 秒后谁都能捡、**180 秒（3 分钟）**消失，全过程落库可查。
>
> **三条硬约束**：① **不碰新手引导**（第 3 步「把掉落捡起来」的判据、步骤表、
> 文案一律不动，见 6.6 与 11.6）；② **末段零提示**——最后 10 秒**不闪烁、不变色、
> 不显示秒数、也不做视觉弱化**，让掉落静静地到点消失；③ **只做怪物掉落**——
> 玩家主动丢弃暂放（见第十二节）。

## 零、已确认的决策

| # | 决策 | 选择 | 为什么 |
|---|---|---|---|
| 1 | 归属与拾取权 | **归属者 + 队友优先 30 秒；之后任何人可捡；180 秒消失** | 既防抢怪，又不让「没人捡的掉落」白白浪费 |
| 2 | 过期规则 | **统一 180 秒（3 分钟），末段零提示** | 3 分钟够逛一圈回来还看得见；末段什么都不画，是因为「挂机时看见倒计时/闪烁」既救不回东西，又平白加噪声 |
| 3 | 进程重启 | **清空地面掉落，每条记一条 `restart_lost`** | 无刷物品风险；管理端仍能看到「因重启丢了多少」 |
| 4 | 管理端范围 | **实时地面 + 最终结果流水 + 掉落反查 + 清空按钮**（四项全做） | 既能查「现在地上有什么」，也能查「这件东西最后去哪了」，还能反查爆率、必要时清理现场 |
| 5 | 新手引导 | **不参与本次改造**：步骤表、判据、文案全不动，只保证兼容 | 引导第 3 步靠 `picked` ok 推进，是「一改就卡死新号」的位置，见 6.6 |

## 一、为什么必须改结构（不是加两个字段能解决的）

### 1.1 现在的三份真相

```
配置真相 = 库表 monster_drops / drop_tables / runtime_params.drop_params   永久
内容真相 = 实时进程内存 dropLedgers: Map<accountId, Map<castId, entry[]>>   会话级
实体真相 = 客户端 DropManager.dropMap: Map<Node, DropItem>                  场景级
```

三份数据不在一个地方、生命周期不同 —— 这是目前所有掉落问题的根源。

### 1.2 六个硬缺陷（逐条带代码位置）

| # | 缺陷 | 现状 | 后果 |
|---|---|---|---|
| 1 | **账本按账号隔离** | `combat-settlement.service.ts` 的 `private readonly dropLedgers = new Map<string, Map<number, DropLedgerEntry[]>>()`，第一层键是 `accountId` | 别人的掉落**查不到账**，所以只能演不能捡（`spawnRemoteDrops` 明确注释「纯演出不可拾取」） |
| 2 | **定位用客户端生成的 castId** | `pick` 帧只带 `{ castId, index }`，`castId` 由 `CombatChannel.castSeq` 自增 | 不同玩家的 castId 完全撞车（都是 1、2、3…），**没有全局唯一标识**，无法做「世界里的一个东西」 |
| 3 | **没有 TTL** | `DropManager.dropMap` 只在「拾取成功 / 换图 reset / 节点被销毁后清残留」三处删除 | 地上的东西永不消失；别人击杀的更是只增不减，挂机久了场景节点堆积 |
| 4 | **拒绝原因几乎不告诉玩家** | `applyPickedFrame` 里只有 `bag_full` 弹提示，其余一律 `console.warn` | 玩家点掉落物没反应，不知道为什么；`unknown_drop` 还会 5 秒一次无限重试 |
| 5 | **服务端不校验位置** | `pickDrop(accountId, castId, index)` 没有任何坐标判断 | 只要知道 dropId/index，隔着整张图也能捡（改包即可），多人化后是明确的漏洞 |
| 6 | **全程不落库** | `dropLedgers` 纯内存，`world_drops` 这种表根本不存在 | 管理端查不到任何掉落记录；「这件装备最后被谁捡走了」永远无法回答 |

### 1.3 结论

第 1、2 条决定了**账本的归属主体必须从「账号」改成「世界（区 + 图）」**；
第 3、4、5、6 条是新实体模型上必须一次补齐的能力。所以这次是**结构改造**，不是补丁。

## 二、目标规则（玩家视角）

### 2.1 五条规则

| 规则 | 内容 |
|---|---|
| **可见** | 同区同图的所有玩家都能看到掉落物（图标、名称、数量、光柱），与「谁杀的」无关 |
| **归属** | 掉落物归击杀者所有；击杀时有队伍则同时归该队（记录掉落那一刻的 `partyId`） |
| **保护期** | 掉落后的 **30 秒**内，只有归属者本人与「掉落时同队」的在线队友能捡 |
| **开放期** | 30 秒后到 **180 秒**前，**任何人**都能捡 |
| **过期** | 掉落满 **180 秒**自动消失；**最后 10 秒不显示秒数、不闪烁、不变色、不做视觉弱化** |

### 2.2 时间轴

```
t=0        掉落生成 · 所有人看到 · 归属者与队友可捡
           │
t=30s      保护期结束 · 全图任何人可捡    ← 画面上没有任何变化
           │
t=170s     末段                        ← 画面上依然没有任何变化（零提示）
           │
t=180s     过期消失 · 广播 dropRemove(reason=expired) · 记一条 expired 流水
```

> **为什么是 180 秒**：60 秒对「打完一波、回头清背包、再回来捡」的节奏不够用，
> 尤其多人图里掉落一多就会有人捡漏；3 分钟既能让人从容绕回来，又不会让地面无限堆积。
> 挂机场景有 `maxGroundPerMap`（单图 200 件）兜底，所以时长放大不会撑爆内存。

### 2.3 谁能捡（判定矩阵）

| 拾取者 | t < 30s | 30s ≤ t < 180s | t ≥ 180s |
|---|---|---|---|
| 归属者本人 | ✅ 可捡 | ✅ 可捡 | ❌ 已消失 |
| 归属者当时同队的队友 | ✅ 可捡 | ✅ 可捡 | ❌ 已消失 |
| 同图其他玩家 | ❌ `protected`（主动点才提示，见下） | ✅ 可捡 | ❌ 已消失 |
| 不同图 / 不同区的玩家 | ❌ `not_on_map` | ❌ `not_on_map` | — |
| 归属者已下线 | 保护期仍生效（队友仍可捡） | ✅ 任何人可捡 | — |

> **队伍判定的口径（已定）**：`partyId` 在**掉落那一刻**快照进掉落物；拾取者的队伍用**当前** `partyId`。
> 所以归属者退队 / 队伍解散后，原队友立刻失去优先权（30 秒后大家平等）。
> 不额外存成员名单 —— 队伍解散时 `partyId` 自然失效，退化为「全员可捡」，不需要第二份真相。
>
> **「零提示」不等于不给反馈**：末段画面上什么都不画，但玩家**主动去点**保护期内的掉落时，
> 仍然回一句「XX 击杀的物品，还可拾取 N 秒」（见 6.3）。区别是「点击后的应答」与
> 「挂在屏幕上的倒计时」—— 前者只在玩家已经想捡时才出现。

## 三、新数据模型

### 3.1 核心实体 `DropEntity`

```ts
/** 世界里的一个掉落物（内存权威；实时进程持有） */
interface DropEntity {
  /** 服务端生成的全局唯一 id：`d_<zone>_<mapId>_<seq>`（seq 每区自增，重启从 1 开始也不冲突，见 5.7） */
  dropId: string;
  zoneId: number;
  mapId: string;
  /** 落点（世界坐标）—— **由服务端算好**，客户端不再自己散落（见 5.2） */
  x: number;
  y: number;
  goodId: string;
  count: number;
  /** 绑定状态：拾取时原样写进背包格子（能力不变） */
  bound: boolean;
  /** 溯源，只有装备有（能力不变） */
  from?: { role?: string; monster?: string; at?: number };
  /** 归属（#325 的归属设计保留，只是载体从账号账本变成实体字段） */
  owner: { accountId: string; roleId: string; name: string };
  /** 掉落那一刻归属者所在队伍（null = 无队伍）；保护期判定的依据 */
  partyId: string | null;
  /** 来源怪物（管理端与溯源用） */
  source: { instanceId: string; monsterKey: string; label: string };
  createdAt: number;
  /** = createdAt + ttlMs（默认 180000，即 3 分钟） */
  expireAt: number;
  /** = createdAt + protectMs（默认 30000） */
  protectUntil: number;
  status: "ground" | "picked" | "expired" | "overflow";
  /** 被拾取后填（落库流水用） */
  pickedBy?: { accountId: string; roleId: string; name: string; at: number };
}
```

`status` 的五个取值里，`picked` / `expired` / `overflow` 是**终态**，终态实体在写进
`drop_records` 后立即从内存与 `world_drops` 删除（只保留流水）。

### 3.2 内存索引 `DropField`

```ts
/** 实时进程持有：`zone:mapId` → dropId → 实体 */
private readonly ground = new Map<string, Map<string, DropEntity>>();
/** 全局反查（pick 帧只带 dropId，需要 O(1) 找到实体与所属图） */
private readonly byId = new Map<string, DropEntity>();
```

**与图实例解耦**：`world` 在「最后一个观看者离开」时会卸载图，但掉落物**不随图卸载**——
它的生命周期只由 `expireAt` 决定。理由：玩家逛一圈回来（< 180 秒）应该还能看到原地的东西，
这是「正常游戏」的直觉。图卸载时只需要停掉该图的 AI，掉落留着（数据量很小）。

### 3.3 新表 `world_drops`（当前地面投影）

实时进程写、存档进程（管理端接口）读。**跨进程只有 SQLite 这一条路**，与
`map_monitor_state` 同一范式。

```sql
CREATE TABLE IF NOT EXISTS world_drops (
  drop_id            TEXT PRIMARY KEY,
  zone_id            INTEGER NOT NULL,
  map_id             TEXT    NOT NULL,
  good_id            TEXT    NOT NULL,
  count              INTEGER NOT NULL,
  bound              INTEGER NOT NULL DEFAULT 0,
  x                  REAL    NOT NULL,
  y                  REAL    NOT NULL,
  owner_account_id   TEXT    NOT NULL,
  owner_role_id      TEXT    NOT NULL,
  owner_name         TEXT    NOT NULL,
  party_id           TEXT,
  monster_key        TEXT    NOT NULL,
  monster_instance_id TEXT   NOT NULL,
  origin_role        TEXT,
  origin_at          INTEGER,
  created_at         INTEGER NOT NULL,
  expire_at          INTEGER NOT NULL,
  protect_until      INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_world_drops_map ON world_drops(zone_id, map_id, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_world_drops_expire ON world_drops(expire_at);
```

这是**投影不是配置**：`config-tables.cjs` 的 `RUNTIME_TABLES` 里登记，不进 `config-sync.sql`。
重启后清空（见 5.5）。

### 3.4 新表 `drop_records`（最终结果流水）

append-only，一条掉落的一生只写一行终态。

```sql
CREATE TABLE IF NOT EXISTS drop_records (
  id                 INTEGER PRIMARY KEY AUTOINCREMENT,
  drop_id            TEXT    NOT NULL,
  zone_id            INTEGER NOT NULL,
  map_id             TEXT    NOT NULL,
  /** 冗余物品类型与名称：物品日后被删，这条记录仍要能看懂 */
  good_id            TEXT    NOT NULL,
  good_type          TEXT,
  good_label         TEXT,
  count              INTEGER NOT NULL,
  bound              INTEGER NOT NULL DEFAULT 0,
  monster_key        TEXT    NOT NULL,
  monster_label      TEXT,
  monster_instance_id TEXT   NOT NULL,
  owner_account_id   TEXT    NOT NULL,
  owner_role_id      TEXT    NOT NULL,
  owner_name         TEXT    NOT NULL,
  /** 结果：picked / expired / overflow / restart_lost */
  result             TEXT    NOT NULL,
  picked_account_id  TEXT,
  picked_role_id     TEXT,
  picked_name        TEXT,
  created_at         INTEGER NOT NULL,
  resolved_at        INTEGER NOT NULL,
  /** 存活时长（毫秒，= resolved_at - created_at），管理端排序用 */
  lived_ms           INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_drop_records_time ON drop_records(created_at DESC);
CREATE INDEX IF NOT EXISTS idx_drop_records_map ON drop_records(zone_id, map_id, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_drop_records_owner ON drop_records(owner_name, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_drop_records_result ON drop_records(result, created_at DESC);
```

**保留策略**（照抄 `map_monitor_events` 的攒批裁剪做法）：

- 保留 **7 天**，且每张图最多 **2000** 条；
- 裁剪不是每写一条就 `DELETE`，而是攒够 `trimEvery = 200` 条跑一次
  （`MapMonitorService` 的既有范式：每杀一只都 DELETE 会让 WAL 白涨）。

### 3.5 与旧账本的对照

| 旧 | 新 | 变化 |
|---|---|---|
| `dropLedgers: Map<accountId, Map<castId, entry[]>>` | `ground: Map<zone:mapId, Map<dropId, entity>>` | 归属主体从账号改成世界 |
| 定位 `{ castId, index }` | `dropId: string` | 全局唯一，跨玩家不撞车 |
| `picked: boolean` | `status` 四态 | 能区分「被捡 / 过期 / 挤掉」 |
| 无 | `owner` / `partyId` | 支持归属与队友共享 |
| 无 | `expireAt` / `protectUntil` | 支持 TTL 与保护期 |
| 无 | `x` / `y`（服务端算） | 支持距离校验与多人一致 |
| 无 | `world_drops` / `drop_records` | 管理端可查 |

`resetTargets()` / `dropAccount()` **不再清掉落**（世界级，与连接无关），只清幂等账
`recentSettles`。这是行为变化，要写进注释。

### 3.6 写放大与批量策略

挂机刷怪时掉落写入可能到 **10~20 行/秒**。策略：

| 动作 | 时机 | 是否同步写库 |
|---|---|---|
| 生成掉落 | `spawn()` | **否** —— 先进内存 + 标记 dirty，`flushMs`（默认 100ms）批量 UPSERT |
| 拾取 / 过期 / 挤掉 | `resolve()` | **否** —— 进 `pendingRecords` 队列，同一拍批量 INSERT + DELETE |
| 广播 | 同一拍 flush 后 | 合并成 `dropSpawn` / `dropRemove` 各一帧（群怪同死只发一帧） |

**代价**：实时进程被硬杀时，最多丢最后一拍（100ms）的生成记录。可接受，
且这类掉落本来就会随重启清场（记不到 `restart_lost` 也无所谓，它从没进过库）。

### 3.7 新表 `drop_clear_requests`（跨进程指令）

```sql
CREATE TABLE drop_clear_requests (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  zone_id      TEXT    NOT NULL,
  map_id       TEXT    NOT NULL,
  requested_at INTEGER NOT NULL,           -- 毫秒
  done_at      INTEGER,                    -- NULL = 还没执行
  cleared      INTEGER NOT NULL DEFAULT 0  -- 实际清掉多少件（3101 回写）
);
CREATE INDEX idx_drop_clear_pending ON drop_clear_requests(done_at, id);
```

只有 3101 会改 `done_at` / `cleared`；3100 只负责插入。这张表**只增不删**，
保留 30 天由现有备份清理带走即可（写操作本来就要留痕）。

> 为什么不复用 `runtime_params` 里的一个时间戳：清空是「按图」的，可能同时对三张图发起，
> 时间戳会互相覆盖。一行一次请求是最小且不会错的形状。详见 7.7。

## 四、协议改造

### 4.1 帧清单

| 帧 | 方向 | 状态 | 说明 |
|---|---|---|---|
| `world` | S→C | **改造** | `data.drops: RealtimeDropSnapshot[]` —— 进图/重连时的地面全量 |
| `dropSpawn` | S→C | **新增** | 一批掉落出现（同图广播，含击杀者） |
| `dropRemove` | S→C | **新增** | 一批掉落消失（被捡/过期/挤掉） |
| `pick` | C→S | **改造** | `{ dropId }` 取代 `{ castId, index }` |
| `picked` | S→C | **改造** | 带 `dropId` + 细分 `code` |
| `dropNotice` | S→C | **新增** | 稀有掉落全服公告（`tier='boss'` 掉落时，30 秒最多一条，不落库） |
| `settle` | S→C | **保留** | `reward.drops` 仍填（带 `dropId`），但客户端**不再用它铺地** |
| `monster-ai` | S→C | **保留** | `kills` 仍带 `drops`，但客户端只用来清场，不铺掉落 |

> **为什么保留 `reward.drops` 却不铺地**：`settle` 的 reward 是击杀者结算的一部分
> （经验/升级/掉落内容都要能一次拿到），删字段会牵动 e2e 断言与客户端多处。
> 保留字段、只改「谁来铺」这一件事，改动面最小且不丢信息。

### 4.2 逐帧字段

**`RealtimeDropSnapshot`（`world.drops` 与 `dropSpawn` 共用一个形状）**

```ts
interface RealtimeDropSnapshot {
  dropId: string;
  goodId: string;
  count: number;
  bound: boolean;
  x: number;
  y: number;
  /** 归属者显示名（客户端用来显示「XX 的物品」） */
  ownerName: string;
  /** 归属者账号（客户端判断「是不是我的」；只用于展示，不作权威） */
  ownerAccountId: string;
  /** 保护期结束时刻（绝对毫秒，服务端时钟） */
  protectUntil: number;
  /** 过期时刻（绝对毫秒，服务端时钟） */
  expireAt: number;
  /** 距离过期还有多久（服务端算好的相对量）—— 客户端**只用它**做倒计时，避免时钟漂移 */
  expireInMs: number;
  /** 距离保护期结束还有多久（同上，0 = 已开放） */
  protectInMs: number;
}
```

**`picked`（S→C）** —— 成功形状基本不变，错误码扩充：

```ts
interface RealtimePickedOk {
  dropId: string;
  ok: true;
  revision: number;
  placed: RealtimePlacedCell[];
  alreadyPicked: boolean;
  /** 这次实际入包的物品与数量（客户端飘字用，不再从节点上取） */
  goodId: string;
  count: number;
}

interface RealtimePickedError {
  dropId: string;
  ok: false;
  code:
    | "unknown_drop"      // 不存在 / 已从内存移除
    | "already_picked"    // 被别人抢先，或自己重传
    | "expired"           // 已过期
    | "protected"         // 保护期内且不是归属者/队友
    | "too_far"           // 距离超限
    | "not_on_map"        // 不在同一图/区
    | "bag_full"          // 背包满
    | "no_role"           // 没有在线角色
    | "role_kicked"       // 被踢下线
    | "item_gone"         // 物品配置已被删
    | "pick_failed";      // 其它
  message: string;
  /** protected 专用：还要等多少毫秒 */
  waitMs?: number;
  /** protected 专用：归属者名字，用于文案 */
  ownerName?: string;
  /** already_picked 专用：拾取者名字 */
  byName?: string;
}
```

### 4.3 时序：自己击杀

```
客户端A 出手 ──cast──▶ 服务端
                        ├─ 结算伤害 → 击杀
                        ├─ rollDrops（纯抽取，不带 id）
                        ├─ DropService.spawn()   → 内存实体 + dirty + pendingSpawn
                        ├─ settleKillReward()    → reward.drops 带 dropId
                        └─ 100ms 后 flush：写 world_drops + 广播 dropSpawn 给全图
客户端A ◀─ settle（经验/升级/掉落内容）
客户端A+B ◀─ dropSpawn（同一份，两个客户端走完全相同的路径铺地）
```

**关键**：掉落不再有「击杀者专属路径」和「旁观者演出路径」两条。只有一条。

### 4.4 时序：别人击杀 + 抢捡

```
客户端B 击杀 → spawn(owner=B, partyId=B的队伍) → 全图 dropSpawn
客户端A 走上去自动拾取 → 本地预判：保护期内且 A 不是 owner、不在同队
                        → 不发请求，直接提示「B 击杀的物品，还可拾取 23 秒」
t=30s 后
客户端A 走上去 → 发 pick{dropId}
服务端 → 校验通过 → RolesService.pickDrop 入包
       → 广播 dropRemove(reason=picked, byName=A)
       → picked{dropId, ok:true, placed, revision}（只回给 A）
       → 记 drop_records(result=picked, picked_name=A)
```

### 4.5 时序：过期

```
DropService 的 sweep 定时器（1000ms）扫描 expireAt <= now
  → status=expired → 广播 dropRemove(reason=expired) → 记流水 → 删内存与 world_drops
```

## 五、服务端改造

### 5.1 新服务 `DropService`

位置：`server/src/modules/realtime/drop.service.ts`，注册进 `RealtimeModule`。

| 方法 | 职责 |
|---|---|
| `spawn(input): DropEntity[]` | 生成实体（算散落坐标）+ 进内存 + 标 dirty + 排队广播 |
| `snapshotOf(zoneId, mapId): RealtimeDropSnapshot[]` | 进图快照（`world` 帧用） |
| `pick(accountId, dropId): RealtimePickedData` | **唯一拾取入口**：全部校验 + 委托入包 + 状态迁移 + 排队广播 + 记流水 |
| `flush()` | 定时器：批量写 `world_drops`、批量写 `drop_records`、批量广播 |
| `sweep()` | 定时器：过期扫描 + 单图超限裁剪 |
| `onBootstrap()` | **仅实时进程**：把上次残留的 `world_drops` 全部转 `restart_lost` 并清表 |
| `statsOf(zoneId, mapId)` | （可选）给管理端「当前地面」计数用；管理端也可以直接读库 |

注入：`DatabaseService`、`RolesService`、`PlayerPresenceService`、`PartyService`、
`RuntimeParamsRepository`、`GameEventsService`（可选，广播 `drop:picked` 给任务/成就）。

### 5.2 散落坐标改由服务端决定

现在是客户端 `DropScatter.scatterDropPositions()` 算偏移 —— **多人化后必须搬服务端**，
否则两个客户端对同一堆掉落摆的位置不一样，距离校验也对不上。

做法：

- 把 `scatterDropPositions(count, minDistance)` 这份纯函数**原样复制**到
  `server/src/modules/realtime/drop-scatter.ts`（无引擎依赖，可直接搬）；
- 服务端在 `spawn()` 里算好每件的绝对坐标 `x = deathX + offset.x`，写进实体；
- 客户端 `DropScatter.ts` **删除**，`createDropNode` 直接用服务端坐标。

**跨击杀的重叠**：同一片区域连续死亡时，两次击杀的散落点仍可能重合。处理：
`spawn()` 时如果新点与**该图已有掉落**距离 < `scatterMinDistance / 2`，沿径向推一圈
（最多试 8 次）。这一段是新逻辑，文档里单列，避免「一堆东西叠在一个点上」的老问题。

### 5.3 拾取校验九步（顺序不能改）

```
1. dropId 在 byId 里？                      → 否则 unknown_drop
2. 实体 zoneId/mapId == 拾取者当前图？        → 否则 not_on_map
3. status === "ground"？                    → picked → already_picked（带 byName）
                                              expired → expired
4. now < expireAt？                          → 否则 expired（顺手 resolve）
5. 归属判定：
   a) accountId === owner.accountId          → 通过
   b) now >= protectUntil                    → 通过
   c) 实体 partyId 非空 且 拾取者当前 partyId 相同 → 通过
   d) 其余                                    → protected（带 waitMs / ownerName）
6. 距离：presence 位置已知？                  → 未知则放行（刚进图还没上报）
   距离 > pickRange（默认 120）？             → 否则 too_far
7. 在线角色在？                              → 否则 no_role
8. RolesService.pickDrop（背包放不下 → bag_full；物品被删 → item_gone）
9. 成功：status=picked + pickedBy → 排队 dropRemove + 记流水 + 返回 ok
```

**为什么第 6 步「位置未知就放行」**：`presence` 的位置来自客户端节流上报，刚进图的
几百毫秒内可能是空。这里如果拒绝，正常玩家会莫名捡不起来。放行的风险是「位置未知期间
可以远程捡」，但那个窗口只有几百毫秒且要求玩家先杀掉怪 —— 比误拒正常玩家划算。
（**已定**：fail-open，见第十二节第 2 条。）

**并发安全**：`pick()` 全程同步（Node 单线程 + `node:sqlite` 同步驱动），两个玩家同时点
同一件时天然串行，第二个看到 `status=picked` 得到 `already_picked`。**不需要额外加锁**，
但注释里要写明这个前提（以后有人改成 async 就会破）。

### 5.4 过期与清理

| 定时器 | 间隔 | 做什么 |
|---|---|---|
| `dropSweep` | 1000ms（可配） | 扫 `expireAt <= now` → 过期；扫单图超 `maxGroundPerMap` → 挤掉最旧 |
| `dropFlush` | 100ms（可配） | 批量写库 + 批量广播 |

**单图超限**（`maxGroundPerMap = 200`）：内存与帧大小都要有上限。超出时按 `createdAt`
从旧到新挤掉，记 `overflow` 流水并广播 `dropRemove(reason=overflow)`。
理由：一张图同时有 200 件掉落已经是「完全没人捡」的极端。

### 5.5 重启清场

`DropService` 实现 `OnApplicationBootstrap`，但**只有实时进程执行**：

```ts
if (!this.options.realtime) return;   // AppModule.register({ realtime: true })
```

启动时：

1. `SELECT * FROM world_drops` 读残留（上一个进程没来得及清的地面掉落）；
2. 每条写一行 `drop_records(result = "restart_lost", resolved_at = now)`；
3. `DELETE FROM world_drops`；
4. 内存为空，开始接客。

**为什么必须限定实时进程**：`server`（3100）与 `server-realtime`（3101）共用同一份代码、
同一个库。如果两个进程都跑这段，**管理端重启也会把游戏里地上的东西清空**。
判据用 `AppModule.register({ realtime })` 注入的选项，与 `main.realtime.ts` 同源。

### 5.6 图卸载与掉落解耦

`world` 在最后一个观看者离开时会卸载图（连 `world_monsters` 一起清）。掉落**不跟着清**：

- `DropService.ground` 的键虽然是 `zone:mapId`，但**没有**任何「图卸载」回调去删它；
- 只有 `expireAt` / `overflow` / `picked` 三种原因会移除实体；
- 图重新加载时，`world.join()` 里拼 `drops: this.drops.snapshotOf(...)` 即可恢复到新进图者的屏幕。

代价：极端情况下（图长期没人、掉落不断产生）内存里会留一批过期实体 —— 已经被 `sweep`
清掉了，不会留。

### 5.7 dropId 的生成

```ts
// 每区一个自增序号；进程重启后从 1 开始也没关系 —— 旧 id 已随清场消失
dropId = `d_${zoneId}_${mapId}_${++seq}`;
```

- **不用 UUID**：日志与 SQL 里可读，且能一眼看出属于哪张图；
- **重启不会撞车**：清场时 `world_drops` 清空、旧 id 全部写进 `drop_records` 但不再被引用；
  即使管理端按 id 查，`drop_records` 里可能有两个同 id 的历史行 —— 所以查询按
  `drop_records.id`（自增）排序，不按 `drop_id` 去重。这一点写进接口注释。

### 5.12 稀有掉落全服公告（新增出口）

现有的 `chat` 帧里 `world` 频道**只广播给同图观看者**（见 `CHAT_CHANNELS` 注释），
没有「全服下发」这个出口。所以公告不能借用聊天，要新增一条最小链路：

| 环节 | 做法 |
|---|---|
| 判定 | 击杀者击杀的怪 `monsters.tier = 'boss'`，且本次掉落里**至少有一件非货币物品** |
| 抑制 | 全服**每 30 秒最多 1 条**（进程内一个时间戳；超出的丢掉并计数，供管理端看「被抑制了多少」） |
| 开关 | `drop_params.announceBoss`（默认 `true`），关掉就完全不发 |
| 出口 | `RealtimeService.broadcastAll(frame)` 遍历 `this.connections`（实时进程持有全部 WS 连接，不需要跨进程） |
| 帧 | 新 `dropNotice`（服务端→客户端，无上行）；正文由服务端拼好，客户端不做字符串拼接 |
| 不落库 | 公告是瞬时事件，不进 `drop_records`；要追溯就看流水的 `picked` 行 |

```ts
/** 服务端 → 客户端：稀有掉落公告（全服，不落库；30 秒内最多一条） */
export interface RealtimeDropNotice {
  type: "dropNotice";
  data: {
    /** 服务端拼好的整句，客户端原样展示 */
    text: string;
    goodId: string;
    count: number;
    /** 击杀者角色名（已脱敏：只给名字，不给 roleId） */
    killerName: string;
    monsterLabel: string;
    ts: number;
  };
}
```

> **为什么给整句而不是给字段让客户端拼**：同一件事要出现在飘字、聊天系统行、
> 以后的公告栏三处，拼装逻辑留在服务端就只有一份；客户端换皮不用改文案结构。
> 文案模板放 `server/src/common/constants/drop-notice.ts`，与客户端 `texts.ts` 不同源（避免两份真相）。

### 6.2 过期（零提示，不给任何末段表现）

- 每条掉落记录在 `onDropSpawn` 里算一次：`receivedAt = Date.now()`、
  `expireAtLocal = receivedAt + expireInMs`、`protectUntilLocal = receivedAt + protectInMs`，
  并置 `hasExpiry = true` —— **不用服务端的绝对时间**，避免客户端时钟错乱；
  任一相对量缺失时 `hasExpiry` 保持 `false`，`canPickLocally` 直接放行（fail-open，见 6.6）；
- **末段不做任何表现**：不显示秒数、不变色、不改 alpha、不做缩放脉冲、不加呼吸灯。
  `update(dt)` 里只用 `expireAtLocal` 判「本地到期」，不参与任何绘制；
  也因此**不建 `warnMs` 这一列**（建了没人读就是死配置，见 #747 的教训）；
- 到 0：不自己销毁，**等 `dropRemove`**。理由：服务端才是权威，客户端提前删会与
  「服务端刚广播被捡走」打架（会出现「东西没了但没入包」的错觉）。
  到点后如果还没收到 remove（网络断了），按 `expireInMs + 3s` 兜底隐藏。

> **为什么不给末段提示**：TTL 是 180 秒，末段在 170 秒 —— 玩家多半在挂机，
> 屏幕上的倒计时既救不回东西，又会被读成「必须马上跑过去」而制造焦虑；
> 挂着时反复闪更烦。真正要回答的是「怎么没了」，而那由下面两个**事后**动作回答：

| 时机 | 玩家的感知 |
|---|---|
| 服务端 `dropRemove(reason=expired)` 到达 | 掉落节点直接消失（无过渡动画） |
| 玩家点了一个本地已到期的节点 | 一句「物品已消失」（见 6.3，只在主动点击时出现） |

> 若将来真要做末段提示，正确顺序是**先加列再改客户端**，并同步 `config-sync.sql` 与快照；
> 暂放这一列，避免留一列没人读的配置。

### 6.3 归属预判（减少无谓请求）

判定函数见 **6.6 的 `canPickLocally`**（那里是唯一一份实现，含 fail-open 的每个分支）。
行为口径：

- `protected` 时**不发 pick 帧**，直接提示「XX 击杀的物品，还可拾取 N 秒」（节流 1.5 秒）；
- `expired` 时直接移除节点（并提示「物品已消失」）；
- 其余一律发请求，由服务端裁定 —— 客户端预判永远是**提示优化**，不是权限判断。
- **判不出来就放行**（owner 未知 / 队伍未知 / 时间戳缺失），这条同时保护了新手引导（见 6.6）。

> 需要 `RealtimeDropSnapshot` 增加 `partyId?: string`（只有非空时下发），
> 以及客户端 `PartyStore` 暴露 `myPartyId`（已有队伍态，确认字段名即可）。

### 6.4 拾取失败文案表（每个 code 一句话）

| code | 文案（`configs/texts.ts` 新增 key） | 提示形式 |
|---|---|---|
| `protected` | `「{owner}」击杀的物品，{n} 秒后可拾取` | 中央飘字，节流 1.5s |
| `bag_full` | 沿用现有 `pickup_full_tip` | 中央飘字，节流 `fullTipInterval` |
| `already_picked` | `物品已被「{name}」拾取` | 中央飘字 |
| `expired` | `物品已消失` | 中央飘字 |
| `too_far` | `距离太远，请靠近后再拾取` | 中央飘字 |
| `not_on_map` | `不在同一地图，无法拾取` | 中央飘字 |
| `unknown_drop` | `物品已不存在` | **静默移除节点**，不再无限重试 |
| `item_gone` | `该物品已下架，无法拾取` | 中央飘字 + 移除节点 |
| `no_role` / `role_kicked` | `登录状态异常，请重新登录` | 中央飘字 |

**统一节流**：所有提示共用一个 `lastTipAt`，最小间隔 **800ms**，避免「一踩上去刷十条」。

### 6.5 进图 / 重连对齐

- `world` 帧带 `drops`：**先 `reset()` 再按快照重建**（换图时旧图的节点必须清掉）；
- 断线重连：`world` 帧会重发，同样重建 —— 这修掉了现在「重连后残留不可拾节点」的老问题；
- `DropManager.reset()` 保留，但只在**换图 / 重连**时调用，不再用于「清掉落」的日常逻辑。

### 6.6 自动拾取与新手引导（**新手引导零改动**）

自动拾取三条不变：

- `autoPickup` 遍历 `items`，跳过 `canPickLocally() !== true` 的（省请求）；
- `pendingPicks` 机制保留（在途去重 + `pickReplyTimeout` 5s 超时重试）；
- 自动拾取半径 `autoPickupRadius`（默认 40）与「踩上去就捡」手感完全不变。

**新手引导的兼容要求**（这是本次最容易失手的地方 —— 引导第 3 步「把掉落捡起来」
就卡在掉落链路中间，判据一变新号就永久卡步）：

| 契约 | 现状 | 本次要求 |
|---|---|---|

**`canPickLocally` 必须 fail-open**（这条直接决定引导会不会卡）：

```ts
// 只有「明确知道是别人的、且明确在保护期」才拦；任何一环判不出来就放行，
// 让服务端去裁定 —— 客户端预判只用来省请求，绝不能变成权限判断。
// receivedAt / expireAtLocal / protectUntilLocal / hasExpiry 都在 onDropSpawn 里算（相对量 + 本地时钟）
private canPickLocally(drop: DropItem): true | "protected" | "expired" {
  if (!drop.hasExpiry) return true;                                  // 时间戳没算出来 → 放行
  if (Date.now() >= drop.expireAtLocal) return "expired";
  const me = RealtimeClient.onlineUserId;
  if (!me || !drop.ownerAccountId) return true;                      // 任一侧未知 → 放行
  if (drop.ownerAccountId === me) return true;                        // 自己的：恒可捡
  if (Date.now() >= drop.protectUntilLocal) return true;              // 已开放 → 放行
  if (drop.partyId && PartyStore.myPartyId && drop.partyId === PartyStore.myPartyId) return true;
  return "protected";
}
```

推论（写进实现注意事项）：**引导期间不做任何特判** —— 不因为「玩家在引导第 3 步」就延长 TTL、
放宽归属、跳过保护期。特判会让「引导能过、真机不能过」的差异藏起来，反而更难查。
新号自己杀的怪，掉落归自己、自己恒可捡、自动拾取照常触发 → 第 3 步与今天完全一致。

> 唯一的行为差异：老版本掉落后 60 秒消失，新版本 180 秒。新号从第 2 步（打怪）到第 3 步
> （捡起来）之间通常几秒，**不可能**因为 TTL 变化而失败。

### 7.5 权限点

```ts
// server/src/common/constants/permission.ts
/** 查看掉落监控与掉落流水（只读业务数据，不含个人信息） */
DROP_READ: "drop:read",
/** 清空某图地面掉落（写操作；不给 viewer） */
DROP_CLEAR: "drop:clear",
```

- `ROLE_PERMISSIONS`：`SUPER` / `ADMIN` 自动有（`ALL_PERMISSIONS`）；**`VIEWER` 只给 `drop:read`** ——
  掉落流水里只有玩家角色名（`role:read` 已给 viewer），没有邮箱/IP 这类个人信息；
  但 `drop:clear` 会**删掉玩家还没捡的东西**，属于不可逆写操作，viewer 与运营只读账号一律不给；
- `PERMISSION_LABELS` 加两条中文名「查看掉落记录」「清空地面掉落」。

### 7.6 审计：两个只读页不进审计，清空必须进

`AuditInterceptor` 只审**写方法**（POST/PATCH/PUT/DELETE）。掉落监控与流水全是 GET，
天然不进审计；**新增的 `POST /admin/drops/clear` 是写操作**，必须：

- `@AuditTarget("drop")`，并在 `audit-target.decorator` 的 `AUDIT_TARGET_TYPES` 里登记 `"drop"`；
- 审计正文记 `zoneId / mapId / 清掉多少件 / 请求人`（**不记每件物品明细** —— 明细在同一次操作
  写出的 `drop_records` 里，重复存两份会很快把审计表撑爆）；
- 二次确认：请求体必须带 `confirm: true` 且 `mapId` 与路径参数一致，否则 400。

### 7.7 清空某图地面（跨进程指令）

地面掉落活在 **3101（实时进程）的内存**里，管理端打的是 **3100（存档进程）** ——
两个进程共享 SQLite 但不共享内存，所以这次「清空」本质上是一条**跨进程指令**，
不能像普通写接口那样改完库就完事：

| 步 | 谁做 | 做什么 |
|---|---|---|
| 1 | 管理端 | `POST /admin/drops/clear {zoneId, mapId, confirm:true}` |
| 2 | 3100 | 落一行 `drop_clear_requests(id, zone_id, map_id, requested_at, done_at, cleared)`，立刻返回「已受理」 |
| 3 | 3101 | `sweep` 每拍（1 秒）读一次「`done_at IS NULL` 的请求」；对目标分域执行 `clearMap()`：每条写一条 `drop_records.result='overflow'`（原因记 `manual_clear`），然后广播 `dropRemove(reason="cleared")` 给同图观看者 |
| 4 | 3101 | 回写 `done_at` + `cleared`（实际清掉多少件） |
| 5 | 管理端 | 页面 3 秒轮询里看 `cleared`，显示「已清空 N 件」；超过 10 秒未完成 → 提示「实时进程可能没起来」 |

**为什么走表而不是 HTTP 回调**：3101 此刻可能正在重启、也可能只在内网某端口上；
落表 + 轮询读是唯一在「进程挂了、重启后补做」时仍然正确的做法 —— 重启后 3101 会先执行
未完成的清空请求，再开始 tick。这与 #809 计划的 `world_reload_requests` 是同一形状，
将来合并成一张通用 `world_commands` 表即可（本期不合并，避免动 #809 的范围）。

**不允许的偷懒**：不要去 3100 直接 `DELETE FROM world_drops WHERE map_id = ?` 就返回成功 ——
内存里那批掉落还活着，会在下一次 `flush` 里被写回库，页面看起来「清了又出现」。

## 八、新增配置项

全部落在 `runtime_params.drop_params`（JSON 列，服务端每次击杀/拾取现读，**改完立即生效**），
管理端「运行时参数 → 掉落手感」增加对应输入框（`RuntimeParamsDto` 的 `drop` 组要加字段，
否则管理端改不了 —— 这正是 `monster_ai` 那组至今没有入口的原因）。

| 键 | 默认 | 范围 | 含义 |
|---|---|---|---|
| `bindChance` | 0 | 0~100 | 随机绑定概率（已有，不动） |
| `ttlMs` | **180000** | 10000~300000 | 掉落存活时长（默认 3 分钟，上限 5 分钟） |
| `protectMs` | 30000 | 0~`ttlMs` | 归属保护期 |
| `pickRange` | 120 | 40~400 | 服务端校验的最大拾取距离（像素） |
| `maxGroundPerMap` | 200 | 20~1000 | 单图地面掉落上限（TTL 变长后这一条是唯一的堆积兜底） |
| `announceBoss` | true | 布尔 | 稀有掉落全服公告开关（只对 `tier='boss'` 生效，30 秒最多一条） |
| `autoPickupRadius` | 40 | 20~120 | 客户端自动拾取半径（已有，不动） |
| `scatterMinDistance` | 52 | 20~120 | 散落最小间距（已有，现在服务端也要用） |
| `fullTipInterval` | 1500 | 500~10000 | 背包满提示间隔（已有） |
| `pickReplyTimeout` | 5000 | 1000~15000 | 拾取应答超时（已有） |

**校验**：`protectMs ≤ ttlMs`、`pickRange ≥ autoPickupRadius`。
不满足时服务端按「取小 / 取大」夹逼并 warn，管理端保存时直接 40000 报错。

> **没有 `warnMs`**：末段零提示是已定决策（见 2.2 与 6.2），这一列不建 ——
> 建了没人读就是死配置（#747 的教训）。将来要做末段提示，先加列再改客户端，别反过来。

**改 `ttlMs` 的容量提醒**：单图上限 200 件在「60 秒 TTL」下约等于 3.3 件/秒的吞吐，
180 秒下就只剩 1.1 件/秒 —— 刷怪密集的图会比以前更早触发 `overflow`。
管理端改 `ttlMs` 超过 180000 时，表单要提示「建议同时上调 `maxGroundPerMap`」。
（不自动联动：两个值各自独立，联动会让运营以为自己只改了一个。）

代码常量（不进运行时参数，改需要发版）：`dropFlushMs = 100`、`dropSweepMs = 1000`、
`dropRecordsKeepDays = 7`、`dropRecordsPerMap = 2000`。

### 11.5 手工验收清单（你来点）

```
1. 两个客户端（或一个客户端 + 一个旁观账号）进同一张图
2. A 杀怪 → 两边**同时**看到同一堆掉落，位置一致
3. B 走上去 → 提示「A 击杀的物品，还可拾取 N 秒」，捡不起来
4. 等 30 秒 → B 再走上去 → 捡起来，A 那边该掉落立刻消失
5. A 杀一只怪后不管 → 挂机到 170 秒，**画面上什么都没有变化**（无秒数、无闪烁、不变色）
   → 180 秒掉落直接消失，不留过渡动画
6. A 杀怪 → A 自己立刻捡 → 正常入包（保护期对自己无感）
7. 背包塞满 → 捡 → 提示「背包已满」，物品还在原地
8. 管理端「掉落监控」→ 能看到当前地上的东西、剩余时间（进度条按 180 秒走）
9. 管理端「掉落流水」→ 能看到上面每一次的结果（picked / expired）
10. 重启 realtime 容器 → 地上东西消失，流水多出 restart_lost
11. **新号走一遍引导**：走路 → 打怪 → 第 3 步「把掉落捡起来」自动过 → 背包 → 技能 → 聊天
    （全程不看掉落存在时长，只确认第 3 步没有卡住）
12. 掉落物名字左侧有归属者小头像（B 视角看 A 的掉落）；A 下线后头像消失、只剩「A的」
13. 杀一只 boss → 全服（不同图的两个号）同时看到一行公告飘字，3 秒后消失
14. 管理端「怪物掉落」反查：输一件装备名 → 列出会掉它的怪与权重
15. 管理端「掉落监控」点「清空本图地面」→ 勾选 + 输地图名 → 3 秒内两客户端该图掉落全部消失，
    流水多出 N 条 `overflow`（原因 `manual_clear`），审计里有一条清空记录
```

### 11.6 新手引导回归（为什么单列一节）

引导的致命失败模式是**静默卡步**：第 3 步推进不了，气泡一直挂着，玩家以为游戏坏了，
而服务端日志一片正常。所以验收里单列一条，并且实现时按下面顺序自查：

| # | 自查 | 判据 |
|---|---|---|
| 1 | `GuideStore.notify(GUIDE_EVENT.PICKUP)` 还在 ok 分支 | `Grep "GUIDE_EVENT.PICKUP"` 命中 `DropManager.ts` 且调用点仍在 `applyPickedFrame` 的 ok 之后 |
| 2 | ok 分支的 `StorageManager.applyPickResult` 先执行 | 没应用背包就 notify，玩家会「引导过了但包里没东西」 |
| 3 | `canPickLocally` 对自己的掉落恒 `true` | 用真实账号杀一只怪，自动拾取必须触发；若被拦，日志会显示没发 pick 帧 |
| 4 | 重连 / 换图后引导进度不丢 | 进度存在 `role.guide`，走 `StorageManager.updateOnlineRole`，与掉落无关 |
| 5 | 引导期间一次 `DropManager.reset()` 都没有被顺手调用 | `reset()` 只挂在换图 / 重连 |
| 6 | 引导第 3 步不依赖「掉落物存在 60 秒」 | 文案里没有秒数；TTL 改 180 秒后更宽松，不存在「以前刚好够、现在不够」 |

## 附录 A · 状态机

```
                 spawn()
                   │
                   ▼
              ┌─────────┐
              │  ground │◀── 保护期结束（只改时间，不改状态）
              └────┬────┘
      ┌────────────┼─────────────┬──────────────┐
      │ pick 成功  │ 到 expireAt │ 超单图上限   │ 进程重启
      ▼            ▼             ▼              ▼
  ┌────────┐  ┌─────────┐  ┌──────────┐  ┌───────────────┐
  │ picked │  │ expired │  │ overflow │  │ restart_lost  │
  └────────┘  └─────────┘  └──────────┘  └───────────────┘
      │            │             │              │
      └────────────┴─────────────┴──────────────┘
                   ▼
        写 drop_records（终态）· 删内存 · 删 world_drops
```

**不变式**：一个 `dropId` 只能有一次终态迁移；终态之后 `byId` 里立刻查不到
（所以第二次 pick 得到 `unknown_drop`，而不是 `already_picked`）。
唯一例外：`already_picked` 只在「同一次 pick 的重传」与「两人同时点、后者晚到」两种情况下返回 ——
实现上靠**终态迁移与删除之间不留 await** 保证。
