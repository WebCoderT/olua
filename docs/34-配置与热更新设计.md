### 0.2 已落形态（2026-11-10，#881 / #882 / #883）

设计稿里写的东西大多按原样落了，下面六处**与上面表格不一样**，以此为准：

| 设计稿写的 | 实际落的 | 为什么改 |
|---|---|---|
| `GET /config/version` | **`GET /game-config/version`** | 现有快照在 `GET /game-config/snapshot`，元信息与内容同前缀；另开 `/config` 前缀会让「同一个东西的两个地址」变成两处登记 |
| 快照返回体加 `version` 字段 | 快照**响应头带 `ETag: W/"cfg-<version>"`** + `Cache-Control: no-cache`，客户端 `If-None-Match` 命中即 **304**；另外单给一个 `GET /game-config/version` | 往 12 个 service 组装的体里塞一个字段 = 改 DTO + 客户端 `apply-snapshot` 区 0 + 快照契约审计 + 几十套客户端单测；ETag 走响应头，**客户端一行不用改**（这轮只做服务端，Cocos 侧零改动） |
| `config_revisions` 六列 | 多了 **`table_count` / `row_count`** | 列表页要显示「这一层影响了多大面」，否则每层都得点开 diff 才知道；落层时顺手算，读取零成本 |
| diff「按表统计改了几行，到字段级」 | **只到行级**：逐表 `added` / `removed`（行签名比较），改一行显示成「一删一加」 | 字段级要存列级快照并做跨列对齐，收益仅「看是哪个字段变了」；见 §八 |
| 刀 ⑥ 导出接口化 + 「未导出」红字 | 暂时放置（`make config-export` 仍是唯一出口） | 接口化要先回答「导出的文件落到哪、谁能下」，且现有命令已幂等；重开条件见 §八 |
| 刀 ②⑤ 客户端轮询 + `configDirty` 推送 | 暂时放置（服务端已能回答「是不是最新」，客户端还不会问） | 这一轮按用户口径「只做服务端」，见 §八 |

**已实测的能力**（`server/test/e2e-config-version.cjs`，57 条断言）：
写配置 → 版本 +1 且落一层 · 非配置写（如公告）**不** +1 · ETag 命中 → 304、`*` 命中、旧值不命中 ·
同版本两次快照**同一对象**（缓存） · 回滚单事务全量恢复且历史不删 · 节流合并 / 跨人不合并 / 回滚不吃节流 ·
保留 20 层 · 导入版本闸（落后即拒，`--force` 放行）。

## 一、五个问题

### 1.1 客户端不知道自己是不是最新

`snapshot()` 返回一个纯数据对象，没有版本号。客户端拿到就填表，
之后**再也不会问**。于是运营改了技能伤害，在线玩家打到下次重登都还是旧数值 ——
而且客户端**无法自查**（它连「我这份是哪一版」都不知道）。

### 1.2 没有「发布」这个动作

管理端 50 个页面，每个保存按钮都直接写库。写库之后：

- 服务端**下一个请求**就用新值（读库，好）；
- 客户端**永远不知道**（拉了快照就不再看）；
- 没有「这次改动是一批」的概念（改 20 张表要么全生效要么全不生效，现在只能一条条点）。

### 1.3 没有回滚（已定：留 20 层）

`audit_logs` 记的是「PUT /admin/equipments/xxx，detail 里有前后值」。
理论上能人工照着改回去，但：

- `detail` 是字符串，不是结构化 diff；
- 一次改 50 个字段就是 50 条日志，人工还原等于重做一遍；
- 改错后**没有一条命令能回到 10 分钟前**。

### 1.4 出厂 SQL 与库是两份真相

`config-sync.sql` 与运行库靠 `make config-check` 比。运营在管理端改了数，
没重新导出 SQL → 下次部署用出厂 SQL 起新库，**改动就没了**。
现在靠人记得「改完要 export」，这是流程而不是机制。

### 1.5 「加一张表登记五处」靠人记

`config-tables.cjs` 两份清单 + `gen-api.cjs` 的 MODULES + 两套审计的类型表。
漏一处通常是**审计报错**才发现（有时候审计本身也漏了，就成了假绿）。

## 二、目标形态

### 2.1 配置版本：一个自增值

```sql
CREATE TABLE config_version (
  id          INTEGER PRIMARY KEY CHECK (id = 1),  -- 单行
  version     INTEGER NOT NULL DEFAULT 1,
  updated_at  INTEGER NOT NULL DEFAULT 0,
  updated_by  TEXT NOT NULL DEFAULT ''
);

CREATE TABLE config_revisions (
  version     INTEGER PRIMARY KEY,
  label       TEXT NOT NULL DEFAULT '',      -- 运营填的一句話说明
  payload     TEXT NOT NULL,                 -- 全量配置 JSON（38 张表）
  byte_size   INTEGER NOT NULL DEFAULT 0,
  created_by  TEXT NOT NULL DEFAULT '',
  created_at  INTEGER NOT NULL
);
```

| 规则 | 说明 |
|---|---|
| 谁 +1 | **任何**配置写接口成功后（统一在拦截器里做，不在每个 service 里写） |
| 谁读 | `snapshot()` 返回体加 `version`；`GET /config/version` 只回一个数字（约 20 字节） |
| 暂放项 | **不设草稿态**（已定：改完即生效）—— 版本号只标记「态」，不标记「待发布」 |
| 保留 | `config_revisions` 保留最近 **20** 层（超出删最老），payload 是全量 38 表 JSON |

**为什么 payload 存全量而不是 diff**：回滚要「一键」，diff 回滚需要按顺序重放，
任一环失败就半回滚。全量恢复是 `DELETE + INSERT`，一个事务，要么全成要么全不动。
代价是每层约 2~5MB（38 张表 JSON），20 层 ≤ 100MB —— 可接受。

### 2.2 客户端：轻量轮询 + 变更后重拉

```
每 60 秒（或切回前台时）：GET /config/version → { version: 42 }
  ├─ 相同 → 什么都不做
  └─ 不同 → GET /config/bundle（现有快照接口）→ applySnapshot() → 本地 version = 42
```

| 项 | 规则 |
|---|---|
| 轮询间隔 | **60 秒**（`config_poll_interval_ms` 可配），只在游戏内轮询 |
| 立即触发 | 服务端推送一帧 `configDirty { version }`（实时连接存在时）→ 客户端立刻拉，不等 60 秒 |
| 应用时机 | **只在安全点应用**：不在战斗中、不在交易/拍卖进行中；否则排队到下一个安全点 |
| 失败处理 | 拉取失败保留旧表继续用，下一轮再试（**绝不因为配置拉不到把人踢下线**） |
| 首次 | 进游戏照旧拉一次，带上 version |

**「安全点应用」是必须的**：技能表在放技能的中途被替换，会让「已经起手的技能」
按新数值结算 —— 这类不一致排查起来极贵。排队应用把问题变成「延迟 3 秒生效」。

### 2.3 发布与回滚（已定：改完即生效 + 留 20 版 + 一键回滚）

| 动作 | 接口 | 说明 |
|---|---|---|
| 改动 | 各配置页现有保存接口 | 成功后：`version +1`、写一条 `config_revisions`（**节流**：同一操作人 10 秒内合并成一层） |
| 查看 | `GET /admin/config/revisions?limit=20` | 版本列表（版本号 / 说明 / 人 / 时间 / 大小） |
| diff | `GET /admin/config/revisions/:a/diff/:b` | 按表统计「改了几行」，到字段级 |
| 回滚 | `POST /admin/config/revisions/:v/restore` | 单事务全量恢复 + `version +1`（**回滚本身也是一次新版本**，不删历史） |
| 导出 | `POST /admin/config/export` | 生成 `config-sync.sql`（现有工具的接口化） |

**回滚时正在跑的进程**：服务端读库，下一个请求即是新值（无需重启）；
客户端靠 2.2 的轮询在 60 秒内跟上。**唯一需要人工确认的是「回滚后是否要踢人重进」** ——
默认不踢。

### 2.4 出厂 SQL 与库的一致性

| 项 | 做法 |
|---|---|
| 门禁 | `make config-check` 保持（比 SQL 与库） |
| 提醒 | 管理端顶部常驻「配置有 N 处未导出」提示：`config_revisions` 里 `version > last_export_version` 即未导出 |
| 记录 | `config_meta` 加 `last_export_version` / `last_export_at`（复用现有键值表，不新建） |
| 导出即发布 | `POST /admin/config/export` 成功后自动更新 `last_export_version` |

这样「改了没导出」从**靠人记**变成**页面上一行红字**。

### 2.5 登记五处的自检（治假绿）

新增一个脚本 `server/scripts/check-config-registration.cjs`：

```
对数据库里每张表：
  ├─ 在 CONFIG_TABLES 或 RUNTIME_TABLES 里？      否 → 报错
  ├─ 有对应 REPO_EDGES 条目？                     否 → 报错
  ├─ 有 @ApiAdminDoc 类型登记（若是管理端可写）？  否 → 报错
  └─ 若是新快照段：客户端 game-config.ts 区 0 有键？否 → 报错
```

**为什么要有这条**：现有审计是「已登记的东西对不对」，缺的是「有没有东西没登记」。
前者保正确性，后者保**完整性** —— 完整性只能靠遍历全表来查。

### 2.6 热更新的边界（写清楚免得误期待）

| 能热更 | 不能热更（要重启） |
|---|---|
| 数值（伤害/经验/掉落/价格/上限） | 表结构（DDL） |
| 文案、图标路径、布局参数 | NestJS 模块依赖图 |
| 地图几何 / 刷怪区 / NPC 位置 | 客户端代码与资源包 |
| 怪物 AI 参数 | 实时协议的帧结构 |

**判定标准**：只改「行」能热更；要改「列」或「代码」必须重启。
这条写在这里，是为了让「为什么改了没生效」有一个统一的答案。

## 三、协议与接口

| 接口 | 说明 | 状态 |
|---|---|---|
| `GET /game-config/snapshot` | 现有快照；**响应头** `ETag: W/"cfg-<version>"` + `Cache-Control: no-cache`，`If-None-Match` 命中回 **304**（空体） | **已落** #881 |
| `GET /game-config/version` | `{version}`，约 20 字节；客户端拿它判断「我这套表是不是最新」 | **已落** #881 |
| `configDirty`（S→C 帧） | `{version}`，实时连接存在时推送 | 暂时放置（§八） |
| `GET /admin/config/version` | 管理端读当前版本（与客户端同一个数字） | **已落** #881 |
| `GET /admin/config/revisions` | 版本列表（默认 20 层，上限 100） | **已落** #882 |
| `GET /admin/config/revisions/:from/diff/:to` | 按表 diff（行级：`from` / `to` / `added` / `removed`） | **已落** #882 |
| `POST /admin/config/revisions/:version/restore` | 回滚（权限 `config:restore`，审计目标 `config`） | **已落** #882 |
| `POST /admin/config/export` | 导出出厂 SQL | 暂时放置（§八） |

**版本自增判据是权限点不是路径**：71 个写接口散在 `game-config` / `map` / `ui-effect` / `audio-setting`
四个模块，按路径列清单必漏（漏掉的那个表现为「改了、客户端永远 304」，日志里一个字都没有）；
它们**都带 `gameConfig:write`**，全局拦截器按这个权限点拦，写成功（`tap next`）才 +1。

新增权限点两个：`config:read`（看历史与 diff）、`config:restore`（回滚 + 导出）。
**回滚是「一次改 38 张表」的动作，敏感度高于任何单表写权限**，必须单列。

**版本行同时进了 `config-sync.sql`**（`-- config-version: N`，#883）：
导入前比一次文件版本与库版本，文件更旧即拒（`--force` 放行），避免「拿三天前的 SQL 盖掉今天的运营改动」。
`compare()` 与 `config-check` 会先剥掉版本行再比 —— 否则两台机器永远「有差异」。

## 四、分刀

| 刀 | 内容 | 规模 | 前置 | 状态 |
|---|---|---|---|---|
| ① | `config_version` + 写接口拦截器自增 + 快照带 version | 小 | 无 | **已落**（快照走 ETag 而非体字段，#881） |
| ② | `GET /config/version` + 客户端 60 秒轮询 + 安全点应用 | 中 | ① | 服务端接口**已落**（`/game-config/version`）；客户端轮询暂时放置 |
| ③ | `config_revisions` + 节流落层 + `config:read` 页面 | 中 | ① | **已落**（#882） |
| ④ | 回滚（单事务全量恢复）+ diff + `config:restore` | **大** | ③ | **已落**（#882） |
| ⑤ | `configDirty` 推送（省掉 60 秒等待） | 小 | ② | 暂时放置 |
| ⑥ | 导出接口化 + 「未导出」红字提示 | 小 | ③ | 暂时放置 |
| ⑦ | `check-config-registration.cjs` 完整性自检 | 中 | 无 | 暂时放置 |
| ⑧ | 导入版本闸（#883，设计稿里没有） | 小 | ① | **已落**：`config-sync.sql` 带版本行，文件落后即拒，`--force` 放行 |

**④ 是唯一有真实风险的**：全量恢复要保证「38 张表一个事务」，
且恢复期间不能有读请求读到半套配置。SQLite 单写者天然串行，加一个
`BEGIN IMMEDIATE` 事务即可，但要确认 38 张表的 DELETE+INSERT 在里面跑得完（预计 <2s）。

## 五、边界情况

| # | 情形 | 期望 |
|---|---|---|
| 1 | 回滚时正好有玩家在打架 | 数值在事务提交后瞬间生效；**不踢人**，客户端在安全点换表 |
| 2 | 回滚中途崩溃 | 单事务，要么全回滚要么全不动（SQLite WAL 保证） |
| 3 | 20 层满了又来新版本 | 删最老一层（**先删再加**，保证不会因满而写失败） |
| 4 | 同一人在 10 秒内点 8 次保存 | 合并成一层（节流），否则 20 层瞬间用完 |
| 5 | 客户端轮询时服务端重启 | 连接失败 → 保留旧表继续用，指数退避重试（1/2/4/8…上限 60 秒） |
| 6 | 快照拉取成功但 `applySnapshot` 抛错 | 保留旧表 + 上报（客户端不崩），下一轮再试 |
| 7 | 配置版本号回退（DB 被恢复成旧备份） | 客户端只要 `version` **不等于**本地值就重拉（不判大小），避免回退时永久不更新 |
| 8 | 回滚到一个「表结构不兼容」的旧版本 | 不做结构迁移：**payload 里缺的表跳过、多的表忽略**，并记一条 warning |
| 9 | 导出 SQL 时有人正在改配置 | 导出取一个读事务快照（`BEGIN` + 全表读 + `COMMIT`），保证自洽 |
| 10 | `config_revisions.payload` 超过 5MB | 记 `byte_size`，超阈值告警（说明配置膨胀了，该拆） |
| 11 | 客户端在战斗中收到 `configDirty` | 排队，战斗结束后应用 |
| 12 | 两个管理员同时改不同表 | 版本号 +2（两次改动两层），不合并（合并会丢一方的 diff 归属） |
| 13 | 只改了「运行时参数」 | 也算配置（进 `RUNTIME_TABLES`），同样 +1 版本 |
| 14 | 服务端读库缓存（若有）与版本号不一致 | 拦截器 +1 版本时**同时**清进程内配置缓存（若有），保证二者同源 |

## 八、暂时放置（含重开条件）

| 项 | 现在的口径 | 重开条件 |
|---|---|---|
| **客户端 60 秒轮询 + 安全点换表（刀 ②）** | 服务端已能回答「是不是最新」（`/game-config/version` + ETag/304），**客户端还不会问**：改完配置，在线玩家仍要重登才看到新数值 | 运营提出「改完在线玩家 1 分钟内看到」时。落地只需客户端加 `ConfigSync`（轮询 + 战斗中排队），服务端不用再改 |
| **`configDirty` 实时推送（刀 ⑤）** | 无推送 | 刀 ② 落地后再评估（它只是把 60 秒缩短到 1 秒） |
| **导出接口化 + 「N 处未导出」红字（刀 ⑥）** | `make config-export` 是唯一出口，靠人记得跑 | 出现「非开发者也必须导出」或「忘导出导致仓库与线上不一致」的实际事故时 |
| **`check-config-registration.cjs` 完整性自检（刀 ⑦）** | 加表仍靠人记「登记五处」 | 下一次「加表漏登记」造成事故时（现在由 `audit-server-boundaries` / `audit-snapshot-contract` 兜大半） |
| **回滚的故障注入测试** | 「要么全成要么全不动」靠单事务 + `PRAGMA defer_foreign_keys` + 人工 review | 回滚路径再次改动之后（现在改一次就要重看一遍 `restore()`） |
| 草稿 / 待发布态 | 改完即生效（已定） | 出现「一次要改几十张表、不能改一半被玩家看到」的运营诉求时 |
| 灰度发布（按区 / 按比例） | 全量同时生效 | 分片上线后需要「先在一个区验证数值」时（28 篇已按区分片，具备条件） |
| 字段级结构化 diff 的完整回放 | diff 到表 + 行数，回滚走全量 | 需要「只回滚某一张表」时（现在只能整层回滚） |
| 配置变更影响面分析（改这个数值会影响哪些玩法） | 靠人看文档 | 配置表超过 60 张且改动经常互相影响时 |
| 客户端配置增量下发（只发变化的段） | 全量快照重拉 | 快照体积 > 1MB 或移动网络占比高时 |
| 配置审计与 `audit_logs` 合并成一条时间线 | 两处分别看 | 需要「一条改动从点到生效全链路」追溯时 |

## 九、已定参数

| 项 | 结论 |
|---|---|
| 发布方式 | **改完即生效 + 全量审计留痕**（不设草稿态） |
| 版本 | 单一自增 `version`，每次配置写成功 +1 |

| 回滚 | **一键全量回滚**，回滚本身是一次新版本（不删历史） |
