# 30 · 聊天与公告设计

> **状态**：设计稿，未实现。[21 总表](./21-系统差距总表.md) 判定「扩写 · P3」。
> 依赖：[28 分片](./28-实时同步与分片设计.md)（全服频道的广播范围）、[29 队伍](./29-社交重构设计.md)（`party` 频道）。
>
> **一句话**：现在的 `world` 频道**其实只到同图**（代码注释写得很清楚），没有队伍频道、
> 没有系统频道、没有历史、没有禁言。本篇把频道补齐，并把「全服公告」收成一个出口。

---

## 零、现状（实测）

| 项 | 现状 |
|---|---|
| 频道 | `CHAT_CHANNELS = ["world", "map", "guild", "private"]`（#876 起，拆出同图频道） |
| `world` 范围 | **全服在场者**（进过图的在线账号，不限图；#876 已落，名实相符） |
| `map` 范围 | 同图观看者（复用互见集合；#876 前 world 就是它） |
| 服务端校验 | 限频、长度上限、敏感词；无禁言、无等级门槛 |
| 历史 | **不保存**（进来之前的看不到） |
| 公告 | `announcements` 表 + `GET /announcements/active`（时间窗内生效，登录页可读，无需令牌） |
| 全服广播 | **没有出口**（18 篇做掉落公告时发现，只能遍历 `connections` 现写） |

## 一、四个结构性问题

### 1.1 `world` 名不副实

叫「世界」但只到同图。玩家在 A 图喊话，B 图听不见 —— 这不是世界频道，是「本地频道」。
**已定：改成全服。**

> **#876 已落（2026-11-10）**：`world` 改全服在场者广播，同图就近说话拆成独立的 `map` 频道。
> 2.1 的五频道目标形态里没有单独的 `map` —— 拆出来不是为了留着，是先让「名实相符」这一步
> 可独立验收；`party` / `system` 与按频道分级限频、等级门槛仍是目标形态，未落。

### 1.2 缺队伍频道

见 29 篇。组队没有专属频道，协作只能靠私聊。

### 1.3 公告有三套写法

- `announcements` 表（运营公告，时间窗生效）；
- 18 篇的 `dropNotice`（瞬时全服公告）；
- 27 篇的 `bossNotice`（瞬时全服公告）。

后两者形状几乎一样，却各写一套。应统一成 `AnnounceService` 的一个出口 + 不同 `kind`。

### 1.4 没有禁言与门槛

`role_blocks` 是「玩家拉黑」，不是「系统禁言」。没有禁言就无法处理刷屏与广告；
没有等级门槛，1 级小号可以在世界频道刷广告（这是最常见的滥用）。

## 二、目标形态

### 2.1 五个频道

| 频道 | 范围 | 谁能发 | 门槛 |
|---|---|---|---|
| `world` | **全服（同区所有图）** | 所有人 | 等级 ≥ `world_chat_min_level`（默认 15） |
| `guild` | 本帮会在线成员 | 帮会成员 | 无 |
| `party` | 本队在线成员（跨图可达） | 队伍成员 | 无 |
| `private` | 指定角色（仅在线） | 所有人 | 对方未拉黑你 |
| `system` | 全服 | **只有服务端** | — |

`world` 改成全服之后，频率限制要更严（见 2.2），否则一定刷屏。

### 2.2 频率与长度

| 项 | 默认 | 说明 |
|---|---|---|
| `world` 频率 | 1 条 / 3 秒 | 比现在的同图频道严一倍 |
| 其余频道 | 1 条 / 1 秒 | 与现状接近 |
| 长度 | 80 字（`world`）/ 200 字（其他） | 按字符算，不按字节 |
| 重复内容 | 10 秒内相同内容 → 拒（`duplicate_message`） | 防刷屏的第一道 |
| 敏感词 | 保留现有实现 | 命中 → 拒 + 记 `chat_violation` |

### 2.3 历史：内存 200 条（已定）

| 项 | 规则 |
|---|---|
| 存储 | **只在内存**：每频道最近 **200** 条（环形缓冲） |
| 拉取 | `GET /chat/history?channel=world&limit=50` —— 只返回内存里的，**重启即空** |
| `private` | 不存历史（私聊本来就是「仅在线可达」，与现状一致） |
| 为什么不落库 | 见「暂时放置」：落库需要一张高频写表 + 保留期策略；先做最省的版本 |

### 2.4 禁言

```sql
CREATE TABLE chat_mutes (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  role_id    TEXT NOT NULL,
  channel    TEXT NOT NULL DEFAULT 'all',  -- all / world / guild / party / private
  reason     TEXT NOT NULL DEFAULT '',
  until      INTEGER NOT NULL,             -- 毫秒；0 = 永久
  created_by TEXT NOT NULL DEFAULT '',     -- 管理员账号
  created_at INTEGER NOT NULL
);
```

| 项 | 规则 |
|---|---|
| 校验 | 每条消息先查 `chat_mutes`（内存缓存 60 秒，避免每条都查库） |
| 生效 | 立即（管理端操作后清缓存） |
| 提示 | 被禁言者发消息 → `muted`（带 `until` 与 `reason`） |
| 自动 | 敏感词命中 3 次/小时 → 自动禁言 1 小时（记 `chat_violation`） |

### 2.5 公告：一个出口，三种形态

`AnnounceService`（**新建**）是唯一的全服广播出口：

| 方法 | 用途 | 形态 |
|---|---|---|
| `broadcast(text, kind)` | 瞬时全服公告（掉落 / BOSS / 活动 / 手动） | `announce` 帧，客户端飘字 |
| `announcementOf(zoneId)` | 运营公告（时间窗） | 现有 `announcements` 表，**保持独立**（它要能离线读） |
| `toRole(roleId, text)` | 单人提示 | `notice` 帧 |

**统一的好处**：18 篇的 `dropNotice`、27 篇的 `bossNotice` 都收敛成 `announce` 帧 +
不同 `kind`，客户端只实现一个飘字组件。

## 三、协议

| 帧 / 接口 | 说明 |
|---|---|
| `chat`（C→S） | `channel` 扩成 5 值，但 `system` **服务端拒绝客户端发送** |
| `chat`（S→C） | `RealtimeChatEntry` 加 `kind?: "user" \| "system"`；`party` 频道广播到队伍 |
| `announce`（S→C） | **新增**：`{kind, text, ts}`，替代 `dropNotice` / `bossNotice` |
| `GET /chat/history` | 内存历史（最多 200 条/频道） |
| `POST /admin/chat/mute` | 管理端禁言（权限 `chat:mute`） |

## 五、边界情况

| # | 情形 | 期望 |
|---|---|---|
| 1 | 全服频道在分片前调用 | 退化成同图（不报错），并在日志里标「未分片」 |
| 2 | 玩家在 A 图、帮会在 B 图 | `guild` 频道正常（帮会不看图） |
| 3 | 队伍跨图 | `party` 正常 |
| 4 | 私聊对方离线 | 拒（`target_offline`），暂不转邮件（见暂时放置） |
| 5 | 被对方拉黑后私聊 | 拒（`blocked`） |
| 6 | 被禁言时发 `private` | 若 `channel='all'` 则拒；若只禁 `world` 则可私聊 |
| 7 | 禁言缓存导致延迟生效 | 管理端操作后**主动清该角色缓存**（不能等 60 秒） |
| 8 | 历史拉取时频道为空 | 返回空数组（不是 404） |
| 9 | 消息含控制字符 / 超长 | 先 trim + 截断，再校验长度（否则长度校验可被绕过） |
| 10 | 同一条消息重发（网络重试） | 10 秒内相同内容 → `duplicate_message`（也顺带解决重发） |
| 11 | `announce` 与 `announcements` 同时存在 | 前者是瞬时飘字，后者是登录可见的运营公告，**不合并** |
| 12 | 全服公告 1 秒内多条 | 客户端只显示最新一条（与 18 篇一致），但历史里全记 |

## 七、验收

| 用例 | 断言 |
|---|---|
| `e2e-chat-world-global` | A 图发言 → B 图在线角色收到 |
| `e2e-chat-party` | 队伍频道消息只有本队收到 |
| `e2e-chat-rate` | `world` 连发两次（<3s）→ 第二次 `rate_limited` |
| `e2e-chat-mute` | 禁言后发 `world` → `muted`；解除后立即恢复 |
| `e2e-chat-history` | 发 3 条 → `history` 返回 3 条；重启后为空 |
| `e2e-announce` | `broadcast()` 一次 → 全服所有连接都收到一条 `announce` |

## 八、暂时放置（含重开条件）

| 项 | 现在的口径 | 重开条件 |
|---|---|---|
| 聊天历史落库 | 只存内存 200 条 | 玩家投诉「漏看重要消息」成为主要反馈时；需要一张按天分区的表 |
| 离线私聊转邮件 | 暂放（仅在线可达） | 32 篇邮件扩写后，可作为「离线消息」子类型 |
| 语音 / 表情包 | 暂放 | 有素材与审核能力时 |
| 频道自建（玩家开频道） | 暂放 | 需要 moderation 工具与成本模型时才考虑 |
| 聊天举报自动处罚 | 只记录不处置 | 有明确申诉流程后（与 26 篇「脚本风控不自动封号」同一原则） |
