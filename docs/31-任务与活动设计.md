## 一、五个结构性问题

### 1.1 日常没有「每天一次」，实际是「可无限重刷」【P1 经济洞】

`submit` 里 `kind === "daily"` 就 `remove` 整行。下一毫秒 `accept` 查不到行 →
判定「没接过」→ 许可。于是：**打 10 只怪 → 交 → 再打 10 只 → 再交**，金币与经验无限产出，
没有任何「今天已经领过」的记录。

这不是「日常任务」，是**无限循环的经验矿**。凡是能刷的产出，都必须有日闸门；
凡是有日闸门的产出，闸门就必须落在**服务端可审计的一行**上。

### 1.2 目标类型太窄，事件源接不进来

只有 `kill` / `collect` / `talk`。玩家实际会做的事里，**到达某地图**、**使用某物品**、
**强化成功 N 次**、**组队通关**都没有任务能表达。而这四类事件在服务端**已经都在发生**
（`world` 帧换图、`money-use` / `drug-use` 接口、强化结算、队伍快照），只是没人订阅。

补法不是「在 quest.service 里写 if」，而是**把事件源统一到 `GameEventsService`**：
结算侧只 `emit`，任务与成就各自订阅。现状 `monster:killed` / `quest:claimed` 已经是这个形状，
只是事件种类太少。

### 1.3 任务链是单链，配不出支线

`prev_quest_id` 一个字段只能表达「A 之后是 B」。做不了「主线之外还有三条支线并行」，
也做不了「二选一分支」（选剑还是选盾）。而 `docs/22` 的技能树、`docs/23` 的转生
都需要「任务前置」当门槛 —— 单链表达不了。

### 1.4 没有活动层

节日、签到、限时 BOSS、赛季排行赛 —— 一个都没有。运营要发一波活动，只能
「手动改配置 + 手动发邮件 + 群里喊」，既不可回滚也不可观测。

活动层的本质是**一张带时间窗的表 + 一个到点自动的调度器**，不是新玩法。

### 1.5 发奖出口散在三处

- 任务：`grantQuestRewards()`；
- 成就：`achievement.service` 自己发；
- 邮件：`game-mail.claim()` 自己发。

三处各有各的「背包满怎么办」。活动奖励一来，就变成第四处。
**必须先有一个 `RewardService`，再谈活动。**

## 二、目标形态

### 2.1 发奖唯一出口：`RewardService`

```ts
// 三个动词，一层比一层低
grant(roleId, rewards, source): RewardResult   // 在线：直入背包，满则转邮件
deliver(roleId, rewards, mail): MailRow        // 强制走邮件（离线、排行赛结算）
claim(mailId): RewardResult                    // 领邮件附件（现有 game-mail.claim 收编）
```

| 场景 | 走哪条 | 结果 |
|---|---|---|
| 交付任务（在线） | `grant` | 背包放得下 → 直入；放不下 → 自动转邮件 |
| 签到（在线） | `grant` | 同上 |
| 排行赛结算（可能离线） | `deliver` | 一律邮件，登录后自己领 |
| 活动结束补偿 | `deliver` | 一律邮件 |
| 邮件附件领取 | `claim` | 背包满 → 20012，邮件保持未领（**现状已如此，保持**） |

`source` 是幂等键的一部分（见 2.8）。

### 2.2 目标类型扩成「事件驱动」

| `objective_type` | 事件 | 现状 | 说明 |
|---|---|---|---|
| `kill` | `monster:killed` | ✅ 已有 | 保持 |
| `collect` | 交付时查背包 | ✅ 已有 | 保持（不订阅事件，避免「捡了又扔」误判） |
| `talk` | `npcTalk()` | ✅ 已有 | 保持 |
| `reach_map` | `map:entered` | **新增** | `world` 帧换图成功后 emit |
| `use_item` | `item:used` | **新增** | `money-use` / `drug-use` / `level-scroll-use` 成功后 emit |
| `enhance` | `enhance:done` | **新增** | 24 篇的强化结算成功后 emit（含成功/失败，按 `success` 过滤） |
| `party_clear` | `dungeon:cleared` | **新增** | 29 篇的队伍快照，本队全员推进 |

**订阅纪律**（沿用 `quest.service.ts` 现有写法）：订阅方抛异常**不影响**事件发起方。
击杀进度的写库失败只打日志 —— 任务进度不该回滚世界击杀与掉落。

### 2.3 每日 05:00 闸门（已定）

```ts
/** 05:00 统一重置：把「现在」映射到一个整数天号 */
function resetDayOf(now: number, offsetHour = 5): number {
  return Math.floor((now - offsetHour * 3600_000) / 86_400_000);
}
```

| 项 | 规则 |
|---|---|
| 重置时点 | 服务器本地时间**每日 05:00**（`daily_reset_hour` 可配，默认 5） |
| `quest_progress` | 加 `reset_day INTEGER NOT NULL DEFAULT 0` |
| `daily` 接取 | `status='accepted' AND reset_day=today` 视为「今天已接」；`reset_day < today` 则**覆盖重置**（进度清零、状态回 accepted） |
| `daily` 交付 | **不再删行**，改 `status='claimed', claimed_at=now`；今天内不能重接，明天 `reset_day` 落后自动重置 |
| `main` 交付 | 保持 `claimed` 行作链门控（现状不变） |
| 跨天正在交付 | 以 `submit` 时刻的 `reset_day` 为准：T23:59 接、T+1 05:00 交 → 按**接取那一档**结算，不重复发 |

**为什么保留行而不删**：删行就抹掉了「今天领过」的证据，闸门只能靠另建计数器；
保留行 + `reset_day` 天然一行一状态、天然幂等、天然可审计。

### 2.4 任务链：单链 → 链 + 支线

新增两张表，`prev_quest_id` **保留**（老配置不动，仍作同链内前置）：

```sql
CREATE TABLE quest_chains (
  chain_id     TEXT PRIMARY KEY,          -- main_ch01 / side_smith / branch_sword ...
  kind         TEXT NOT NULL DEFAULT 'main', -- main | side | branch | daily
  label        TEXT NOT NULL DEFAULT '',
  unlock_level INTEGER NOT NULL DEFAULT 1,
  sort_order   INTEGER NOT NULL DEFAULT 0,
  updated_at   INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE quest_chain_nodes (
  chain_id   TEXT NOT NULL,
  quest_id   TEXT NOT NULL,
  seq        INTEGER NOT NULL DEFAULT 0,   -- 链内顺序
  group_no   INTEGER NOT NULL DEFAULT 0,   -- >0 = 互斥分支组（同组只能选一条）
  PRIMARY KEY (chain_id, quest_id)
);
```

| 规则 | 说明 |
|---|---|
| 可接判定 | `min_level` 满足 **且** 本链上一个 `seq` 已 `claimed` **且** 同 `group_no` 的其他任务未 claimed |
| 互斥分支 | `group_no > 0` 的节点，选了一条其余永久锁定（记 `quest_progress.locked=1`） |
| 链上限 | 单链节点数 ≤ 200（保护客户端渲染）；支线数不设限 |
| 老数据 | 4 条主线挂到 `main_ch01`（seq 1~4），日常不挂链 |

### 2.5 活动日历：到点自动（已定）

「到点自动」= **读时按时间算 + 写时调度器落状态**，双保险：

```sql
CREATE TABLE activities (
  id          TEXT PRIMARY KEY,
  kind        TEXT NOT NULL,              -- checkin | buff | boss | season
  label       TEXT NOT NULL DEFAULT '',
  zone_id     INTEGER NOT NULL DEFAULT 1,
  start_at    INTEGER NOT NULL,
  end_at      INTEGER NOT NULL,
  config      TEXT NOT NULL DEFAULT '{}', -- 每类活动自己的参数
  enabled     INTEGER NOT NULL DEFAULT 1,
  created_by  TEXT NOT NULL DEFAULT '',
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL
);
CREATE INDEX idx_activities_window ON activities(zone_id, start_at, end_at);
```

| 层 | 做法 |
|---|---|
| 读时算 | `ActivityService.active(zoneId, now)` = `enabled=1 AND start_at <= now < end_at`。**重启、改钟、漏调度都不会错** |
| 写时落 | `ActivityScheduler` 每 60 秒扫一次，跨越边界的活动 `emit("activity:started")` / `"activity:ended"`（供 30 篇全服播报、27 篇开 BOSS 窗） |
| 手动开关 | **不提供**（已定：只要日历）。要提前结束就改 `end_at`，要取消就 `enabled=0` |
| 时区 | 全部存**毫秒时间戳**，不存字符串日期 —— 避免时区解析分歧 |

### 2.6 四类活动（首批全做）

#### 2.6.1 签到（7 日循环）

```sql
CREATE TABLE activity_checkins (
  activity_id TEXT NOT NULL,
  role_id     TEXT NOT NULL,
  day_index   INTEGER NOT NULL,   -- 1..7
  reset_day   INTEGER NOT NULL,   -- 与任务同一把尺子（05:00）
  claimed_at  INTEGER NOT NULL,
  PRIMARY KEY (activity_id, role_id, reset_day)
);
```

| 项 | 规则 |
|---|---|
| 循环 | 7 天一轮，第 8 天回第 1 天（`day_index = (累计签到次数 % 7) + 1`） |
| 断签 | 断一天不清零（可选「连续」口径）—— **先按累计**，连续额外奖励见暂时放置 |
| 补签 | 1 次/天，消耗元宝（价格进 `activity.config`），只能补**昨天** |
| 领奖 | `RewardService.grant`（在线直入 / 满转邮件） |
| 幂等 | 主键 `(activity_id, role_id, reset_day)`，重复点只返回已领 |

#### 2.6.2 节日倍率

`config = { expRate: 1.5, dropRate: 1.5, maps: [] }`（`maps` 空 = 全图）。

| 项 | 规则 |
|---|---|
| 作用点 | 经验：`combat-settlement` 加算后乘；掉落：18 篇的掉落 roll 前乘概率 |
| 叠加 | **取最大不叠乘**（两个活动同时开，取 `max`），上限 `expRate ≤ 3.0` / `dropRate ≤ 3.0` |
| 生效判定 | 结算瞬间调 `activeBuff(zoneId, now)`；活动刚结束的那一刀按结束时间算（不追补） |

#### 2.6.3 限时 BOSS / 世界事件

复用 27 篇的 `world_boss` 定时窗，活动只做两件事：

1. 把 `start_at`/`end_at` 内的 BOSS 窗**打开**（27 篇的窗是常驻配置，活动是「额外一次」）；
2. `ended` 时按参与度发奖（`RewardService.deliver` 一律邮件）。

`config = { bossKey, respawnAt: [ts...], participateMinDamage }`。

#### 2.6.4 排行赛（周期结算）

```sql
CREATE TABLE activity_seasons (
  id           TEXT PRIMARY KEY,
  activity_id  TEXT NOT NULL,
  season_no    INTEGER NOT NULL,
  metric       TEXT NOT NULL DEFAULT 'power', -- power | level | kills | quests
  start_at     INTEGER NOT NULL,
  end_at       INTEGER NOT NULL,
  settled_at   INTEGER,                        -- 非空 = 已结算（幂等标记）
  UNIQUE (activity_id, season_no)
);
```

| 项 | 规则 |
|---|---|
| 榜单 | 复用 `leaderboard` 物化（`ranks` 表），不改榜单实现 |
| 结算 | `end_at` 后由 scheduler 扫一次；`settled_at` 非空直接跳过（**幂等**） |
| 发奖 | 名次 → 奖励表（配置在 `activity.config.rewards`）→ 全部 `deliver` 邮件 |
| 中途退出 | 不结算，不补偿（赛季是个完整周期） |

### 2.8 奖励幂等

`RewardService` 的幂等键：`${source}:${roleId}:${refId}`，落 `reward_log`：

```sql
CREATE TABLE reward_log (
  idem_key   TEXT PRIMARY KEY,   -- quest:8001:role_x / checkin:act1:role_x:45123 / season:7:no1
  role_id    TEXT NOT NULL,
  source     TEXT NOT NULL,
  gold       INTEGER NOT NULL DEFAULT 0,
  exp        INTEGER NOT NULL DEFAULT 0,
  items      TEXT NOT NULL DEFAULT '[]',
  mail_id    TEXT,
  created_at INTEGER NOT NULL
);
```

**先插幂等键再发奖**（同一个事务）；冲突 → 直接返回上次结果。
这样「客户端连点两次」「调度器重启重跑」「邮件重试」都不会重复发。

## 四、边界情况

| # | 情形 | 期望 |
|---|---|---|
| 1 | 日常在 04:59 交付，05:00 后再接 | 正常（新 `reset_day`） |
| 2 | 日常在 04:59 接，05:10 交付 | 按接取那档结算，**发一次**；`reset_day=昨天`，今天还能再接一次 |
| 3 | 客户端连点交付 | 第二次 `claimed` → 20019（状态非法），`reward_log` 也不会重复 |
| 4 | 交付时背包满 | 20012，进度行保持原状（可补格子再来） |
| 5 | 分支任务选了一条 | 另一条 `accept` → `QUEST_BRANCH_LOCKED`；已在进行的另一条不受影响（选中即锁） |
| 6 | 活动 `start_at == end_at` | 视为不生效（零宽窗），调度器跳过 |
| 7 | 服务器改钟/时区 | 活动用绝对时间戳，不受影响；`reset_day` 可能回退 → **加单调保护**：`reset_day` 只增不减（记 `daily_reset_meta.last_day`） |
| 8 | 赛季结算跑到一半崩溃 | `settled_at` 未写 → 重跑；单角色发奖靠 `reward_log` 幂等，不会双发 |
| 9 | 赛季结束玩家离线 | `deliver` 邮件，30 天后过期（32 篇） |
| 10 | 签到跨活动周期 | 主键含 `activity_id`，两个活动互不影响 |
| 11 | 补签时昨天已签到 | 拒（`already_checked_in`） |
| 12 | 倍率活动与 18 篇掉落倍率叠加 | 取 `max`，不乘算（防 3×3=9 倍失控） |
| 13 | 限时 BOSS 与常驻 BOSS 窗重叠 | 同时存在（常驻的照刷，活动的额外刷） |
| 14 | 任务目标怪物被删配置 | 进度停在原地不报错；管理端删怪物时提示「有 N 个任务引用」 |
| 15 | 事件订阅方抛异常 | 只打日志，不影响击杀/经验/掉落（沿用现状） |
| 16 | 活动 `config` JSON 解析失败 | 该活动视为不生效 + 告警日志（不 500 全站） |

## 六、验收

| 用例 | 断言 |
|---|---|
| `e2e-quest-daily-gate` | 交一次 → 今天不能再接；改 `reset_day` 为昨天 → 可以再接 |
| `e2e-quest-daily-once` | 连续两次 `submit` → 第二次 20019，`reward_log` 只有一条 |
| `e2e-quest-branch` | 选 A 后接 B → `QUEST_BRANCH_LOCKED` |
| `e2e-quest-event-reach` | 进图 → `reach_map` 任务进度 +1 |
| `e2e-activity-window` | `start_at` 前 `GET /activities` 无此项；之后有；`end_at` 后无 |
| `e2e-activity-checkin` | 同一天领两次 → 第二次返回已领，`reward_log` 一条 |
| `e2e-activity-buff-max` | 两个倍率活动叠加 → 结算用 `max` 不是乘积 |
| `e2e-activity-season-idem` | 结算跑两次 → `settled_at` 已有，第二次跳过；邮件不重复 |
| `e2e-reward-offline` | 离线发奖 → `role_mails` 一条，`gold`/`items` 一致 |

## 七、暂时放置（含重开条件）

| 项 | 现在的口径 | 重开条件 |
|---|---|---|
| 连续签到额外奖励 | 只按累计天数发 7 日奖励，不断签/连续的区别 | 有留存数据表明「连续」对次留有正向作用时 |
| 活动手动开关 | 只有日历（改 `end_at` / `enabled`），无「立即开启」按钮 | 出现「紧急开活动」的运营诉求（如事故补偿活动）时 |
| 活动互斥（同时只能开一个） | 允许多活动并行，倍率取 `max` | 出现两个活动数值互相放大到不可控时（加互斥组） |
| 任务委托 / 每日委托池（随机刷 3 选 1） | 固定配置，无随机 | 任务量上到 50+ 且玩家反映「每天都一样」时 |
| 任务奖励预览与概率公示 | 固定奖励，无随机箱 | 活动奖励引入随机箱时（与 26 篇概率公示同一条规则） |
| 赛季分段（青铜/白银/黄金） | 单榜，只有名次 | 参赛人数过千、头部固化后 |
| 成就与活动的联动（活动专属成就） | 成就独立，活动不加成就 | 做第二个赛季时（届时成就的 `condition_type` 已事件化，加一个即可） |

## 八、已定参数

| 项 | 结论 |
|---|---|
| 重置时点 | **每日 05:00 统一重置**（`daily_reset_hour=5` 可配） |
| 日常口径 | 一行一状态 + `reset_day`，**不再删行**，天然每天一次 |
| 活动开启方式 | **日历 + 到点自动**（读时算 + 调度器落状态），无手动开关 |
| 奖励发放 | **在线直入背包，离线走邮件**；背包满自动转邮件 |
| 邮件保留 | **30 天**（详见 32 篇） |
| 首批活动 | **签到（7 日循环）、节日倍率（经验/掉落）、限时 BOSS / 世界事件、排行赛（周期结算）** 四类全做 |
| 倍率上限 | `expRate ≤ 3.0` / `dropRate ≤ 3.0`，多活动**取 max 不叠乘** |
