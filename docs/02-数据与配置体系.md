# 02 · 数据与配置体系

> 一句话：**游戏数据的唯一权威是数据库**；`server/data/config-sync.sql` 是它的出厂快照；
> 客户端与管理端都只是「读它」的两种壳子，代码里没有第二份数值副本。

这一篇讲清四件事：库里有什么、快照怎么下发、运营改一个数要动哪几处、以及那些「改了没生效」的坑。

---

## 一、65 张表 = 38 张配置 + 27 张运行时

分类清单只有一处：`server/scripts/lib/config-tables.cjs` 的 `CONFIG_TABLES` / `RUNTIME_TABLES`。
**库里每张表都必须在两个清单之一**，`assertAllClassified()` 在导出时全量比对，多一张就报错点名——
因为「漏分类」的两个后果都很隐蔽：配置表漏了 → 别人同步过来少一张（页面显示「一个都没有」）；
运行时表误加 → 账号 hash / 邮箱跟着 git 走，仓库是 PUBLIC，发出去收不回来。

### 1.1 配置表（38 张，跟着 git 走）

判据：**管理端能改、改完要下发给客户端或参与结算**。三类都算：进快照的、不进快照但服务端现算要用的、

### 1.2 运行时表（27 张，绝不进仓库）

`accounts` `admins` `roles` `audit_logs` `announcements` `mail_queue` `world_monsters` `world_meta`
`zones` `parties` `party_members` `guilds` `guild_members` `guild_applications`
`role_friends` `role_enemies` `role_blocks` `role_reports` `role_mails` `role_achievements`
`quest_progress` `role_status` `map_monitor_state` `map_monitor_events` `config_meta`
`config_version` `config_revisions`

其中三张值得单独记：

- `roles` 是**一行一个角色**：索引列（`level` / `kills` / `revision` / `online` 相关）用于排序筛选，
  `data` 列是客户端 `Role` 实体的 **JSON 字符串**（不透明文档，服务端只校验结构与体量）。
- `world_monsters` 是**世界权威的状态表**（`instanceId = m<mapId>_<n>`，跨重启稳定发牌），
  实时进程 tick 落盘，重启后靠它恢复。
- `map_monitor_*` 是**投影不是权威**：删掉不影响游戏，重启第一帧采样就补上——所以它们不进 `config-sync.sql`。

完整表清单（含行数、字段）见 [15-数据表清单](./15-数据表清单.md)。

## 三、`config-sync.sql`：出厂快照

```
-- olua 配置快照（由 `make config-export` 从本地库生成，不要手改）
-- 表 38 张 / 行 13772 条
-- olua config snapshot v1
-- tables: achievements,audio_settings,...
-- counts: achievements=24,audio_settings=12,...

PRAGMA foreign_keys = OFF;
BEGIN;
-- ===== achievements（24 行）=====
DELETE FROM "achievements";
INSERT INTO "achievements" (...) VALUES (...);
...
COMMIT;
```

四条硬规则：

1. **逐表整表替换**（`DELETE` + 逐行 `INSERT`）：upsert 表达不了删除，会让对方库里删掉的行永远留着。
   代价是文件必须全量，所以导入前会校验「表清单完全一致 + 每表恰好一条 DELETE + 不含运行时表」。
2. **只在空库首启生效**：`bootstrapConfigSnapshot()` 在 `config_meta` 里留 marker，之后不再自举。
   所以**改 `config-sync.sql` 不会影响已经在跑的库**——要么管理端改库，要么 `make config-import`。
3. **后加的表要给存量库补数据**：已经跑过很久的库不会重新自举，只改 SQL 的话老库重启后表是空的
   （管理端页面空白、玩家拿到道具也用不了，而且**没有任何报错**）。做法是 `migrate()` 末尾一段
   `INSERT OR IGNORE` + 自己的 marker（`seedMoneyItemsOnce` / `seedLevelScrollsOnce`），
   与 `common/constants/*` 的种子同源；`updated_at > 0` 的行（运营改过）一个字都不动。
4. **新加列必须是建表语句最后一列**：存量库靠 `ensureColumn` 的 `ALTER TABLE ADD COLUMN` 补，
   列序不同会让 `SELECT *` 的导出产生整份假 diff（10275 行全部重写一遍，review 时看不出真正改了什么）。
   加列的完整动作见 §六。

## 四、两条下发通道：快照 vs 单开接口

**这是「管理端明明改好了，客户端还是旧的」最常踩的坑**：不是口径不一致，是缓存。

| 通道 | 拉取时机 | 放什么 | 客户端落点 |
|---|---|---|---|
| `GET /game-config`（快照） | **进程内只拉一次**（`snapshotLoaded` 守卫） | 32 段结构性配置（下表） | `configs/apply-snapshot.ts` |
| `GET /game-config/equip-align` | 每次进图 | 装备外观几何（人眼调出来的点位） | `applyEquipAlignRows` |
| `GET /game-config/equip-in-align` | 每次进图 **+ 每次开角色信息弹窗**（`refreshInAlign`） | 内观几何 | `applyEquipInAlignRows` |
| `GET /game-config/equipment-appearance` | 每次进图 | 边框 / 详情背景映射与效果 | `applyAppearanceSection` |
| `GET /game-config/audio` | 登录场景（**免令牌**） | 12 项音效 | `applyAudioRows` |

**判据一句话**：验收动作是不是「保存 → 退回选角再进图 → 看效果」。
是 → 必须每次进图拉（「退回选角再进图」只是场景重载，JS 上下文不重来，快照那条路永远给旧值）；
否 → 进快照。

快照是**硬依赖**：`ok === false` 就停在 Loading 并给文案 + 重试，**不许按空表进游戏**。
后三路失败只 `console.warn` 并沿用快照值——缺行本来就是「还没调过」的语义，但绝不静默吞掉（一个 404 会被当成「保存没生效」）。

### 4.1 快照的 32 段 → 客户端落点

`ClientConfigService.snapshot()` 只做编排（逐表调各配置服务的列表方法，**不引入第二套 row → DTO 映射**），
所以「快照里有几条」就等于「库里有几条」。

| # | 段 | 来源表 | 客户端消费 |
|---|---|---|---|
| 1-3 | `titles` / `souls` / `ranks` | 三张成长表 | 成长弹窗、属性汇总的加成项 |

| 5 | `drugs` | `drugs` | 背包使用、格子图标 |
| 6-7 | `moneyItems` / `levelScrolls` | 两张新道具表 | 背包使用与本地预检 |
| 8 | `items` | `items` | 材料 / 杂物 |
| 9-10 | `monsters` / `monsterPresentations` | 两张怪物表 | 客户端**只演**，数值仍以服务端为准 |
| 11-12 | `npcs` / `fashions` | NPC 与时装 | 场景 NPC、时装面板 |
| 13-14 | `levelCurves` / `growthScalars` | 曲线 24 段 + 6 标量 | 本地算「这一级多少血」（与服务端同一套公式） |
| 15 | `combatWeights` | 七项权重 | 「这件装备是不是更好」的比较提示 |

| 27-28 | `equipmentSlots` / `equipmentMeta` | 槽位表 + 前后缀倍率 | 装备格底图、变体名拆段染色 |
| 29 | `runtimeParams` | 四组 JSON（掉落手感 / 自动战斗 / 帮会规则 / 怪物 AI） | 本地覆写 |

### 4.2 落库方向只有一条

```
apply-snapshot.ts  →  configs/game-config.ts（运行时表）  →  types/*
```

`configs/` 与 `types/` **不许反向引用 UI 组件**；`apply-*` 只能被 `ConfigLoader` 调。
这条方向由 `audit-snapshot-contract` 守着——写反了会形成循环 import，Cocos 打包时表现为「某个配置是 undefined」。

## 五、服务端怎么用同一份数据（内存投影 + 覆盖层）

服务端不查「生成物」，读的是**启动时装载的内存投影** `common/runtime-config-cache.ts`：

```
数据库（配置表）
   ↓ RustConfigService.refreshAll()  启动时 + 管理端每次写操作后
runtime-config-cache：
   · equipmentVariants / equipmentBases        —— equipmentAttributesOf / equipmentLevelOf / equipmentSlotOf
   · titles / souls / ranks                    —— titleAttributesOf / soulAttributesOf / rankAttributesOf
   · roleLevelCurveRows                        —— roleLevelAttributesOf（按需求值 + memo）
   · combatWeights                             —— combatWeightsOf
   · skills / statuses / monsterSkills         —— skillOf / statusOf
   · dropTables / monsterDrops                 —— 结算侧现读库（1 秒 TTL 的那批除外）
```

三条纪律：

1. **派生值也落库**：`equipment_variants` 的八项属性与 `sell_price` 是**逐条写好的列**，
   运行时**零现算**（不再乘倍率）。所以「改了 `equipment_meta` 的倍率」不会影响已有变体行——
   必须去管理端点「重建变体」。
2. **等级是唯一的例外**：100 万级存不下，库里只放段参数，`roleLevelAttributesOf(level)` 按需求值并带 memo。
3. **没配就是没配**：曲线为空 → 返回 `null`（不是 0），调用方据此报错或拒绝，不凭空造一份属性。

运营改完配置后：
- 存档进程：`RuntimeConfigService` 每次写操作后 `refreshAll`，**同进程内立即生效**；
- 实时进程：**跨不过进程边界**，靠「读库 + 短 TTL 缓存」自己回查（怪物 AI 的 `SKILL_CACHE_TTL_MS = 1000`），
  其余靠 `roleUpdate` 的周期重装。

## 六、加一个可配项 / 加一列的完整动作

### 6.1 加一个「可配的字段」（已有表）

四件事缺一不可，漏最后一件的症状是「管理端保存成功、值没变」：

1. **库**：建表语句加列（**最后一列**）+ `migrate()` 里 `ensureColumn`；
2. **服务端**：`database/rows.ts` 行类型 + 仓储的 `INSERT/UPDATE` 列清单（漏一处就是 200 但值不动）
   + DTO（`@ApiProperty` 描述写清语义）+ `swagger/models.ts` 登记；
3. **管理端**：页面表单 + 提交体；
4. **客户端**：只有「玩家侧要看的」才加进快照段（`ClientConfigService.snapshot()` + `GameConfigSnapshotDto`
   + 客户端 `configs/game-config.ts` 区段 + `apply-snapshot` 落库），否则不加。

### 6.2 加一张新表（登记五处 + 快照三处）

| 位置 | 文件 | 漏了会怎样 |
|---|---|---|
| ① 表分类 | `server/scripts/lib/config-tables.cjs`（两份清单） | 导出直接报错（`assertAllClassified`） |
| ② 接口生成 | `tools/gen-api.cjs` 的 `MODULES` | `gen:api` 报「operationId 的模块段没登记」 |
| ③ 跨域边界 | `tools/audit-server-boundaries.cjs` 的 `REPO_EDGES` | 边界审计判违规 |
| ④ 审计目标 | `tools/audit-target.decorator` 的类型表 | 写操作日志时目标类型不认识 |
| ⑤ 快照 | `ClientConfigService.snapshot()` + `GameConfigSnapshotDto` + 客户端 `configs/game-config.ts` 区段 | 客户端拿不到这段（几十套单测齐炸） |

### 6.3 加一列的三个连带检查

- **`SELECT *` 导出顺序**：新列必须建表语句末尾（见 §三.4）。
- **`runtime-config-cache` 要认识每张物品表**：`itemTypeOf` / `itemLabelOf` / `sellPriceOf` 三处
  （回收价、掉落文案、道具判定都读它）。漏一处的表现是「回收价 0 / 名字显示 id / 认不出道具」，
  **全都不报错**。
- **快照契约测试**：`audit-snapshot-contract` 会比对「DTO 字段 ↔ 客户端解构」，加段漏改就红。

## 七、`make config-*` 的正确姿势

```bash
make config-export     # 库 → config-sync.sql（提交它 = 同步给别人）
make config-import     # config-sync.sql → 库（整表替换；账号与角色存档不动）
make config-check      # 报「哪张表第几行落后了」，落后退出码 1
```

- **导入三道自保**：导入前留档 `data/backups/config-before-import-*.sql` → 导入前校验表清单 →
  导入后**重新生成快照与文件逐字节比对**。别用「没抛异常」当成功。
- **导入后必须重启服务端**（两份内存副本）。
- **本机库常有未导出的运营改动**，所以 `make config-check` 常年红——判断「我这次改的有没有漏」时，
  看它报的表是不是你动过的那几张。
- 只想给**某张表**补几行时，别整份导出（几千行假 diff）：照既有格式手动拼那一节 + 改文件头三行
  （`表 38 张 / 行 N 条`、`tables:`、`counts:`），再 `make config-import` 验一遍。
- `cp` 库文件前先 `PRAGMA wal_checkpoint(TRUNCATE)`，否则拷到的可能是缺 WAL 的旧数据。

## 八、守点：谁在看着这一套

| 审计 | 守什么 |
|---|---|
| `audit-shared-data` | 快照完整（表齐 / 每表非空 / 行数自洽）+ 枚举与客户端逐值一致 + 业务代码里没有第二份枚举 + 跨端常量对齐 |
| `audit-snapshot-contract` | 快照 DTO ↔ 客户端解构字段一一对应 |
| `audit-api-generated` | 生成物与 openapi 逐字节一致 + 悬空 `$ref` |
| `audit-config-leak` | `assets/ui` 里不许出现可配置项（魔法数字 / 中文 / 资源路径） |
| `audit-server-boundaries` | 跨模块 import 只能走白名单边、仓储只由 `DatabaseModule` 装配 |
| `audit-role-authority` | 存档里「哪些字段归服务端」的清单与客户端赋值来源 |
