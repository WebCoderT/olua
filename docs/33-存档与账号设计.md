### 0.2 封禁语义（`common/utils/ban.util.ts`）

```
active                                  → 从没被封过
disabled + ban_until = null             → 永久封禁
disabled + ban_until <= now             → 已到期（ban-scheduler 扫回 active）
disabled + ban_until > now              → 封禁中
```

判据只能是「`disabled` **且** 有结束时间 **且** 已到期」—— 只看 `ban_until`
会把「永久封禁」误判成「从没被封过」。这个坑已经在注释里钉住了。

| 项 | 现状 |
|---|---|

## 一、账号状态机

现在两态不够用了。加两态，**但不动 `active` / `disabled` 的语义**（老数据零迁移）：

```
                 ┌────────── 解封（到期扫 / 人工）──────────┐
                 ↓                                        │
   active ──封禁──→ disabled ──玩家申请注销──→ deleting ──30 天──→ deleted
     │                  │                        │
     └──玩家申请注销────→┴───────────────────────┘
                        └──登录即撤销──────────────→ active
```

| 状态 | 能否登录 | 角色是否可见 | 说明 |
|---|---|---|---|
| `active` | ✅ | ✅ | 正常 |
| `disabled` | ❌ | — | 封禁（临时/永久），沿用现状 |
| `deleting` | ✅ | ✅（带「注销中」标记） | **冷静期 30 天，登录即撤销**（已定） |
| `deleted` | ❌ | ❌ | 已注销：**匿名化**，不硬删 |

**为什么匿名化而不硬删**：`audit_logs` 与 `economy_log` 里有大量 `account_id` 引用，
硬删会让审计链断裂（26 篇的对账就再也还原不出来）。匿名化 = 改名 + 清邮箱 + 清密码，
行留着。

## 二、角色删除冷静期 7 天（已定）

### 2.1 语义

| 项 | 规则 |
|---|---|
| 触发 | `DELETE /roles/:id` → 写 `deleted_at`（**软删**），不再 `deleteById` |
| 冷静期 | **7 天** |
| 期间能否登录 | **能**（已定）；进游戏自动撤销删除 |
| 撤销 | `POST /roles/:id/cancel-delete`，或该角色被选中进入游戏 |
| 名字 | 冷静期内**仍占用**（防抢注后原主撤销失败） |
| 到期 | `RolePurgeScheduler` 每天扫一次，`deleted_at + 7d <= now` → 真删（级联） |
| 可见性 | 选角界面显示但置灰 + 「已申请删除，进入游戏可撤销」 |

```sql
ALTER TABLE roles ADD COLUMN deleted_at INTEGER;
CREATE INDEX idx_roles_deleted ON roles(deleted_at) WHERE deleted_at IS NOT NULL;
```

**级联真删**：`quest_progress` / `role_mails` / `role_achievements` / `role_friends` /
`role_blocks` / `role_reports` / `party_members` / `guild_members` / `ranks` 全部按
`role_id` 清；**`roles` 行删除前先落一条 `audit_logs`（`kind='role_purged'`，带存档 JSON 摘要）** ——
这是「删了还能举证」的最后一道。

### 2.2 为什么不是账号级

角色是「玩家能主动放弃的东西」，账号是「资产」。两者冷静期不同：
角色 7 天（已定），账号 30 天（已定）。**不要把两个数字统一** ——
统一的结果一定是短的那个不够用、长的那个被骂。

## 三、存档版本与迁移【本篇最值钱的一条】

### 3.1 加版本号

```ts
// data.schemaVersion
const ROLE_DATA_VERSION = 3; // 当前（1 = 无版本号的老档；4 预留给 C1）
```

| 版本 | 含义 | 状态 |
|---|---|---|
| 1 | 无版本号的存量老档（缺字段即按 1 处理） | — |
| 2 | 存档里带 `schemaVersion`（1→2 只盖章，不动任何字段） | 已落地（#818） |
| 3 | **装备槽位从裸 id 改成 `{ id, bound?, from? }`**（#816；穿上不再丢绑定与溯源） | 已落地（#816） |
| 4 | **预留**给 C1「删元宝 / 银子、金币不可流通」（见 3.4） | — |

| 规则 | 说明 | 落在哪 |
|---|---|---|
| 读 | **进入游戏**（`POST /roles/:id/select`）时比 `schemaVersion`，落后则走迁移链 | `RolesService.migrateBeforeEnter` |
| 迁移 | 一环一个函数，「从 N 到 N+1」**顺序执行、幂等**；版本号由链条统一盖 | `role-migration.ts` 的 `migrateRoleData` |
| 写 | 迁移后**当场落一次库**（`updateDataKeepRevision`，不推进 `revision`） | 同上 |
| 失败 | 迁移抛错 / 版本比代码新 → **拒进游戏**（20028 + 告警日志），存档原样保留 | 同上 |
| 老档 | `schemaVersion` 缺失 = 1；非整数 / ≤0 / 字符串脏值一律按 1 | `schemaVersionOf` |
| 批落 | `make migrate`（发布前跑；`--dry-run` 只看分布） | `scripts/migrate-role-data.cjs` |
| 自检 | 链条必须连续到 `ROLE_DATA_VERSION`，否则**模块加载即抛**（启动失败） | `assertRoleMigrationChain` |

**为什么在选角就落库，而不是「等下一次正常存档一起落」**（对上一版设计的修订）：
服务端的读口有十几处（战斗 / 任务 / 拾取 / 实时快照…），只在内存里迁完**只对这一条路径生效**；
紧接着一次用药、一次受击就会把库里的老形状原样写回去，版本号永远不前进，于是每次进入游戏
都要重跑一遍链。落一次库的代价是每个角色一次 UPDATE，换来的是「库里那份从此就是当前版本」——
后续所有读路径不需要知道迁移这回事。

**为什么不用「一次发布跑完就不用管」的严格模式**：`make migrate` 漏跑一次就会把全服老档关在门外，
而线上补跑又得再走一次发布。惰性迁移让「漏跑」退化成「登录时多一次 UPDATE」，闸门仍然在
（迁不动就拒登），代价可控。

**幂等怎么保证**：每个迁移函数只做「从 N 到 N+1」的形状变换，且带
`if (data.schemaVersion >= N+1) return data;` 前置判断。重跑无害。

### 3.2 迁移必须写测试

每个版本一个 fixture（真实老档快照）+ 断言「迁移后 30 个键都在、关键字段值不变」。
这是唯一能在上线前发现「迁移把金币清零」的手段。

### 3.3 一条硬纪律：不能用兜底代替版本号

不要用「按字段名 try/catch 兜底」代替版本号 —— 兜底只能处理**缺字段**，
处理不了**字段含义变了**（比如 `attack` 从「物理」变成「总攻」）。
一旦含义变了而版本号没变，兜底会把错数当对数用，且永远查不出来。

### 3.3.5 已落地的 `2 → 3`：装备槽位存对象（#816 / B4 的槽位那一半）

`equipments` 的槽位原来是裸 id（`"weapon_1"`）。问题是 **`bound`（绑定角色）与 `from`（掉落溯源）
是这件东西的属性，不是格子的属性**：槽位只存 id 时，穿上那一刻这两项就没了 ——
脱下来变成一件未绑定、无溯源的新东西。表现就是「绑定装备穿一次就能卖」。

| 项 | 规则 | 落在哪 |
|---|---|---|
| 形状 | `equipments[slot] = { id, bound?: true, from?: BagOrigin } \| null`，**与 `BagCell` 同一套字段口径** | `role-inventory.ts` 的 `WornItem` / `wornIdOf` |
| 穿脱 | 只搬地方不改值：格子 → 槽位搬 `bound` / `from`，卸下时原样搬回格子（`toBagCell`） | `equipAt` / `unequipSlot` |
| 迁移 | 裸 id → `{ id }`；空串 → `null`；已是对象原样保留（**幂等**，链重跑不磨元数据） | `role-migration.ts` 的 `2→3` 环 |
| 回填绑定 | 老档里「已经穿在身上」的件，绑定痕迹已丢 —— 按**配置事实**回填：`bindOnDropOf(id)` 为真 → `{ id, bound: true }`；问不到的一律不写 | 同上（`RoleMigrationContext.wornBoundOf`） |
| 双路径一致 | 惰性迁移（Nest，读运行时配置缓存）与 `make migrate`（独立进程，自己 `applyEquipmentBases`）必须给出**同一份结果** | `roles.service.ts` / `scripts/migrate-role-data.cjs` |
| 客户端 | 取 id 一律 `wornIdOf`（同时认裸字符串，远端互见帧仍是裸 id 协议）；读档 `wornItemOf` 把裸 id / 完整快照收敛成对象 | `configs/items.ts` / `StorageManager.ensureRoleDefaults` |
| 管理端 | `PATCH /admin/roles/:id` 的入参**不变**（槽位 → id 简表）：同 id 沿用现有元数据，换 id 才新建 `{ id }` | `role-data.util.ts` 的 `mergeWornEquipments` |
| 测试 | `e2e-role-migration`（脚本按库里 `bind_on_drop` 回填 + 惰性路径 `{ id }`）、`e2e-combat` 十一·E（穿脱元数据不丢）、`client/tools/test-worn-item.cjs` | — |

**为什么回填只用「配置事实」而不是「一律 bound: true」**：老档里也可能穿着运营临时发的、
本来就不绑定的件；凭空锁死玩家的东西比少绑一件更糟。所以只回填「掉落即绑定」这一种可证实的情形，
其余按未绑定 —— 这条与 `readBagOrigin` 的「宁可少一行展示，不猜」同一取向。

**为什么形状改动也要顺手修客户端读档**：`StorageManager.ensureRoleDefaults` 原来把槽位对象
**折叠成 id**（为了兼容更早的快照存档）。那行不改成 `wornItemOf`，新形状一进客户端就被磨平，
存档再写回去服务端看到的是 id，迁移环等于白做。

### 3.4 预留的下一环：货币收敛到 `bindGold`（C1，`3 → 4`）

| 项 | 规则 |
|---|---|
| 数值 | `bindGold = bindGold + gold + silver`；随后 `delete data.gold` / `delete data.silver` |
| 为什么 `silver` 也并入 | 删列必须处理数值，不并入就是吞玩家资产。`silver` 现存量只有运营发放，并入无争议 |
| 货币道具 | `money_items` 里 16 条 `currency='gold'/'silver'` **保留行、下架投放**（移出商城与掉落引用），已持有的仍可使用 |
| 使用口径 | `useMoney()` 遇到 `currency` 不在现存货币集合 → 按 `amount` 入 `bindGold`，`economy_log.kind='money_item_legacy'` 且 `currency` 记原值 |
| 显示 | 所有 UI 统一叫**金币**；「绑定」一词只用于物品（不可交易），不再修饰货币 |
| 前置 | `make migrate --dry-run` 必须先输出「N 个角色 / 将合并 X 金币 / 16 条道具转 legacy」，人工确认后再执行 |
| 回滚 | **不可回滚**（列已删）。执行前强制备份，与 34 篇 J2 的 20 层配置版本不是同一件事 |

### 3.5 坏档：标记 + 拒登，不再「坏档当空档」（#819 / B61 / I6）

`decodeStoredRoleData` 把解析失败折成 `{}` —— 那是给**展示**路径用的。但空对象在收权判定里
意味着「库里没有这个字段 → 客户端那份是唯一来源」，于是**一行坏 JSON 就是一条提权通道**：
改包只要能触发一次坏档，就能自己写 `gold` / `bag` / `equipments`。

| 项 | 规则 | 落在哪 |
|---|---|---|
| 识别 | 入口一律用 `decodeStoredRoleDataStrict`（`ok: false` + 原因），不再和空对象混淆 | `role-data.util.ts` |
| 标记 | 置 `roles.corrupted = 1`；**不删行、不改 `data`**（删行毁证据，改 data 是把坏档洗成空档） | `RoleRepository.markCorrupted` |
| 拒登 | 选角 / 存档都返 20029「存档已损坏，暂时无法进入游戏，请联系客服」 | `RolesService.select` / `save` |
| 解封 | 人工把 JSON 修好，**下一次解析成功自动清掉标记**（不需要运维再点一次） | 同上 |
| 发现 | 管理端角色详情的 `corrupted` 字段；也可直接 `SELECT id FROM roles WHERE corrupted = 1` | `AdminRoleDto` |
| 收权 | `enforceServerAuthority` 不再「库里没有这个字段就放行」，一律按空值回填（`level` 的空值是 1，其余 `0` / `[]` / `{}` / `null`） | `role-authority.ts` |

**代价说明**：这条收紧会影响到「服务端接管之前由客户端建的号」—— 那种档里可能真的没有
`bindGold` 等键，收紧后它们的余额会按空值处理。本地库实测 127 个角色里只有 2 个探针号命中
（背包为空），所以按 37 篇 I6 的口径执行；真要救某个号，走管理端 PATCH 人工决定，
**不要**再开一条「缺字段就采信客户端」的自动通道。

### 3.6 乐观锁：基线必填 + 落库复核（#820 / B62 / I2）

`revision` 原来是**可选**的：不传就直接覆盖，等于「最后写入者胜」。管理端刚改的数值会被
客户端那份「改之前」的存档整体盖掉，查不到、也不报错 —— 这是最坏的一类 bug：
数据错了，但所有日志都在说「保存成功」。

| 项 | 规则 | 落在哪 |
|---|---|---|
| 必填 | 10 个写入 DTO 的 `revision` 都是必填；缺了就是 **400 / 40000**（参数校验层，够不到业务逻辑） | `dto/*.dto.ts` |
| 业务比对 | 每条写入路径开头 `if (dto.revision !== existing.revision) → 409 / 20006`，而且**不再判 `undefined`** | `roles.service.ts` |
| 落库复核 | `UPDATE … WHERE id = ? AND revision = ?`；`changes === 0` 即「读完之后被别人改过」→ 409 / 20006 | `RoleRepository.replace` |
| 统一出口 | 13 条写入路径都走 `persistOrConflict(row, expectedRevision, 动作名)`，错误文案带动作（「保存存档时…」） | `RolesService.persistOrConflict` |
| 例外 | **击杀经验入账**是服务端自己的节拍驱动、没有客户端基线可重试，冲突时记 warn 后返回 `null`（丢一笔经验，好过盖掉别人的改动） | `RolesService.applyKillExp` |

**为什么两道比对**：业务层的比对只覆盖「读的那一刻」；从读到写之间还隔着整段结算
（技能判定、掉落、属性重算、血蓝结算）。把那句 `AND revision = ?` 压进 UPDATE，
一致性就由数据库用一条语句判掉，不依赖「这段代码碰巧没有 `await`」。

**为什么客户端不重推一次**：#820 验收原文是「重拉存档再重试一次」，但这接口是**全量覆盖** ——
拿刚拉下来的新修订号把本地旧数据推上去，等于把后台改动原样盖回去。所以客户端拿到 20006 的
处理是「拉一次详情、换基线、**丢弃本轮**」，下一轮防抖推送自然就成功了（见 `utils/net/RoleSync`）。
真要支持重试得先有「按字段合并」，**暂时放置**（重开条件：存档改成按字段增量上报，或服务端提供三方合并）。

## 四、在线权威与幽灵在线

### 4.1 现在的判据

`accounts.online_role_id` + `online_heartbeat_at`。心跳停了但进程没优雅退出时，
`online_role_id` 留在库里 → 玩家再登录被「角色已在别处登录」挡回去。

### 4.2 目标判据（三层）

| 层 | 判据 | 用途 |
|---|---|---|
| 内存 | `connections`（实时进程私有） | 正常路径的唯一权威 |
| 库 | `online_role_id` + `online_heartbeat_at` | 跨进程 / 重启后的残留判断 |
| 兜底 | `now - online_heartbeat_at > 90s` → **判定幽灵**，登录时直接接管（清标记 + 允许进入） | 崩溃残留 |

| 规则 | 说明 |
|---|---|
| 心跳间隔 | 客户端 15 秒一次（现状）；超过 **90 秒**（6 个周期）判幽灵 |
| 单账号单角色 | 保持（`online_role_id` 单值）；同账号第二个角色登录 → 踢掉第一个（现状语义） |
| 踢下线 | 保持 `token_version` + 清 `online_role_id` |
| 重启 | 进程启动时**不清库**（悲观），只清内存；玩家登录时按 90 秒规则接管 |

### 4.3 存档写入时机

| 时机 | 写 | 说明 |
|---|---|---|
| 关键动作（穿脱装备 / 交易 / 邮件领取 / 升级） | **立即写** | 这些动作丢一次就是玩家损失 |
| 移动 / 血量变化 | **节流写**（≥5 秒一次 + 离图必写） | 高频、可丢，丢了玩家只回退几步 |
| 心跳 | 只写 `online_heartbeat_at`（单列 UPDATE） | 不碰 `data` |
| 下线 | **强制写**（含 `online_role_id` 清理） | 正常路径 |
| 进程退出钩子 | 遍历 `connections` 全部写一次 | 优雅停机 |

**崩溃丢档窗口 = 5 秒**（节流上限）。可接受，且明确写在这里 —— 以后有人问「为什么掉线回退了」有答案。

## 五、角色数量上限

改之前**不设上限**，只有一个「同账号重名校验」。问题不是「能建很多」，
而是「大量空号占用名字空间 + 刷初始资源」。

**#878 已落（实现口径，与原设计的两处差异写在下表）**：

| 项 | 已落口径 |
|---|---|
| 上限来源 | `.env` 的 `ROLE_MAX_PER_ACCOUNT`（默认 6，见 `common/constants/role.ts`）—— 与组队 / 帮会 / 好友上限同一套做法；e2e 把它钉成 6 才验得稳 |
| 上限行为 | 超限 `POST /roles` → **400 / 20018**（`ROLE_LIMIT_EXCEEDED`，文案带上限数字）；已存在的角色不受影响 |
| 查重顺序 | 先重名（20005）再上限（20018）：重名是玩家自己能解决的事，先给他那个理由 |
| 并发兜底 | 表上 `UNIQUE(account_id, name)`；应用层「先查再插」只是快路径 |
| 存量重复行 | 启动时先查重复，有就**跳过建索引**并打 ERROR（列出账号 / 名字），**不擅自改玩家名字**；人工改名后重启自动补上 |
| 下调 | 运营把上限调低时，**存量不删**，只禁止新建（`list` 不看上限） |

与原设计不同的两处（都属**暂时放置**，不是「不做」）：上限**没有**进 `runtime_params`
（重开条件：运营需要「不改配置文件、不重启」就调上限时，再挪进去）；错误码用了 20018
而不是新造 `ROLE_SLOT_FULL`（同一个语义没必要再开一个码）。
「删除冷静期仍占槽位」随冷静期一起**暂时放置**（重开条件：冷静期落地，见 37 篇 D-40）。

原设计原文（保留作对照）：

| 项 | 口径 |
|---|---|
| 上限来源 | 配置项 `role_slot_count`（`runtime_params`），**默认值沿用客户端选角网格的可见槽位数** —— 不发明新数字 |
| 上限行为 | 达到上限后 `POST /roles` → `ROLE_SLOT_FULL`（新码）；已存在的角色不受影响 |
| 与删除冷静期 | `deleted_at IS NOT NULL` 的角色**仍占槽位**（否则删了再建，等于无限建） |
| 下调 | 运营把上限调低时，**存量不删**，只禁止新建 |

## 六、登录安全与可追溯

| 项 | 现在 | 目标 |
|---|---|---|
| 登录失败限流 | ✅ 已有（用户名 + IP 双层） | 保持 |
| 令牌失效 | ✅ `token_version`（改密 / 踢人 / **玩家主动登出**，见 #880） | 保持 |
| 登录 IP | ❌ | `account_logins`（`account_id` / `ip` / `ua` / `at` / `result`），保留 90 天 |
| 异地登录提示 | ❌ | 与上一次登录 IP 不同 → 站外邮件提醒（32 篇的 `mail_queue`）+ 收件箱一条 `system` |
| 设备指纹 | ❌ | 见暂时放置 |
| 二次验证 | ❌ | 见暂时放置 |

**IP 只存不判**：不做「异地即冻结」（误伤太大），只做「告知」。这条与 26 篇
「脚本风控不自动封号」是同一个原则 —— 自动处置的误伤成本高于漏检成本。

## 九、边界情况

| # | 情形 | 期望 |
|---|---|---|
| 1 | 冷静期内角色被选中进入游戏 | 自动撤销删除 + 记 `audit_logs`（`kind='role_delete_cancelled'`） |
| 2 | 冷静期到期时角色正好在线 | **跳过一次**（在线不删），下次扫到再删；避免删在线角色导致连接崩 |
| 3 | 冷静期到期前玩家建满槽位 | 冷静期角色仍占槽位（见五） |
| 4 | 撤销时角色名已被别人占用 | 不可能：冷静期内名字仍占用 |
| 5 | 存档迁移失败 | 拒绝进入游戏 + 告警；**存档原样保留**（迁移在内存里做，失败不写） |
| 6 | 老档 `schemaVersion` 是字符串 | 按 `Number()` 解析，`NaN` 视为 1（不报错） |
| 7 | 迁移链缺一环（有 1→2 没 2→3，但数据是 1） | 启动时自检：版本数必须连续，否则**启动失败**（比运行时炸好） |
| 8 | 幽灵判定误杀（玩家网络抖动 90 秒） | 玩家重连即回；顶号只影响「同一账号另一处登录」 |
| 9 | 账号封禁时角色正在游戏 | 立即踢下线（现有 kick）+ 清 `online_role_id` |
| 10 | 注销冷静期内收到邮件 / 活动奖励 | 邮件照收（32 篇），奖励照发 —— 撤销后一切都在 |
| 11 | 注销到期时角色在冷静期 | 账号先匿名化，角色随账号一并清理（账号优先级更高） |
| 12 | 存档 JSON 被手工改坏（`JSON.parse` 失败） | 拒进 + 告警；从 `audit_logs` 找最近快照人工恢复（见暂时放置） |
| 13 | 同账号两个客户端同时登录 | 后登录踢先登录（现状） |
| 14 | `zone_id` 与角色所在区不一致（跨区分片后） | 登录时校验，不一致 → 拒（`ZONE_MISMATCH`）；防跨区读档 |
