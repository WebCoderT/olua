# 10 · 任务、成就、排行与社交

> 这一篇的四个系统有一个共同点：它们**都不拥有数值**，只是「记录已经发生的事」。
> 所以它们的副作用一律可丢 —— 世界状态才是权威。

## 一、一条采集线：事件总线

任务进度、成就进度、BOSS 战报、地图监控的原料都来自同一处：

```ts
// common/events/game-events.service.ts（@Global）
emit("monster:killed", { accountId, roleId, monsterKey, monsterLabel, monsterTier });
emit("quest:claimed",  { accountId, roleId, questId, kind });
```

- **结算只 emit**，不认识任务也不认识成就；订阅方在各自 `onModuleInit` 里 `events.on(...)`。
- **同步分发**是硬约束：击杀结算返回时任务与成就进度必须已落库，
  否则「打完怪立刻打开任务面板」看到旧进度。所以这不是消息队列，**别拿它跨进程**。
- **订阅方异常各自兜**：成就写库失败只打日志，**绝不回滚一次真实击杀**。
- `listenerCount` 供启动自检与单测问「这条事件真有人接吗」—— 少一个订阅不报错，只会静默不生效。

## 二、任务

### 配置（`quests`，5 行）与进度（`quest_progress`）

| 列 | 含义 |
|---|---|
| `id` / `kind` | `main`（主线）/ `daily`（日常） |
| `prev_quest_id` | **主线链前置**（前置没 claimed 就不能接） |
| `min_level` | 接取等级 |
| `npc_id` | 交付 NPC |
| `objective_type` | `kill` / `talk` / `collect` |
| `objective_target` / `objective_count` | 目标（怪物 key / NPC id / 物品 id）与数量 |
| `reward_gold` / `reward_exp` / `reward_items` | 奖励（物品是 JSON 数组） |

### 状态机

```
available（无进度行）→ accepted（进行中）→ ready（可交付）→ claimed（已领奖）
```

- **可接任务不在快照里**：客户端拿「配置快照 + 自己的进度行」自己算哪些能接（等级 / 前置链都是纯读计算）。
- **进度只有三个写入口，全在服务端**：

| 目标类型 | 谁推进 | 时机 |
|---|---|---|
| `kill` | 订阅 `monster:killed` | 击杀结算时（`objective_target` 匹配怪物 key） |
| `talk` | `npc-talk` 接口 | 与 NPC 对话时（只看 `accepted` 行，配置对得上才 +1） |
| `collect` | **不推进进度** | 交付时直接查背包（`status === accepted` 才能交） |

客户端**永远不能上报「我完成了」**。这是这一整套的底线。

### 接取与交付

```
accept:  等级不够 → 200xx；已有行（claimed / accepted）→ 拒；主线前置没 claimed → 拒
submit:  collect → 查背包够不够（差一个就 20017，进度行保持 accepted，补齐再来）
         kill/talk → 必须 ready，否则「任务还未完成，不能交付」
         发奖走 grantQuestRewards 的**单次落库**（材料消耗 + 奖励 + 升级一次写完）
         daily 删行（可重接、进度清零）；main 保留 claimed 行作链门控
         emit("quest:claimed")
```

**单次落库**是关键：材料不足与背包放不下都在校验阶段抛出，不会出现「材料扣了奖励没发」。

### 推送

`quest` 帧只推给本人连接（`onProgress` 由 `RealtimeService` 启动时接线）。
HTTP 进程不装 realtime 模块时回调为空 —— 那时对话 / 接取 / 交付的进度变化由**响应体自己带回**。

## 三、成就

### 配置（`achievements`，24 行）与记录（`role_achievements`）

| 列 | 含义 |
|---|---|
| `category` | `battle` 等分类（分页签用） |
| `condition_type` | `kill` / `quest` / `level` / `combat` / `collect` |
| `condition_target` | 目标（怪物 key，`*` = 任意） |
| `condition_count` | 需要的次数 / 数值 |
| `reward_gold` / `reward_exp` / `reward_items` | 奖励 |
| `hidden` | 未达成的隐藏成就（不显示） |

### 一条最重要的分界：累计型 vs 状态型

| 类型 | 条件 | 进度从哪来 | 是否落进度 |
|---|---|---|---|
| **累计型**（`kill` / `quest`） | 「做过多少次」 | 订阅 `monster:killed` / `quest:claimed` 把 `progress` +1 | ✅ 落库 |
| **状态型**（`level` / `combat` / `collect`） | 「现在是什么样」 | 每次查询按角色当前状态**现算** | ❌ 不落库 |

状态型为什么不落进度：存一份投影的唯一后果是「角色变强了成就进度没动」，还得为它写同步逻辑。

### 达成与领奖是两件事

- `achieved_at` 非空 = 达成（可领）；`claimed_at` 非空 = 已领。
- **不自动发奖**：上线瞬间给全员背包塞东西是事故，而且背包满时自动发奖只能丢。
- **背包放不下时不堵玩家**（#429）：整份奖励转成一封邮件，照常记 `claimed_at`，接口回 `mailId`。
  玩家去收件箱领，不用先猜是哪件东西放不下。
- 累计型的 `achieved_at` 是真实时刻（事件驱动）；**状态型的 `achieved_at` 在领取时补写**，
  语义等同「首次确认达成」。查询（GET）**不写库** —— 一个读接口顺手改数据，
  会让「刷新一下进度变了」这种误会永远解释不完。

## 四、排行榜（`#400`）

### 三个榜

| 榜 | 排序依据 | 为什么是它 |
|---|---|---|
| `level` | `roles.level` 索引列 | 升级路径一直在维护它 |
| `combat` | `summarizeRoleAttributes().combat` | 把等级 / 装备 / 战魂 / 称号 / 军衔全算进去，是「谁更能打」最接近的答案 |
| `kills` | `roles.kills` | 结算路径 +1 |

**并列同分同名次**（竞赛排名 1、2、2、4），同分再按 `roleId` 升序 ——
二次键的意义不是「公平」，是**稳定**：没有它，两次重算之间同分的人会互换位置，
玩家看到名次上下抖，而实际什么都没变。

**离线也上榜**：读的是 `roles` 表，不要求在线。

### 为什么是「进程内物化」

| 方案 | 问题 |
|---|---|
| 每次现算 | 一次现算 = 全表读 + 逐行解析存档 + 三个排序；榜会被频繁打开，而榜的价值恰恰是「所有人看到同一份」 |
| 落一张快照表 | 多出第二个真相（角色升级了而快照没跟上，谁对？）。派生数据不落库就没有这个问题 |
| **进程内物化** ✅ | 首次请求惰性算一次 → 整份快照一次赋值替换（读侧永不会读到「等级榜新、战力榜旧」） |

两个实现细节：

- **定时器在「第一次有人看榜」时才起**（`unref`，不阻止进程退出）。这个模块在两个进程里都装载，
  若在 `onApplicationBootstrap` 起定时器，**实时进程会白白每分钟扫一次全表**。
  `LEADERBOARD_REFRESH_MS=0` 表示「不起定时器」—— e2e 用它测「快照语义」。
- **`me` 走全量索引**：榜只保留 `topN`（默认 100），但名次在**全量排序**里算，
  排 3000 名的人也看得到「你是第 3000 名」。名次排不下时返回 `0`（客户端判 `rank > 0` 即可）。

## 五、邮件（奖励的兜底投递口）

`role_mails`（表头：`channel / kind / title / body / gold / exp / attachments / read_at / claimed_at / expires_at`）。

### 四个频道必须收敛（`MAIL_CHANNELS`）

| channel | 玩家视角的分类 |
|---|---|
| `system` | 系统 |
| `reward` | 奖励 |
| `social` | 社交（好友申请） |
| `combat` | 战斗（BOSS 战报） |

- **`channel` = 分类（固定四个），`kind` = 来源标签（自由扩展，只用于日志与排查）**。
  典型错位：一条 `kind: "achievement"` 的消息属于 `channel: "reward"` ——
  玩家不关心它是哪个玩法发的，只关心「这是不是奖励」。
- 新增频道只能改 `MAIL_CHANNELS`：否则面板上会冒出「没有页签能装下」的消息（那条邮件永远看不到）。
- `toMailChannel` 兜底归到 `system`：**绝不让消息因为频道不认识而丢掉**。
- 人工补发只允许 `system` / `reward`（#437）：往 `social` / `combat` 里发会污染语义。

### 保质期

`expires_at` 由**投递方**给（BOSS 战报 7 天、运营补发永久）。集中在清理任务里算就表达不了这个差异。
**带未领附件的行不会因此被清**（判据在清理 SQL）。

## 六、队伍（`#399`）

### 为什么落库 + 为什么走帧

| 选择 | 理由 |
|---|---|
| **落库**（`parties` + `party_members`） | 纯内存的队伍在实时进程重启时就全没了，而「重连回来还在同一个队」才是玩家的预期；顺带把「一人一队」交给数据库唯一约束 |
| **走 WS 帧** | 邀请必须即时送达。HTTP 在存档进程、WS 在实时进程，存档进程推不到别人的通道；而队伍快照本来就要跟互见帧一起变（队友金色名字、头顶队标） |

### 缓存只有一张表

`roleId → partyId` 进内存（热路径：互见帧 200ms 一拍、每次击杀分经验一次都要问）。
**其余一律读库** —— 缓存成员名单就得在改名 / 升级 / 入队 / 退队四条路径上同步，
多出来的只是漂移的机会。写全部走本服务，所以这张表不需要 TTL 刷新。

### 权限（刻意的宽严之分）

| 动作 | 谁能做 | 为什么 |
|---|---|---|
| 邀请 | **任何队员** | 组队是协作，门槛只会挡住正常玩家 |
| 踢人 / 转让 / 解散 | 只有队长 | 这三件事会伤到别人 |
| 退出 | 谁都能退 | 队长退出**自动移交**给最早加入的成员（没人就删队）——「队长不能退」在队长掉线不回来时会把整队锁死 |

### 与屏蔽的关系（#398）

**双向都不能互邀**，但两种说法分开：

- **我拉黑他** → 明说「先解除」（那是自己的设置）；
- **他拉黑我** → 只说「对方不在线」（说破等于把屏蔽变成可观测信号，与私聊同一纪律）。

### 经验分成

同图在线队友各得 `floor(killExp(他自己等级, 怪物等级) × share)`，击杀者拿全额（见 [07](./07-战斗与伤害结算.md) 第七节）。
队友分经验**不补满血蓝**、**不推进自己的 revision 基线之外的东西** —— 帧里带 `revision` 让队友客户端照搬做新基线。

## 七、好友 / 黑名单 / 举报 / 帮会（一张表看全）

| 系统 | 表 | 关键口径 |
|---|---|---|
| 好友 | `role_friends` | 两态 `pending` / `accepted`；**不放「拉黑」**（屏蔽与好友关系正交，独立一张表）；上限 100 |
| 黑名单 | `role_blocks` | 拉黑一个陌生人不需要先加好友；私聊 / 邀请 / 世界消息三处都过滤 |
| 举报 | `role_reports` | 只记录，不做自动处置（人工看） |
| 帮会 | `guilds` / `guild_members` / `guild_applications` | 职位 `leader` / `vice` / `member`（`leader` 与 `guilds.leader_id` 必须指向同一人）；人数上限 50 与等级**脱钩** |
| 帮会名 / 公告 / 留言长度 | 运行时参数 `guild` 组 | #605 起升级为配置，**不写常量**（写常量就成了第二份真相） |

帮会战（#403）**尚未实现** —— 表结构留着，逻辑不在。

## 八、聊天（`#395`）

**聊天是转发不是存储**：服务端不留历史（连内存都不留），只对每条消息做四件事 ——
**身份核实、正文净化、限频、按频道选收件人**。客户端的校验只是省一次往返，全部以服务端为准。

| 频道 | 收件人 | 口径 |
|---|---|---|
| `world` | 同图观看者（复用互见的 `viewersOf`） | 不做区服级全服广播（那需要「账号 → 区」的连接索引） |
| `guild` | 帮会全部在线成员 | 帮会身份**每次查库** —— 准入判断错一次（刚退帮的人还能喊一嗓子）比一次 DB 读贵得多 |
| `private` | `toRoleId` 对应账号 | **仅在线可达、不落库**；收件人不在线时整条拒绝（含发送者回显）——「发出去了但对面永远收不到」比「发不出去」更伤体验 |

- **屏蔽过滤必须在服务端**：客户端根本不知道「谁拉黑了我」。
- **回显**：发送者自己也收到这条帧（与收件人同形），客户端只在收到帧时上屏、
  不在发送时本地追加 —— 顺序、成功与否都以服务端为准。

## 九、排障

| 症状 | 第一嫌疑 | 查法 |
|---|---|---|
| 打怪任务不涨进度 | 订阅没接上（`listenerCount` 为 0）／`objective_target` 与怪物 key 不符 | 看启动自检；查 `quests` 那行 |
| 任务交付后材料没扣 | 发奖走了两次写（应该单次落库） | 看 `grantQuestRewards` 调用点 |
| 日常任务今天做不了了 | 正常：领奖后行留 claimed，今天再接返 20027，明天 05:00 后自动可接 | 查 `quest_progress.reset_day` |
| 日常还显示「可接」但接了报错 | 天号没推进（改钟 / 时区异常） | 比对 `reset_day` 与服务端当前天号 |
| 成就进度不动（等级类） | 状态型**不落**进度，靠现算 | 正常行为 |
| 成就领奖提示背包满 | 走的是邮件兜底（回 `mailId`） | 查 `role_mails` |
| 排行榜名次一直不变 | 物化快照（默认 60s 重算） | 看 `computedAt`；e2e 用 `LEADERBOARD_REFRESH_MS=0` |
| 排 3000 名看不到自己 | 客户端读的是 `page` 而不是 `me` | 用 `me` 接口 |
| 邮件「看不到」 | `channel` 不在四个之内（被兜底到 system） | 查那行的 `channel` |
| 队伍重启后丢了 | 写库失败 / 走了内存路径 | 查 `parties` / `party_members` |
| 拉黑后还能收到世界消息 | 过滤在客户端而非服务端 | 见第八节 |
| 私聊对方收不到 | 对方不在线（整条拒绝是设计） | 看接口返回 |
