# 13 · 部署、运维与质量门禁

这篇讲「代码怎么变成一个能用的线上服务，以及怎么保证它没坏」。
和前面几篇不同，这里的主角不是业务链路，而是**五个容器、两份密钥、三套备份、两个 CI job、15 项审计**。

---

## 一、全景：五个容器，一个入口

```
                           ┌───────────────────────────────────────────┐
                           │  :80  admin 容器（nginx，唯一公网入口）    │
   浏览器 ─────────────────►│  按 server_name 分流，域名全是环境变量     │
                           └───┬────────────┬──────────────┬───────────┘
        yimw.cn / www          │            │ admin.yimw.cn│ game.yimw.cn
              ▼                │            ▼              ▼
      ┌──────────────┐         │   ┌────────────────┐  ┌──────────────┐
      │ website 容器 │         │   │ 管理端静态页    │  │ game 容器     │
      │ nginx 挂      │         │   │ (本容器内 dist)│  │ nginx 挂      │
      │ ./website:ro │         │   └───┬────────┬───┘  │ ./game:ro    │
      └──────────────┘         │       │        │      └──┬────────┬──┘
                               │  /api/│  /game-│resources/│ /api/  │
                               │       ▼        ▼         ▼        │
                               │  ┌──────────────────────┐         │
                               └─►│ server 容器 :3100    │◄────────┘
                                  │ 存档 / 配置 / 管理端 │
                                  │ 接口（compose 内网） │
                                  └──────────┬───────────┘
                                             │  同一份 .env、同一个库文件
                                  ┌──────────▼───────────┐
                                  │ server-realtime :3101│
                                  │ WS / 世界 / 结算     │
                                  └──────────┬───────────┘
                                             ▼
                                  ┌──────────────────────┐
                                  │ 具名卷 olua-data     │
                                  │ /app/data/olua.db    │
                                  │ (WAL，双进程各写各表)│
                                  └──────────────────────┘

   :8080  game 容器直连（:80 那条 game 入口的等价物，调试 / 客户端默认用这个）
```

`docker-compose.yml` 里五个服务：

| 服务 | 镜像 | 端口 | 镜像来源 | 干什么 |
|---|---|---|---|---|
| `server` | `olua-server:local` | 3100（**不映射**） | `./server` | 存档、配置、管理端全部 HTTP 接口 |
| `server-realtime` | 同一镜像，`command` 换入口 | 3101（**不映射**） | `./server` | WS 实时通道、取票、世界权威、伤害结算 |
| `admin` | `olua-admin:local` | **80（唯一对外）** | `context: .` + `admin/Dockerfile` | 三站分流 + 管理端静态页 + 两条反代 |
| `game` | `nginx:1.27-alpine` | **8080** | 挂 `./game` | Cocos Web 产物 + `/api` 反代 |
| `website` | `nginx:1.27-alpine` | 不映射 | 挂 `./website` | 官网纯静态，只从 :80 进 |

> 📌 **`server` 与 `server-realtime` 是同一个镜像、不同入口**（#37 拆进程）。
> 镜像 build 两次也是同一份（`image:` 同名，第二次直接复用），差别只在 `command`。
> 拆的理由不是性能，是**隔离**：世界状态在内存里跑、每秒 tick，不该和存档写入抢同一个事件循环。

## 二、三条部署约束（改配置前必须知道）

`docs/deploy.md` 里明确列了「改动时别破坏」，这里按「破坏了会怎样」重排一遍：

| 约束 | 破坏了会怎样 | 为什么这么定 |
|---|---|---|
| 管理端与接口**同源**（都从 :80 进，`/api` nginx 反代） | 浏览器开始发跨域请求 → 要么配 CORS、要么全站 502 | 不配 CORS 就**没有一处会配错且配错难发现的地方**；`CORS_ORIGINS` 默认就是空 |
| `server` 的 3100 **不映射到宿主机** | 签名接口与 Swagger 一起暴露到公网 | 对外多开一个端口没有收益；本地调试把 compose 里那四行 `ports:` 注释打开即可 |
| `server-realtime` 的 3101 **同样不映射** | 客户端得改地址、还要自己处理 WS 直连与跨域 | `game` 容器把 `/api/realtime*` 按路径反代过去（**带 WS upgrade 头**），对外仍只有一个端口 |
| 管理端 server 块**必须 `default_server`** | IP 直访会落到 :80 的第一个 server 块（官网站）拿 404 | nginx 的 `_` 不是通配符，得显式标默认站点 |
| `TRUST_PROXY=true`（compose 已设） | 所有请求的 `req.ip` 都是 nginx 容器地址 → **登录限流把全部玩家当成一个人一起锁死** | 反代之后必须信 `X-Forwarded-For` |
| `:8080` 用独立端口，不塞进 :80 的子路径 | Cocos 产物的资源路径相对根目录 → 子路径会大面积 404 | 引擎产物不做 path prefix |
| `deploy/nginx-game.conf` **故意不写** SPA 兜底 | 缺图时回一段 HTML 给资源加载器，错误极难定位 | 缺资源必须报 404 |

### 卷与镜像的边界（最容易搞混的一处）

```
镜像内：  /app/config-sync.sql     ← Dockerfile COPY data/config-sync.sql，出厂快照
卷内：    /app/data/olua.db        ← 全部运营数据 + 玩家存档
          /app/data/olua.db-wal
          /app/data/backups/       ← 自动备份落这里
挂载：    ./game/resources → /app/game-resources:ro   （只读，数边框/背景素材用）
```

- **出厂快照在镜像里，不在卷里**。`CONFIG_SNAPSHOT_PATH=/app/config-sync.sql` 是刻意的：
  `/app/data` 被具名卷挂载盖住，卷里不会有这个文件。空库首次启动靠它自举出全部配置表。
- **种子只对空库生效**，不动已有运营数据 —— 所以升级镜像不会覆盖线上配置。
- **`BACKUP_DIR` 容器部署别乱改**：数据卷挂在 `/app/data`，备份写到没挂载的路径上就是
  「容器一重建全丢」，而「自动备份在跑」这件事表面上完全看不出异常。

> ⚠️ `docs/deploy.md` 第 6 节写「应有 server / server-realtime / admin / game 四个」——
> 实际是**五个**（还有 `website`，它不映射端口，所以 `docker compose ps` 里容易被忽略）。

## 三、密钥：三份 `.env`，各管一段

这是全项目唯一有「绝对不能提交」文件的地方。仓库是 **PUBLIC**。

| 文件 | 提交 | 在哪 | 管什么 |
|---|---|---|---|
| `deploy.env.example` | ✅ | 仓库根 | 模板，值全是占位符 |
| `deploy.env` | ❌ **永不提交** | 管理机（本机） | `DEPLOY_HOST` / `DEPLOY_USER` / `DEPLOY_KEY` / `JWT_SECRET` / `ADMIN_REGISTER_CODE` |
| `server/.env.example` | ✅ | `server/` | 模板，60+ 项运行参数（全部带注释） |
| `server/.env` | ❌ **不提交** | 本机 + 服务器 `/opt/olua/server/.env` | 真实运行参数；`deploy.sh` 每次部署从模板重新生成，**只覆盖两个密钥** |
| compose 目录 `.env` | ❌ | 服务器 `/opt/olua/.env` | 三站域名（`OLUA_SITE_DOMAINS` / `OLUA_ADMIN_DOMAIN` / `OLUA_GAME_DOMAIN`），`deploy.sh` 生成 |

`.gitignore` 已排除 `deploy.env` 与 `*.pem`，`server/.gitignore` 排除 `server/.env`。
**提交前 `git status` 看一眼，它们不该出现在待提交列表里** —— 提交一次等于把服务器交出去。

### `deploy.sh` 怎么生成 `server/.env`

不是整份覆盖，是 **`cp` 模板后用 `awk` 替换两个键**（避开 BSD `sed -i` 的坑）：

```
server/.env.example  ──cp──►  server/.env
                              ↑ awk 替换 JWT_SECRET / ADMIN_REGISTER_CODE
                              ↑ 其余 60 项保持模板默认（端口、tick 间隔、限流阈值…）
```

好处：模板加了一个新参数，下次部署自动带上去，不会因为线上 `.env` 是三个月前的而缺键。
代价：**线上手工改过的非密钥参数会被覆盖** —— 要长期改就该改模板（走 PR），而不是改服务器上的文件。

### 三个「留空不等于开放」的坑

| 变量 | 留空的行为 |
|---|---|
| `ADMIN_REGISTER_CODE` | **不再等于开放注册**：留空时必须显式 `ADMIN_REGISTER_OPEN=true` 才允许注册，否则管理端压根注册不了（首个超管也建不出来）。启动日志与「系统信息」页都会喊 |
| `SMTP_HOST/USER/PASS` | 三者非空才算配齐；不配 = 通道整体禁用，发信接口**直接返回「邮件通道未启用」**，不会静默丢信 |
| `EQUIPMENT_APPEARANCE_RES_DIR` | 留空 = 开发口径（`../client/assets/resources`）；**容器部署别留空**，compose 已设成 `/app/game-resources` |

`MAIL_TRANSPORT` 还有个更凶的：`fake` / `fail` **只服务于回归测试**。
带着它们上线，邮件要么永远发不出去、要么永远假装成功 —— 启动自检会喊。

## 四、上线流程：归档导出，不是 `git pull`

**为什么不用 `git pull`**：那台服务器访问 GitHub 极不稳定（clone 跑 10 分钟未完成，
`curl https://github.com` 直接失败，只有 `codeload` 偶尔能通）。

所以改成**从管理机导出归档再上传**：确定性高、不受连通性影响，且 `git archive`
天然只含**已提交文件**（不会带 `node_modules`、素材、`deploy.env`）。

```
管理机                                     服务器 /opt/olua
────────                                   ────────────────
git archive HEAD  ──►  olua-src.tgz  ──scp──►  解压（覆盖式）
                                              │
deploy.env ─────────────────── awk ──────────► server/.env
                                              │
                                              ▼
                                    docker compose up -d --build
                                              │
                                              ▼
                                   验收（curl 5 个点）
```

### `deploy.sh` 的五个模式

```bash
bash .workbuddy/skills/olua-deploy/scripts/deploy.sh --no-build      # 只换代码，不重建镜像
bash .workbuddy/skills/olua-deploy/scripts/deploy.sh --env-only      # 只更新 server/.env 并重启服务端
bash .workbuddy/skills/olua-deploy/scripts/deploy.sh --game [目录]   # 同步游戏 Web 产物到 :8080
bash .workbuddy/skills/olua-deploy/scripts/deploy.sh --resources     # 同步管理端素材到 game/resources/
bash .workbuddy/skills/olua-deploy/scripts/deploy.sh --verify        # 只做验收检查
```

| 模式 | 什么时候用 | 做了什么 |
|---|---|---|
| 默认 | 代码改了 | 6 步：导归档 → 上传 → 解压 → 生成 `server/.env` 与 compose `.env` → `up -d --build` → 验收 |
| `--no-build` | 只改了 `website/` 或纯文本类文件 | 跳过 `up --build`（`website` 是只读 bind mount，解压即生效） |
| `--env-only` | 只改密钥或域名 | 只重写两个 `.env` + `restart server`，不碰代码 |
| `--game` | Cocos 重新构建后 | 校验源目录有 `index.html` → `rsync -az --delete` → `up -d game` → 验收 |
| `--resources` | 管理端要选新图 / 新音效 | 校验 `image-manifest.json` 存在 → `rsync -a --delete` 到 `game/resources/` |
| `--verify` | 怀疑线上有问题 | 下面那 5 个点全部重跑 |

**两道防呆**都值得记住：`--game` 与 `--resources` 都用 `rsync --delete`，
所以脚本先确认「源看起来像一份完整的」—— 没有 `index.html` 的目录、没有清单的素材目录直接停。
否则一次误传会把服务器上的游戏清成空目录。

### 验收的 5 个点

```bash
admin page:      curl http://127.0.0.1/                        → 200
admin api:       curl http://127.0.0.1/api/health              → JSON
game page:       curl http://127.0.0.1:8080/                   → 200
game api:        curl http://127.0.0.1:8080/api/health         → JSON
三域名分流:      curl -H "Host: <域名>" http://127.0.0.1/       → 200（三个域名各一次）
image-manifest:  curl -H "Host: admin域名" .../game-resources/image-manifest.json → 200
```

三域名分流用 `-H Host:` 模拟，**不依赖本机 DNS**，所以在服务器上就能验完再改解析。
`curl --noproxy '*'` 是必须的 —— 服务器若配了 `http_proxy`，`127.0.0.1` 会被发到代理上去。

## 五、日常更新与回滚

### 更新

```bash
. ./deploy.env
git archive --format=tar.gz -o /tmp/olua-src.tgz HEAD
scp -i "$DEPLOY_KEY" /tmp/olua-src.tgz "$DEPLOY_USER@$DEPLOY_HOST:/tmp/"
ssh -i "$DEPLOY_KEY" "$DEPLOY_USER@$DEPLOY_HOST" \
  'cd /opt/olua && tar xzf /tmp/olua-src.tgz && rm -f /tmp/olua-src.tgz && docker compose up -d --build'
```

两个注意：

- **覆盖式解压不会删除服务器上已删掉的文件**。本次更新若包含文件删除，先清空目录再解压，
  但**必须保留** `server/.env` 与 `backup/`（清空脚本见 `docs/deploy.md` 第 4 节）。
- 改了 `docker-compose.yml` / `admin/nginx.conf` / 任一 `Dockerfile`，**本机先跑 `make audit`** ——
  其中 `audit-deploy` 会校验服务名、端口、卷、反代前缀、密钥隔离是否还接得上。

### 回滚

回滚 = 导出**旧提交**的归档重新上传，数据卷不受影响。

```bash
git log --oneline -5
git archive --format=tar.gz -o /tmp/olua-src.tgz <旧commit>
# 再走上传 + 解压 + up -d --build
```

> ⚠️ **前提**：新版本没改数据库结构。若改过（加了表 / 加了列 / 改了语义），
> 回滚后的旧代码面对新库可能直接起不来 —— **先按第六节备份**，必要时连库一起回退。

## 六、数据：三套备份，别混

| 备份 | 触发 | 产物 | 用途 |
|---|---|---|---|
| **自动备份**（进程内） | `BACKUP_INTERVAL_HOURS`（默认 24h） | `/app/data/backups/` | 日常兜底；结果露在管理端「系统信息」页 |
| **手动备份** | `make db-backup` | `server/backups/olua-<时间戳>.db` | 改配置 / 改结构 / 部署前 |
| **紧急拷贝** | `docker run --rm -v ...` | 宿主目录 | 容器还活着但服务起不来时 |

三者底层都是 **`VACUUM INTO`**，不是 `cp`：

```
VACUUM INTO '备份.db'
  → 产出一份**一致性快照**：把 WAL 里未合并的事务一起算进去、去掉碎片
  → 服务正在写也能备（这是 cp 做不到的：cp 出来的 .db 可能缺 -wal 里的事务）
  → 产出后当场做完整性校验
```

保留策略是**三闸独立**，不是「取最严」：

| 变量 | 管什么 | 默认 |
|---|---|---|
| `BACKUP_KEEP_COUNT` | 按份数，超出清最旧 | 7 |
| `BACKUP_RETENTION_DAYS` | 按天数，早于它清掉 | 30 |
| `BACKUP_INTERVAL_HOURS` | 多久备一次；`0` = 关闭 | 24 |

### 手工恢复

```bash
make db-restore FILE=server/backups/olua-20261009-153000.db
make db-restore FILE=... FORCE=1     # 跳过「服务在跑」检查
```

恢复是**整库替换**，会丢掉备份点之后的所有写入。所以流程永远是：
**先备当前 → 再恢复旧 → 再 `restart server`**。

## 七、配置发布：三层，别跳

改一个数值到线上生效，走的是不同的路 —— 这是「我改了怎么没生效」的标准答案
（细节在 [12-管理端](./12-管理端.md) 第九节，这里给发布视角）：

| 改的是什么 | 怎么发布 | 生效时机 |
|---|---|---|
| 运营数值（掉率、价格、曲线、刷怪区…） | 管理端页面 → **写库** | 存档进程立即（写操作后重装）；实时进程最迟 `REALTIME_CONFIG_REFRESH_MS`（10s） |
| 要随仓库分发的配置 | `make config-export` → 提交 `server/data/config-sync.sql` | 别人 `make config-import` 或空库首次启动 |
| 结构 / 枚举 / 字段 | 改代码 → 走 PR → 部署 | 整个流程 |

`config-sync.sql` 相关三条命令：

```bash
make config-export   # 当前库里的配置表 → 覆盖写 config-sync.sql（提交它 = 同步给别人）
make config-import   # config-sync.sql → 灌进当前库（整表替换；账号与角色存档不动）
make config-check    # 检查 config-sync.sql 是否落后于当前库（落后退出码 1）
```

> ⚠️ **本地库有未导出的运营改动时，`make config-check` 常红**，这是设计如此（提示你该导出了），
> 不是门禁坏了。用户正改表的时候别整份 `export` —— 会把半成品固化进快照。

## 八、CI：两个 job，只在 PR 跑

```
PR 打开 / 更新
   │
   ├─ paths-ignore 命中？（**/*.md / .workbuddy/** / design/** / website/**）
   │        └─ 是 → 整个 workflow 不触发
   │
   ├─ job: static        （15 min 上限）
   │     checkout → node 22 → make ci-static TSC=node_modules/.bin/tsc
   │        ├─ client-check   客户端 tsc（类型声明 vendoring 进 client/types/engine/）
   │        ├─ audit          15 项跨端审计
   │        ├─ server-build   服务端编译
   │        └─ admin-build    管理端类型检查 + 构建
   │
   └─ job: e2e × 4 分片  （并行，fail-fast: false）
         checkout → node 22 → make server-install-ci → make server-build
         → make server-e2e-shard I=<0..3> N=${{ strategy.job-total }}
```

### 什么时候跑

| 场景 | 跑不跑 | 原因 |
|---|---|---|
| 开 / 更新 PR | ✅ 全套 | 门禁 |
| **合并到 master** | ❌ **不跑** | PR 的 CI 跑的是 `refs/pull/N/merge`（master + 本次改动）；squash 后 master 的树与它**相同**，再跑一遍测不到新东西 |
| 纯文档 / 记忆 / 设计稿 PR | ❌ 不触发 | `paths-ignore`；改 `.md` 跑不动任何代码 |
| 手动 | ✅ `workflow_dispatch` | 想重跑全量时 |
| **直接 push master** | ❌ 无保护 | 所以别那么干 |

`concurrency: ci-${{ github.ref }}` + `cancel-in-progress: true`：同一 PR 连续 push 取消上一轮。

### 不跑什么（刻意，不是漏跑）

| 项目 | 状态 | 原因 |
|---|---|---|
| 客户端单测 `make client-test` | ❌ 不进 CI | 若干套断言 `assets/resources/` 下的**真实素材**（图集 / 帧序列 / 怪物帧 `.meta`）；素材体积大、有意不入库，干净 clone 上这些断言不可能成立。**客户端单测是「本地专属」** |
| 客户端类型检查 | ✅ 进 CI | 类型声明 vendoring 进 `client/types/engine/`（相对路径 + 真实 `cc.d.ts`），CI 无需 Cocos 编辑器 |

### 分片为什么不写死清单

`make server-e2e-shard` 的**套件清单派生自 `server/package.json`**（所有 `test:e2e*` 脚本），
按实测耗时**贪心装箱**（重的先放、丢给当前最轻的一片）。

> 📌 以前 Makefile 里手写清单，漏了 3 套（`admin-mail` / `mail-expiry` / `ui-effect`），
> **谁都没发现**。现在新增 e2e 脚本自动进 CI，不需要改 workflow。

### 跑法

```bash
make server-build            # 先编译（e2e 跑 dist/）
make server-e2e              # 只跑主套
make server-e2e-bag          # 单跑一套（每个专项都有自己的目标）
make e2e-all                 # 全部（清单派生自 package.json）
make server-e2e-shard I=0 N=4  # 只跑第 0 片（共 4 片）—— 与 CI 一致
make server-verify           # 一条命令全验：编译 + 全部 e2e + 生成物审计
```

### 三个本地跑 e2e 的坑

| 坑 | 表现 | 解法 |
|---|---|---|
| 忘了 `make server-build` | 改了 `src` 但 e2e 还是旧行为 | e2e 跑 `dist/`，**改源码先编译** |
| 期望值硬编码数值 | 运营改了数 → 本机绿、CI 红（或反之） | 期望值从快照算，不写死 |
| `checkEqual` 是 `===` | `1` 与 `'1'` 判不等 | 断言前显式转类型 |

还有两条纪律（不是坑，是设计）：

- **`e2e-quest` 成功时静默**，判绿只能看 **exit code**，不要 grep 输出。
- **本机绿 ≠ CI 绿**：耦合断言 + 冷却周期在慢机器上会被超时盖过。

## 十、15 项跨端审计

审计不是单测：它们**静态扫描**代码 / 配置 / 部署文件，抓的是「两边接不上」「同一件事有两份」这类
人眼很难持续守住的约定。`make audit` 会遍历 `tools/audit-*.cjs`，逐个跑、汇总 PASS/FAIL。

| 脚本 | 守什么（破坏了会怎样） |
|---|---|
| `audit-api-generated` | 客户端 / 管理端的接口文件必须由 swagger 生成。手改一次生成物**下次重新生成就悄悄回滚**；加了接口忘了重新生成 → 两端停在旧契约 |
| `audit-api-hardcode` | 接口地址不许写进代码、请求只能从唯一那层发出。**地址与请求实现各有唯一来源** |
| `audit-config-leak` | `ui/` / `skills/` / `entities/` 只做「怎么跑」，不写「可调的数」——位置、尺寸、颜色、资源路径、时长、概率、魔法数字、中文文案都该沉到 `configs/` |
| `audit-ui-click-through` | 全屏模态是否**两条路**都拦住点击穿透（Cocos 的 touch 通道与 pointer 通道各走一套派发） |
| `audit-deploy` | Docker / compose / nginx 跨文件接线：**nginx 反代的上游主机名 = compose 服务名**、端口、卷、反代前缀、密钥隔离。改一边忘了另一边不会报错，只会在运行时 502 |
| `audit-shared-data` | 快照完整（**表齐 / 每张非空 / 行数自洽**）+ 枚举与客户端逐值一致 + **业务代码里没有第二份枚举** + 跨端常量对齐 |
| `audit-snapshot-contract` | 客户端「要什么」与服务端「发什么」是同一张清单。**#604 之前每段都是可选的，缺段静默跳过**，表现是「管理端改了游戏里没变，日志一个字都没有」 |
| `audit-equip-align-catalog` | 管理端工作台的对齐清单与客户端 configs **逐字节一致**，且没有展开变体 / 缺方向 / 缩成点 |
| `audit-role-authority` | 服务端独占字段客户端不许本地改（#548）。见 [04-角色与存档权威](./04-角色与存档权威.md) |
| `audit-world-authority` | 怪物的生成与掉落**只认服务端**（#581） |
| `audit-server-boundaries` | 跨模块 import 只能走白名单边，仓储只由 `DatabaseModule` 装配（#36） |
| `audit-map-origin` | 世界坐标 = 地图左上角为原点，TMX 只差一次 y 取反（#566）。错了不报错，只表现为「NPC 全体偏半张图」「怪物刷到地图外」 |
| `audit-resource-refs` | 资源引用是否都指向真实存在的路径（目录口径见 `client/RESOURCES.md`） |
| `audit-admin-ui` | 管理端页面的一致性：页头各写一份 `<div><h1/><p/></div>`、字号从 `text-lg` 漂到 `text-xl` 这类复制粘贴漂移 |
| `audit-iterator-spread` | Babel loose 模式下 `[...map.values()]` 会静默出错，必须用 `Array.from()`（见 [11-客户端](./11-客户端.md) 的已知坑表） |

单跑某一项：`make audit-deploy` / `make audit-shared-data` / `make audit-equip-align-catalog` 等。

> 为什么这些值得单独做成脚本：它们的**共同特征是「错了不崩」**。
> 缺一段快照、坐标少取反一次、反代上游改个名字 —— 全都表现为「看起来正常，但数据是错的」，
> 靠人眼在每次 PR 里复查是不现实的。

## 十一、常用命令快查

| `make env` | 生成 `server/.env`（已存在则跳过） |

| `make code-prune` / `code-dup` | 死代码扫描 / 重复代码扫描（输出需人工复核） |

### 数据与配置

| 命令 | 干什么 |
|---|---|
| `make db-backup` | `VACUUM INTO` 备份（服务运行中也能备；默认留 7 份） |
| `make db-restore FILE=…` | 整库恢复（加 `FORCE=1` 跳过在跑检查） |

### 服务器

| 命令 | 干什么 |
|---|---|
| `docker compose ps` | **应有五个**：server / server-realtime / admin / game / website |
| `docker compose logs -f server` | 存档进程日志 |
| `docker compose logs -f server-realtime` | 实时进程日志（WS / 世界 / 结算都在这） |
| `docker compose restart server` | 只重启存档进程（实时连接不受影响） |
| `docker compose restart server-realtime` | 只重启实时进程（世界状态会全量落盘后退出，重启恢复） |
| `docker compose down` | 收容器，**卷保留** |
| `docker compose down -v` | 收并删卷 —— **会丢库**，别乱用 |

### 客户端产物

## 十二、排障

| 症状 | 第一嫌疑 | 查法 |
|---|---|---|
| `docker info` 报权限错 | `ubuntu` 不在 docker 组 | `sudo usermod -aG docker ubuntu`，**重新登录**才生效 |
| 觉得「Docker 没启动」 | `docker info` 受 socket 权限影响 | 看 `systemctl status docker` |
| 管理端 502 | 反代上游 `server:3100` 是 compose 内网域名 | `docker compose logs server` 看是否真起来了 |
| 能登录但实时通道连不上 | `/api/realtime*` 没反代到 realtime 或漏了 WS upgrade 头 | `docker compose logs server-realtime`；`make audit-deploy` |
| 页面能开但接口 404 | 反代前缀 `/api/` 与服务端 `API_PREFIX` 不一致 | 比对两者；`make audit-deploy` |
| **登录限流把所有人锁死** | `TRUST_PROXY` 不是 `true` | 来源 IP 全是 nginx 容器的 → 全部玩家被当成一个人 |
| IP 直访拿 404 | 管理端 server 块没标 `default_server` | 看 `admin/nginx.conf.template` |
| 上传 40M 归档被中断 | `scp` 超过前台命令时限，**不是网络故障** | 放后台跑 |
| `pkill -f "git clone"` 把自己也杀了 | 模式匹配到自身命令行 | 写成 `pkill -f "git clon[e]"` |
| 管理端注册不了 | 配了 `ADMIN_REGISTER_CODE` 就必须带相同邀请码 | 留空**不等于**开放注册，需 `ADMIN_REGISTER_OPEN=true` |
| 改配置没生效 | 走了快照（进程内只拉一次）或实时进程还没重装 | 见第七节与 [12-管理端](./12-管理端.md) 第九节 |
| 自动备份「在跑」但找不到文件 | `BACKUP_DIR` 写到了没挂载的路径 | 容器一重建全丢；确认落在 `/app/data/backups/` |
| 回滚后服务起不来 | 新版本改过库结构 | 回滚前先备份（第六节）；结构变更就得连库一起回 |
| 邮件永远发不出去 / 永远成功 | `MAIL_TRANSPORT` 还是 `fake` / `fail` | 启动自检会喊；改回 `smtp` |
| 客户端素材 404 但服务器上有文件 | `--resources` 没跑，或 `EQUIPMENT_APPEARANCE_RES_DIR` 指向别处 | `/game-resources/image-manifest.json` 应能 200 |
| CI 没跑 | PR 只改了 `.md` / `.workbuddy/` / `design/` / `website/` | `paths-ignore`，设计如此 |
