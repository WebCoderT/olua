| 项 | 实测 |
|---|---|
| 格子 | 背包 7 行 × 11 列 = **77 格**（行优先） |
| 物品类型 | 6 类：装备 / 药品 / 材料 / 货币 / 卷轴 / 时装（`items` 表 + 各专表） |

## 一、四个结构性问题

### 1.1 只有一个容器，交易一上线就不够

77 格要装：装备本体 + 强化材料 + 药品 + 卷轴 + 时装 + 任务物品。现在**没有仓库**，
所以玩家唯一的腾挪方式是「回收」。交易上线后，玩家要「攒着卖」，77 格会在两天内满。

### 1.2 整理是客户端行为，不是权威

一键整理（`cocos-bag-tidy` 技能）在客户端算出新布局再上报。问题有两个：

- **并发**：双端同时整理，后到的会覆盖先到的，可能出现两件物品落同一格；
- **不可复现**：整理规则只在客户端，改版本后同样的背包排版不同，排查「东西去哪了」时对不上。

### 1.3 丢弃没有（且不能简单加）

玩家想把垃圾扔出去，现在只能回收（要跑到 NPC 或点回收按钮）。丢弃不能直接「从背包删掉」——
那就是凭空销毁物品，既不可查也给脚本刷包留了后门。正确做法是**复用掉落的世界实体模型**
（[18 篇](./18-掉落系统重构设计.md)）：丢到地上 → 变成一条 `world_drops` → 谁都能捡 → 180 秒消失。

**暂放**（18 篇已定），但本篇要给结构留位（见 2.4）。

### 1.4 堆叠上限是隐含的

`count` 是整数，没有上限。理论上可以一格放 999999 个药。显示与排序都会出问题，
且「一格一个上限」是交易与摆摊的最小单位前提。

## 二、目标形态

### 2.1 两段容器：背包 77 + 仓库 120

| 容器 | 容量 | 位置 | 能否在战斗中使用 |
|---|---|---|---|
| 背包 | 77（不动） | `roles.data.bag` | 能 |
| 仓库 | **120**（6×20） | `roles.data.warehouse` | **不能**（必须开仓库界面，且只能在安全区/NPC 处开） |

**为什么仓库也放 `roles.data`**：存档权威只有一个（[04 篇](./04-角色与存档权威.md)），
把仓库拆到独立表就有两份真相，`save` 的十三步与乐观锁都要改两遍。
代价是 `roles.data` 变大（120 格 ≈ 每格 60 字节 ≈ 7KB），可接受。

**为什么是 120**：已定「背包不动 + 仓库 120」。120 = 6×20 便于客户端用同一套网格组件；
按每件装备一行算，120 格约等于「两套完整装备 + 材料」。

### 2.2 容器操作统一到一个入口

```
容器操作 = move(from: ContainerRef, to: ContainerRef, ...)
ContainerRef = { kind: "bag" | "warehouse" | "equip" | "mail", index }
```

现在的五个动作各自实现一遍（`move/merge/split/use/recycle`），加仓库会变成十遍。
改成**一个 `transfer()` + 四个薄封装**：

| 动作 | 本质 |
|---|---|
| 移动 | `transfer(bag[i] → bag[j])` |
| 存仓 / 取仓 | `transfer(bag[i] ↔ warehouse[j])` |
| 并堆 | `transfer` 时目标格 id 相同则累加（受 `max_stack` 限制） |
| 拆分 | `transfer` 时带 `count < 原数量` |
| 穿戴 | `transfer(bag[i] → equip[slot])`（装备走 24 篇的实例校验） |

**这是本篇唯一的结构改动，也是最大的一处**：`reconcileBagCells` 的守恒断言要从「背包内」
扩展成「所有容器总账」。

### 2.3 整理改为服务端权威

```
POST /roles/:id/bag/tidy   { target: "bag" | "warehouse" }
```

服务端排序规则（写死，不接受配置，否则两端不一致）：

1. 类型序：装备 → 药品 → 材料 → 卷轴 → 时装 → 货币
2. 同类型内按 `id` 字典序
3. 同 id 按 `bound` 分堆（已绑定在后）
4. 装备按 `enhanceLevel` 降序（+15 在最前）
5. 从左上角按行优先填充，**不留空洞**

返回新的两个容器快照，客户端整体替换（不返回增量 diff —— 整理本来就是个低频全局操作）。

### 2.4 丢弃：留结构，暂不接功能

| 本期做 | 暂时放置 |
|---|---|
| `transfer` 支持 `to: { kind: "ground" }` 的**参数位**（抛 `not_implemented`） | 真正落地的逻辑（重开条件：[18 篇](./18-掉落系统重构设计.md) 世界实体稳定后） |
| 背包格子的 `locked` 标记（交易/摆摊占用时不可移动） | 丢弃后的无归属拾取规则（与上一行同批） |

> 为什么留参数位：将来做丢弃时，只要实现 `ground` 分支 + 调 18 篇的 `spawn()`，
> 不用再改一遍 `transfer` 的所有调用点。

### 2.5 堆叠上限

`items.max_stack`（新列），默认：药品 999、材料 999、卷轴 99、装备 **1**、时装 1。

- 超过上限的转移要**自动拆成多格**（不能拒，否则「捡 1000 个药」会因为一格放不下而失败）；
- `max_stack = 1` 的物品（装备/时装）**禁止并堆**，`bagGroupKeyOf` 按 `instId` 区分（见 24 篇）。

### 2.6 守恒断言（扩展后）

```
Σ(bag 件数) + Σ(warehouse 件数) + Σ(equip 件数) + Σ(邮件未领取附件件数)
  = 上次结算的总数 + 本次获得 − 本次消耗
```

任何一次容器操作**前后总账必须相等**（整理、移动、存取的内部转移不改变总数）。
这一条比现在的「背包内守恒」严格得多，也是交易能安全落地的前提。

### 2.7 物品品质（本轮纳入）

| 项 | 规则 |
|---|---|
| 字段 | `items.quality` 0~4：普通 / 精良 / 稀有 / 史诗 / 传说（默认 0） |
| 归属 | **定义级**（不是实例级）—— 同一件装备的品质固定，不掉落随机档 |
| 展示 | 名称颜色 + 边框；颜色表放 `configs/item-quality.ts`，**由快照下发**（不写死在客户端） |
| 回收价 | `sellPriceOf` 乘 `qualityFactor`（1 / 1.2 / 1.5 / 2 / 3） |
| 掉落公告 | 18 篇的「稀有掉落全服公告」判定从「`tier='boss'` + 非货币」升级成 **`quality ≥ 2` 或 boss 掉落**（更准） |
| 与变体 | 正交：品质是「这一类物品有多珍贵」，变体是「同一件的强度档」 |

> 为什么品质是定义级：如果做成实例级（同样一把剑有的是紫色有的是白色），
> 掉落就要为每件物品 roll 一次品质，等于给 10275 条变体再乘一层随机 —— 数值会彻底不可控。

## 三、数据模型

**不新增容器表**，只改 `roles.data` 的形状：

```jsonc
{
  "bag": [ {"row":0,"col":0,"id":"sword_001","count":1,"bound":0,"instId":"i42_7"}, … ],   // 77 格
  "warehouse": [ {"row":0,"col":0,"id":"drug_hp_1","count":200}, … ],                      // 120 格，新
  "equipment": { "weapon": {"id":"sword_001","instId":"i42_7","enhanceLevel":7}, … }
}
```

改两张配置表：

| 表 | 加什么 | 默认 |
|---|---|---|
| `items` | `max_stack` | 药品/材料 999、卷轴 99、装备/时装 1 |
| `items` | `container` | `bag` / `warehouse` / `both`（哪些能进仓库） |

> **`container` 列的价值**：货币与任务物品通常不该进仓库（会绕开「货币统一在钱包」的口径）。
> 有这个列就能按类型一刀切，而不是在代码里写 if。

## 四、接口

| 接口 | 方法 | 说明 |
|---|---|---|
| `/roles/:id/container/transfer` | POST | `{from:{kind,index}, to:{kind,index}, count?}` 统一入口 |
| `/roles/:id/bag/tidy` | POST | 服务端整理，返回新容器 |
| `/roles/:id/warehouse/open` | POST | 校验位置（安全区/NPC 旁）后返回仓库快照 |

**为什么 `transfer` 走 HTTP 而不走实时帧**：容器是存档的一部分，必须走 `save` 的乐观锁。
走实时帧会绕开 revision，双端并发就会丢物品。

## 六、边界情况

| # | 情形 | 期望 |
|---|---|---|
| 1 | 老档没有 `warehouse` 字段 | 读成 120 个空位（不写库，第一次操作才落盘） |
| 2 | 仓库操作时不在安全区/NPC 旁 | 400（`warehouse_not_here`）—— 服务端校验位置 |
| 3 | 战斗中打开仓库 | 拒（同上） |
| 4 | 存仓时目标格已有同 id 且未满堆 | 累加，不超过 `max_stack` |
| 5 | 存仓时目标格已有同 id 但 `bound` 不同 | **不并堆**（分成两格） |
| 6 | 存仓时仓库满 | 400（`warehouse_full`），**背包不动** |
| 7 | 转移 `count` 大于源格数量 | 400（`bad_count`），不采用「有多少转多少」的宽容处理 |
| 8 | 转移 `count` 为 0 或负数 | 400 |
| 9 | 双端同时整理背包 | 乐观锁 20006 拦第二次；客户端提示「背包已在别处变更」 |
| 10 | 转移时源格为空 | 400（`empty_slot`） |
| 11 | 把一个 999 个的药转进只剩 100 空间的格子 | **拆成多格**（100 落地 + 899 回原格或找下一格），总数不变 |
| 12 | 拆堆拆出来的格子放不下 | 400，源格不动 |
| 13 | 装备（`max_stack=1`）与同名装备并堆 | 禁止（`instId` 不同） |
| 14 | 货币进仓库 | 拒（`container='bag'`），货币必须在钱包 |
| 15 | 任务物品被存进仓库导致任务无法交付 | 服务端交付时**两个容器都查**（不要求玩家取出来） |
| 16 | 邮件附件与背包同时领取同一件 | 邮件领取走同一把乐观锁，不会双发 |
| 17 | 整理时空格中间有 `locked` 格 | 被占用的格视为不可移动，参与排序但保持原位 |
| 18 | 整理后 `instId` 丢失 | **绝不允许** —— 这是 24 篇的核心断言（实例集合不变） |
| 19 | 仓库里放装备实例，被回收 | 回收要能从仓库取（`container` 校验），或直接拒「请先取出」 |
| 20 | 存档体积 | 120 格全满 ≈ +7KB；`save` 的 payload 变大，需实测单次保存耗时 |
| 21 | 丢弃参数位被调 | 返回 `not_implemented`（明确不是 500） |
| 22 | 客户端旧版本（不认识 `warehouse`） | 服务端照样下发，旧客户端忽略该字段；但**旧客户端不能做容器操作**（接口版本校验） |

## 八、验收

| 用例 | 断言 |
|---|---|
| `e2e-container-total` | 任意 50 次随机转移后，四容器总件数不变 |
| `e2e-container-stack` | 999 个药转进 100 空格 → 100 + 899 分两处，总数不变 |
| `e2e-container-bound` | 绑定与未绑定同名物品不并堆 |
| `e2e-warehouse-guard` | 非安全区 / 战斗中开仓库 → 拒 |
| `e2e-tidy-inst` | 整理前后 `instId` 集合完全相等 |
| `e2e-tidy-order` | 固定背包 → 整理结果与预期排序逐格相等 |
| `e2e-container-concurrent` | 双端同时整理 → 一个成功一个 20006 |

手工验收：仓库 120 格布局在手机上不挤；整理后装备按强化等级从前到后；
存取时若有物品放不下，提示要指出「哪一格放不下」而不是笼统「操作失败」。
