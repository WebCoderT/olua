# 04 · 角色与存档权威

> 一份 JSON 里混着三种字段：玩家能改的、服务端说了算的、服务端算出来的。
> 这一篇讲清它们怎么在同一份文档里共存，以及一次 `PUT /roles/:id` 落地前到底发生了什么。

## 一、一句话概括

角色的全部状态存在**一行数据库记录**里，其中 `data` 是一份不透明 JSON。

```sql
-- roles 表（索引列 + 一份文档）
id | account_id | name | occupation | sex | level | kills | data | revision | created_at | updated_at
                                                            ↑
                                              这一坨JSON里装着 back/装备/货币/血蓝/引导…
```

`data` 里**没有** schema 校验（只校验结构）。所以真正的问题不是「字段对不对」，而是
**「同一个字段名，谁有资格写」** —— 那件事全部定义在 `server/src/modules/roles/role-authority.ts`，
其余地方（`save`、`revive`、`applyMonsterHit`、管理端 PATCH）都只是它的消费者。

**改权威边界的正确做法**：只改 `role-authority.ts` 的字段清单，别在 `save` 里加 `if`。
那边加了字段而这边没跟上，就是「改了没生效」的经典现场。

## 二、九类字段：谁说了算

表里的「权威」列不是设计意图，是**现在代码的行为**。

| # | 类别 | 字段 | 权威 | 为什么必须这样 |
|---|---|---|---|---|
| 1 | 账本 | `bindGold`（唯一货币，#843/#844 收敛后 `gold` / `silver` 已删） | **服务端** | 商城、回收、成长线、任务、成就、邮件、后台各有服务端写点；客户端**没有任何本地改写的代码**（唯一入口是 `StorageManager.applyServerRoleUpdate`，照搬 `roleUpdate` 帧） |
| 2 | 成长阶位 | `title` / `soulOfWar` / `rank` | **服务端** | 只有 `RolesService.upgradeGrowth` 能推进（扣费 + 成长链校验都在里面）；客户端 `upgradeGrowthOnServer` 只把返回值抄回来 |
| 3 | 进度 | `level` / `exp` | **服务端** | 经验只由服务端结算（击杀 / 队友分账 / 任务 / 成就 / 邮件 / 后台）。客户端**没有**本地加经验路径（#550 删掉了泡点组件与其兜底） |
| 4 | 背包与穿戴 | `bag` / `equipments` / `skills` | **服务端** | 穿戴 / 卸下 / 丢弃 / 整理 / 搬运五个动作全走 `POST /roles/:id/bag-op`（#556）；`equipments` 还是属性重算的输入 —— 不收权等于「塞一件没拥有的顶级装备」直接换战力 |
| 5 | 派生值 | `combat` / `maxHp` / `hpRecover` / `maxMp` / 六项攻防 | **服务端重算** | 每次写档由 `applyAuthoritativeAttributes` 现算覆盖（见第六节），**不走回填** |
| 6 | 血蓝 | `hp` / `mp` / `hpRecoverAccumulator` / `mpRecoverAccumulator` / `vitalsSettledAt` | **服务端结算** | 受击、用药、升级补满、复活各有服务端写点；自然回复由 `settleVitalsAuthority` 在写档时按经过时间补齐（见第七节）。客户端那份只是**演出预测** |
| 7 | 时装 | `fashionCloth` / `fashionsOwned` | **服务端** | 购买（扣费 + 渠道校验）与穿脱（拥有才给穿）各有一个接口；清单是**独占字段** |
| 8 | 体验状态 | `shortcutKeys` / `guide` / `soulShow` | 客户端书写、服务端存证 | 纯本地体验（换设备要跟着走，篡改无收益）：save 照收，`roleUpdate` 帧原样带回 |
| 9 | 客户端全权 | `onMap` / `avatar` / `speedRate` / `relationShip` | **客户端** | 走图、头像、速度倍率、关系展示都在本地且不改数值。`onMap` 另有实时侧的**互见最小仲裁**（非有限拒绝 / 瞬移帧屏蔽 / 持续异常跟随） |

代码里的两份清单：

```ts
// 需要「回填」的（库里有值就覆盖上报值）
SERVER_OWNED_FIELDS = 账本 + 阶位 + 进度 + 背包穿戴 + 时装穿着
// 需要「库里有就覆盖、库里没有就删除」的（没有老档放行）
SERVER_EXCLUSIVE_FIELDS = ["fashionsOwned", "mapAt"]
```

### `mapAt` 与 `onMap` 为什么是两个字段

| | `onMap` | `mapAt` |
|---|---|---|
| 谁写 | 客户端（走图时自报） | 服务端（**被接受的 worldJoin** + 管理端摆位） |
| 用途 | 走图、统计、复活点 | **进图门槛**拿它当「他现在在哪」 |
| 客户端能否改 | 能（无收益） | 不能 —— 连知道都不需要 |

混成一个字段就只能在「相信客户端」和「不信客户端」里二选一。分开之后：
走图照旧自由，但「改包把位置改成高级图再登录」绕不过门槛（#606）。

## 三、两条纪律（比字段清单更容易踩）

### 纪律一：回填，而不是拒收

客户端推上来的账本值和库里不一致 → **用库里的值覆盖，继续落库**，并打一条 warn。

理由是「拒收会把『客户端少收了一帧』这种无害情况变成玩不了」。回填之后下一次
`roleUpdate` 帧自动纠正。真正要拦的是「写进去」，不是「发过来」。

```ts
// 症状日志（可检索）
账号存档里改动了服务端独占字段，已按库中值为准：bindGold（库里 0，上报 999999）
```

### 纪律二：库里没有这个字段就放行

老存档（服务端接管之前的本地档）第一次上传时，文档里没有 `bindGold` 这类键。
这时**客户端那份是唯一来源** —— 删掉等于把玩家的钱清零。

```ts
for (const field of SERVER_OWNED_FIELDS) {
  if (!hasOwn(stored, field)) continue;   // ← 这一行就是「老档放行」
  ...
}
```

所以只在「服务端写过这个字段」之后才执行回填，其余情况原样放行。
上线时就不存在会写它的旧客户端 → 那类字段进 `SERVER_EXCLUSIVE_FIELDS`，**没有放行例外**
（否则改包第一次 PUT 就能白得全部时装）。

### `bag` 的特例：内容取库、尺寸取客户端

背包网格尺寸由**客户端配置**管（`bagRow × bagCol`），服务端不认识它：

```ts
// role-authority.reconcileBag → role-inventory.adoptBagShape
// 库里的内容 → 铺进客户端上报的尺寸
// 新尺寸装不下某一格 → 整份退回原网格（不静默丢东西，也不替玩家挪位置）
```

整份照抄库里的：第一次改格子数之后老角色背包永远不长个。
整份照抄客户端的：等于把背包还给客户端。两边都解析不出 → 退回库里原值（背包动不了总比玩不了强）。

## 四、`PUT /roles/:id` 的完整流水线（顺序不能改）

`RolesService.save`，每一步都有「为什么必须在这里」：

| # | 步骤 | 为什么必须在这个位置 |
|---|---|---|
| 1 | `mustAccount` + `mustOwnRole` | 归属校验；别人的角色 → 403（不是 404，别诱导下一个人去补权限） |
| 2 | **被踢判定** `account.online_role_id !== roleId` → 409 `20007` | 必须**早于**乐观锁：被踢的玩家需要「回选角」，不是反复重试同一个冲突。不拦的话客户端本地档会一直写回来，踢了等于没踢 |
| 3 | **乐观锁** `dto.revision` 对不上 → 409 `20006` | 不带 revision = 旧行为（最后写入者胜）；带了才校验 |
| 4 | `parseRoleData(input, { name, occupation, sex })` 结构规整 | 索引字段（id / 名称 / 职业 / 性别 / 等级）合法、体量上限、引导三项、剔掉 `revision`。**身份三字段的入参是库里的值**（#879）：先把客户端上报的 `name` / `occupation` / `sex` 盖掉再校验 —— 这样「改包转职 / 改名」在解析这一步就不存在，也不会因为报了个非法职业被 20003 卡死（忽略 ≠ 拒收） |
| 5 | ~~同账号重名检查~~ **已删除（#879）** | 存档不再能改名，这条判据的前提消失了；重名只剩「建号」一个入口，那是 `create` 的事（20005），库里有 `UNIQUE(account_id, name)` 兜底 |
| 6 | `enforceAuthority(stored, data)` | 服务端独占字段回填（第三节）。`stored` 额外把 `level: existing.level` 压进去 —— 索引列才是等级真相 |
| 7 | **从回填后的文档重取 `level`** | 否则 `roles.level`（客户端报的）与 `data.level`（库里的）各说一套，列表与详情对不上。#899 起服务端自己的写点（`settleLevelUp` / 卷轴）**两个一起写**，这里只是最后一道兜底 |
| 8 | `sanitizeEquipments` 清脏槽 | 部位不符 / 同一件穿在多个槽 → 必须**在重算之前**清掉。属性重算遍历 `equipments` 的**所有值**，不看键：同一件算三遍就是三倍战力。#816 起槽位是 `{ id, bound?, from? }` 对象（挪槽位时元数据跟着走），取 id 用 `wornIdOf` |
| 9 | `warnIfAttributesMismatch` | 纯观测：只打一条 warn，不拦流程（一致时什么都不打） |
| 10 | `applyAuthoritativeAttributes` | 服务端公式重算，**无条件覆盖**落库值 |
| 11 | `settleVitalsAuthority` | 必须在重算**之后** —— 回复上限要用刚算出的 `maxHp` / `maxMp` |
| 12 | `clampVitals` | 夹回 `[0, 上限]`，纯防御（上一步已保证区间内） |
| 13 | `roles.replace(row)` + `revision: existing.revision + 1` | 响应里的 revision 必须是**落库后**的值，否则客户端拿它做基线会立刻撞乐观锁（自锁死循环） |

```ts
// 一句话版本：位置听客户端的，数值听服务端的
const stored = decodeStoredRoleData(existing.data);
this.enforceAuthority({ ...stored, level: existing.level }, data);
const level = normalizeLevel(data.level);
```

**第 9、10 两条是两条独立的线**：warn 不拦流程，权威不靠 warn。
把「记日志」当成「校验」是这里最容易犯的错。

## 五、派生值重算：属性唯一的算法入口

```ts
// roles.service.ts
private applyAuthoritativeAttributes(level: number, data: Record<string, unknown>): void {
  const summary = summarizeRoleAttributes(roleAttributeSourceOf(level, data));
  if (!summary) { this.logger.warn(...); return; }   // 等级不在曲线内 → 保留原值，不抹成 0
  data.maxHp = summary.maxHp;  data.hpRecover = summary.hpRecover;  data.maxMp = summary.maxMp;
  // 六项攻防是区间（数组），落库要 Array.from
  data.physicalAttack = Array.from(summary.physicalAttack);  /* …五组同理… */
  data.combat = summary.combat;
}
```

- **唯一算法**是 `summarizeRoleAttributes`（等级曲线 + 装备变体 + 称号 + 战魂 + 军衔），
  细节见 [05](./05-装备链路.md) 与 [09](./09-成长与养成.md)。这里只负责「写完盖回去」。
- **算不出就跳过并留痕**（#554）：曲线已外推（#786），「算不出」只剩等级 < 1 的脏存档。
  但脏数据照样会让这里静默 —— 属性从此不再重算，界面上看不出异常，所以必须 warn。
- **`Array.from` 不是风格问题**：babel loose 模式下 `[...map.values()]` 会炸。

## 六、血蓝收权：懒结算，没有定时器

客户端存档里的 `hp` / `mp` 是本地按帧回血让血条平滑的**演出预测**，一律丢弃。
真值由 `settleVitalsAuthority(stored, incoming, now, mpRecoverPerSecond)` 现算：

```
elapsed = now − stored.vitalsSettledAt              （游标不存在 → 0，不补发）
hp = min(maxHp, stored.hp + floor(累加器 + hpRecover × elapsed / 1000))
累加器 = 小数部分（丢掉整数部分，保留下一个 tick 的余数）
incoming.vitalsSettledAt = now
```

四个必须记住的口径：

| 口径 | 原因 |
|---|---|
| **游标不存在 → 不补发**，只落当前时间 | 否则部署后老号第一次写档白送一大段「离线回血」 |
| **死亡（基线 hp ≤ 0）不回复血量**，魔法照常 | 满血复活必须走 `POST /roles/:id/revive`；死亡流程不受蓝量影响（与客户端 `MpHelper` 同口径） |
| **上限算不出 → 跳过回复只落游标** | 别把人改没 |
| **`mpRecoverPerSecond` 为负按 0 处理** | 倒扣蓝比不回复更糟（配置拍错的情形） |

上限夹取保证「离开三天」也只补到满，不会溢出 —— 这是「不用定时器」的前提。

## 七、`revision`：乐观锁与客户端自愈

### 服务端侧

`roles.revision` 是一个**只增计数列**。带上它才校验，对不上就 409 `20006`。

典型场景：玩家在游戏里、管理员在后台改了这个角色 → 客户端那份是「改之前」的基线，
直接放行会把后台改动整体覆盖掉（谁最后写谁赢，后台改动静默丢失）。

### 客户端侧：四条出口

`client/assets/ui/utils/net/RoleSync.ts` —— 防抖推送 + 四条自愈路径：

```ts
static schedule(role)   // 只记最后一份，等 roleSyncDelay（1.5s）后推一次
static flush()          // 切地图 / 退出前必须调，否则防抖窗口里的改动随场景一起没掉
```

| 服务端返回 | 客户端出口 | 做什么 | **不能做什么** |
|---|---|---|---|
| 成功 | `onSaved(roleId, revision)` | 记住新 revision 当下次基线 | 不能忘 —— 下次推送会用旧值撞自己 |
| `20006` 冲突 | `onConflict(fresh)` | 拉一次 `RoleApi.detail`，以服务端为基线，**本轮改动丢弃** | 不能自动重推（会形成循环） |
| `20002` 角色不存在 | `onMissing(roleId)` | 退出到选角 | 不能继续玩一个不存在的角色 |
| `20007` 被踢下线 | `onKicked(roleId)` | **只清本地在线标记**（`clearOnlineRole`），回选角重选 | **绝不能删本地角色** —— 角色还在，删了就是把玩家练的号清了 |

其它失败：本地已落盘，不重排不阻塞，下一次改动重推；提示只在**第一次**失败时给一条
（静默模式 + `notified` 标志），否则后端一挂，打怪期间每 1.5 秒弹一次。

### 哪些写档推进 revision，哪些不推

这条纪律决定了会不会「战斗中存档疯狂失败」：

| 写入 | 推进 | 理由 |
|---|---|---|
| `save` / `upgradeGrowth` / `mallPurchase` / `sellGoods` / `drugUse` / `moneyUse` / `levelScrollUse` / `bagOp` / `fashionBuy` / `fashionWear` / 击杀经验 | ✅ **+1** | 都是「进度型」写入，玩家会等结果 |
| `applyMonsterHit`（怪物普攻落账） | ❌ | 血量以实时帧为准。每次受击都 +1 会让战斗期间的防抖存档频繁撞乐观锁 |
| `revive` | ❌ | 同上（血量型） |
| `setMapAt` | ❌ | 位置不是进度。推进只会让刚好在切图时冲上来的存档撞乐观锁（人停在旧图） |
| `incrementKills` | ❌ | 客户端存档里没有这一列 |

不推进的写入走 `updateDataKeepRevision`，代价是「落库值」与「在途存档」有一个防抖窗口的竞态，
以服务端后续的 `hit` 帧为准自愈 —— 窗口内旧值回写只影响一拍，不累积。

## 八、建号：只收三样东西

`POST /roles` 的入参只有 **名称 / 职业 / 性别**（#597）—— **这是这三个字段唯一的写入口**（#879：
存档写不了它们，改名 / 转职要走将来的专门接口）。同一账号最多 6 个角色（#878，
`ROLE_MAX_PER_ACCOUNT`），超限 400 / 20018；重名 20005；表上有 `UNIQUE(account_id, name)`。
初始文档由服务端 `buildInitialRoleData` 构造：

| 项 | 值 | 说明 |
|---|---|---|
| `level` / `exp` | 1 / 0 | 等级钉 1，不读客户端 |
| `bindGold` | 0 | **不赠送任何物品**（此前客户端 `new Role()` 会塞一套新手装备与初始金币，整体废除）。要发东西走管理端 `PATCH /admin/roles/:id` |
| `equipments` | `{}` | 槽名字段是客户端枚举（`EQUIPMENT_TYPE`），服务端复制必然漂移 |
| `bag` | `[]` | 尺寸是客户端配置（`bagRow × bagCol`） |
| `skills` | 全部 1 级 | `skills` 表里 `owner = role` 的行（怪物技能不发给玩家）。全 0 会让新角色无法战斗 |
| `shortcutKeys` | `[]` | 按键码在客户端配置里 |
| `speedRate` | 11 项默认（普攻 4 倍，其余 1） | 与客户端 `role.defaultRoleSpeedRate` 同语义 |
| `guide` | `{ step: 0, done: false, skipped: false }` | 老号「没有 guide = 已完成」不受影响 |

落库前：`applyAuthoritativeAttributes(1, data)` → `hp = maxHp` / `mp = maxMp` → 累加器清零
→ `vitalsSettledAt = now`（回复结算从这里起算）→ `revision = 1`。
第一个角色自动设为在线（`setOnlineRole` 顺带写心跳，否则会被在线清算判成「没人」）。

**空壳字段的补齐责任在客户端**：`StorageManager.ensureRoleDefaults` 读档时按**当前配置**补齐。
这就是「服务端不复制客户端配置」的落点 —— 服务端发空对象，客户端永远认识自己那套枚举。

## 九、读路径宽容、编辑路径严格

两个几乎同名的函数，语义**必须**不同：

| 函数 | 用途 | 解析失败时 |
|---|---|---|
| `decodeStoredRoleData(raw)` | 对外读取（详情、列表、实时取行） | 返回 `{}` —— 一行坏数据不能打断整个列表 |
| `parseStoredRoleData(raw)` | **编辑路径**（管理端 PATCH、徽章式改字段） | `throw ROLE_DATA_INVALID` |

编辑路径用空对象兜底 = 把角色的背包装备全清了。所以它有独立的函数，而不是加个参数。

## 十、客户端读档补齐链

`findOnlineRole()` → `ensureRoleDefaults(role)`，逐项处理「老存档缺什么」：

| 字段 | 补齐规则 |
|---|---|
| `mp` / `maxMp` / `mpRecoverAccumulator` | `MpHelper.ensureDefaults` |
| `hpRecover` / `hpRecoverAccumulator` | `HpHelper.ensureDefaults` |
| `equipments` | 按 `EQUIPMENT_TYPE` 枚举补缺失槽；槽位值**规整成 `{ id, bound?, from? }`**（#816）：裸 id / 完整快照 / 对象三种老形状都由 `wornItemOf` 收敛，**元数据原样带回**（不再折叠成裸 id，那会一进客户端就把绑定洗白）；装备数据仍经配置表实时解析 |
| `bag` | 旧快照（带 `type` 的完整物品对象）→ `{ id, count }`；再 `normalizeBagGrid(bag, bagRow, bagCol)` 对齐当前配置尺寸 |
| `shortcutKeys` | 按 `initialShortcutKeys` 对齐按键码：保留已绑定技能、补新增槽、**多出的槽自然丢弃**（曾有的第 6 格） |
| `soulOfWar` / `title` / `rank` | 缺 → 0 |
| `fashionCloth` | 非字符串 / 不在配置表 → `null`（历史遗留数字一律按没穿） |
| `fashionsOwned` | 缺 → `[]`（只过滤字符串 id，**不做存在性校验**：清单归服务端） |
| `guide` | 读不到 → 补成「已完成」，老号不该突然被弹一脸引导 |

**唯一落盘出口**是 `StorageManager.updateOnlineRole(role)`：写 localStorage + `RoleSync.schedule`。
打怪升级、拾取、买卖、换装、吃药全都走到这里 —— 所以同步必须防抖，且调用方不需要关心同步结果
（本地已落盘，游戏内读到的永远是这一份）。

`updateOnlineRole` 里有一行细节值得留意：

```ts
// 修订号只信「有的那一边」：内存里的 role 可能是旧存档解析出来的（没有 revision），
// 直接 Object.assign 会把已存下的基线抹掉，下一次推送就退回「无乐观锁」的旧行为
const revision = typeof role.revision === "number" ? role.revision : i.revision;
```

## 十一、`roleUpdate` 帧：所有数值的汇合点

实时进程轮询 `onlineRoleRow`，组装 `roleUpdate` 帧推给客户端；客户端
`applyServerRoleUpdate` **照搬不算**：

```
等级 / 经验 / 战力 / 三货币 / 血蓝 / maxHp / hpRecover / maxMp / 六项攻防
  + 称号 / 战魂 / 军衔（#551，后台改完不重进也生效）
  + shortcutKeys / guide / soulShow（体验态云同步）
  + fashionCloth / fashionsOwned（换外观）
  + revision
```

两条纪律：

- **迟到帧守卫（#732）**：帧由「行变了」触发，但 `bagOp` / 称号等 HTTP 应答可能先一步改了本地
  （revision 更大）；随后才到的旧帧**整帧丢弃**，否则战力与货币会被拉回旧值再弹回来（显示抖动）。
  revision 相同的帧照常应用（幂等快照）；任一侧没有 revision 不设防。
- **只刷显示、不触发存档**：帧的内容就是服务端现状，推回去是白推还多占一个防抖节拍。
  唯二的副作用是「货币真的变了才响音效」与「称号 / 战魂变了才重建动画」（重建就闪一下）。

## 十二、排障清单

| 症状 | 第一嫌疑 | 查法 |
|---|---|---|
| 数值改了玩家看不到 | `roleUpdate` 帧没带这个字段 | 看实时侧帧组装；直接查库确认落库值对不对 |
| 后台改完不生效 | 客户端那份存档把它盖回来了 | 搜 warn `已按库中值为准`；确认字段在 `SERVER_OWNED_FIELDS` 里 |
| 玩着玩着弹「已在别处被修改」 | 有写档在推进 revision 而你以为是血量型 | 对照第七节的表；看是不是新加的写点忘了用 `updateDataKeepRevision` |
| 玩家被踢了还在玩 | `save` 里没拦住 `online_role_id` 不一致 | 第 2 步必须在乐观锁之前 |
| 属性突然变成 0 | 等级不在曲线内 + 跳过重算时没人看 warn | 搜 `战斗属性未重算` |
| 背包物品「不见了」 | 尺寸变化导致 `adoptBagShape` 退回原网格 | 查 `bagRow × bagCol` 是否被调小 |
| 血蓝上限对但显示溢出 | `clampVitals` 被挪到了重算之前 | 它必须在上限算出来之后 |
| 管理端保存提示「数据已损坏」 | 走了 `parseStoredRoleData` | 这是设计：坏数据不能拿空对象覆盖 |
