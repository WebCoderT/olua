# 17 · 物品掉落流程（从击杀到消失的完整一生）

> **一句话**：掉落物是「服务端算一次、客户端演一份、两边各拿一半真相」的东西 ——
> **内容**由服务端抽（`rollDrops`），**实体**由客户端造（`DropManager` 的节点），
> **拾取**要拿服务端账本（`dropLedgers`）对号入座。
> 所以它**既不在存档里，也不在世界状态里** —— 这是理解「不捡会怎样」「刷新后去哪了」的前提。
>
> **分工**：[05 装备链路](./05-装备链路.md) 讲「一件装备从表到身上」（属性、变体、穿戴、外观、回收）；
> 本篇讲「一堆掉落物从地上到包里，以及到不了包里」—— 配置怎么配、怎么抽、怎么摆在地上、
> 怎么捡、不捡会怎样、刷新后去哪了。两篇都提到 `monster_drops` 和 `pickDrop`，但角度不同。

## 一、先分清三份「真相」

掉落这条链上同时存在三份数据，**它们不在同一个地方，也不同步**。搞混了就会问出「东西明明在地上为什么捡不起来」。

| 真相 | 存在哪 | 谁写 | 生命周期 | 丢了会怎样 |
|---|---|---|---|---|
| **配置真相** | 库表 `monster_drops` / `drop_tables` / `runtime_params` | 管理端 | 永久（随 `config-sync.sql` 出厂） | 抽不出东西 / 走兜底 |
| **内容真相** | 实时进程内存 `dropLedgers`（`Map<accountId, Map<castId, entry[]>>`） | 结算服务 `rememberDrops` | **会话级**：换图 / 断线 / 容量 256 / 进程重启 | 地上的东西**捡不起来**（`unknown_drop`） |
| **实体真相** | 客户端内存 `DropManager.dropMap`（`Map<Node, DropItem>`） | 客户端 `spawnResults` | **场景级**：换图 / 关客户端 | 看不见地上的东西（但账本可能还在） |

**存档里没有掉落物。** `roles.data.bag` 里只会有「已经捡进背包的格子」，从来不会有「地上那堆」。
**世界状态里也没有。** `world_monsters` 只记怪物，不记掉落。

> 这三份真相的错位，是所有掉落类 bug 的根源。第五节讲拾取时会看到：**实体在、账本不在 → 捡不起来**；
> **账本在、实体不在 → 捡得起来但没有地面反馈**（`applyPickedFrame` 里 `if (!node) return`）。

## 二、怎么配置

### 2.1 三处入口，各管一件事

掉落相关的配置**散在三处**，很多人只找到第一处就以为配完了（[16 篇第四节](./16-配置位置总表.md#四隐藏入口这些入口不在你以为的页面里) 记过这个坑）。

| 想配什么 | 去哪 | 改哪张表 / 哪个键 | 生效 |
|---|---|---|---|
| **某只怪掉什么** | 战斗配置 → 怪物配置 → 该行尾「**掉落**」按钮 | `monster_drops` | **立即**（击杀时现查库） |
| **一批怪共用一张表** | 战斗配置 → **掉落配置**（只有具名表） | `drop_tables` | **立即** |
| **这只怪掉的东西全绑定** | 同一个掉落弹窗 → 顶部「**掉落整体强制绑定**」 | `monster_drops.bind_drops` | **立即** |
| **这件装备一掉出来就绑定** | 装备配置 → 列表第 9 列「**掉落绑定**」/ 编辑弹窗 | `equipments.bind_on_drop` | **立即** |
| **全局按概率随机绑定** | 参数与引导 → **运行时参数** → 掉落手感与绑定 | `runtime_params.drop_params.bindChance` | **立即**（服务端结算侧现读） |
| **拾取半径 / 散落间距 / 满包提示间隔 / 应答超时** | 同上 → 运行时参数 → 掉落手感 | `runtime_params.drop_params` 其余四键 | **重进游戏**（走快照下发客户端） |
| **掉落光柱的大小 / 位置 / 时长 / 开关** | 表现配置 → **特效管理** → `light-1` ~ `light-6` | `ui_effects` | **重进游戏**（走快照 `uiEffects` 段） |
| **掉落物图标尺寸 / 名称字号** | 客户端代码 `configs/layout/hud.ts` 的 `dropItemLayout` | 代码常量 | 重打客户端包 |

⚠️ **「掉落配置」页只有具名表**。你在那一页找不到「某只怪掉什么」，也找不到绑定 ——
这是 2026-11 真实踩过的坑。怪物的掉落一律在**怪物配置的弹窗**里。

### 2.2 每怪掉落：三态 + 字段语义

表结构（`PRAGMA table_info(monster_drops)`，7 列）：

| 列 | 类型 | 含义 |
|---|---|---|
| `monster_key` | TEXT **PK** | 怪物 key（`monsters.monster_key`） |
| `source` | TEXT | `table` = 引用具名表 / `entries` = 内联条目池 / 空 = 走兜底 |
| `table_id` | TEXT | `source='table'` 时指向 `drop_tables.id` |
| `picks` | TEXT | 抽取次数：`"1"`（固定）或 `"[1,3]"`（区间随机）。`table` 态可留空 = 用表的；`entries` 态服务端缺省兜 1，管理端必填 |
| `entries` | TEXT | `source='entries'` 时的条目池（JSON 数组） |
| `bind_drops` | INTEGER | 1 = 这只怪掉什么绑什么（#789） |
| `updated_at` | INTEGER | 管理端保存时写入 |

**三态是互斥的**（管理端弹窗用三个按钮切换，服务端整份替换）：

```
① 引用具名表   source='table'    table_id='elite'     picks="[1,3]"（可留空 = 用表的）
② 内联条目池   source='entries'  table_id=NULL        picks="[1,3]"（必填）  entries=[...]
③ 清空走兜底   source=NULL       table_id=NULL        picks=NULL           entries=NULL
                             ↓
                    读不到行 / source 为空 → 取 drop_tables 里的 'default'
```

**`picks` 是「抽几次」，不是「掉几件」**。每次抽取独立做权重随机，所以抽 3 次可能命中同一条目 3 次
（最后合并成一份数量叠加）。这就是为什么 `[10,10]` 的 `elite_1_10` 能一次给 10 件 `cloth_1`。

### 2.3 具名表：出厂 5 张，真实内容

| `id` | `picks` | 条目数 | 定位 | 内容概要 |
|---|---|---|---|---|
| `common` | `1` | 9 | 普通怪 | 血蓝药 30/20 权重、材料 20/15/10/4、`shoes_1` 权重 1 且 **chance 0.5** |
| `elite` | `2` | 9 | 精英 | 高级血蓝药、`material_gem` chance 0.6、四件装备各 chance 0.3 |
| `boss` | `3` | 8 | BOSS | `drug_sun` 2~5 个、`material_gem` 1~3 个、`weapon_2`/`cloth_1` chance 0.5 |
| `default` | `[1,2]` | 5 | **兜底**，没配的怪都用它 | 血药 40 权重、两种百分比药、两种材料 |
| `elite_1_10` | `[10,10]` | 1 | 特殊（`monster_key='1'` 引用） | 抽 10 次，每次必得 1 件 `cloth_1` |

条目（`entries` 数组里每个元素）的五个字段：

```json
{ "goodId": "weapon_1_p1s2", "weight": 0.97, "chance": 1, "count": [1, 1] }
```

| 字段 | 缺省 | 语义 | 坑 |
|---|---|---|---|
| `goodId` | 无 | 物品 id（基础件或**变体 id** 都行） | 配了不存在的 id → 拾取时 `ROLE_DATA_INVALID`（抽取不报错） |
| `weight` | `1` | 权重，**可重复命中** | 权重 0 或负数 = 这条永不掉 |
| `chance` | `1` | 命中后的概率（0~1） | **默认必掉**，不是「必掉一次」 |
| `count` | `[1,1]` | 数量区间，含两端 | 区间颠倒会自动纠正（`min/max` 兜住） |

📌 **出厂数据里 `monster_drops` 已经是「逐怪全量」**：220 只怪 → 220 行（219 条 `entries` + 1 条 `table`），
`picks` 为 NULL 的行数是 **0**。也就是说**现在没有任何一只怪走兜底** ——
`default` 只在「管理端点了『清空（走兜底）』」或「新加的怪没配掉落」时才真正被用到。

📌 **220 只怪的 `entries` 里已经把 15 个变体全量铺开了**（`weapon_1` + `weapon_1_p0s1` … `p4s2`），
权重从 `6.29`（p0s0）递减到 `0.17`（p4s2）。这是 #777 批量装备留下的口径：
**掉落表里写的变体 id 就是最终掉出来的那一件**，不需要再乘倍率。

### 2.4 绑定：三条规则，先硬后软

判定在**抽取侧**（`rollDrops`），不在拾取侧 —— 这样「账本里记的」和「客户端看到的」必然是同一件事：

```
bound = monsterBind                      // ① 怪物级：monster_drops.bind_drops === 1
     || bindOnDropOf(goodId)             // ② 物品级：equipments.bind_on_drop === 1（按基础件读）
     || Math.random() * 100 < bindChance // ③ 全局：runtime_params.drop_params.bindChance（%）
```

| 规则 | 粒度 | 配置处 | 归一化 |
|---|---|---|---|
| ① 怪物级 | 这只怪掉的**所有**东西 | 掉落弹窗顶部下拉 | `row.bind_drops === 1`（缺行/空 = false） |
| ② 物品级 | 这一**类**物品 | 装备列表「掉落绑定」列 | 变体 id 先 `baseKeyOf` 再读 `bind_on_drop` |
| ③ 全局 | 每一件**独立掷一次** | 运行时参数「随机绑定概率（%）」 | `clamp(0, 100)`；**缺键 = 0** |

**当前实测值（2026-11）**：`bind_drops=1` 的行 **0 条**，`bind_on_drop=1` 的装备 **0 / 685**，
`bindChance = 10`（10%，本轮刚开）。所以现在**每次掉落有 10% 概率绑定，且每件独立判定**。

📌 **缺键 = 0，不是「全绑」**。`dropBindChance()` 对缺键、坏 JSON、非有限数一律返回 0 ——
配漏了应该是「这个玩法没开」，不该是「全服掉落都被锁」。这条和 [04 篇](./04-角色与存档权威.md) 的
「回填而不是拒收」是同一个取向：**沉默失败要偏向玩家可玩，不是偏向系统严格**。

### 2.5 手感参数：`drop_params` 五个键

`runtime_params` 是一行四列（`drop_params` / `auto_battle` / `guild_rules` / `monster_ai`），
掉落占第一列，是个 JSON 对象：

```json
{"autoPickupRadius":40,"fullTipInterval":1500,"scatterMinDistance":52,"pickReplyTimeout":5000,"bindChance":10}
```

| 键 | 出厂 | 谁读 | 语义 | 改大了会怎样 |
|---|---|---|---|---|
| `autoPickupRadius` | 40 | 客户端 `DropManager.autoPickup` | 脚底到掉落物的距离 < 它 = 自动拾 | 隔空吸物；过大像磁铁 |
| `fullTipInterval` | 1500 | 客户端 `notifyBagFull` | 满包提示 / 重试节流（ms） | 提示刷屏；**也影响重试频率** |
| `scatterMinDistance` | 52 | 客户端 `scatterDropPositions` | 多件掉落的最小中心间距（px） | 散得太开，一件要走一步 |
| `pickReplyTimeout` | 5000 | 客户端 `requestPick` | `pick` 帧发出后等应答的上限（ms） | 帧丢失后重试变慢 |
| `bindChance` | **0（库）** / 本轮改 10 | 服务端 `dropBindChance` | 随机绑定概率（%） | 100 = 全绑 |

**两条通道，别搞混**：

- `autoPickupRadius` / `fullTipInterval` / `scatterMinDistance` / `pickReplyTimeout`
  → **走快照** `GET /game-config` 的 `runtimeParams.drop` 段，客户端进游戏拉一次 → **重进游戏生效**。
- `bindChance` → **只在服务端结算时现读库**，客户端根本不拿这个值 → **改完下一刀立即生效**。

📌 客户端 `configs/drop.ts` 里 `dropRuntime` 初始**全是 0**，注释写得很清楚：
「0 = 快照没到」。这是 #724 去兜底的产物 —— 客户端不保留第二份出厂值，避免「后台改了没生效」。
所以 `DropManager` 用 `static get` 现读，而不是 `static readonly`（#605 踩过：静态字段在模块加载时求值，
那一刻快照还没到，取到的是 0，运营改了永远不生效且无报错）。

### 2.6 表现参数：光柱与布局

| 参数 | 在哪 | 当前值 | 说明 |
|---|---|---|---|
| 光柱偏移 / 缩放 / 时长 / 开关 | `ui_effects` 的 `light-1`~`light-6` 行 | `offset_y=70`、`scale=1`、`1400~1500ms`、全开 | 只有**装备**有光柱；关掉时**连节点都不建** |
| 光柱画布 | 客户端 `configs/layout/lights.ts` | `400×400` | 素材原始尺寸，缩放交给上面那行 |
| 图标尺寸 | `configs/layout/hud.ts` `dropItemLayout` | `40×40` | |
| 节点高度 | 同上 | `iconSize.height + 14` | 多出的 14px 留给名称行 |
| 名称行 | 同上 | 字号 10 / 行高 12 / 段间距 2 / 下偏 3 | 装备是「前缀+名称+后缀」三段着色 |

光柱用哪一张由 `getEquipmentLightKey(good)` 决定（前缀 → 光柱映射在 `configs/light`），
**这里只决定「用哪张」，「多大 / 多久 / 开不开」归服务端 `ui_effects`** —— 表现参数不写在客户端。

## 三、怎么掉落（服务端）

### 3.1 时序：一次击杀到东西落地

```
客户端                              服务端（实时进程）
  │                                   │
  │  cast{castId,skillId,            │
  │       targetId,monsterKey}  ────► │  CombatSettlementService.settle
  │                                   │   ① 幂等账查重（castId 重发 → 原样重发）
  │                                   │   ② 技能 / 目标 / 区归属 / 距离 校验
  │                                   │   ③ 伤害 = rollRange(攻) × 系数 − rollRange(防) × 倍率
  │                                   │   ④ world.applyDamage → 扣血，判 killed
  │                                   │   ⑤ killed → settleKillReward
  │                                   │        ├ 经验入账（applyKillExp）
  │                                   │        ├ 队友分成（sharePartyExp）
  │                                   │        └ rollDrops(monsterKey)  ← 现查库！
  │                                   │             ├ monster_drops.findByKey
  │                                   │             ├ drop_tables.findByKey（按需）
  │                                   │             ├ rollDropTable（权重 → 概率 → 数量 → 合并）
  │                                   │             └ 逐条判绑定（三规则）
  │                                   │   ⑥ rememberDrops → 写进 dropLedgers
  │  ◄──── settle{ok,damage,hp,      │   ⑦ remember → 幂等账
  │         killed,reward{exp,        │
  │         drops[{goodId,count}]}}   │
  │                                   │
  │ MonsterManager.applyServerSettle  │
  │   → applyDamage(killed,reward)    │
  │     → DropManager.spawnResults    │
  │        (reward.drops, 死亡坐标, castId)
  │   → 地面出现 N 个节点              │
```

**关键：`reward.drops` 里只有 `goodId` 和 `count`，没有 `bound` 和 `from`。**
绑定与溯源存在**服务端账本**里，拾取时才写进背包格子。客户端在地面上**看不出这件东西绑不绑**
（详情弹窗要等你捡进包才显示「已绑定」）。

### 3.2 抽取六步（`rollDropTable`，纯函数）

```ts
// server/src/modules/realtime/combat-settlement.service.ts
function rollDropTable(table) {
  const picks = Array.isArray(table.picks)
    ? Math.max(0, dropRandomInt(table.picks[0], table.picks[1]))   // ① 定次数（区间或固定）
    : Math.max(0, Math.floor(table.picks ?? 1));
  if (!picks || !table.entries.length) return [];

  const weighted = table.entries.filter((e) => (e.weight ?? 1) > 0); // ② 剔掉零权重
  const total = weighted.reduce((s, e) => s + (e.weight ?? 1), 0);

  for (let i = 0; i < picks && weighted.length && total > 0; i++) {
    let roll = Math.random() * total;                                // ③ 权重轮盘（可重复命中）
    let entry = weighted[weighted.length - 1];
    for (const c of weighted) { roll -= c.weight ?? 1; if (roll < 0) { entry = c; break; } }
    if (Math.random() > (entry.chance ?? 1)) continue;               // ④ 过概率（默认必过）
    const count = dropRandomInt(entry.count?.[0] ?? 1, entry.count?.[1] ?? 1); // ⑤ 数量区间
    if (count <= 0) continue;
    const existed = results.find((r) => r.goodId === entry.goodId);  // ⑥ 同 id 合并
    if (existed) existed.count += count; else results.push({ goodId: entry.goodId, count });
  }
  return results;
}
```

六个细节，每一个都能独立配错：

| # | 细节 | 配错的后果 |
|---|---|---|
| ① | `picks` 是**抽取次数**，不是掉落件数 | 以为填 3 就掉 3 件，实际可能抽到 3 次同一条（合并后变成 1 件数量 ×3） |
| ② | 权重 ≤ 0 的条目被**整个剔除** | 想「临时关掉一条」可以设 0，但它在管理端仍显示 |
| ③ | 权重是可重复命中的轮盘 | 期望「不重复掉同一样」是错的，重复是设计 |
| ④ | `chance` 默认 **1（必掉）** | 忘了写就是必掉；写了 0.3 才是 30% |
| ⑤ | `count` 区间含两端、颠倒自动纠正 | `[3,1]` 不会报错，会当成 `[1,3]` |
| ⑥ | 同 `goodId` 合并成一条 | 所以地面上一堆药只会显示「血药 x5」一个节点 |

### 3.3 一个算例（`monster_key='2'`，真实配置实算）

配置（**112 条**条目，`picks="[1,3]"`）—— 权重之和是 **261.640**，不是条目数，也不是「几个大数」：

| 条目 | 权重 | 单次占比 | 说明 |
|---|---|---|---|
| `drug_hp_1` | 30 | **11.47%** | 最常见的产出 |
| `weapon_1` | 6.29 | **2.40%** | 基础件（`p0s0`） |
| `weapon_1_p4s2` | 0.17 | **0.065%** | 最高档（超神的 + 神级） |

```
picks=[1,3] → 先随机抽 1~3 次
每次：
  ▸ 11.47% 命中 drug_hp_1（count [1,2] → 再随机 1~2 个）
  ▸  2.40% 命中 weapon_1
  ▸  0.065% 命中 weapon_1_p4s2
同 id 合并 → 得到 1~3 组 {goodId, count}
逐条判绑定（10% 概率）→ rememberDrops
```

**「打一只这种怪掉一件超神武器」的真实概率**：3 次抽取内至少命中一次 =
`1 − (1 − 0.00065)³ ≈ 0.19%`，约 **520 只怪出一件**；再乘 90%（未绑定）—— 也就是说
「打到一件不绑定的超神武器」大约要 **580 只怪**。

这就是为什么「我打了半天什么都没有」是正常体感：**分母不是「几条」，是权重总和 261.64**。
想调爆率就调 `weight` —— 但要知道**改一条会影响全部条目**（分母变了）。

### 3.4 绑定判定：为什么放在这一侧

```ts
return rollDropTable(table).map((drop) => ({
  ...drop,
  bound: monsterBind || bindOnDropOf(drop.goodId) || Math.random() * 100 < bindChance,
}));
```

判定放在**抽取侧**的唯一理由（源码注释原话）：
> 同一次击杀的同一份掉落，掉落账本与客户端拿到的 `reward` 必须说同一件事，拾取时再算一次就可能前后不一致。

`bindOnDropOf(drop.goodId)` 内部会先 `baseKeyOf` —— 所以掉的是变体 `weapon_1_p1s2` 时，
读的是 `weapon_1` 的 `bind_on_drop`。**装备的绑定是按「基础件」配的，不是按变体配的。**

### 3.5 账本写入：`rememberDrops`

```ts
private rememberDrops(accountId, castId, drops, origin) {
  if (!drops.length) return;                       // 什么都没掉 → 不建账
  let book = this.dropLedgers.get(accountId) ?? new Map();
  if (book.size >= CAST_DEDUPE_CAPACITY) {         // 256 次击杀上限
    const oldest = book.keys().next().value;       // 挤掉最旧的一次
    if (oldest !== undefined) book.delete(oldest);
  }
  const at = Date.now();
  book.set(castId, drops.map((d) => ({
    goodId: d.goodId,
    count: d.count,
    bound: d.bound,
    from: itemTypeOf(d.goodId) === "equipment"      // 溯源只给装备
      ? { role: origin.killerName, monster: origin.monsterKey, at }
      : undefined,
    picked: false,
  })));
}
```

| 字段 | 作用 | 谁会读 |
|---|---|---|
| `goodId` / `count` | 拾取时告诉 `pickDrop`「放什么、放几个」 | 服务端 |
| `bound` | 拾取时原样写进背包格子 | 服务端 → 客户端详情 |
| `from{role,monster,at}` | 溯源三行（**只有装备**） | 客户端详情弹窗 |
| `picked` | 幂等：同一件不能入包两次 | 服务端 |

📌 **`from` 只给装备**。用户口径是「只有装备会溯源，其他物品只按是否绑定分成两种」——
一堆药记「谁掉的」没有意义，而且会让存档无谓变大。

📌 **账本容量 256 是按「击杀次数」算的，不是按「件数」**。一次击杀掉 10 件，占 1 个槽。
256 次击杀之后，最早的账被挤掉 —— **那时地上那堆东西还在，但已经捡不起来了**（`unknown_drop`）。

## 四、掉在地图上（客户端）

### 4.1 两条铺场入口，差别只有「能不能捡」

| 入口 | 触发 | 有 `pick` 定位？ | 能不能捡 | 代码 |
|---|---|---|---|---|
| `spawnResults` | **自己**击杀的 `settle.reward.drops` | ✅ `{castId, index}` | ✅ | `MonsterManager.applyDamage` |
| `spawnRemoteDrops` | **别人**击杀的 `monster-ai` 帧 `kills[]` | ❌ `null` | ❌ 纯演出 | `MonsterManager.applyRemoteKill` |

```ts
// 自己的击杀：settle 帧带回来，castId + 下标就是账本坐标
DropManager.spawnResults(reward.drops, target.getWorldPosition(), castId);

// 别人的击杀：monster-ai 帧的 kills 广播，纯演出

```

**为什么要分两条**：服务端账本按**击杀者账号**记（#325 归属设计）。别人的账号既没有这笔账，
也不该能拾。所以别人的掉落物节点：
- **不注册**悬停指针（鼠标移上去不显示「可拾取」光标，不误导）
- 自动拾取**跳过**（`if (!this.dropMap.get(node)?.pick) return`）
- 点击**不发** `pick` 帧（`requestPick` 里 `if (!drop.pick) return`）

演出部分（掉落音 / 散落 / 图标 / 数量）与自己的掉落**完全同一套** —— 所以你看到别人打死的怪掉了一地，
视觉上没有任何区别，**但走过去不会捡**。这是有意设计，不是 bug。

### 4.2 散落算法：同心环贪心

```ts
// client/assets/ui/utils/drop/DropScatter.ts
export function scatterDropPositions(count, minDistance = dropRuntime.scatterMinDistance) {
  positions.push(new Vec2(0, 0));                  // 第 0 件就在落点
  for (let i = 1; i < total; i++) {
    for (let ring = 1; ring <= total + 1 && !placed; ring++) {   // 从内圈往外
      const radius = ring * minDistance;
      const steps = Math.max(8, Math.ceil((2π × radius) / (minDistance × 0.5)));
      for (let step = 0; step < steps; step++) {
        const angle = (2π × step) / steps + ring * 0.7;          // 每圈错开相位，不排成直线
        const candidate = (cos × radius, sin × radius);
        if (所有已放点距离 ≥ minDistance) { placed = candidate; break; }  // 贪心铺满最内圈
      }
    }
  }
}
```

四个特性：

1. **任意两件都不重叠**（与所有已放点距离 ≥ `scatterMinDistance`）
2. **整体尽量紧凑**（从内圈往外找，第一个站得下的位置就用）
3. **形状固定、不随机旋转** —— 同一次掉落的相对位置可复现，方便排查
4. **第 0 件永远在落点本身**（怪物死亡坐标）

📌 `minDistance` 默认取 `dropRuntime.scatterMinDistance`，而它初始是 **0**。如果快照没到就铺掉落
（理论上不会，契约保证进游戏前快照到），`limit = 0` 会让所有点都满足条件，**全部叠在落点**。
这是「初始 0」这个设计的代价，靠进游戏前的快照契约兜住。

### 4.3 节点结构：三层

```
drop_item (40 × 54)                       ← 节点中心 = 落点 + 偏移
├── drop_light_<key>  (400×400 动画)      ← 只有装备有；排在图标之前 = 画在下层
├── drop_icon_<type>  (40×40，上偏 7px)   ← 关标，按物品大类取图
└── drop_name         (FlexRow，下偏)     ← 名称行
    ├── [装备] 前缀 + 名称 + 后缀 三段着色
    └── [其他] 「名称」或「名称 x5」
```

要点：

- **光柱先挂**（`applyEquipmentLight` 在 `addChild(icon)` 之前）→ 画在图标**下层**，
  图标压住光柱中心、光柱从四周透出，物品本身始终清晰可辨。
- 光柱是**掉落物节点的子节点**，随掉落物一起销毁 —— 拾取 / 换图清空都不必单独清理。
- 装备的名称行三段（前缀 / 名称 / 后缀）**与详情弹窗同源**（`getEquipmentNameParts`），
  地面与弹窗永远一致，不各写一份色表。
- 名称行宽 = 各段宽度之和（`Layout.ResizeMode.CONTAINER` + `Overflow.NONE`），
  整行在图标正下方居中 —— 首帧各段还没算出宽度，等 Label 定尺后 Layout 会自动重排。

### 4.4 图层：`DROP` 在 `GAME` 之下

```ts
enum Layer {
  MAP     = 1 << 0,
  DROP    = 1 << 1,   // ← 掉落物
  GAME    = 1 << 2,   // ← 主角、NPC
  MONSTER = 1 << 3,   // ← 怪物（在 GAME 之上）
  EFFECT  = 1 << 4,
  UI      = 1 << 5,
}
```

掉落物挂在 `LayerManager.DropLayer`（世界坐标），**用 `setWorldPosition` 落位**，不受父节点偏移影响。

为什么掉落物要在主角**下面**：走过去的时候主角应该踩在物品上，而不是被物品挡住。
为什么在怪物**下面**：怪物的血条和身体要压住地上的东西，否则一堆掉落物会糊住怪物。

### 4.5 掉落音：一次结算只响一次

```ts
private static spawnAt(results, position, place) {
  if (results.length > 0) void SoundManager.play("item_drop");  // 按件播会叠成噪音
  const offsets = scatterDropPositions(results.length);
  results.forEach((result, index) => place(result, index, offsets));
}
```

拾取音用**同一个 key**（`item_drop`），但带 80ms 节流（`PICKUP_SOUND_MIN_GAP_MS`）：

> 自动拾取会「走到哪捡到哪」，一片掉落物在几百毫秒内连着回十来个 `picked` 帧 ——
> 每帧都响就成了持续的嗡嗡声。80ms 大致等于「一次弯腰能听清的间隔」。

## 五、捡起来

### 5.1 两条触发路径，一个出口

| 路径 | 触发 | 代码 |
|---|---|---|
| **自动拾取** | 每帧检查脚底到节点的距离 `< autoPickupRadius` | `Game.update` → `DropManager.autoPickup(rolePosition)` |
| **点击拾取** | 点击命中掉落物节点 | `ScreenClickInput` → `DropManager.pickup(node)` |

两条路径最终都走**同一个** `requestPick(node)`：

```ts
private static requestPick(node): PickRequest {
  const drop = this.dropMap.get(node);
  if (!drop) return { outcome: "pending" };            // 竞态：刚被别的路径拾走
  if (!drop.pick) return { outcome: "pending" };       // 别人的掉落，不发帧
  const sentAt = this.pendingPicks.get(node);
  if (sentAt !== undefined) {
    if (Date.now() - sentAt < dropRuntime.pickReplyTimeout) return { outcome: "pending" }; // 在途
    this.pendingPicks.delete(node);                    // 超时（帧丢/断线）→ 允许重试
  }
  if (!CombatChannel.sendPick(drop.pick.castId, drop.pick.index)) return { outcome: "pending" };
  this.pendingPicks.set(node, Date.now());
  return { outcome: "pending" };
}
```

**只有两种结果**：`pending`（已发帧，等应答）和 `full`（背包满）。没有「本地已入包」这一种 ——
#581 删掉了那条回滚，因为那等于给客户端开了一条「自己造物品」的路。

📌 `pick` 帧里只有两个数字：`castId` 和 `index`（这次击杀的第几件）。**没有物品 id、没有数量、没有角色 id** ——
服务端只认账本，不信客户端说的任何内容。伪造 `castId` 在账本里查不到账，直接 `unknown_drop`。

### 5.2 在途状态：为什么需要它

```
点一下 → 发 pick → pendingPicks.set(node, now)
  ├─ 应答回来（< 5s）→ 删在途标记 → 入包 / 提示
  └─ 5s 内没应答      → 标记过期 → 下一帧 autoPickup 会再发一次
```

**没有在途标记会怎样**：自动拾取每帧都跑，一次 `pick` 帧来回可能要 100ms，这期间每帧都会再发一次，
服务端会收到几十个重复请求（虽然有 `picked` 幂等挡着，但流量白烧）。

**超时后为什么要允许重试**：帧丢失 / 断线期间发出去的帧永远回不来，不重试的话这件东西就永远捡不起来了。

📌 **`pickReplyTimeout` 是「等应答的上限」，不是「拾取冷却」**。改大它不会让人捡得更慢，
只会让「帧丢了以后多久重试」变长。

### 5.3 服务端：九步校验

`CombatSettlementService.pickDrop(accountId, castId, index)`：

```
① 查账本        dropLedgers.get(accountId)?.get(castId)
                 ↓ 没有 → fail("unknown_drop", "找不到这次掉落…不存在、已随会话清理或不属于你")
② 下标范围      index >= 0 && index < ledger.length
                 ↓ 越界 → fail("unknown_drop")
③ 幂等          entry.picked === true
                 ↓ 已拾过 → ok: true, placed: [], alreadyPicked: true（不报错，照常应答）
④ 角色在线      roles.onlineRevision(accountId)
                 ↓ 不在线 → fail("no_role")
⑤ 入包          roles.pickDrop(accountId, goodId, count, { bound, from })
                 ├ 物品类型      itemTypeOf(goodId) —— 不认识的 id → ROLE_DATA_INVALID
                 ├ 读存档        decodeStoredRoleData(existing.data)
                 ├ 两轮放格      placeGoodsIntoBag
                 └ 落库          revision + 1
⑥ 标已拾        entry.picked = true        ← **必须在入包成功之后**
⑦ 应答          { castId, index, ok: true, revision, placed, alreadyPicked: false }
```

**第 ⑥ 步的位置是整段代码最关键的细节**（源码注释原话）：

> **标记放在入包成功之后**：背包满被拒时地面掉落物必须还在，玩家腾出格子后同一 `castId/index` 可以再拾。

如果标在入包之前，背包满一次，那件东西就永久消失了。

**异常映射**（业务异常转成 `picked` 错误帧，连接不断，地面掉落物保留）：

| 抛出 | 帧里 `code` | 客户端表现 |
|---|---|---|
| `MALL_BAG_FULL`（20012） | `bag_full` | 节流提示「背包已满」，节点保留 |
| `ROLE_KICKED` | `role_kicked` | 只 `console.warn` |
| `ROLE_NOT_FOUND` | `no_role` | 只 `console.warn` |
| 其他 `BizException` | `pick_failed` | 只 `console.warn` |

### 5.4 入包：两轮放格

```ts
// RolesService.placeGoodsIntoBag
const stackable = itemType !== "equipment";
const maxStack = stackable ? (drugOf ?? itemBaseOf)?.maxStack || 99 : 1;

// 第一轮：吃已有堆（只有可叠加物品走得到）
for (每个格子) {
  if (cell.id !== goodId) continue;
  if ((cell.bound === true) !== bound) continue;     // ← #789：绑定状态不同不并堆
  const room = maxStack - current; if (room <= 0) continue;
  cell.count = current + take; ...
}

// 第二轮：占空格（可叠加按 maxStack 分堆，不可叠加每格一件）
for (每个空格) { line[col] = { id, count: take, ...(bound && {bound:true}), ...(from && {from}) }; }

if (remaining > 0) throw MALL_BAG_FULL;   // 放不下整份 → 全部回滚（data 已改但异常路径不落库）
```

| 规则 | 后果 |
|---|---|
| 装备**不可叠**（`maxStack = 1`） | 掉 3 件同款装备 = 占 3 格 |
| 药品 / 材料按表里 `max_stack`，读不到按 **99** | `drugs.max_stack` / `items.max_stack` |
| **绑定状态不同不并堆** | 同一种药最多分成两堆（绑定一堆、未绑定一堆） |
| **放不下整份就全拒**（不是放一半） | 掉 5 个药、只剩 3 格，一件都进不去 |

📌 **为什么「绑定不同不并堆」是必须的**：否则「捡到一堆绑定的药」会并进未绑定的那堆，
绑定就从有变成没有（或反过来 —— 那更糟，等于白送一堆可交易品）。

📌 **背包 7 行 × 11 列 = 77 格**（实测存档）。新号的 `bag` 是空数组，靠**第一次存档**时
`adoptBagShape(库里的, 上报的)` 撑成客户端上报的形状 —— 所以刚建号如果还没存过档就拾取，
可能被判「背包满」。

### 5.5 应答落地：`applyPickedFrame`

```ts
static applyPickedFrame(data: PickResult): void {
  const node = this.findNodeByPick(data.castId, data.index);   // 倒查节点（应答只带两个数）
  if (node) this.pendingPicks.delete(node);

  if (data.ok === false) {
    if (data.code === "bag_full") this.notifyBagFull();
    else console.warn(`[drop] 拾取被拒（castId=… index=… code=…）：${data.message}`);
    return;                                                     // ← 节点保留
  }

  StorageManager.applyPickResult(data.placed, data.revision);   // ① 先照搬格子
  void SoundManager.play("item_drop", 80);                      // ② 拾取音
  GuideStore.notify(GUIDE_EVENT.PICKUP);                        // ③ 新手引导
  if (!node) return;                                            // ④ 节点已不在（换图清场）→ 到此为止
  const drop = this.dropMap.get(node);
  this.removeDropNode(node);                                    // ⑤ 再移除地面节点
  if (drop) GameUiHelper.createTip("pickup_tip", { names: … }); // ⑥ 飘字
}
```

**① 和 ⑤ 的顺序不能反**（源码注释原话）：

> 先把服务端实际写入的格子与修订号照搬进本地背包（`StorageManager.applyPickResult`），
> 再移除地面节点 —— 顺序不能反，背包要合并的是「服务端落账后」的形状。

**`revision` 必须照搬**：入包在服务端推进了修订号，本地基线不更新的话，下一次防抖存档必撞乐观锁（20006）。

**幂等重放（`alreadyPicked: true`）** 的处理：`placed` 是空数组，但节点还在，说明上一份应答丢了 ——
照常收尾（移除节点 + 飘字），不报错。

### 5.6 背包满：节流，但不放弃

```ts
static notifyBagFull() {
  const now = Date.now();
  if (now - this.fullTipTime < this.fullTipInterval) return;   // 1.5s 内不重复提示
  this.fullTipTime = now;
  GameUiHelper.createTip("pickup_full_tip");
}
```

**自动拾取在节流期内直接跳过**（不只是不提示）：

```ts
static autoPickup(rolePosition, radius) {
  if (Date.now() - this.fullTipTime < this.fullTipInterval) return;  // 整段跳过
  ...
}
```

所以「背包满了站在一堆东西上」的表现是：提示一次，然后 1.5 秒内完全不重试，
1.5 秒后再试一次、再提示 —— 不会每帧刷屏，但**也不会自动放弃**。腾出格子后下一轮就捡进去了。

### 5.7 绑定与溯源怎么显示

绑定信息只在**捡进包之后**才可见（在地面上看不出来）：

```
背包格子 → meta { bound: true, from: { role, monster, at } }
         ↓
详情弹窗（GameUiHelper.showGoodDetail）
  ├── 「已绑定 · 不可交易」        ← 只有 bound === true 才占一行（未绑定不留空位）
  └── 装备专属三行溯源
       ├── 「掉落者：张三」        ← origin.role
       ├── 「来自：赤月恶魔」      ← origin.monster（monsterLabelOf 翻中文，未知 key 直接显示 key）
       └── 「掉落时间：11月8日 12:34」  ← origin.at
```

**缺哪项就少一行，不填「未记录」**（源码注释原话）：

> 服务端只记到一半时，空白比假数据诚实。

时间格式是「月日 + 时分」而不是完整年月 —— 一件装备的掉落时间大概率就在最近几天，
年月占位只会把这一行挤成两行 `（`formatOriginTime` 用 `00${v}`.slice(-2) 补零，
因为客户端 tsconfig 不引 ES2017，不能用 `padStart`）`。

## 六、不捡起来怎么办

这是本篇最需要说清的一节，因为**答案是反直觉的**。

### 6.1 没有 TTL —— 掉落物不会自己消失

`DropManager` 里**没有任何定时清理逻辑**。`dropMap` 只在三种情况下删条目：

| 删条目的地方 | 触发 |
|---|---|
| `removeDropNode` | 拾取成功 |
| `reset` | 换图（`GameMap` 构造） |
| `autoPickup` 里的 `if (!isValid(node))` | 节点被别处销毁后清残留 |

**没有「掉落物存活 N 秒后自动消失」这种机制**。所以：

> 你打完怪不捡，走开了，那堆东西**一直在地上**。你绕地图跑一圈回来，它还在原地。
> 你站在旁边挂机一小时，它还在。

这是「场景级生命周期」的直接后果 —— 掉落物节点挂在场景的 `DropLayer` 上，
场景不销毁，节点就不销毁。

### 6.2 但账本会先没：容量 256

服务端 `dropLedgers` 每次击杀占一个槽（`castId`），上限 `CAST_DEDUPE_CAPACITY = 256`：

```ts
if (book.size >= CAST_DEDUPE_CAPACITY) {
  const oldest = book.keys().next().value;    // Map 保持插入顺序
  if (oldest !== undefined) book.delete(oldest);
}
```

**256 次击杀之后，最早那次的账被挤掉** —— 那堆东西**还在你屏幕上，但已经捡不起来了**：

```
点它 → pick 帧 → 服务端 unknown_drop → 客户端 console.warn（不删节点）→ 5 秒后又试一次 → 又失败
```

而且 `applyPickedFrame` 在 `unknown_drop` 分支里**只 `warn`、不删节点**（只有 `bag_full` 会提示，
其他都是 `console.warn`）—— 所以这堆东西会变成**永久的幽灵**，一直躺在地上、一直捡不起来、
每 5 秒往控制台吐一条 warn。

### 6.3 四种「真的消失」的时机

| 时机 | 客户端节点 | 服务端账本 | 结果 |
|---|---|---|---|
| **换图**（走 `worldJoin` 到别的图） | `DropManager.reset()` 全销毁 | `targetsReset` → `dropLedgers.delete(accountId)` | ✅ 两边同清，干净 |
| **断线**（网络断 / 服务端挂） | **不销毁**（没有重连清理钩子） | `dropAccount` → 清 | ⚠️ 账本没了，节点还在 → **残留不可拾** |
| **关客户端 / 刷新网页** | 进程结束，全丢 | 连接断开 → 清 | ✅ 两边同清 |
| **进程重启（服务端）** | 断线 → 同「断线」 | 内存全丢 | ⚠️ 同「断线」 |

**只有「换图」和「关客户端」是两边一致地清干净。** 断线（含服务端重启）会留下错位：
客户端还画着，服务端已经不认了。

### 6.4 会不会被别人捡走

**不会。** 账本按 `accountId` 隔离，别人的 `castId` 在你的账本里查不到。而且：

- 别人屏幕上**看不到**你掉的这堆东西 —— `settle` 帧只发给你本人
- 别人能看到的只有**自己击杀**的掉落（`monster-ai` 帧的 `kills[]` 广播）
- 即使他改包伪造 `pick` 帧，服务端 `dropLedgers.get(他的 accountId)` 里没有这个 `castId` → `unknown_drop`

同账号换角色呢？账本按**账号**记，理论上换角色后还能查到你上个角色掉的账。
但换角色会回选角 → 重建场景 → `MonsterManager.reset()` → **发 `targetsReset`** → 账本清掉。
所以实际不可跨角色拾取。

📌 **`castId` 从不清零**。源码注释写「断线重连 / 换图（`worldJoin`）后清掉旧账重新计数」，
但客户端 `CombatChannel.castSeq` 是 `private static castSeq = 0`，只在 `sendCast` 里 `+= 1`，
**没有任何重置点** —— 注释后半句已过期。这反而更安全：`castId` 永远单调增长，不会撞上旧账。

## 七、刷新后物品去哪里了

「刷新」有五种，结果完全不同。先看对照表，再看逐条解释。

### 7.1 五种「刷新」对照

| 你说的「刷新」 | 实际发生 | 地上的东西 | 服务端账本 | 还能捡吗 |
|---|---|---|---|---|
| **① 换一张图再回来** | `worldJoin` → 重建 `GameMap` | 全没了 | 清空 | ❌ **永久消失** |
| **② 刷新网页 / 重开客户端** | WS 断开 → 重连 → 重新进图 | 全没了（进程重启） | 断开时清 | ❌ **永久消失** |
| **③ 掉线重连（网络抖动）** | WS 断开 → 自动重连 → 重发 `worldJoin` | **还在**（没重建场景） | **已清** | ❌ **看得见但捡不起来** |
| **④ 服务端重启** | 所有连接断 → 客户端重连 | **还在**（同 ③） | 内存全丢 | ❌ **同 ③** |
| **⑤ 打太多怪（> 256 次击杀）** | 无事发生 | 还在 | 最旧的被挤掉 | ❌ **那几堆捡不起来** |

### 7.2 逐条说明

#### ① 换图再回来 —— 永久消失

```
GameMap 构造
  ├── MonsterManager.reset()   → 发 targetsReset → 服务端清账本
  ├── DropManager.reset()      → 销毁所有节点 + 清 dropMap + clearDropLayer
  └── OtherPlayerManager.reset()
```

两边都清，且**清得很干净**。你换到别的图再回来，地上那堆东西不会「等你回来」——
新图的 `GameMap` 是重新构造的，`dropMap` 是空的。

📌 这也解释了为什么「掉落物」不占服务端存储：它从来就没被持久化过。

#### ② 刷新网页 / 重开客户端 —— 永久消失

浏览器刷新 = JS 进程重启，`DropManager.dropMap` 这个静态 Map 直接没了。
同时 WebSocket 断开触发服务端 `dropAccount(accountId)` → 账本清。

两边同清，掉落物**永久消失**。这是设计如此，不是 bug —— 掉落物本来就不进存档。

#### ③ 掉线重连 —— 看得见，捡不起来（已知问题）

这是唯一一个**两边不一致**的场景：

```
客户端：WS 断开
  ├── RealtimeClient.onClose → 安排指数退避重连（reconnectBaseDelay × 2^attempts，封顶）
  ├── **没有清理 DropManager**（没有断开钩子）
  └── 断线期间地面节点照常渲染

服务端：连接断开
  └── realtime.service.ts:431 → combat.dropAccount(accountId) → dropLedgers.delete(accountId)

客户端：重连成功
  └── CombatChannel 重发缓存的 worldJoin（lastJoin.mapId）
        └── 服务端 world.join() —— **不清账本**（账本已经在断开时清了）
        └── 客户端 **不重建 GameMap** → 节点还在

结果：节点在、账本没了 → 点它 = unknown_drop → warn → 5 秒后重试 → 无限循环
```

**为什么会这样**：`worldJoin` 只负责「进图登记」，它**不清账本**（只有 `targetsReset` 清）。
客户端换图会发 `targetsReset`（`MonsterManager.reset` 里），但**断线重连不换图**，所以不发。
而服务端在断开那一刻已经把账清了。

**表现**：断线前掉在地上的东西，重连后还在原地，但走过去不捡、点它也没反应
（只有 `console.warn`，玩家看不到任何提示）—— 因为 `unknown_drop` 不是 `bag_full`，不弹提示。

**怎么绕**：换一次图（或重开客户端）就干净了。

#### ④ 服务端重启 —— 同 ③

服务端重启 → 所有 WS 断开 → 客户端走 ③ 的路径。账本在内存里，重启即全丢。
客户端节点还在（进程没重启），所以表现与 ③ 完全一样。

#### ⑤ 打太多怪 —— 那几堆捡不起来

不是「刷新」，但是同一类问题的来源：账本容量 256，超出挤掉最旧的。
地上最老的那几堆会变成幽灵（同 ③ 的表现）。

### 7.3 一条判断口诀

> **「东西还在但捡不起来」= 客户端节点还在、服务端账本没了。**
> 原因只有三种：断线重连、服务端重启、账本被 256 挤掉。
> **解法只有一种：换一次图（或重开客户端），让两边都清干净。**

反过来：「东西不见了但账本还在」也会发生 —— 换图清场后、迟到的 `picked` 应答回来时，
`applyPickedFrame` 里 `if (!node) return` 会跳过地面部分，**但入包照常应用**（因为服务端真的放进去了）。
这是正确的：东西确实进包了，只是地面上没东西可收了。

## 八、已知问题与设计缺口

写文档时实测出来的四条，都还没修。

### 8.1 没有 TTL：多人场景地面会堆积

`spawnRemoteDrops` 铺的节点**不可拾取、也不会消失** —— 只能等换图清空。
一个热闹的地图上，别人打的怪掉的每一样东西都会留在你的客户端内存里，直到你换图。

- 影响：挂机久了 `dropMap` 会越来越大（每个节点 = 1 个 Node + 3~5 个子节点 + 可能的光柱动画）
- 建议方向：给掉落物一个统一的存活上限。**v2 已定为 180 秒统一过期，末 10 秒只显示秒数小字、不闪烁**
  （见 [18 · 掉落系统重构设计](./18-掉落系统重构设计.md) 第 2 节与 6.2 节）

### 8.2 断线重连留下不可拾的残留节点

见第七节「7.2 ③ 掉线重连」。根因是「客户端没有断开清理钩子」+
「`worldJoin` 不清账本」。两个可能的修法：

- 客户端：`RealtimeClient` 的 `Disconnected` 回调里调 `DropManager.reset()`（最省事，但断线期间会看到东西突然消失）
- 服务端：`worldJoin` 也清一次账本（与 `targetsReset` 同效，但会让「重连不换图」也清）

### 8.3 没有条目级绑定开关

`DropEntryDto` 只有 `goodId` / `weight` / `chance` / `count`。所以配不出
「这只怪的 A 装备绑定、B 装备不绑定」，只能在三个粒度里选：

- 整只怪绑（`monster_drops.bind_drops`）
- 整类物品绑（`equipments.bind_on_drop`）
- 全局概率（`drop_params.bindChance`）

### 8.4 `bindChance` 本地库曾缺键

`config-sync.sql` 里是 `"bindChance":0`，但本地 `olua.db` 的 `drop_params` 一度**没有这个键**。
服务端缺键按 0 处理（行为正确），但管理端保存一次「掉落手感」才会把键补上。
本轮已手工补成 `10`。

📌 改完这个键**不用重启**：`runtimeParams.get()` 在每次 `rollDrops` 时现读，
而实时进程还有 10 秒一次的 `runtimeConfig.refreshAll()` 兜底。

## 九、排障表

| 症状 | 第一嫌疑 | 查法 |
|---|---|---|
| **怪死了什么都不掉** | `monster_drops` 没这行 → 走 `default`；或 `default` 本身是空的 | `SELECT * FROM monster_drops WHERE monster_key='X'`；再查 `drop_tables` 里 `default` |
| 掉的东西永远是那几样 | 条目池被覆盖成了少量条目 | 看 `length(entries)` 与 `picks` |
| 想要的东西一次都不掉 | 权重太小 / 忘了 `chance` 默认是 1 但被写成了 0.0x | 算一下「该条目权重 ÷ 总权重 × picks 次」 |
| 掉了一堆看不见的东西 | `goodId` 配了不存在的 id → 客户端 `getItem` 返回 null → warn 后**不建节点** | 搜客户端 `掉落物品不存在` |
| 地面上的东西全部叠在一点 | `scatterMinDistance` 是 0（快照没到） | 看 `drop_params` 与是否在进游戏前就铺了掉落 |
| **东西在地上但捡不起来** | 账本被清（断线 / 重启 / 256 挤掉） | 点一下看 console：`拾取被拒（code=unknown_drop）` |
| 捡起来提示背包满 | 真的满了（77 格） | 或「绑定不同不并堆」导致可用堆更多 |
| 捡起来进包了但地面还在 | 应答晚到 / 节点 id 对不上 | 看 `findNodeByPick` 是否命中（`castId` + `index`） |
| **掉落物没有绑定标记** | 三个开关全 false | 查 `bind_drops` / `bind_on_drop` / `bindChance` 三个值 |
| 绑定标记有了但没溯源 | 拾的不是装备（`from` 只给装备） | 看 `itemTypeOf(goodId)` |
| 别人的掉落走过去不捡 | **设计如此**（无账本定位） | 看节点是否有 `pick`（`spawnRemoteDrops` 传的是 null） |
| 改了掉落没生效 | 其实立即生效 —— 是不是改错了怪 | 击杀时现查库，改完下一刀就生效；确认 `monster_key` 对得上 |
| 改了拾取半径没生效 | 走快照，要**重进游戏** | 退到选角不算，要真的重进 |
| 光柱不显示 | `ui_effects` 那行 `enabled=0`，或该前缀没有光柱映射 | 查 `ui_effects WHERE effect_key LIKE 'light-%'` |
| 拾取音连成一片 | 正常（80ms 节流） | 若明显更密，检查 `PICKUP_SOUND_MIN_GAP_MS` |
| 地面掉落物越堆越多 | 别人击杀的掉落没有 TTL（[8.1](#81-没有-ttl多人场景地面会堆积)） | 换图即可清；要根治得加存活上限 |

## 附录 B：加一只「会掉东西」的怪（五步，顺序不能反）

```
① 怪物本体    战斗配置 → 怪物配置 → 新增（monsters）
② 掉落配置    同一行的「掉落」按钮 → 选三态之一
                ├ 引用具名表：选表 + 可覆盖 picks
                ├ 内联条目池：填 picks + 条目（goodId / weight / chance / count）
                └ 清空走兜底：什么也不填（用 default）
               ← 此时已可掉落（服务端击杀时现查库，无需重启）
③ 绑定（可选） 同弹窗顶部「掉落整体强制绑定」，或去装备配置开「掉落绑定」列
④ 刷怪区      地图管理 → 该图的「刷怪区」弹窗（map_spawn_areas）
               ← ⚠️ 对**已存在**的分域不自动回溯（#669），要清怪或重启实时进程
⑤ 表现（可选） 特效管理 → light-* 行调光柱；掉落图标走物品配置
```

**只做 ①② 就已经能掉了**，③④⑤ 是可选。

⚠️ **`goodId` 一定要存在于三张表之一**（`equipment_variants` / `drugs` / `items`）——
抽取时**不校验**，配错了会在拾取那一刻才报 `ROLE_DATA_INVALID`，而客户端在地面上根本建不出节点
（`getItem` 返回 null → warn 后跳过）。所以「配了掉落但地上什么都没有」的第一嫌疑是 `goodId` 写错。
