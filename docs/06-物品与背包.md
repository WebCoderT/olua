# 06 · 物品与背包

> 背包是「一份二维数组」还是「一堆格子」？答案决定了守恒怎么验、绑定怎么存、整理为什么会被拒。

## 一、六档物品类型（两端同名）

```ts
// client/assets/types/good.ts + server 的 itemTypeOf() 认同一套字符串
equipment  装备      不可叠加（maxStack 恒 1），每件一格，有 15 个变体
drug       药品      可叠加，用完扣 1，回复血/蓝
material   材料      可叠加，只有名字/图标/卖价 —— 没有使用动作
money      货币道具  可叠加，用完给账本入账（bindGold / gold / silver）
scroll     升级卷轴  可叠加，用完硬性 +1 级（带等级区间）
other      其他      兜底档，目前库里没有实际数据
```

四张表各管一档，**同名列刻意保持一致**：`id / label / description / sell_price / max_stack / bind_on_drop / icon`。

| 表 | 行数 | 独有列 |
|---|---|---|
| `equipments` + `equipment_variants` | 685 + 10275 | 12 个属性列、`slot`、`level`、外观几何（见 [05](./05-装备链路.md)） |
| `drugs` | 11 | `cooldown`、`effect_hp/mp`、`effect_hp_percent/mp_percent` |
| `items` | 5 | `type`（目前全是 `material`） |
| `money_items` | 24 | `currency`（`bindGold` / `gold` / `silver`）、`amount` |
| `level_scrolls` | 7 | `min_level` / `max_level`（卷轴只能用在这段等级内） |

出厂的 `max_stack`：药品 99、材料 99、货币 999、卷轴 999、装备 1（无该列）。
`sell_price = 0` 的意思是**不可回收**（升级卷轴与货币道具出厂都是 0，别让它们变成印钞机）。

`bind_on_drop` 五张表各一列 —— 掉落绑定判定的第 1 条规则就查它（见 [05](./05-装备链路.md) 第四节）。

## 二、背包的数据形状

存档里 `role.bag` 是一个**二维稠密数组**，空格是 `null`：

```json
[
  [{ "id": "drug_hp_1", "count": 12 }, null, { "id": "weapon_1_p2s1", "count": 1, "bound": true,
                                              "from": { "role": "李四", "monster": "3", "at": 1793713758226 } }],
  [null, null, null]
]
```

- **格子只存 `id` + `count`**（#556 起），物品的全部数据经配置表实时解析 —— 改配置重启即生效，
  不会出现「存档里还留着旧属性快照」。
- **`bound` / `from` 是服务端写的元数据**（#789），客户端只读、搬运与整理时原样带走。
- **尺寸归客户端**（`configs/role` 的 `bagRow × bagCol`）。服务端不认识这个尺寸，
  所以在 `save` 时走「内容取库、尺寸取客户端」（`adoptBagShape`）。
  新尺寸装不下某一格 → 整份退回原网格（不静默丢东西，也不替玩家挪位置）。

管理端提交背包用**稀疏格子**（只报「哪一格放了什么」），`applyBagCells` 铺进原网格；
空数组 = 清空背包（网格尺寸保留），这也是管理端的「清空背包」动作。

## 三、五个动作（都走 `POST /roles/:id/bag-op`）

| 动作 | 谁算 | 服务端做什么 | 失败码 |
|---|---|---|---|
| `equip` | 服务端 | 判部位 / 认得出 / 等级够 → 换上（**格子的 `bound` / `from` 一起搬进槽位**，#816），旧的回原格 | 20020 / 20021 |
| `unequip` | 服务端 | 判槽位合法且非空 → 放进第一个空格（**槽位的 `bound` / `from` 原样搬回格子**，#816） | 20020 / **20012**（满了） |
| `discard` | 服务端 | 整格置空，**不返还任何东西** | 20020 |
| `move` / `tidy` | 客户端排布 + 服务端验 | 只验守恒，不重算排布 | 20022 |
| —— 拾取进包 | 服务端 | `placeGoodsIntoBag` 两轮放格 | 20012 |

为什么前三个必须服务端算，后两个只验守恒：

> 复刻一遍客户端的 move / merge / swap 会让两端慢慢漂开（客户端那份还带着「合并超过上限留在原格」
> 这类细节）。改成「客户端给排布、服务端验内容守恒」—— 少一件多一件都过不去。

**穿脱只换地方、不改值**（#816）：槽位存 `{ id, bound?, from? }`，与背包格子同一套元数据口径 ——
「五瓶绑定药用到剩一瓶仍是绑定的」和「绑定装备穿一次就该还能证明它绑定」是同一件事。
`move/tidy` 那条 `reconcileBagCells` 认领绑定态的理由也在这里：上报的格子契约里没有 `bound`。

**穿戴 / 卸下会当场重算属性**（`equipments` 是属性输入），`move/tidy/discard` 不会。
所以 `bagOp` 的返回体在 equip/unequip 时多了 `combat / maxHp / maxMp / hpRecover / hp / mp`，
客户端 `runBagOp` 一把抄回本地（脱掉加血装备时，血量当前值由服务端夹到新上限内）。

## 四、两条守恒（`move` / `tidy` 的唯一判据）

```
① sameGridShape(旧, 新)              行列数必须一致
② sameBagContent(旧, 新)             按「绑定态 + id」分组，各组合计件数必须一致
```

分组键两端必须**逐字相同**：

```ts
// 客户端 configs/items.bagGroupKeyOf
`${cell.bound === true ? 1 : 0}|${cell.id}`
```

为什么键要对齐：绑定堆与未绑定堆**互换位置**本身是合法整理，但若允许它们**并成一堆**，
就等于凭空送出一件可交易的（或把可交易的锁死）。客户端按这个键合并，服务端按这个键验守恒 ——
两边不同步，一次普通整理就会被判成作弊（20022）。

### `reconcileBagCells`：先认领、再守恒

上报的格子契约只有 `row/col/id/count`，**没有 `bound`**。直接拿上报排布去比守恒，
「绑定的那一堆挪了个位置」就会被读成「凭空冒出几个可交易的」—— 整理必失败。

所以服务端先按 id 归堆、用旧网格的桶件数反推、深搜挑出「件数之和 = 绑定桶件数」的那批
（多解时按「旧绑定格原址 > 空格 > 旧未绑定格原址」择优），认领元数据之后再比守恒。
交叉合并（绑定 2 + 未绑定 4 报成一格 6 个）会因另一桶归零被抓到 —— 认领不会放过作弊。

## 五、绑定与溯源：怎么显示

| 位置 | 表现 |
|---|---|
| 背包格子角标 | 绑定件带锁标；同 id 的绑定堆与未绑定堆**分两格显示**（不会看起来「突然只剩一堆」） |
| 物品 tooltip | 三行溯源：`击杀者` / `怪物名`（客户端用怪物配置把 key 翻成中文）/ `掉落时间` |
| 未绑定件 | 无溯源行（`from` 只给装备，且只有装备会记） |

时间格式化的一个实现坑（`GameUiHelper.formatOriginTime`）：

```ts
// 补零不用 padStart（客户端 tsconfig 不引 ES2017），也不用数字比较（`< 10` 会被
// audit-config-leak 当成魔法阈值）；借两位常数前缀切尾两位，两个坑一起绕开
const pad = (value: number) => `00${value}`.slice(-2);
```

口径提醒：**绑定只拦交易，卖店回收照常**。本期只做「标记 + 展示」，不做交易禁令之外的联动。

**回收入账只进 `bindGold`**（#845 / B2 逐字落地）：`sellGoods` 根本不读格子的 `bound` ——
绑定件与未绑定件走同一条计价与入账路径，卖完都进绑定元宝。所以「绑定装备洗成流通币」
那条路不存在，写进 `gold` / `silver` 才是漏洞（C2：金币不可流通，玩家之间只能以物易物）。
`e2e-sell` 的第八段盯着这条：卖一件之后 `bindGold` 涨一份价、`gold` 与 `silver` **一分不动**。

## 六、药品使用（`POST /roles/:id/drug-use`）

```
回复量 = effect_hp + effect_hp_percent ÷ 100 × maxHp          （魔法同理，四舍五入，负值按 0）
```

顺序上有两个必须：

1. **先结算自然回复，再判「已满」** —— 两次用药之间攒的回复要先入账，否则「攒一会儿就够满」的药
   会被误判成「无需使用」拒掉。
2. **血蓝各自封顶**，血满蓝不满照用（只回蓝的部分）。两项都满 → 20014 拒用且**不扣药**。

其它口径：
- `maxHp/maxMp` 用**服务端重算**的战斗属性；等级不在曲线里（重算不出）时退回存档里那份 ——
  用药是恢复性操作，兜底比拒绝更符合玩家预期。
- 四项回复效果全 0 的药 → 20013（配置写了但等于没实现）。
- **服务端冷却**（#848）：`drugs.cooldown` 单位**秒**、`0` = 无冷却，按「角色 + 药品 id」计
  （红的喝完不影响蓝的）。冷却中 → **20030**，响应体 `details` 带 `remainingMs` / `cooldownMs`，
  客户端据此把按钮灰到点。校验顺序也定死了：**先判「已满」（20014），再判冷却** ——
  满血点药本来就该是「不用喝」，不该顺带吃掉一个冷却；落库失败（20006）会把占位退掉。
- 用完扣 1，减到 0 清格；格子对象整个换新（避免共享引用）。

## 七、货币道具使用（`POST /roles/:id/money-use`）

客户端只报「用背包哪一格」，**币种与金额一律读 `money_items` 表** ——
运营把 100000 改成 1，玩家下次使用就只加 1，改包也改不出钱。

| 判定 | 失败码 |
|---|---|
| 格子空 / 不是货币道具 / 币种不合法 / 没配金额 | 20023 |
| 冷却中（同一道具 1 秒内第二次） | 20031（`details.remainingMs`） |
| 带 revision 撞乐观锁 | 20006 |
| 被踢下线 | 20007 |

与用药的区别：**不结算血蓝、不判「已满」**；冷却固定 1 秒（`MONEY_ITEM_COOLDOWN_MS` 常量，
不进 `money_items` —— 那张表进快照，为一列冷却要动五处）。#847 之前这里**完全没有间隔**，
改包就能把 999 个道具在一秒内全部变现。
币种只认 `MONEY_KINDS` 三种（`gold` / `bindGold` / `silver`），库里存了第四种 → 拒用，
而不是往一个不存在的字段上写钱。

## 八、升级卷轴使用（`POST /roles/:id/level-scroll-use`）

**硬性 +1 级，不扣经验。** 经验原样保留（下次打怪入账时继续按曲线判定），也不清零。

三条判定，**顺序有意义**：

| 序 | 判定 | 失败码 | 为什么在这个位置 |
|---|---|---|---|
| 1 | 等级在 `min_level ~ max_level` 内 | 20025 | 这是卷轴的核心规则（Lv1 用到 1000 级就该换卷了），不是配错 |
| 2 | 未到 `roleMaxLevel` | 20026 | 「抬上限」与「加卷轴」是两件事，运维看码要知道去改哪个 |
| 3 | 属性重算 + 补满血蓝 | — | 与击杀侧 `refillOnLevelUp` 同一惯例（升级就该满血满蓝） |

区间本身坏掉（手改库 / 老数据 0 值，`min < 1` 或 `max < min`）→ 20024 拒用，
而不是「任何等级都能用」。

## 九、客户端的背包算子（纯函数，可单测）

| 函数 | 作用 | 不变量 |
|---|---|---|
| `tidyBagGrid(bag)` | 合并（同 id **且同绑定态**）→ 排序 → 铺回左上角 | 行列数不变、按「绑定态+id」分组数量守恒、认不出的 id 原样保留排最后、不改入参 |
| `moveBagCellGrid(bag, from, to)` | 一格拖到另一格：空 → 移动；同 id 且同绑定态且未满 → 合并；其余 → 交换 | 同上 |
| `normalizeBagGrid(bag, rows, cols)` | 按当前配置尺寸补齐 / 裁掉 | 正常存档走不到裁剪（裁掉会留日志） |
| `summarizeBagRecycle(bag)` | 一键回收的**预览**：件数 + 合计价 | 与 `recycleBagEquipmentGrid` 同一份实现（判定与计价只有一处） |
| `findBagEquipmentUpgrade(bag, slot, canUse, worn)` | 找同槽位「更好的装备」（角标提示 + 一键替换共用） | 「更好」= 战斗力贡献**严格大于**当前件；平手不提示 |
| `getStackBadge(good, count)` | 堆叠角标（如 `12/99`） | 不可叠加物不显示 |

`tidyBagGrid` 的排序（`compareBagGoods`）：装备按等级 / 部位 / 前后缀，其余按等级，id 兜底；
这个顺序由 `bagTidyTypeOrder` 决定类型先后（药品/材料 → 装备 → …）。

**一键回收只动装备**：药品、材料原样留在原格；解析不出配置的 id 也原样保留（不认识它就不替它决定）。
重复调用同一份背包，第二次必为空结算（幂等）。

## 十、加一种新道具（按类型选路径）

| 类型 | 加什么 | 连带检查 |
|---|---|---|
| 药品 | `drugs` 插一行 | `max_stack` / `effect_*` / `icon` 素材存在；掉落表加上它 |
| 材料 | `items` 插一行（`type = material`） | 同上 |
| 货币道具 | `money_items` 插一行 | 币种必须在三种之内；`amount > 0`（否则 20023） |
| 升级卷轴 | `level_scrolls` 插一行 | **区间不能重叠、也不能留空档**；`icon` 按卷号指向素材（`item/scroll/level-scroll-N`） |
| 装备 | 见 [05](./05-装备链路.md) 第十一节（六步） | 15 个变体、几何、边框 |

共同的三件事（漏一个就会「掉出来但用不了 / 卖不出价」）：

1. **`itemTypeOf` 必须认识它** —— 服务端按 `equipment_variants` → `drugs` → `money_items` → `level_scrolls` → `items` 的顺序查，
   哪张表都没有就是 `null`，拾取直接 `ROLE_DATA_INVALID`。
2. **`sellPriceOf` / `itemLabelOf` 同步覆盖** —— 否则回收价 0（不可卖）与名字退回 id。
3. **`rebuildItemIndex` / `getMallGoods` 覆盖到** —— 客户端可售清单与商城陈列靠它们（#777 曾漏「7 部位部分视图」）。

改完：

```bash
make audit                                  # 含 audit-resource-refs（图标断链会点名）
cd server && npm run test:e2e:roles         # 用药 / 货币 / 卷轴 / 背包动作都在这套里
cd client && npm test -- items              # 背包算子单测（tidy / move / 回收）
```

## 十一、排障

| 症状 | 第一嫌疑 | 查法 |
|---|---|---|
| 背包里物品「少了一堆」 | 绑定堆与未绑定堆被合成一格（旧客户端） | 看两堆的 `bound`；确认客户端走的是 `tidyBagGrid` |
| 整理提示「内容与服务器不一致」 | 客户端与服务的分组键不同步 | 比对 `bagGroupKeyOf` 与 `sameBagContent` |
| 物品显示成 id | `getItem(id)` 查不到（配置没下发给客户端） | 查快照段里有没有这个 id |
| 回收按钮是灰的 | `sell_price = 0` 或 `sellPriceOf` 没覆盖该表 | 查表里那行 |
| 用药没反应 | 血蓝都满（20014）或该格不是药品（20013） | 看服务端 message |
| 药品冷却不生效 | 冷却归客户端，服务端不计时 | 查客户端快捷键节流 |
| 货币道具用不了 | 币种不合法 / `amount` 为 0（20023） | 查 `money_items` 那行 |
| 卷轴提示「该换卷了」 | 等级超出该卷区间（20025，正常规则） | 查 `min_level / max_level` |
| 卷轴提示已达上限 | `roleMaxLevel` 到了（20026） | 改成长标量，不是加卷轴 |
| 拾取报「掉落物品不存在」 | `itemTypeOf` 不认识这个 id | 查五张表 |
