# 15 · 数据表清单（69 张）

这篇是**查阅型附录**：每张表存在、哪个进程读写、字段是什么意思、改它会影响哪条链路。
链路的「为什么」在前面各篇，这里只做索引与字段级索引。

> 数字来自本地库实测 + 建表语句（`sqlite3 server/data/olua.db`，2026-11 快照）：**71 张表 = 39 配置表 + 32 运行时表**。
> 表结构定义在 `server/src/database/`（`database.service.ts` 的建表语句 + `repositories/`）。

## 一、分类判据：为什么非得分成两类

配置表与运行时表**混在同一个 SQLite 文件里**，但它们的去向完全不同 —— 配置要跟着 git 走，运行时绝不能。

`server/scripts/lib/config-tables.cjs` 是**唯一分类处**，判据写在文件头：

| 类别 | 判据（三条任一） | 去向 |
|---|---|---|
| **配置表**（38） | ① 进 `GET /game-config` 快照的（物品 / 怪物 / 技能 / 称号 / 地图…）<br>② 不进快照但服务端现算要用的（`growth_scalars` 标量、`monster_skills`、`map_spawn_areas`）<br>③ 走独立接口下发的外观几何（`equip_aligns` / `equip_in_aligns`） | 进 `config-sync.sql`，提交进仓库 |
| **运行时表**（32） | 一行代表「某个玩家 / 某台服务器此刻的状态」：账号、角色、公会成员、队伍、邮件队列、审计、**玩家行为流水**、世界怪物实例、区服、公告、角色身上的状态 | **永不进同步文件** |

### 强制「每张表都必须归类」

`assertAllClassified()` 在导出时对**实际库表**做一次全量比对：库里每张表都必须在两个清单之一
（`sqlite_%` 系统表除外），**多一张就当场报错并指名道姓**。

为什么这么狠 —— 忘了分类的后果分两种，都很隐蔽：

| 漏了哪边 | 后果 |
|---|---|
| 配置表漏了 | 别人同步过来少一张，页面上显示「一个都没有」，看起来像**数据没配**（而不是「表没导」） |
| 运行时表误加 | **账号 scrypt 哈希跟着 git 走，发出去就收不回来**（`olua` 是 PUBLIC 仓库） |

> 比「按清单挨个导、导完不管」强 —— 后者永远绿。

## 三、通用约定

| 约定 | 说明 |
|---|---|
| **主键类型** | `TEXT` 用 uuid / 业务键（`equipments.id`、`roles.id`、`skills.id`）；`INTEGER` 用**业务等级**（`titles.level`、`ranks.level`、`souls.level`）—— 等级本身就是主键，不另给自增 |
| **时间戳** | 一律 `INTEGER`（**Unix 毫秒**），列名 `created_at` / `updated_at` / `at` / `banned_at` / `claimed_at` |
| **布尔** | `INTEGER` 0/1（SQLite 没有 bool），如 `enabled` / `alive` / `success` / `hidden` |
| **JSON 列** | `TEXT` 存 JSON，读出后由仓储层解析：`roles.data`、`maps.content`、`equipment_variants` 的 `*_positions`、`skills.damage_coefficients`、`monster_drops.entries`、`role_mails.attachments`、`map_monitor_state.payload` |
| **外键** | 只有 `roles.account_id → accounts.id`（`ON DELETE CASCADE`）等少数显式声明；其余靠**应用层**维护（如 `equipment_variants.base_id → equipments.id`） |
| **索引** | 35 个显式索引（不含 SQLite 为 UNIQUE 列自动建的 `sqlite_autoindex_*`；#867 起多一个 `role_mails(expires_at)` 的部分索引，基线 34 个实测自 `sqlite_master`），几乎全落在运行时表的热查询列：`roles(account_id)`、`audit_logs(created_at DESC)`、`event_logs(role_id, created_at DESC)`、`role_mails(box)`、`world_monsters(map_id)`、`map_monitor_events(zone_id, map_id, id)` + `(at)`、`role_status(expire_at)` |
| **唯一约束** | `accounts.username`、`admins.username`、`guilds.name`（重名靠库挡，不靠应用层查） |

## 四、配置表逐域

### 4.1 装备（7 张）

配置 → 展开 → 掉落 → 拾取 → 穿戴的完整链路见 [05-装备链路](./05-装备链路.md)。

#### `equipments`（685）—— 装备**基础件**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT / PK | 基础件 id，也就是变体 `p0s0` 的 id |
| `slot` | TEXT | 7 部位之一（`weapon` / `armor` / `helmet` / `necklace` / `bracelet` / `ring` / `shoes`） |
| `level` | INTEGER | 需求等级；也参与 `sell_price` 与变体缩放 |
| `label` | TEXT | 名字（变体会在前后加词缀） |
| `occupation` / `sex` | TEXT | 限职业 / 限性别；空 = 不限 |
| `icon` | TEXT | 背包图标素材路径 |
| `description` | TEXT | 描述 |
| `sell_price` | INTEGER | **基础价**；变体价由 `scale(10*level)` 重算 |
| `max_hp` / `hp_recover` | INTEGER | 生命上限 / 每秒回复 |
| `physical_attack_min/max` | INTEGER | 物攻区间（**区间形态**，不是单值） |
| `magic_attack_min/max` | INTEGER | 魔攻区间 |
| `taoist_attack_min/max` | INTEGER | 道攻区间 |
| `physical_defense_min/max` | INTEGER | 物防区间 |
| `magic_defense_min/max` | INTEGER | 魔防区间 |
| `taoist_defense_min/max` | INTEGER | 道防区间 |
| `in_atlas` / `out_atlas` | TEXT | 内观 / 外显图集 |
| `in_pos_x/y`、`in_scale_x/y`、`in_rotate` | 数值 | 内观几何（单件覆盖，优先于 `equip_in_aligns`） |
| `out_scale` / `out_positions` | 数值 / JSON | 外显缩放与逐方向位置 |
| `tags` | TEXT | 标签 |
| `bind_on_drop` | INTEGER | **掉落即绑定**（按基础件读，不看变体） |

> 📌 八个属性都是 `_min/_max` 成对的**区间**。伤害结算时先 `rollRange()` 取值再算 ——
> 所以「属性怎么来的」永远是「区间 → 掷点 → 系数」，不存在「装备给一个固定攻击力」。

#### `equipment_variants`（10275）—— 15 个变体，最终值已展开

| 字段 | 说明 |
|---|---|
| `id` | 变体 id（`<base>_p<前缀档>s<后缀档>`）；`p0s0` 就是基础件 id 本身 |
| `base_id` | 指回 `equipments.id`（有索引 `idx_equipment_variants_base`） |
| `prefix` / `suffix` | 词缀档位 0~4 / 0~2 |
| `label` | 展开后的完整名（`超神的·裁决之刃·神级`） |
| `level` / `sell_price` | `sell_price = scale(10*level)` |
| 八个属性 | **全部是按倍率算好的最终值**，不是基础值 —— 客户端与结算侧都不再乘 |

倍率唯一来源 `equipment_meta`：

```json
{ "prefix_rates": [1, 1.1, 1.2, 1.3, 1.4],
  "prefix_labels": ["普通的","强化的","精良的","极品的","超神的"],
  "suffix_rates": [1, 2, 3],
  "suffix_labels": ["人级","天级","神级"] }
```

`scale(v) = Math.round(v * prefix_rates[p] * suffix_rates[s])`，5 × 3 = **15 组合**。
`685 × 15 = 10275` ✓ —— 行数本身就是「展开完整」的校验。

> 所以**改基础件属性后必须点「重建变体」**，否则 10275 行还是旧值（见 [12-管理端](./12-管理端.md) 第九节）。

### 4.2 物品（4 张）

#### `drugs`（11）

`id` · `label` · `description` · `icon` · `level` · `sell_price` · `max_stack` · `cooldown` ·
`effect_hp` · `effect_mp` · `effect_hp_percent` · `effect_mp_percent` · `bind_on_drop` · `updated_at`

回复量两种形态：**绝对值**（`effect_hp`）与**百分比**（`effect_hp_percent`），两者可并存。
`cooldown` 是同一药品的再次使用冷却。

#### `items`（5，全 `type=material`）

`id` · `type` · `label` · `description` · `icon` · `level` · `sell_price` · `max_stack` · `bind_on_drop` · `updated_at`

`type` 决定它算哪一类物品 —— 目前只有 `material`（任务材料 / 杂物）。

#### `money_items`（24）

`id` · `label` · `description` · `icon` · `currency` · `amount` · `max_stack` · `sell_price` · `bind_on_drop` · `updated_at`

用掉 → 按 `currency` 加 `amount`。**服务端读表，客户端只报格子**（#785，见 [06-物品与背包](./06-物品与背包.md)）。

#### `level_scrolls`（7）

`id` · `label` · `description` · `icon` · `min_level` · `max_level` · `max_stack` · `sell_price` · `bind_on_drop` · `updated_at`

`min_level` 出厂是 `1 / 1000 / … / 6000`（每档跨 1000 级）。使用有三条判定顺序
（等级内 → 20025；超上限 → 20026）。

六个 `*_min/max` 与装备同构：**区间**。`tier` 决定掉落走哪张表（`common` / `elite` / `boss`）。

怪物会哪些技能、优先级、独立冷却。不进快照，服务端现算要用。

| 表 | 差异字段 | 备注 |

`channel`（社交 / 战斗 / 系统 / 成就四频道）与 `kind` 是两回事：前者决定**从哪来**，后者决定**怎么展示**。

| `world_reload_requests` | 0 | `id` · `zone_id` · `map_id` · `slot` · `mode` · `status` · `requested_by` · `force_at` · `attempts` · `detail` · `created_at` · `done_at` | 单图热重载请求（#809）：管理端写 pending、实时进程轮询执行的**跨进程待办**。`mode` = `respawn`（可等空窗）/ `reload`（立刻）；`force_at` 是等空窗上限（到期强制）；同房间 pending 在写库时合并（取最新 mode、`force_at` 取更早的）；连续 3 次失败才标 `failed`。不进快照（纯运行时） |
| `zones` | 2 | `id` · `name` · `merged_into` · `created_at` · `updated_at` | 区服；合区写 `merged_into` |
| `config_meta` | 4 | `key` · `value` | 快照元信息（格式版本 / 导出时间 / 表数 / 行数） |

### 5.7 配置版本（2 张，#882）

配置发布链的两张运行时表。**它们不进快照、不进 `config-sync.sql`、不被 `config-check` 比** ——
回滚恢复的只有 `CONFIG_TABLES` 那 39 张；版本号本身是「这台服务器改到第几版」的本地状态，
跟着库走（从仓库 clone + `make config-import` 得到的是文件里的版本号）。

#### `config_version`（1 行）

| 字段 | 说明 |
|---|---|
| `id` | PK 且 `CHECK (id = 1)` —— **单行表**，不用 `config_meta` 的键值形态：这是一个数字，不是一个集合 |
| `version` | 自增值。任何带 `gameConfig:write` 的写接口**成功之后** +1（全局拦截器 `ConfigVersionInterceptor`） |
| `updated_at` · `updated_by` | 最后一次自增的时间与操作人（`config_revisions` 才是逐层的账） |

#### `config_revisions`（≤ `CONFIG_REVISION_RETAIN`，默认 20 层）

| 字段 | 说明 |
|---|---|
| `version` | PK，与 `config_version.version` 同一个计数（一层一个版本号，不重号） |
| `label` | 这一层是哪个写接口造成的（`operationId`，如 `adminSkill.update`），与操作日志的 `action` 同一个字符串 |
| `payload` | **全量** 39 张配置表的 JSON（`{table: [row...]}`），不是 diff |
| `byte_size` · `table_count` · `row_count` | 落层时算好的元信息：列表页要显示「这一层影响了多大面」，不回 payload |
| `created_by` · `created_at` | 操作人与落层时间；同一人 `CONFIG_REVISION_THROTTLE_MS`（默认 10 秒）内的多次写**合并成一层** |

**为什么存全量不存 diff**：回滚要「一键」。diff 回滚得按逆序重放半年的增删改，任一环对不上就卡在半途；
全量恢复是 `DELETE` + `INSERT`，一个事务（`PRAGMA defer_foreign_keys = ON` 把外键检查推到 COMMIT），
要么全成要么全不动。代价是每层几百 KB~几 MB × 20 层，可接受。

**保留策略**：先删最老再插新的（先删再加，保证「满了写失败」不会发生）；
回滚自身**不参与节流**（否则回滚点会被自己吃掉），且回滚也会 +1 版本、留一层新历史。

### 5.8 商城计数（2 张，#846）

限购与库存的**运行数**。配置只有「限购几次 / 总共几件」（`mall_goods.daily_limit` / `stock`），
「今天买了几个 / 全服已卖几件」必须单独记 —— 写进配置表会被 `config-import` / 快照回滚 / 另一台机器的
`config-sync.sql` 盖回去（同一个商品在两台机器上销量还不一样，本来就不是一份数据）。

两张表都**不进快照、不进 `config-sync.sql`、不被 `config-check` 比**。

#### `mall_sales`（每角色 · 每商品 · 每天最多一行）

| 字段 | 说明 |
|---|---|
| `role_id` · `good_id` · `day` | 复合 PK；`day` 是 `todayResetDay()` 的天号（**05:00 切日**，与 `quest_progress` 的日常同一把尺子） |
| `count` | 这一天买了几件。插入即 1，冲突时 `count = count + 1` |
| `updated_at` | 最后购买时间 |

索引 `idx_mall_sales_day` 服务于清理（`purgeSalesBefore`，购买链路一天顺手清一次旧天号的行；
失败只 warn，不影响购买）。

**切日不需要任何结算动作**：天号对不上就是新的一天，旧行留着也不影响判断。

#### `mall_stock`（每商品一行）

| 字段 | 说明 |
|---|---|
| `good_id` | PK |
| `sold` | 全服累计卖出的件数（**总量仍是配置里的 `stock`**，这里只记分子） |
| `updated_at` | 最后卖出 / 重置的时间 |

**两处都是「条件自增占位」**，不是先查再写：

```sql
UPDATE mall_stock SET sold = sold + 1 WHERE good_id = ? AND sold < ?
INSERT INTO mall_sales … ON CONFLICT(role_id, good_id, day) DO UPDATE SET count = count + 1 … WHERE mall_sales.count < ?
```

靠 `changes > 0` 判成没成。先查再写在 API 与实时两个进程之间留缝（超卖一件 = 限量款凭空多一件）。
占位与扣款在**同一个事务**里，背包满 20012 / 乐观锁 20006 会把名额一起退回。

`mall_stock` 的行在下架时被 `resetStock` 清零（下架 = 这一轮售卖结束），也由运营的
`POST /admin/mall/goods/:id/stock-reset` 手动清零（续货）。

## 六、改表的标准动作

### 加一张配置表

一张新表要**同时登记五处**，漏一处就会在某条链路上静默失效：

| # | 位置 | 作用 |
|---|---|---|
| 1 | `server/scripts/lib/config-tables.cjs` 的 `CONFIG_TABLES` | 导出时带上它 + `assertAllClassified` 检查 |
| 2 | 同上文件的 `RUNTIME_TABLES`（**反过来检查**：别误加） | 保证它不会混进运行时清单 |
| 3 | `tools/gen-api.cjs` 的 `MODULES` | 生成管理端 CRUD 接口 |
| 4 | `tools/audit-server-boundaries.cjs` 的 `REPO_EDGES` | 允许 `roles` 等模块 import 这个仓储 |
| 5 | `server/src/common/decorators/audit-target.decorator.ts` 的 `AUDIT_TARGET_TYPES` | 操作日志能记录这个类型 |

### 加一张运行时表

比配置表轻，但**必须登记 `RUNTIME_TABLES`** —— `assertAllClassified()` 导出时会对实际库表做全量比对，
漏登记的直接报「未归类的表」，`make config-check` / `config:export` 全红。

| # | 位置 | 作用 |
|---|---|---|
| 1 | `server/scripts/lib/config-tables.cjs` 的 `RUNTIME_TABLES` | 声明「这张表不进同步文件」 |
| 2 | 同上文件的 `CONFIG_TABLES`（**反过来检查**：别误加） | 保证它不会被当成配置导出 |
| 3 | `server/src/database/database.service.ts` | `CREATE TABLE IF NOT EXISTS` + 需要的话加索引 |

不需要动 `gen-api`（没有管理端 CRUD）、不需要进快照、不需要进 `config-sync.sql`。
`role_status`（#822）就是按这条加的。

> **例外：如果这张表要新开一个仓储**（表名是数据、或要跨模块读），还要在
> `tools/audit-server-boundaries.cjs` 的 `REPO_EDGES` 里登记「哪个域可以注入这个仓储」——
> 业务模块直连 `DatabaseService` 会被 `audit-server-boundaries` 判 FAIL。
> `config-revision.repository.ts`（#882）就是这条：它必须按 `CONFIG_TABLES` 运行期拼表名，
> SQL 只能待在仓储里，于是边登记成 `["modules/game-config"]`。

### 加一段配置快照（`GET /game-config`）

比加表还容易漏 —— **三处 + 三个测试**：

| # | 位置 |
|---|---|
| 1 | 快照 DTO（`*_DTO`） |
| 2 | `snapshot()` 组装处 |
| 3 | 客户端 `client/assets/configs/game-config.ts` 的 **区 0**（类型声明） |
| 4 | `configs-sandbox` 三处（测试沙箱的默认值） |
| 5 | `tools/audit-snapshot-contract.cjs`（客户端「要什么」= 服务端「发什么」） |

> 漏一处 = **几十套客户端单测齐炸**，而且报错位置跟真正的原因差很远。

### 改字段（哪怕只是改注释）

> **改 DTO 连描述都算改契约。** 逐字段的描述进 `openapi.json`（`swagger:emit`），
> 再进客户端与管理端的生成物 —— 所以流程是：

```bash
cd server && npm run gen:api     # 或 make gen-api
make audit-generated             # 逐字节比对，不重生成就红
```

Response DTO 不在 `swagger/models.ts` 登记就**不会进 openapi**（接口能跑，文档缺一块）。

### 改数值（不涉及结构）

走管理端页面 → 写库 → 存档进程立即重装、实时进程最迟 10s（`REALTIME_CONFIG_REFRESH_MS`）。
不需要重新部署。详见 [12-管理端](./12-管理端.md) 第九节与 [13-部署运维](./13-部署运维与质量门禁.md) 第七节。

## 七、排障

| 症状 | 第一嫌疑 | 查法 |
|---|---|---|
| 导出时报「表未归类」 | 加了表没登记 | 看报错指名的表，按第六节五处补 |
| 别人同步后「一个都没有」 | 配置表漏进 `CONFIG_TABLES` | 对比 `config-sync.sql` 的 `-- tables:` 行 |
| 担心账号进了 git | 运行时表误加进 `CONFIG_TABLES` | `git log -p server/data/config-sync.sql` 搜 `accounts` |
| 客户端某配置死活不生效 | 快照段没加 / 客户端区 0 没加 | `make audit-snapshot-contract` |
| 管理端列表能进但字段空 | `swagger/models.ts` 没登记 Response DTO | 看 `openapi.json` 里有没有它 |
| 改了基础件但属性没变 | 没重建变体（`equipment_variants` 还是旧值） | `SELECT * FROM equipment_variants WHERE base_id=?` |
| 变体行数不是 `685×15` | 展开不完整 | 对比 `equipments` 与 `equipment_variants` 的 `base_id` 覆盖 |
| 刷怪区改了没生效 | 只对空分域播种 | 见 [08-世界与怪物](./08-世界与怪物.md)（#669） |
| 查 `runtime_params` 报 `no such column: value` | 是五个 JSON 列，不是行式 | `SELECT drop_params, auto_battle, guild_rules, monster_ai, movement` |
| 掉落「绑定了但没配」 | `bindChance` 缺键 → 0；或怪 `bind_drops` / 装备 `bind_on_drop` | 查三处（见 [05-装备链路](./05-装备链路.md)） |
| 排行榜里有脏数据 | 榜是进程内物化，不进库 | 重启实时进程或等 `LEADERBOARD_REFRESH_MS` |
| 地图监控表涨到几百万行 | 时间闸关了（`MAP_MONITOR_RETENTION_DAYS ≤ 0`）或某张图还在被写（`MAP_MONITOR_TRIM_EVERY` 没生效） | `SELECT map_id, count(*) FROM map_monitor_events GROUP BY map_id`；`SELECT MIN(at), MAX(at) FROM map_monitor_events`（跨度超过保留天数 = 时间闸没跑） |
| 审计日志把磁盘写满 | 两道闸都设成 0 | 看 `AUDIT_LOG_MAX_ROWS` / `AUDIT_RETENTION_DAYS` |
| 恢复备份后「数据回到几天前」 | 备份是整库快照 | 正常行为；先备当前再恢复 |
