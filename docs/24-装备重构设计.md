## 零、现状（实测）

| 项 | 实测 |
|---|---|
| 装备定义 | `equipments` **685 行** |
| 变体 | `equipment_variants` **10275 行** = 685 × 15（同一 key 的 15 个强度档） |
| 部位 | 7 个（`equipment_slots`） |
| 外观 | `equipment_appearance`（换装用） |
| 背包格子 | `{row, col, id, count, bound, from}` —— **没有装备实例的概念** |
| 掉落 | 抽到时决定 `id` + 变体档，入包就是一个普通格子 |

**关键推论**：因为格子只记 `id`，同一件装备在任何地方都不可区分 ——
所以**没法给某一具体件加强化等级**，也没法在交易里「指定卖这一件 +7 的」。
这是本篇要解决的根本问题。

## 一、五个结构性问题

### 1.1 没有装备实例，强化无处可挂

强化等级必须挂在「一件具体的装备」上。现在唯一的载体是背包格子（`row/col`），
但格子会移动、会并堆、会被回收 —— 把强化等级存格子上，等于「整理一下背包强化就没了」。

### 1.2 变体不是强化

`equipment_variants` 的 15 档是**同一 key 的强度档**（掉落时抽到第几档就是第几档）。
它与「玩家投入材料把 +3 变成 +4」是两件事：

| | 变体 | 强化 |
|---|---|---|
| 谁决定 | 掉落时随机 | 玩家投入 |
| 存在哪 | 装备定义（`equipment_variants`） | 装备实例（本篇新增） |
| 可逆 | 不可（换一件就是另一档） | 可（失败降级，不消失） |
| 上限 | 15 档 | +15 |

两者**正交**，可以叠加（+7 的第 12 档装备）。但叠加后数值必须封顶，见 2.3。

### 1.3 装备不可交易的前提就是「不可区分」

[26 交易篇](./26-交易与商城重构设计.md) 要做的面对面交易，最小单位是「一件装备」。
现在只能按 `id + count` 交易 —— 而装备的 `count` 恒为 1，于是「两件同名不同档」无法分开卖。

### 1.4 强化消耗没有流水

即使加上强化，如果只扣「材料数量」不记账，[26 篇](./26-交易与商城重构设计.md) 的货币与物品
守恒（B2）就对不平。强化必须在**同一套流水**里记「消耗了什么、产出/变化了什么」。

### 1.5 7 部位是硬编码

`equipment_slots` 有表，但代码里若按 7 遍历，加第 8 部位（如披风、护符）要动多处。
本期不扩部位，但**结构上要允许**（按表遍历而非常量）。

## 二、目标形态

### 2.1 实例化模型

```
背包格子 ──(instId)──> item_instances ──(itemId)──> equipments / equipment_variants
                          │
                          └─ enhanceLevel, sockets[], bound, from, locked
```

| 规则 | 内容 |
|---|---|
| 只有装备有实例 | 消耗品 / 材料 / 货币**不建实例**（`instId` 为 null），否则一次刷怪能造几十行 |
| 实例 id | `i<roleId>_<seq>`（与怪物实例同风格，可读、可猜但服务端校验归属） |
| 实例归属 | `ownerRoleId` 冗余存一份（便于反查与清理），真值仍是「在谁的背包/仓库/装备栏」 |
| 装备栏 | 7 个槽位也存 `instId`，不再存 `id` |
| 销毁 | 回收 / 强化破碎 / 交易成功都要删实例行 —— **一处不删就是幽灵实例** |

### 2.2 强化规则

| 段位 | 成功率 | 失败后果 | 说明 |
|---|---|---|---|
| +0 → +5 | 100% | — | 安全段，只花材料 |
| +6 → +8 | 70% / 55% / 40% | **降 1 级** | 有风险但不归零 |
| +9 → +12 | 30% / 22% / 15% / 10% | **破碎**（装备消失） | 已定：高段位可碎 |
| +13 → +15 | 7% / 5% / 3% | 破碎 | 极少数人的目标 |

| 机制 | 规则 |
|---|---|
| 材料 | 每级消耗 `enhance_cost`（绑定元宝 + 强化石），从 `item_instances`/背包扣，**同一事务** |
| 保底 | 连续失败 `pity_count`（默认 5）次后，下一次**必定成功且不破碎**，然后计数归零 |
| 保护符 | 可选道具：破碎时改为「降 1 级」；本期只留字段（`protect_item_id`），暂不投放 |
| 转移（继承） | **做**：把 A 的强化等级继承给同部位的 B。规则见 2.7 |
| 上限 | `+15`，到顶后强化按钮灰 |

**成功率是配置，不是常量**：`enhance_rules(level, success_rate, on_fail)`。

### 2.3 与变体的叠加封顶

```
finalAttack = round(baseAttack(变体档) × (1 + enhanceLevel × enhance_rate))
```

- `enhance_rate` 默认 **0.03**（每级 +3%，+15 = +45%）；
- 变体档最高 15 档，其自身倍率已在 `equipment_variants` 里；
- **总倍率封顶 `max_multiplier`（默认 3.0）**：超过就截断并 warn —— 变体 × 强化 × 转生 × 状态
  四个乘数叠起来极容易失控，必须在属性聚合出口处设一个硬顶。

> 硬顶放在**属性聚合**（`role-attributes.ts`）而不是强化函数里，因为叠加发生在那里。
> 放错地方就会出现「面板显示 3 倍、实际打出 4 倍」这类问题。

### 2.4 装备实例的生命周期

```
  掉落抽取 ──> 创建实例（enhanceLevel=0）──> 入包
                                            │
         ┌──────────────────────────────────┼──────────────────┐
         ▼                                  ▼                  ▼
     穿到装备栏                         仓库/交易            回收 / 破碎
         │                                  │                  │
         └── 强化（改 enhanceLevel）────────┘                  ▼
                                                          删实例行 + 记流水
```

**任意一步失败都必须回滚全部**（扣材料 + 改等级 + 记流水是一个事务）。
现在的 `roles.data` 是单列 JSON，没有事务概念 —— 所以强化**必须走 `save` 那条通道**
（乐观锁保护），不能走实时帧。

### 2.6 镶嵌宝石 / 洗练词条 / 8 部位（本轮纳入）

这三项与强化同属「装备长线投入」，按顺序上线，不要同时开（两套材料经济会互相稀释）。

**镶嵌**：

| 项 | 规则 |
|---|---|
| 孔位 | `item_instances.sockets`（JSON 数组，长度 = 孔数，元素为宝石 id 或空） |
| 孔数 | 由装备定义决定（`equipments.socket_count`，默认 0；稀有装备 1~3） |
| 宝石 | 新增物品类型 `gem`，`items` 表加 `gem_effect`（JSON：`{attack:10}`） |
| 镶嵌 / 取下 | `POST /roles/:id/gem/inlay {instId, slot, gemId}`、`.../remove`；取下**销毁宝石**（不返还，否则可以反复试） |
| 属性 | 宝石加成在**强化乘算之后**相加（不吃强化倍率，否则一颗宝石被 +15 放大 45%） |

**洗练词条**：

| 项 | 规则 |
|---|---|
| 词条 | `equipments.affix_pool`（JSON：可出的词条池）与 `item_instances.affixes`（JSON：这件实际出的） |
| 洗练 | `POST /roles/:id/reforge {instId, lockIndexes?}`：重 roll 全部未锁定词条，消耗材料；锁定每条额外加价 |
| 词条数 | 由装备定义决定（`equipments.affix_count`，默认 0 / 1 / 2 / 3） |
| 上限 | 单条词条按 `affix_rules` 表定范围，**不许随机到超出范围的极端值** |

> 洗练是 [22 篇](./22-战斗与技能重构设计.md) 里「命中/闪避/抗性」重开的**前提** ——
> 那三项只能作为词条出现，不能作为基础属性列。

**8 部位**：

| 项 | 规则 |
|---|---|
| 新增 | 披风（`cloak`）、护符（`charm`）两行插进 `equipment_slots` |
| 代码 | 所有「7 部位」的硬编码改为按表遍历（分刀 ⑥ 已包含） |
| 老档 | 新槽位为空，不影响已有属性；客户端面板要多两格 |
| 掉落 | 先不投放（`equipments` 里没有这两类物品），结构与 UI 先就位 |

### 2.7 强化继承（本轮纳入）

| 项 | 规则 |
|---|---|
| 范围 | 同部位、同职业限定；承继方强化等级为 0 |
| 代价 | 继承后等级 **−2**（+15 → +13），且消耗 `inherit_cost`（绑定元宝 + 材料） |
| 为什么 −2 | 不给折扣的话，「+15 底子」会变成唯一流通资产，685 件装备池变成废纸；−2 让每次换代都有成本但可接受 |
| 反向 | 不可逆（承继方拿走等级，原装备归 0） |
| 与交易 | 继承后的装备可正常交易 |

### 2.8 兼容老档（关键）

老存档的背包格子只有 `id`，没有 `instId`。**不写迁移脚本**，改为**惰性实例化**：

| 时机 | 做法 |
|---|---|
| 读档 | `instId` 缺失 = 普通物品，按现在的语义处理 |
| 第一次「需要实例」时（穿 / 强化 / 交易 / 进仓库） | 就地创建实例并写回 `instId` |
| 掉落 | 直接带 `instId`（新数据） |

这样：**老档不迁移也能玩**，且不会有「迁移跑一半」的风险。代价是「同一件装备在老档里
暂时不可交易」—— 第一次交易时自动实例化即可。

## 三、数据模型

```sql
-- 装备（及将来其他需要实例的物品）实例
CREATE TABLE item_instances (
  id            TEXT    PRIMARY KEY,          -- i<roleId>_<seq>
  item_id       TEXT    NOT NULL,
  variant_id    TEXT    NOT NULL DEFAULT '',  -- 变体档（装备才有）
  enhance_level INTEGER NOT NULL DEFAULT 0,
  owner_role_id TEXT    NOT NULL,             -- 冗余：便于反查与清理
  bound         INTEGER NOT NULL DEFAULT 0,
  from_json     TEXT    NOT NULL DEFAULT '',  -- 溯源（谁杀的/哪个怪/何时）
  locked        INTEGER NOT NULL DEFAULT 0,   -- 交易锁定中
  created_at    INTEGER NOT NULL DEFAULT 0,
  updated_at    INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX idx_item_inst_owner ON item_instances(owner_role_id);

-- 强化规则
CREATE TABLE enhance_rules (
  level        INTEGER PRIMARY KEY,           -- 目标等级 1..15
  success_rate REAL    NOT NULL,              -- 0~1
  on_fail      TEXT    NOT NULL,              -- keep / downgrade / break
  cost_bind_gold INTEGER NOT NULL DEFAULT 0,
  cost_item_id TEXT    NOT NULL DEFAULT '',
  cost_item_count INTEGER NOT NULL DEFAULT 0,
  protect_item_id TEXT NOT NULL DEFAULT ''
);
```

改两张表：

| 表 | 加什么 |
|---|---|
| 背包格子（`roles.data.bag`） | 每格加 `instId?: string`（可选，缺省 = 无实例） |
| `equipment_slots`（角色已穿） | 每槽从 `id` 改成 `{ id, instId, enhanceLevel }` |

> **为什么不新建 `role_equipment_items` 表**：装备已经存在 `roles.data` 里（存档权威），
> 再建一张表就有两份真相。实例表只存「实例独有的信息」，不存「它在哪」—— 「在哪」仍由存档决定。

## 四、协议与接口

| 接口 | 方法 | 说明 |
|---|---|---|
| `/roles/:id/enhance` | POST | `{instId, useProtect?: boolean}` → `{ok, level, broke, cost}` |
| `/roles/:id/equip` | POST | 改：接受 `instId`（不再接受裸 `id`） |
| `/roles/:id/unequip` | POST | 同上 |
| 快照 `enhanceRules` | 下发 | 客户端要显示成功率与消耗；**服务端仍以库为准** |

`enhance` 的响应要带 **`broke: true/false`** 与 **`pityCount`**：
客户端据此播「破碎」动画或「保底触发」提示。**不能让客户端自己算成功率**（改包就能全成功）。

## 五、分刀

| 刀 | 内容 | 规模 | 前置 |
|---|---|---|---|
| ① | `item_instances` + 惰性实例化 + 掉落带 `instId` | 中 | 无 |
| ② | 装备栏与背包格子存 `instId`（`equip/unequip` 改造） | 中 | ① |
| ③ | `enhance_rules` + `POST /enhance`（含保底、破碎、事务） | 大 | ② |
| ④ | 属性聚合加 `enhanceLevel` 与总倍率硬顶 | 中 | ③ |
| ⑤ | 管理端「强化规则」页 + 装备实例反查 | 小 | ③ |
| ⑥ | 部位按表遍历（去 7 硬编码） | 小 | 无 |

**② 是风险最高的一刀**：它同时改背包与装备栏，而 `reconcileBagCells` 的守恒断言依赖格子形状。
建议 ② 单独一个 PR，且先写「老档读进来不动」的回归用例。

## 六、边界情况

| # | 情形 | 期望 |
|---|---|---|
| 1 | 老档装备没有 `instId`，直接强化 | 惰性创建实例（`enhanceLevel=0`）后继续，不报错 |
| 2 | `instId` 不存在 / 不属于自己 | 400（`instance_not_found`）—— 不打「别人的实例」 |
| 3 | 强化时材料不足 | 400（`not_enough_material`），**不扣任何东西** |
| 4 | 强化成功但写库失败 | 整体回滚（事务），响应 `save_failed` |
| 5 | 破碎时背包格子 | 该格清空；若在装备栏则清空该槽；**两处都要删实例行** |
| 6 | 破碎时装备是「已绑定」 | 一样破碎（绑定只影响交易，不影响强化） |
| 7 | 强化到 +15 再强化 | 400（`enhance_max`），按钮本来就灰（双保险） |
| 8 | 同一实例并发强化（双端） | 乐观锁 20006 拦第二次 |
| 9 | 保底计数在成功后 | 归零 |
| 10 | 保底计数在「降级」后 | **也归零**（保底只认「成功」，降级不算成功也不算失败累计？→ 明确：降级算失败累计） |
| 11 | 保护符用掉但本次没破碎 | **不消耗**（保护符只在真要破碎时扣） |
| 12 | 交易中（`locked=1`）的实例被强化 | 拒（`instance_locked`） |
| 13 | 装备被回收 | 实例行删除 + 记回收流水；回收价按 `enhanceLevel` 折价（默认不折，见 26 篇） |
| 14 | 掉落的装备进包 | 立刻建实例（`enhanceLevel=0`）；同一次掉落多件同名装备 = 多个实例 |
| 15 | 并堆（装备不能并堆） | 装备 `count` 恒 1，`instId` 不同 → 不允许并堆；`bagGroupKeyOf` 要按 `instId` 区分 |
| 16 | 装备实例数膨胀 | 一个活跃玩家约 30~60 件；10 万人服 = 300~600 万行。需要按「回收 / 破碎 / 交易成功」及时删，另加每月清理「不在任何容器里」的孤儿实例 |
| 17 | 孤儿实例（背包里找不到对应 instId） | 定时任务扫出并删除，记 warn（这是 bug 信号） |
| 18 | 强化消耗记在哪 | 与 26 篇的货币流水同一张表（`economy_log`），`kind='enhance'` |
| 19 | 变体档 × 强化 × 转生 × 状态 总倍率超 3.0 | 截断到 3.0 并 warn（`max_multiplier`） |
| 20 | 强化成功率改成 1.0 | 允许（运营开关），但管理端提示「等于取消风险」 |
| 21 | 强化成功率 > 1 或 < 0 | 40000 拒 |
| 22 | `on_fail` 改成未知值 | 40000 拒（枚举：`keep` / `downgrade` / `break`） |

## 八、验收

| 用例 | 断言 |
|---|---|
| `e2e-inst-lazy` | 老档（无 `instId`）装备直接强化 → 自动建实例，等级 0，不报错 |
| `e2e-inst-owner` | 用别人的 `instId` 强化 → `instance_not_found` |
| `e2e-enhance-safe` | +0→+5 连续 5 次全成功（成功率 1.0 段） |
| `e2e-enhance-fail` | +6 把成功率压 0 → 失败降 1 级，材料扣掉，实例还在 |
| `e2e-enhance-break` | +9 成功率压 0、`on_fail='break'` → 实例行删除、格子清空、装备栏清空 |
| `e2e-enhance-pity` | 连续失败 5 次 → 第 6 次必成功 |
| `e2e-enhance-multiplier` | 构造变体 × 强化 × 转生叠加超 3.0 → 属性被截断且 warn |
| `e2e-bag-inst-conserve` | 背包整理 / 并堆 / 拆分后，实例集合不变（没有丢实例也没有复制） |

手工验收：强化失败时有明确音效与飘字；破碎时装备从栏位消失且背包对应格清空；
保底第 5 次失败后界面显示「下次必成功」。

## 十一、已定参数

| 项 | 结论 |
|---|---|
| 强化失败 | **+1~+5 安全；+6 起降级；+9 起可破碎** |
| 强化上限 | +15 |
| 每级加成 | 3%（+15 = +45%），总倍率硬顶 3.0 |
| 保底 | 连续失败 5 次后必成功（降级算失败） |
| 老档 | 惰性实例化，不跑迁移脚本 |
| 交易 | 以「实例」为单位（对接 26 篇） |
| **镶嵌** | **做**：`equipments.socket_count` 默认 0，稀有 1~3；取下销毁宝石；宝石加成不吃强化倍率 |
| **洗练** | **做**：`affix_count` 默认 0/1/2/3，重 roll 未锁定词条，锁定加价 |
| **强化继承** | **做**：同部位，继承后 −2 级，消耗材料，不可逆 |
| **8 部位** | **做**：加披风 / 护符两槽，结构先就位、暂不投放 |
