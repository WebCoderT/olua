## 一、五个结构性问题

### 1.1 交易单位不明确

面对面交易卖什么？如果按 `id + count`，两件同名不同强化等级的装备无法区分（[24 篇](./24-装备重构设计.md) 已解决）。
**本篇统一以「容器里的一个格子」为交易单位**：格子里是什么就交易什么，装备格子带 `instId`。

### 1.2 没有托管（escrow），离线交易就不可能

摆摊与拍卖行的卖家会下线。物品必须**离开卖家背包**进入「托管」，否则卖家可以一边挂着卖、
一边把东西穿身上 —— 成交时物品已经不在，买家付了钱拿不到东西。

### 1.3 没有流水，税与手续费无处可记

5% 税必须记成「绑定元宝销毁」（sink），否则经济总量算不平。

### 1.4 商城的 3 件商品没有限购 / 库存 / 时间窗

✅ **限购与库存已落（#846）**：`daily_limit` / `stock` 两列 + 两张运行时计数表 + 两个新错误码
（见 §2.7）。时间窗（`on_shelf_at` / `off_shelf_at`）仍然没有 —— 运营要做「限时特惠」时再开，
在此之前把 `stock` 改成 0 也能立刻停售（比下架轻，不丢配置）。

### 1.5 没有防刷与门槛

不设门槛的话，工作室开小号刷初始资源再交易给大号。网络游戏的常规做法：
**交易有等级门槛 + 新号有冷却 + 同 IP 频繁交易告警**。

## 二、目标形态

### 2.1 三种形态的分工

| 形态 | 谁在线 | 成交方式 | 卖家收货 | 适用 |
|---|---|---|---|---|
| **面对面** | 双方都在线 | 两人锁定后原子提交 | 直接入包 | 朋友间换东西、送人 |
| **摆摊** | 卖家在线（挂机摆摊） | 买家点了就成交（固定价） | 直接入包 | 站街卖货，有讨价感 |
| **拍卖行** | 双方都不用到场 | 一口价即时 / 竞价到期成交 | **走邮件** | 大宗流通、离线卖货 |

### 2.2 面对面交易：状态机

```
invite ──accept──> open ──双方各放物品/钱──> 一方 lock ──> 另一方 lock ──> committed
  │                  │                          │              │
  └──reject/cancel───┴────── 任一方 unlock ─────┘              └── 任一方离图/下线 ──> aborted
```

| 规则 | 内容 |
|---|---|
| 双方 | 必须同图、同一 room、都在线、都满足交易门槛 |
| 锁定 | 锁定后**不能再改**自己的那一侧；要改必须先 unlock（对方会自动解锁） |
| 提交 | 双方都 `locked` 后，由**发起方**点「确认交易」→ 服务端原子提交 |
| 原子性 | 一次事务内：扣 A 的物/钱 + 加 B 的物/钱 + 扣 B 的物/钱 + 加 A 的物/钱；任一步失败全回滚 |
| 超时 | 会话 120 秒无操作自动 abort（防止挂着的会话占内存） |
| 距离开 | 任一方移动超过 `trade_range`（默认 300px）→ abort |

### 2.3 摆摊 ⚠ 已被 C5 推翻（暂放，正文留作以后方案）

| 项 | 规则 |
|---|---|
| 开摊 | 需在安全区、非战斗、等级 ≥ `trade_min_level` |
| 格数 | 一个摊位最多 `stall_slots`（默认 8）格货物 |
| 定价 | 每格独立定价，货币只能是绑定元宝（绑定元宝交易走拍卖行） |
| 浏览 | 按地图列出所有摊位（同图可见），点开看货 |
| 成交 | 买家点某格 → 扣钱 → 物品入买家包 → 卖家收钱（**直接入包，卖家在线**） |
| 下架 | 卖家手动收摊，剩余物品回包；**背包满则拒绝收摊**（不是丢地上） |
| 离线 | 卖家掉线 → 摊位保留 `stall_keep_ms`（默认 5 分钟）后自动收摊，货物走邮件 |

### 2.4 拍卖行 ⚠ 已被 C2/C5 推翻（绑定元宝不可流通 → 竞价不成立）

| 项 | 规则 |
|---|---|
| 挂单 | 物品进**托管**（离开背包），生成一条 `trade_orders`（`kind='auction'`） |
| 定价 | 一口价必填；起拍价可选（有起拍价则允许竞价） |
| 时长 | 12 / 24 / 48 小时三档（`auction_durations`） |
| 搜索 | 按 `item_id` / 类型 / 等级区间 / 价格区间；**分页 20/页** |
| 成交 | 一口价：立即扣买家钱 → 物品入包（背包满则**入邮件**）；竞拍：到期最高价成交 |
| 卖家收款 | **走邮件**（离线也能收到），扣 5% 税 |
| 超时 | 无人买 → 到期后物品走邮件退回（**不是删除**） |
| 手续费 | 挂单费（默认 0，可配 `auction_listing_fee`）；成交税 5% |

**为什么卖家收款走邮件**：拍卖行是异步的，成交时卖家可能在睡觉。直接入包要求
「卖家在线且背包有空间」，两个条件都不满足时就只能丢地上 —— 那是最糟的结果。

### 2.5 5% 税的实现 ⚠ 已被 C6 推翻（交易免费，无税基）

```
tax   = floor(price × 0.05)
sellerGot = price − tax
tax 记 economy_log(kind='trade_tax', delta=-tax, reason='sink')   // 销毁，不进任何人钱包
```

- 税**只对成交收**，挂单与取消不收（否则玩家不敢挂）；
- 税是**绑定元宝 sink**，与「商城买东西」一起构成两个主要回收口；
- 面对面交易**也收税**（否则所有交易都会绕到面对面去避税）—— 这一点必须写进 UI 提示。

### 2.6 货币与物品流水 `economy_log`

这是 [21 总表](./21-系统差距总表.md) 的横切线 T2，本篇先落地，后面 04 / 11 / 12 篇复用。

```sql
CREATE TABLE economy_log (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  role_id     TEXT    NOT NULL,          -- 谁的账（税记卖家）
  currency    TEXT    NOT NULL DEFAULT '',-- bindGold / 空 = 物品
  delta       INTEGER NOT NULL,          -- 正=获得 负=消耗
  balance     INTEGER NOT NULL,          -- 记账后余额（对账用）
  kind        TEXT    NOT NULL,          -- kill / recycle / mall / enhance / trade / trade_tax / mail / admin
  ref_id      TEXT    NOT NULL DEFAULT '',-- 关联单号（订单/流水 id）
  reason      TEXT    NOT NULL DEFAULT '',
  at          INTEGER NOT NULL
);
CREATE INDEX idx_econ_role_at ON economy_log(role_id, at);
CREATE INDEX idx_econ_kind_at ON economy_log(kind, at);
```

**对账口径**（每月跑一次）：

```sql
-- 全服绑定元宝总量变化 = Σ所有绑定元宝 delta（含税为负）
SELECT kind, sum(delta) FROM economy_log WHERE currency='bindGold' GROUP BY kind;
-- 与钱包总和比对
SELECT sum(...) FROM roles  -- 按 data.money 汇总
```

两条必须相等，否则说明有绕过流水的写入点（这是流水表存在的唯一意义）。

### 2.7 商城扩写

`mall_goods` 加 5 列（**不加 `currency`**：C1 之后全局只有 `bindGold`，计价货币不是运营选项）：

| 列 | 用途 | 落地 |
|---|---|---|
| `daily_limit` | 每日限购（0 = 不限），**按角色计**（见 §2.7.0） | ✅ #846 |
| `stock` | 全服库存（-1 = 不限量，0 = 立刻停售） | ✅ #846 |
| `total_limit` | 总限购（0 = 不限） | 暂时放置（重开条件：运营要「一生只能买一次」的礼包） |
| `on_shelf_at` / `off_shelf_at` | 上架时间窗（0 = 一直） | 暂时放置（重开条件：运营要做「限时特惠」） |
| `max_stack` | 单次购买上限 | 暂时放置（重开条件：出现「一次买 99 瓶药」的诉求，现在连点几次结果一样） |

购买时服务端校验：时间窗 → 库存 → 限购 → 货币 → 背包空间。
顺序不能改：**先校验再扣钱**，否则会出现「扣了钱没货」。

已落的实现里顺序是 **等级 → 库存占位 → 限购占位 → 余额 → 入包**，且全部在**同一个事务**内
（`MallRepository.transaction()`）：任何一步失败（背包满 20012 / 乐观锁 20006）都会把已占的
库存与今日名额一起退回去 —— 否则一次失败购买白吃一个名额，限量款会被空转吃光。

#### 2.7.0 限购为什么按角色、不按账号（已定 2026-11-10）

原设计写的是「按 `account` 计，防止开小号」，落地按的是 **`role_id`**：

- **钱包本身是按角色的**（`bindGold` 存在角色存档里）。账号级限购 + 角色级钱包会造出
  「A 角色买满，B 角色自己有钱却不让买」这种没人能向玩家解释的状态；
- 「一人多角色」在当前设计里是正常玩法，不是作弊路径 —— 每个角色独立成长线。

**防小号（同 IP 多账号刷限量款）暂时放置**，重开条件是：① 玩家间交易上线（现在买到的东西
没有转移出口，小号刷了也只能自己用）；② 出现真实的工作室刷货案例。届时按「账号 + IP」两个维度
一起限，而不是只把计数键从 `role_id` 换成 `account_id`。

#### 2.7.1 定价不变式（#814 已落地）

| 约束 | 为什么 |
|---|---|
| **售价 ≥ 1** | 售价 0 + 回收价 > 0 = 无限买 → 无限卖，玩家不用改包，点两次按钮就能印钞 |
| **回收价 ≤ 售价 × 50%** | 只要买价 ≤ 卖价就有正收益；压到一半，买进卖出永远净亏 |
| 两条同时生效 | 只压回收价（价 0 / 回收 0）不产绑定元宝但不拦漏配；只抬售价（价 1 / 回收 1）仍然不亏 |

落地位置：**配置期**（上架 / 改价，`MallPricingService.ensurePriceSane`）先拦，**购买入口**再拦一次（兜 `config-import` 与直接改库造出来的历史脏行）。越界统一 `409 / 50045`。

不在结算时夹取回收价：`sell_price` 列同时是客户端展示的价签与结算依据，夹取会让「看到 100 实得 50」——那正是 #545 修掉的病。
推论要提前知道：售价 1 的商品 `floor(1 × 50%) = 0`，也就是**卖不掉**；想让某件能回收 20，售价至少 40。

### 2.8 邮件索要（本轮纳入）

「我看上你这件装备了，出个价」—— 让对方付费寄过来，避免约时间面对面。

| 项 | 规则 |
|---|---|
| 发起 | A 对某件物品发起索要：填**出价**与有效期（12/24 小时），消耗一封邮件位 |
| 通知 | 走邮件通知物主（离线也能看到） |
| 处理 | 物主「接受」→ 物品进托管 → 生成一条 `trade_orders(kind='request')` → 买家付款 → 成交（**同样抽 5% 税**） |
| 拒绝 / 超时 | 索要失效，**不收任何费用**（不鼓励刷索要） |
| 防打扰 | 同一对角色 24 小时内最多 3 次索要；`role_blocks` 里的人不能发起 |
| 为什么也算交易 | 不抽税的话，面对面 + 索要就成了避税通道；税率必须与其它形态一致 |

### 2.9 玩家间绑定元宝交易 ⚠ 已作废（货币不参与流转，见 C1）

| 项 | 规则 |
|---|---|
| 范围 | **只在拍卖行**支持绑定元宝计价；面对面与摆摊只收绑定元宝（现场交易容易被诱导诈骗） |
| 税 | 绑定元宝交易抽 **8%**（高于绑定元宝的 5%，因为它是真实货币等价物，要更强抑制） |
| 汇率 | **不设官方汇率**（不提供绑定元宝↔绑定元宝兑换），否则等于变相卖金 |
| 上限 | 单笔绑定元宝上限 `yuanbao_trade_cap`（默认 10000），超出拒 |
| 风控 | 绑定元宝交易全部记 `economy_log(currency='yuanbao')`，且单账号每日成交额超阈值 → 告警 |
| 合规 | 绑定元宝由商城充值获得，玩家间转移不产生新绑定元宝（总量守恒由 `economy_log` 对上） |

> 绑定元宝交易是**风险最高的一块**（涉及真实货币）。上面五条里，「只在拍卖行」「不设汇率」
> 「单笔上限」三条是硬约束，不能为了体验放宽。

### 2.10 防刷与门槛

| 机制 | 默认 |
|---|---|
| 交易门槛 | 角色等级 ≥ **10**（C6）且**同一张图**、非战斗态 |
| 新号保护 | 建号 7 天内**只能收不能发**（防「小号刷资源给大号」） |
| 绑定物品 | 不可交易（`bound=1` 直接拒） |
| 自交易 | 不能与自己交易 / 买自己的挂单（服务端拦） |
| 频率告警 | 同一 `account` 每小时成交 > 30 笔 → 记 `trade_suspect` 事件（不拒，只标记） |
| 同 IP | 不做硬拦（会误伤网吧/家庭），只做统计告警 |

### 2.11 货币收敛：只有 `bindGold` 一种（C1；2026-11-11 已落 #843/#844）

> 落地口径与 C1 原表有三处不同（用户 2026-11-11 拍板）：**不迁移、直接删字段**（存量余额作废，
> 见 33 篇 3.4）；**旧币种货币道具行直接删除、不做兼容**；UI 名称就叫**绑定元宝**（不做其他简称）。

| 项 | 规则 |
|---|---|
| 字段 | 存档只留 `bindGold`；其余货币字段**从代码层面整体移除**（存档 / 协议帧 / DTO / 客户端类型），存量余额不迁移（作废） |
| 显示 | 全服统一叫**绑定元宝**（与字段同名） |
| 能花在哪 | 商城购买、装备回收的反向（卖店入账）、三条成长线、时装 |
| 能从哪来 | 打怪掉落、卖店回收、任务/成就、邮件、管理端补发 |
| 边界 | **货币不参与玩家间任何流转**（C2）：交易无货币栏、邮件不带货币、无邮寄绑定元宝、无红包 |
| 货币道具 | `money_items` 里旧币种的 16 条**行直接删除**（启动时 `purgeLegacyMoneyItems` 清理）；出厂只种 bindGold 8 档；已持有的格子变死道具（使用 20023） |
| 对账口径 | （economy_log 尚未建表；重建时以 `currency='bindGold'` 单币种记账） |

> **为什么不再设第二种货币**：其余两条货币账本一条只有收入没有支出（B22）、一条零产出零消耗（B23），都在空转。
> 更关键的是——只要留一种「可流通货币」，拍卖行与抽税就必然复活，而它需要支付、退款、对账、反洗钱一整套，
> 当前项目一件都没有。收敛成一种，等于把这条风险线整体拿掉。

## 三、数据模型

> **本版只建两张表**（C5：只做面对面以物易物）：
> `trade_sessions`（交换会话）+ `economy_log`（流水）。
> 下面 `trade_orders` / `trade_bids` 两张表**暂放不建**，等摆摊或拍卖行重开时再按原文建。

```sql
-- 面对面会话（内存为主，落库只为崩溃恢复与审计；每小时清一次）
CREATE TABLE trade_sessions (
  id          TEXT PRIMARY KEY,          -- t<seq>
  role_a      TEXT NOT NULL,
  role_b      TEXT NOT NULL,
  zone_id     TEXT NOT NULL,
  map_id      TEXT NOT NULL,
  status      TEXT NOT NULL,             -- open / locked_a / locked_b / committed / aborted
  offer_a     TEXT NOT NULL DEFAULT '[]',-- JSON: [{instId|id, count}]
  offer_b     TEXT NOT NULL DEFAULT '[]',
  created_at  INTEGER NOT NULL,
  expire_at   INTEGER NOT NULL
);

-- 挂单（摆摊与拍卖行共用一张表）
CREATE TABLE trade_orders (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  kind          TEXT    NOT NULL,        -- stall / auction
  seller_role_id TEXT   NOT NULL,
  zone_id       TEXT    NOT NULL,
  map_id        TEXT    NOT NULL DEFAULT '',  -- 摆摊才有
  item_inst_id  TEXT    NOT NULL DEFAULT '',
  item_id       TEXT    NOT NULL,
  count         INTEGER NOT NULL DEFAULT 1,
  price         INTEGER NOT NULL,        -- 一口价
  start_price   INTEGER NOT NULL DEFAULT 0,
  currency      TEXT    NOT NULL DEFAULT 'bindGold',
  status        TEXT    NOT NULL,        -- active / sold / cancelled / expired
  buyer_role_id TEXT    NOT NULL DEFAULT '',
  sold_price    INTEGER NOT NULL DEFAULT 0,
  tax           INTEGER NOT NULL DEFAULT 0,
  created_at    INTEGER NOT NULL,
  expire_at     INTEGER NOT NULL
);
CREATE INDEX idx_orders_kind_status ON trade_orders(kind, status, expire_at);
CREATE INDEX idx_orders_item ON trade_orders(item_id, status);

-- 竞价（只有拍卖行且设了 start_price 才有）
CREATE TABLE trade_bids (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  order_id    INTEGER NOT NULL,
  bidder_role_id TEXT NOT NULL,
  amount      INTEGER NOT NULL,
  at          INTEGER NOT NULL
);
CREATE INDEX idx_bids_order ON trade_bids(order_id, amount DESC);
```

**商城计数的两张运行时表（已落 #846）**：

```sql
CREATE TABLE mall_sales (            -- 每角色 · 每商品 · 每天最多一行
  role_id  TEXT NOT NULL, good_id TEXT NOT NULL, day INTEGER NOT NULL,
  count    INTEGER NOT NULL DEFAULT 0, updated_at INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (role_id, good_id, day)
);
CREATE TABLE mall_stock (            -- 每商品一行，只记分子
  good_id TEXT PRIMARY KEY, sold INTEGER NOT NULL DEFAULT 0, updated_at INTEGER NOT NULL DEFAULT 0
);
```

两张都**不进快照、不进 `config-sync.sql`**：配置只有 `daily_limit` / `stock`，销量本来就该各机器不同
（写进同步文件等于「别人的销量盖掉我的」）。字段语义、条件自增写法与清理策略见
[15-数据表清单](./15-数据表清单.md) §5.8。

**托管怎么表示**：挂单时把 `item_instances.owner_role_id` 改成 `'market'`，并从卖家背包格子里移除。
这意味着**容器守恒断言要容忍 `market` 这个「影子持有者」** ——
总账公式改成「背包 + 仓库 + 装备 + 邮件 + **托管**」，否则一挂单就被判不平衡。

## 四、接口

| 接口 | 方法 | 说明 |
|---|---|---|
| `/trade/sessions` | POST | 发起面对面（`toRoleId`） |
| `/trade/sessions/:id/offer` | POST | 放物品（`{instId?, id?, count}`） |
| `/trade/sessions/:id/lock` | POST | 锁定自己那侧 |
| `/trade/sessions/:id/commit` | POST | 提交（仅发起方，双方都 locked 时有效） |
| `/trade/sessions/:id` | DELETE | 取消 |
| `/stalls` | POST / DELETE | 开摊 / 收摊 |
| `/stalls/:id/orders` | POST | 摆摊加货（物品进托管） |
| `/stalls/:id/orders/:oid/buy` | POST | 买摆摊的一格 |
| `/auction/orders` | GET | 搜索（分页/筛选） |
| `/auction/orders` | POST | 挂单 |
| `/auction/orders/:id/buy` | POST | 一口价买 |
| `/auction/orders/:id/bid` | POST | 出价 |
| `/auction/orders/:id` | DELETE | 撤单（仅无出价时可撤） |

**全部走 HTTP**：交易改的是 `roles.data`（钱与物品），必须走乐观锁。
实时帧只负责**通知**（新挂单 / 摊位开张 / 好友成交），不承载事务。

## 五、分刀

| 刀 | 内容 | 规模 | 前置 |
|---|---|---|---|
| ① | `economy_log` + 所有既有收支点接入（击杀/回收/商城/邮件） | 中 | 无 |
| ② | 面对面交易（会话 + 锁定 + 原子提交） | 大 | 25 篇②、24 篇① |
| ③ | 摆摊（托管 + 浏览 + 成交 + 收摊） | 中 | ② · **暂放（C5）** |
| ④ | 拍卖行（挂单 + 搜索 + 一口价 + 超时退回） | 大 | ③ · **暂放（C5）** |
| ⑤ | 竞价（`trade_bids`） | 中 | ④ · **暂放（C5）** |
| ⑥ | 商城扩写 —— **限购 + 库存已落（#846）**；时间窗 / 总限购 / 单次上限暂放（重开条件见 §2.7） | 小 | ✅ 已收（购买流水走 #886 的 `event_logs`） |
| ⑦ | 防刷与门槛（等级、建号时长、告警） | 小 | ② |
| ⑧ | 邮件索要（`kind='request'` 订单 + 通知 + 接受/拒绝） | 中 | ②④ |
| ⑨ | ~~绑定元宝交易~~ | — | **作废（C1：货币不参与流转）** |

**① 必须最先做**：它是后面所有刀的「对账基础设施」。先做交易后做流水，等于先花钱后记账。

## 六、边界情况

| # | 情形 | 期望 |
|---|---|---|
| 1 | 面对面时一方离图/下线 | abort，双方物品与钱**都不变**（本来就没提交） |
| 2 | 一方 lock 后另一方 unlock | 先 lock 的自动 unlock（要重新确认） |
| 3 | 双方同时点 commit | 乐观锁拦一次 |
| 4 | commit 时 A 的钱不够了（并发花掉） | 整体回滚，返回 `not_enough_money` |
| 5 | commit 时 B 的背包满了 | 整体回滚，返回 `bag_full`（**不能只给一边**） |
| 6 | 交易中放入绑定物品 | 拒（`bound_no_trade`） |
| 7 | 交易中放入托管中的物品 | 拒（`item_in_escrow`） |
| 8 | 交易金额为 0 且物品为空 | 拒（`empty_trade`） |
| 9 | 摆摊时背包满 | 拒开摊 |
| 10 | 收摊时背包满 | 拒收摊（货物留在托管，提示「请先腾空背包」） |
| 11 | 摆摊中卖家掉线 | 保留 `stall_keep_ms`（5 分钟）→ 自动收摊 → 货物走邮件 |
| 12 | 摆摊中有人正在买，卖家收摊 | 服务端串行：收摊会先完成/回滚进行中的购买 |
| 13 | 拍卖行挂单后物品被穿上 | 不可能（已在托管，不在任何容器里） |
| 14 | 拍卖行成交时买家背包满 | **入邮件**（不失败、不丢地上） |
| 15 | 拍卖行成交时卖家已删号 | 货款发给「同账号其他角色」；无其他角色则留在托管户（记 `orphan` 供人工处理） |
| 16 | 竞价中有人出价后又有人一口价买走 | 一口价优先，所有竞价作废，押金（若有）退回 |
| 17 | 出价低于当前最高价 | 拒（`bid_too_low`） |
| 18 | 出价后想撤 | 允许撤自己的最高价，价格回落到上一档（需要保留全部出价记录，不能只留最高） |
| 19 | 撤单时已有出价 | 拒（`has_bids`） |
| 20 | 挂单超时那一刻有人正在买 | 服务端串行：以「先到的事务」为准，另一个返回 `already_sold` / `expired` |
| 21 | 税算出 0（价格 < 20） | 允许，记 `tax=0`（不要四舍五入到 1，否则小额交易被吃光） |
| 22 | 面对面也收 5% | 收，且 UI 要显式提示「本次交易将扣税 N 金」 |
| 23 | 交易双方同账号不同角色 | 拒（`same_account`） |
| 24 | 交易自己 | 拒 |
| 25 | 商城购买时刚好库存卖完 | 拒（`out_of_stock`），不扣钱 |
| 26 | 商城限购按账号还是角色 | **按账号**（防小号刷限购） |
| 27 | 商城时间窗到期瞬间购买 | 以服务端时间为准，早 1ms 也拒 |
| 28 | 托管物品的孤儿清理 | 每天扫「`owner_role_id='market'` 但没有任何 active 订单」的实例 → 记 warn 并退回原主（原主不明则保留） |
| 29 | 经济总量对不上 | `economy_log` 与钱包总和不相等 → 每日告警（这是唯一能发现「绕过流水的写入」的手段） |
| 30 | 税率改动 | 只影响新成交（成交时把税率写进 `trade_orders.tax`，不回溯） |

## 八、验收

| 用例 | 断言 |
|---|---|
| `e2e-trade-atomic` | A 放装备、B 放 100 金 → 提交 → 双方物品互换且绑定元宝差值 = 100 − 税 |
| `e2e-trade-rollback` | B 背包塞满 → 提交 → 双方**零变化**，返回 `bag_full` |
| `e2e-trade-swap` | A 给 1 件、B 给 2 件 → 双方确认后物品互换，`economy_log` 记两条 `trade_out` / `trade_in`，**无税记录** |
| `e2e-trade-bound` | 放绑定装备 → `bound_no_trade` |
| `e2e-stall-escrow` | 开摊加货 → 背包少一件、托管多一件、四容器总账不变 |
| `e2e-stall-buy` | 买一格 → 买家得到物品、卖家收到钱 − 税 |
| `e2e-auction-mail` | 成交时买家背包满 → 物品进邮件；卖家离线 → 货款进邮件 |
| `e2e-auction-expire` | 挂单超时 → 物品退回卖家邮件（不是删除） |
| `e2e-econ-balance` | 任意 200 次随机经济操作后，`economy_log` 汇总 == 钱包总和 |
| `e2e-mall-limit` | 当日第 N+1 次购买 → `limit_reached`；换角色同账号 → 仍拒 |

手工验收：面对面交易要能清楚看到「对方锁定了/改了物品」；摆摊招牌上能看到货名与价格；
拍卖行搜索结果按价格排序正确；所有扣税的地方都有明确提示。

## 九、暂时放置（含重开条件）

| 项 | 现在的口径 | 重开条件 |
|---|---|---|
| 跨服 / 跨区交易 | 与单区服模型冲突 | 有第二个区且实现了跨区世界服务时 |
| 账号级仓库与跨角色转移 | 打破「一个角色一个容器」的守恒断言 | 引入「账号钱包 + 角色背包」两段式重构时 |
| 拍卖行「推荐价」 | 需要历史成交统计 | `trade_orders` 积累 ≥ 90 天成交数据后 |
| 交易行脚本风控（自动封号） | 只做告警，不自动处置 | 有明确申诉流程与误封兜底机制时 |
| 官方货币兑换（多币种之间） | 只有 `bindGold` 一种，无兑换 | 出现第二种货币且需要互通时 —— 但「可提现货币」永久是合规红线 |
| 摆摊 / 拍卖行 / 竞价 | 暂放（C5：绑定元宝不可流通，竞价与抽税没有成立条件） | 面对面以物易物跑稳一个版本、且玩家确有「挂单等人来买」的诉求时 |

## 十、已定参数

| 项 | 结论 |
|---|---|
| 形态 | **面对面 + 摆摊 + 拍卖行**（三种全做） |
| 税 | 成交价 **5%**，卖家承担，绑定元宝销毁（sink），面对面也收 |
| 门槛 | 等级 ≥ 20、建号 ≥ 24h、建号 7 天内只能收不能发 |
| 摆摊格数 | 8 格，离线保留 5 分钟 |
| 拍卖时长 | 12 / 24 / 48 小时 |
| 卖家收款 | 走邮件 |
| 流水 | `economy_log` 覆盖所有收支，每月对账 |
| 货币 | 全局**只有 `bindGold` 一种**（C1）；交易免费、无税、无货币栏（C2/C6） |
| 邮件索要 | **做**：出价 + 12/24h 有效，接受后进托管，同样抽 5% 税；同对角色 24h 内最多 3 次 |
