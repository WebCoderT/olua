# 01 · 总览与架构

> 这份文档回答三个问题：**这套代码由哪几块组成**、**数据在它们之间怎么流动**、**出问题时先看哪里**。
> 具体领域（装备 / 背包 / 战斗 / 世界 / 成长 / 社交）各自有一篇，见 [README](./README.md) 的目录。

---

## 一、这是什么

一款 2D 像素风 MMO 手游（Cocos Creator 客户端 + Web 管理端 + 单机可跑的服务端），
玩法骨架是「经典传奇式」：选图刷怪 → 掉装备 → 穿戴变强 → 打更强的图。

代码仓库是**三个平级子工程**，各自能独立构建、独立跑：

| 子工程 | 目录 | 技术栈 | 产物 | 谁在用 |
|---|---|---|---|---|
| 服务端 | `server/` | NestJS 12 + `node:sqlite` + JWT + Swagger | `dist/`（两个入口：存档进程 / 实时进程） | 客户端与管理端都只通过 HTTP / WS 访问它 |
| 游戏客户端 | `client/` | Cocos Creator 3.8.7 + TypeScript | Web / 原生包 | 玩家 |
| 管理端 | `admin/` | React 19 + Vite + Tailwind v4 | 静态站点（nginx 托管） | 运营 / GM |

仓库根只放：总 `README` / `FAQ`、跨端 `tools/`（审计脚本 + 接口生成器）、`Makefile`（唯一命令入口）、
`docker-compose.yml`（一键起）、`deploy/`（远端部署脚本）、`docs/`（本文档）、`website/`（官网，**永不改动**）。

## 二、进程拓扑

```
                        ┌─────────────────────────────┐
        浏览器 / 原生包  │  玩家：Cocos 客户端           │
                        └──────────┬──────────────────┘
                                   │ HTTP /api/*   +   WS /api/realtime
                        ┌──────────▼──────────────────┐
        运营浏览器        │  admin 容器（nginx :80）      │
        （管理端 SPA）    │  ├─ /            → 管理端静态 │
                        │  └─ /api/*       → server    │
                        └──────────┬──────────────────┘
                                   │
              ┌────────────────────┼─────────────────────┐
              │                                          │
   ┌──────────▼───────────┐                   ┌──────────▼──────────────┐
   │ 存档进程 server:3100  │                   │ 实时进程 realtime:3101   │
   │  · 鉴权 / 角色 CRUD   │                   │  · WS 通道 + 心跳        │
   │  · 配置读写 / 管理端   │                   │  · 世界权威（怪物实例）   │
   │  · 邮件 / 任务 / 成就  │                   │  · 伤害结算 / 掉落 / AI  │
   │  · 排行榜 / 静态数据   │                   │  · 在场表 / 聊天 / 队伍   │
   └──────────┬───────────┘                   └──────────┬──────────────┘
              │                                          │
              └────────────► SQLite（WAL，同一文件）◄──────┘
                        server/data/olua.db
```

三条与部署强相关的口径（细节见 [13-部署运维与质量门禁](./13-部署运维与质量门禁.md)）：

- **实时进程可以内嵌**（默认 `REALTIME_EMBEDDED=true`，单进程跑两个角色）也可以**独立进程**
  （`main.realtime.ts`）。独立形态下两进程**唯一的通信方式是共享 SQLite**，没有第二条 RPC 通道——
  所以「实时进程里的东西要给管理端看」只能靠**投影落库**（`map_monitor_state` / `map_monitor_events`）。
- **接口端口不对外**，只由 nginx 反代；`/api/realtime*` 按路径反代到 3101（含 WS upgrade）。
- 反代之后服务端必须 `TRUST_PROXY=true`，否则 `req.ip` 全是 nginx 地址，登录限流的 IP 维度会把全服当一个人锁死。

## 三、谁说了算：四层权威

整个项目最容易被写错的地方，是把**不同种类的东西**当成一种。权威归属是这样的：

| 层 | 内容 | 权威在哪 | 客户端能不能改 |
|---|---|---|---|
| ① 游戏数据（数值 / 文案 / 素材路径 / 掉落 / 地图玩法） | 装备、物品、怪物、技能、称号、曲线、掉落表、地图门槛… | **数据库**（`server/data/olua.db`，出厂快照 `config-sync.sql`） | 不能。只能读快照 |
| ② 玩家状态（等级 / 经验 / 三货币 / 背包 / 穿戴 / 战斗力 / 八项属性） | 角色存档 | **服务端**（`roles` 表 + 服务端算子） | 不能。只能发「意图」等结果 |
| ③ 玩家表现态（血量 / 蓝量 / 位置 / 外观缓存 / 引导进度 / 快捷键） | 客户端本地 | **客户端**（有意留白，见下） | 能 |
| ④ 世界状态（怪物实例 / 血量 / 存活 / 重生） | 实时进程内存 + `world_monsters` 落盘 | **实时进程** | 不能。客户端只是表现层 |

第 ③ 层不是「还没做完」，而是**有意留白**：`hp` / `mp` 的自然回复、`onMap`、外观、快捷键、引导进度
都在客户端；要收权必须先补一套服务端 tick 与接口（`level` / `exp` 已经收回了，`hp` / `mp` 没有）。
判断标准写在 `server/src/modules/roles/role-authority.ts`，由 `tools/audit-role-authority.cjs` 守着。

## 四、五条不变量（改代码前先确认没破）

1. **服务端算，客户端演。**
   伤害、经验、掉落、战力、属性、回收价、使用道具的效果，全部在服务端算完再下发。
   客户端里出现 `calcSkillDamage` / `rollDropTable` / `spawnByAreas` / `static hurt(` 一律被
   `tools/audit-world-authority.cjs` 判红。

2. **一份数据只有一个来源。**
   数值只在库里；接口路径只在 `openapi.json` → 生成物；地址只在 `configs/network.ts`（客户端）与
   `admin/.env`（管理端）；文案 key 只在 `configs/texts.ts`。复制一份就是下一次「改了没生效」。

3. **契约单向生成。**
   `server`（控制器 + DTO + 装饰器）→ `server/openapi.json` → `tools/gen-api.cjs` → 客户端 `Api*.ts`
   与管理端 `routes/models/endpoints.ts`。**顺序不能反**，手改生成物会被 `audit-api-generated` 拦下。

4. **存量库靠 `ensureColumn` 演进。**
   加列一律在 `DatabaseService.migrate()` 里补，并且**追加在建表语句最后一列**——
   存量库是 `ALTER TABLE ADD COLUMN` 补出来的，列序不同会让 `SELECT *` 导出产生整份假 diff。

5. **配置进内存，改完要重启。**
   `RuntimeConfigService` 与实时进程各持一份内存副本；`make config-import` / 管理端保存之后，
   **进程不重启就还在用旧值**（实时侧的怪物 AI 用 1 秒 TTL 缓存，属于例外）。

## 五、一条主链路的全景（打怪掉装备）

先给一条能串起全部模块的线，后面每一篇都是它的放大：

```
① 进游戏
   Loading 场景 → ConfigLoader.loadGameConfig()
        ├─ GET /game-config             （快照 30 段，进程内只拉一次）→ configs/apply-snapshot
        ├─ GET /game-config/equip-align      （每次进图）
        ├─ GET /game-config/equip-in-align   （每次进图 + 每次开角色信息弹窗）
        └─ GET /game-config/equipment-appearance（每次进图）
   Login → RoleSelector → RoleApi.select(id) → StorageManager.cacheServerRole + onlineRole → Game 场景

② 进图
   CombatChannel.requestMapEnter(mapId)  → mapEnterResult（服务端判等级 / 战力 / 战魂阶）
   放行 → 切场景 → CombatChannel.sendWorldJoin(mapId)
   服务端：world.join() 按 map_spawn_areas 播种怪物实例 → world 帧下发全量

③ 出手
   客户端 cast{castId, skillId, targetId, monsterKey}
   服务端 settle：
     取角色存档 → summarizeRoleAttributes（等级曲线 + 装备 + 称号 + 战魂 + 军衔）
     → 技能伤害系数（skills.damage_coefficients[等级-1]）
     → damage = round(攻击区间随机 × 倍率 − 怪物防御区间随机 × 状态倍率)，下限 0
     → world.applyDamage → 死亡判定

④ 击杀（同一笔结算里）
   经验   = round((怪物等级+1) × expPerLevel × (1 − 等级差/maxLevelGap))，差距过大给 0
   击杀数 roles.kills +1（排行榜原料）
   掉落   = rollDrops(monsterKey)：monster_drops → 具名表 / 内联条目 / 兜底 default
            每个条目再过一遍**绑定判定**（物品强制 / 怪物强制 / 随机概率）
            装备额外带**溯源**（击杀者名 / 怪物 key / 时间戳）
   账本   dropLedgers[castId] = [{goodId, count, bound, from, picked:false}]
   事件   emit monster:killed → 任务进度 / 成就进度 / boss 邮件 / 地图监控

⑤ 拾取
   客户端 pick{castId, index}
   服务端：查账本 → 原子入包（addGood 会按 (bound,id) 分堆）→ 写 bound/from
   → picked 帧回 {placed:[{row,col,id,count,bound,from}]}

⑥ 穿戴
   客户端 equipFromBag → POST /roles/:id/bag-op {action:"equip", row, col, revision}
   服务端：查部位（equipments.slot）/ 等级门槛（equipment_variants.level）/ 换下的旧件回包
        → applyAuthoritativeAttributes（重算八项 + 战力）→ clampVitals（血蓝夹回上限）
        → 返回整份 bag / equipments / combat / maxHp … / revision
   客户端：整份抄回 + updateUi；RoleSync 防抖把改动推存档（撞 20006 则拉最新）

⑦ 展示
   装备详情弹窗：读 bag 格子 → configs/items.bagMetaOf → 「已绑定 · 不可交易」+ 三行溯源
   战力：服务端算的那个数，客户端不自己加总
```

## 七、排障入口（症状 → 先看哪）

| 症状 | 第一嫌疑 | 查法 |
|---|---|---|
| 管理端改好了，客户端还是旧的 | 该数据走的是**快照**（只拉一次）而不是每次进图拉 | 见 [02](./02-数据与配置体系.md) 的「两条下发通道」 |
| 管理端改好了，服务端伤害没变 | 服务端读到的是内存投影，进程没重启 | 重启 server 与 realtime |
| 面板战力与伤害对不上 | 有一处自己加总了属性 | 只允许 `summarizeRoleAttributes` 一个出口 |
| 背包整理报「与服务器不一致」 | 守恒判据 / 绑定态认领顺序 | 见 [06](./06-物品与背包.md) |
| 存档撞 20006 反复重试 | 客户端拿了旧 `revision` 基线 | `applyServerRevision` / `applyPartyExpGain` 有没有照抄 revision |
| 被踢下线后还能存档 | 只清了 `online_role_id`，没叠 `20007` 拒收 | `RolesService.save` 两道判定顺序 |
| 掉率为 0 或掉落是空的 | `monster_drops.source` 三态 / 兜底表 `default` 缺失 | 见 [05](./05-装备链路.md) |
| 图里没怪 | 分域没有卸载，世界不会重新播种 | 换分域进图或重启实时进程 |
| 客户端一帧一条 `_uiProps` 报错 | 帧动画状态没停就销毁 | `AnimationHelper` 的 `stopTree` |

## 八、怎么跑起来

```bash
# 本机最小闭环
make install                       # 装两端依赖
make env                           # 生成 server/.env（JWT_SECRET / ADMIN_REGISTER_CODE 要自己换）
make dev                           # 服务端 3100 + 管理端 5173
make client-open                   # 用 Cocos Creator 打开 client/（首次要等导入）

# 一条命令验全（服务端编译 + 全部 e2e + 生成物审计）
make server-verify

# 门禁全景
make audit                         # 15 项跨端审计
make client-check && make client-test
make admin-build
```

首次启动时，空库会由 `bootstrapConfigSnapshot()` 把 `server/data/config-sync.sql` 整表灌入——
**没有它就只有一个空库**，客户端进游戏会拿不到快照（停在 Loading）。
