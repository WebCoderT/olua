# 03 · 服务端与接口契约

> 服务端只做四件事：**鉴权**、**存档落库**、**产出接口契约**、**实时通道**（战斗/世界/聊天）。
> 它同时是「三端接口契约的唯一源头」——客户端与管理端的接口文件全部由它生成，**顺序不能反**。

本篇讲：模块划分、请求怎么进来、响应怎么出去、权限怎么判、契约怎么生成、加接口要做哪些事。

---

## 一、模块地图（26 个模块）

| 模块 | 职责 | 关键点 |
|---|---|---|
| `auth` | 玩家注册 / 登录 / 当前账号 | 登录限流（用户名 + IP 双维度）、登录审计、`token_version` 作废 |
| `roles` | 角色 CRUD + 存档写入 + **背包五动作** | 权威边界（`role-authority.ts`）、修订号乐观锁、踢下线拒收 20007 |
| `admin` | 管理端认证 / 账号 / 角色 / 管理员 | 权限点、重置口令、踢下线、批量删除 |
| `game-config` | **所有配置的读写 + 玩家快照** | 30+ 控制器的「配置面」，`ClientConfigService.snapshot()` 是玩家侧唯一出口 |
| `realtime` | WS 通道 / 伤害结算 / 怪物 AI / 在场 / 聊天 / 监控 / 泡点 / 屏蔽 | 1004 行 `realtime.service.ts` + 678 行结算 + 1153 行 AI |
| `world` | 世界权威：怪物实例、播种、tick 重生、空闲回收、dirty 落盘 | `world_monsters` 是状态表，重启可恢复 |
| `map` | 地图玩法配置 + 刷怪区 + NPC + 碰撞 + **进图门槛** | `enterRejectOf(mapId, {level, combat, soulOfWar})` |
| `combat` | 属性汇总（**唯一算法**，纯函数） | `summarizeRoleAttributes`：等级曲线 + 装备 + 称号 + 战魂 + 军衔 |
| `quest` | 任务：接取 / 交付 / 进度 | 三目标（talk / kill / collect）+ 日常重接 |
| `achievement` | 成就：累计型 / 状态型 | 达成与领取分离；背包满转邮件 |
| `leaderboard` | 三个榜（`level` / `combat` / `kills`） | 进程内物化，不落库 |
| `social` | 好友 / 敌人 / 屏蔽 / 举报 | 屏蔽必须服务端过滤，且**不下发「谁拉黑了我」** |
| `party` | 队伍 | 队伍落库、动作走 WS 帧、经验按各自等级差分 |
| `guild` | 帮会 | 建帮 / 申请审批 / 转让 / 解散级联 |
| `game-mail` | 游戏内收件箱（四个频道） | 附件领取才入包、未领不可删、一键领取不合并 |
| `mail` | **外发 SMTP** 投递队列 | 与 `game-mail` 无代码关系，别混 |
| `announcement` | 公告（含免令牌的「生效中」） | `enabled + starts_at + ends_at` 三列决定 |
| `audit` | 操作日志（只读两接口 + 拦截器） | 动作 = operationId，敏感字段递归打码 |
| `system` | 系统信息（运行时 / 表行数 / 脱敏配置） | 快照走白名单，密钥只报形态 |
| `zone` | 区服（开区 / 合并区） | 区是账号的归属分身，合并是重操作 |
| `audio-setting` | 音效 12 项 | 出厂行随 `AUDIO_DEFAULTS`，运营改过的行不动 |
| `ui-effect` | 升级特效 / 掉落光效参数 | 只许改不许增删 |
| `token` | JWT 签发与校验 | `aud = player / admin` |
| `health` | 健康检查 | 部署探针 |
| `game-mail` 之外还有 `mail` | — | 见上 |

**内部边界**（`tools/audit-server-boundaries.cjs`）：跨模块 import 只能走白名单边（`ALLOWED_EDGES`），
仓储只由全局 `DatabaseModule` 装配（业务模块 providers 里再注册同名仓储 = 第二个实例），
`combat/` 是纯函数库**不许引任何 modules 与 database**。加一条边 = 改白名单 = 有意识的决策。

## 二、一个请求怎么进来、怎么出去

```
HTTP 请求
  ↓ main.ts 装配
  ① ValidationPipe({ whitelist: true, transform: true })   ← 未声明字段直接剥掉
  ② AuthGuard          受众校验：aud 对得上吗？账号还在吗？token_version 对得上吗？
  ③ PermissionGuard    权限点校验（管理端；注册在 AuthGuard 之后，用 request.user.role）
  ④ AuditInterceptor   只审「管理端写方法」，action = operationId
  ⑤ 控制器 → service → repository → SQLite
  ↓
  统一响应包裹（ExceptionFilter / TransformInterceptor）
  { code: 0, message: "ok", data: <业务数据>, timestamp: 1699999999999 }
```

### 2.1 响应包裹与业务码

- **`code === 0` 才是成功**；HTTP 状态码照旧语义化（400/401/403/404/409/429/500），
  `code` 只表达「业务上发生了什么」，客户端据 code 决定提示与分支。
- 业务码共 **145 个**，按模块分段：

| 段 | 域 | 典型码 |
|---|---|---|
| `4xxxx` | 通用 | `40000` 参数校验 / `40100` 未登录 / `40101` 令牌非法 / `40102` 过期 / **`40103` 令牌被作废** / `40300` 无权 / `40400` 不存在 / `40900` 冲突 |
| `1xxxx` | 账号 | `10001` 已存在 / `10003` 密码错 / `10004` 封禁 / `10005` 登录锁定 / `10006` 注册关闭 / `10007` 邮箱占用 |
| `2xxxx` | 角色与玩法 | `20002` 角色不存在 / `20003` 存档结构非法 / **`20006` 修订号冲突** / **`20007` 被踢下线** / `20012` 背包满 / `20020~20026` 背包与道具使用 |
| `3xxxx` | 管理端 | `30001` 管理员已存在 / `30006` 权限不足 / `30007` 保护性拒绝（最后一个超管）/ `30009` 登录锁定 |
| `5xxxx` | 配置与业务实体 | `50019` 怪物不存在 / `50032` 地图不存在 / `50101~50108` 帮会 / `50109~50120` 社交 / `50121~50144` 队伍与邮件 |

客户端侧只把三类码当成「要回登录」：`RELOGIN_BIZ_CODES`（40100/40101/40102/40103 + 10004）；
存档同步另有 `ROLE_SYNC_BIZ_CODES`（20006 冲突 / 20002 角色没了 / 20007 被踢），三条走完全不同的分支。

### 2.2 全局 `whitelist` 的坑（最容易静默出错的一处）

`ValidationPipe({ whitelist: true })` 会把**未声明的字段剥掉**，包括「嵌套裸对象里的属性」。
把入参声明成 `cells?: unknown[]` 时，请求里的 `[{row,col,id,count}]` 到 service 层会变成 `[[]]`——
不报错、也不为空，只是全空。

正解：带装饰器的 DTO 类 + `@ValidateNested({ each: true })` + `@Type(() => XxxDto)` + 登记 `SWAGGER_MODELS`。
`RoleBagCellsDto` / `DropEntryDto` / `MonsterDropBodyDto` 都是这么写的。

## 三、鉴权与权限

### 3.1 两层，都在守卫里

| 层 | 谁管 | 解决什么 | 关键实现 |
|---|---|---|---|
| 受众 audience | `AuthGuard` | 「谁能进这扇门」 | `aud = player / admin` 两套令牌；**每次请求回查库**（封禁 / 删除即时生效）+ 比对 `token_version` |
| 权限点 permission | `PermissionGuard` | 「进门之后能干什么」 | 注册在 `AuthGuard` **之后**，直接用 `request.user.role`，不再查库 |

- 管理员在**独立 `admins` 表**（注册需 `ADMIN_REGISTER_CODE`，**第一个注册者自动是超管**）。
- 三级角色：`super_admin`（全给）/ `admin`（除 `admin:manage`）/ `viewer`（7 个读权限）。
- **26 个权限点**：

```
stats:read
account:read  account:status  account:password  account:delete  account:email
role:read     role:write      role:select       role:delete
announcement:read  announcement:write
mail:read     mail:write      gameMail:send
admin:read    admin:manage
audit:read    system:read
gameConfig:read    gameConfig:write
zone:read     zone:write
guild:read    guild:write
report:read
```

- `viewer` 只有 7 个：`stats:read` / `account:read` / `role:read` / `announcement:read` /
  `gameConfig:read` / `zone:read` / `guild:read`。**不给** `account:email`（个人信息）、
  `mail:read`（投递记录里有玩家邮箱）、`audit:read` / `system:read`（暴露人与部署形态）、`report:read`。
- 无权限 → `403` + `30006`（message 写出缺哪个权限）；保护性拒绝 → `30007`（最后一个超管不能降级/停用/删除）。
- **加管理端接口必须 `@ApiAdminDoc({ permissions: [...] })`**：它同时落三处（文档说明、`x-olua-permissions`、运行时元数据）。
  只写文档不写装饰器 = **权限全放行**（真出过，被 e2e 抓出来）。

### 3.2 `@Public()` 只有一类正当理由

**玩家还没拿到令牌那一刻要用的数据**，且里面没有任何玩家 / 账号数据。现有三处：
`GET /announcements/active`（登录页弹公告）、`GET /game-config/audio`（登录场景要播背景音）、
`GET /zones`（注册时选区）。进游戏之后就该走带令牌的那条路，别让同一个值有两个来源。

## 四、接口契约的生成链

```
控制器方法 + 装饰器 + DTO
        ↓  npm run swagger:emit（编译 + 离线 emit）
server/openapi.json            （提交进仓库，227 个 operationId / 6 个文件）
        ↓  node tools/gen-api.cjs
client/assets/ui/utils/net/{ApiRoutes,ApiModels,Api}.ts
admin/src/api/{routes,models,endpoints}.ts
```

三档装饰器（**按方法标，控制器禁写类级 `@ApiTags`**）：

```ts
@ApiAdminDoc({
  operationId: "adminRole.patch",        // 必填：<模块>.<方法>；也是审计日志的 action
  summary: "修改角色",
  description: "……",
  permissions: [Permission.ROLE_WRITE],  // 管理端**必带**
})
@ApiQueryModel(RoleQueryDto)             // 有 query DTO 时（列表接口）
@ApiDataResponse(RoleDto)                // 有响应体时；无响应体不写
```

`createDocument(..., { autoTagControllers: false })` **必须显式传**：默认 `true` 会拿控制器类名当分组，
`@ApiTags()` 空标签清不掉，文档分组全乱（e2e 钉了「每个接口恰好属于一个分组」）。

### 4.1 六个高频坑

| 坑 | 症状 | 正解 |
|---|---|---|
| 嵌套数组声明成 `unknown[]` | 请求体被静默剥成 `[[]]` | DTO 类 + `@ValidateNested({each:true})` + `@Type` |
| 只写 `nullable: true` 不写 `type` | 生成物里是 `unknown`，两端类型退化 | 可空字段一律 `type` + `nullable: true` |
| 新 DTO 忘了登记 `SWAGGER_MODELS` | 文档里出现悬空 `$ref` | 登记；`audit-api-generated` 的 D 段会报 |
| 分页响应用 `isArray: true` | 文档写数组、实际是 `{list,total,page,size}` | 用 `PageMetaDto` 派生 `XxxPageDto` |
| 新模块没登记 `tools/gen-api.cjs` 的 `MODULES` | `gen:api` 直接报错 | 补映射（`adminAudit: { target: "admin", export: "auditApi" }`） |
| 响应里的 `revision` 忘了 `+1` | 客户端拿旧基线，下一次推送**立刻撞锁自锁死循环** | 返回 `existing.revision + 1`（SQL 只管落库） |

另外两个「看着能用其实是空壳」的坑：
`keyword` 这类继承自 `PageQueryDto` 的字段**忘了在仓储实现**——请求带上不报错、只是不筛；
筛选布尔值一律用字符串 `"true" | "false"`（`class-transformer` 会把 `"false"` 变成 `true`，静默筛错）。

## 五、数据层

- **仓储一个表一个文件**（`database/repositories/`），只由 `DatabaseModule` 全局装配。
- **加列走 `migrate()` 的 `ensureColumn`**（内部读 `PRAGMA table_info`），别只改建表语句——存量库不会重建。
- **`revision` 乐观锁**：`roles.revision`，每次落库 `revision = revision + 1` **写在 SQL 里**（不读出来加一）；
  玩家 `PUT /roles/:id` 可选带 `revision`，对不上 → `409` + `20006`；**不带 = 旧行为**（最后写入者胜）。
- **角色 `data` 是不透明文档**：读路径 `decodeStoredRoleData` 容错（解析失败给安全默认）；
  **编辑路径 `parseStoredRoleData` 解析失败必须报错**——用空对象兜底等于清空玩家背包。
- **删除顺序**：`accounts.clearOnlineRole` 必须**早于**删角色行（角色行没了就判不出当初指向谁）。

## 六、事件总线（进度采集点唯一）

「打怪 / 交付任务」这类事实会引出越来越多消费者（任务进度 → 成就进度 → boss 邮件 → 地图监控）：

```ts
// common/events/game-events.service.ts（@Global）
emit("monster:killed", { accountId, roleId, monsterKey, monsterLabel, monsterTier });
```

- 结算**只 emit**，不认识任务也不认识成就；订阅方在各自 `onModuleInit` 里 `events.on(...)`。
- **同步分发**是硬约束：击杀结算返回时任务与成就进度必须已落库，否则「打完怪立刻打开任务面板」看到旧进度。
  所以这不是消息队列，别拿它跨进程。
- `listenerCount` 供启动自检与单测问「这条事件真有人接吗」——少一个订阅不报错，只会静默不生效。
- **进度类副作用一律可丢，世界状态是权威**：成就写库失败只打日志，绝不回滚一次真实击杀。

## 七、加一个接口的标准动作（顺序不能反）

1. **DTO**（`modules/<域>/dto/*.dto.ts`）：每字段 `@ApiProperty` / `@ApiPropertyOptional`；
   嵌套必须 DTO 类 + `ValidateNested`；分页用 `PageMetaDto`；登记 `SWAGGER_MODELS`。
2. **权限点**（若管理端）：先在 `common/constants/permission.ts` 加，再决定哪些角色持有（**只改 `ROLE_PERMISSIONS`**）。
3. **控制器方法**：挂三档装饰器之一 + `operationId` + `permissions`；有 query DTO 时挂 `@ApiQueryModel`。
4. **service / repository**：业务校验放 service，`BizException(code, msg)` 默认 400；
   「资源不存在」必须 `BizException.notFound(...)`（403 与 404 不能混：「你没权限」会诱导下一个人去补权限）。
5. **`cd server && npm run gen:api`**：重出 `openapi.json` + 两端接口文件。
6. **两端 `tsc` / `npm run build`**：签名不兼容会**直接编译报错**（这正是设计目的），按报错改调用点。
7. **补 e2e 断言**：这几套是服务端唯一的行为护栏（没有单测框架）。

```bash
cd server
env -u NODE_OPTIONS npm run gen:api
env -u NODE_OPTIONS npm run test:e2e:roles   # 改角色接口先跑它
env -u NODE_OPTIONS npm run verify           # 编译 + 全部 e2e + 生成物审计
```

## 八、验证

| 命令 | 覆盖 |
|---|---|
| `make server-verify` | 编译 + 全部 e2e + `verify:api` |
| `make server-e2e-shard I=0 N=4` | CI 用的分片（按实测耗时装箱） |
| `make audit` | 15 项跨端审计（边界 / 生成物 / 权限 / 硬编码 / 快照契约…） |

e2e 的写法：**真实起服务进程 + 真实 HTTP 请求 + 自带临时库**；它们会调 `setupSwagger(app)` 生成**真文档**，
用来验「分组 / 权限标注 / 悬空 `$ref`」。完整套件清单见 [13](./13-部署运维与质量门禁.md)。
