## 零、现状（实测）

| 项 | 现状 |
|---|---|
| 管理端审计 | `audit_logs` **823 行**（`actor` / `action` / `target` / `ip` / `method` / `path` / `status_code` / `detail`） |
| 地图监控 | `map_monitor_state` + `map_monitor_events`（**伤害 / 追击 / 技能 / 命中** 四类，见 #745 / #459） |
| 排行榜 | `ranks` 物化（战力 / 等级 / 击杀） |
| 经济 | **无流水**（26 篇才建 `economy_log`） |
| 登录防护 | 用户名 + IP **双层限流**（#155）；`token_version` 令牌失效；踢下线 |
| 玩家行为埋点 | **已落（#886）**：`event_logs`（登录 / 进图 / 击杀 / 拾取 / 获得 / 消耗 / 邮件 / 任务八类），管理端 `/event-logs`；**聚合与信号仍是 0** |
| 客户端校验 | **无**（无包体哈希、无签名校验、无字段一致性检查） |
| 反外挂 | 只有「入口防护」（限流 / 封禁），**游戏内零检测** |

### 0.1 为什么现在必须补

22 篇把冷却与法力搬到服务端之后，「改包连放技能」这条路会被堵上。
但堵住一条路不等于没有外挂：**加速、穿墙、拾取抢怪、脚本挂机**这些
都发生在「服务端看得见但没在看」的地方。

没有埋点 = 没有证据 = 只能靠玩家举报 + 人工看录像。这是最贵的一种处置方式。

## 一、五个问题

### 1.1 只有「发生了什么」，没有「谁做了什么」

`map_monitor_events` 记的是**怪物**视角（这只怪被谁打了、追了谁），
反向的「这个角色一晚上杀了 8000 只怪」查不出来。

### 1.2 经济完全没有痕迹

26 篇之前，金币/物品的增减只有最终状态（`roles.data.bag`），
中间过程一条不剩。这意味着**复制道具查不出来** —— 你只知道他有两把，
不知道第二把是哪来的。

### 1.3 入口防护 ≠ 游戏内检测

限流防的是「撞库」，防不了「已登录的加速齿轮」。当前没有任何一项
「服务端可独立判定」的游戏内异常检测。

### 1.4 没有留存与漏斗

哪个等级段掉人最多、新手引导第几步卡住 —— 全靠猜。31 篇的活动、29 篇的帮会
做完之后，没有数据就无法判断「做对了没有」。

### 1.5 客户端零校验

客户端可以随意改内存里的数值（虽然最终以服务端为准），
但它**上报的东西**（位置、目标、操作意图）没有一致性约束 —— 22/28 篇
的校验是「逐条判合法」，不是「判这个人整体像不像人」。

## 二、事件模型

### 2.1 一条事件长什么样

```sql
CREATE TABLE event_log (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  ts         INTEGER NOT NULL,
  zone_id    INTEGER NOT NULL DEFAULT 1,
  role_id    TEXT NOT NULL,
  kind       TEXT NOT NULL,           -- login / enter_map / kill / pick / trade / enhance / quest / ...
  target     TEXT NOT NULL DEFAULT '',-- 对象（怪物 key / 物品 id / 对方角色 / 任务 id）
  value      INTEGER NOT NULL DEFAULT 0,  -- 数值（数量 / 金额 / 伤害 / 次数）
  extra      TEXT NOT NULL DEFAULT '{}',  -- 少量补充（地图 key / 装备 slot / 结果）
  session_id TEXT NOT NULL DEFAULT ''     -- 一次登录一个 id，用于串成行为序列
);
CREATE INDEX idx_event_role_ts ON event_log(role_id, ts DESC);
CREATE INDEX idx_event_kind_ts ON event_log(kind, ts DESC);
```

| 纪律 | 说明 |
|---|---|
| **只记服务端已确认的事实** | 不记客户端上报的「我打了 100 伤害」，只记**结算后**的 `settle` 结果 |
| **不在事务里写** | 事件落库走**异步队列**（同 `GameEventsService` 总线 + 批量 flush），绝不与业务事务同生共死 |
| **失败不影响业务** | 队列写失败只打日志 + 计数（成功的一次击杀不该因为埋点挂掉而回滚） |
| **按天分表** | `event_log` 按 `ts` 归档到 `event_log_YYYYMM`（每月一张）；在线表只保 7 天，其余进月度表 |
| **体积预算** | 单条 ≤ 200 字节（`extra` 上限 200 字符，超了截断）。日均 50 万事件 ≈ 100MB/月 |

#### 2.1.1 落地口径（#886）与上面设计的差异

上面的 DDL 是**设计稿**；实际落地按「先用起来、能查得到」做了取舍，逐项对照如下（差异不藏着，
下一个人改这张表时要知道现在的真实形状）：

| 设计里写的 | 实际落地 | 为什么 |
|---|---|---|
| 表名 `event_log`（单数） | `event_logs`（**复数**，与 `audit_logs` / `map_monitor_events` 同风格） | 全库表名统一复数，少一个记忆点 |
| `kind` / `value` / `extra` / `ts` | `type` / `amount` / `detail` / `created_at` | 与全库列名约定一致（时间一律 `created_at`，Unix 毫秒） |
| **异步队列 + 批量 flush** | **同步写 + 调用方内合并** | 异步要 flush 定时器 + 进程退出兜底，还会出现「刚打完怪查库没有」；同步写返回即落库，一次操作的多条记录由调用方攒成一条多值 INSERT（群攻 8 条击杀仍只一次 WAL 提交） |
| 按月分表 `event_log_YYYYMM` | **单表 + 两道保留闸**（`EVENT_LOG_MAX_ROWS` 默认 10 万 / `EVENT_LOG_RETENTION_DAYS` 默认 30 天） | 分表要改所有查询与清理路径；当前量级单表 + 索引就够。**暂时放置** —— 重开条件：单月流水超过千万行、或库体积成为部署问题 |
| `session_id`（一次登录串成行为序列） | **暂时放置**（没有这一列） | 重开条件：要做会话级反外挂（「这一次登录像不像人」）时才需要稳定的会话标识 |
| 12 个采集点 | **八类实做**：`login` / `enter_map` / `kill` / `pick` / `gain` / `consume` / `mail` / `quest` | 见下表 |
| `event_daily` 聚合 + 每日 rollup | **暂时放置** | 重开条件：要做留存 / 漏斗 / 日报看板（那时才需要 `event_daily` 与 05:00 rollup；现在报表与看板仍读各自物化表） |

采集点对照（设计 12 个 → 落地 8 类）：

| 设计 `kind` | 落地 | 说明 |
|---|---|---|
| `login` | ✅ `login` | 成功与失败都记（失败时 `account_id` 为空、尝试的用户名在 `detail`） |
| `enter_map` | ✅ `enter_map` | 记的是「真的站进去了」（`worldJoin` 成功），不是 `mapEnter` 的意图 |
| `kill` | ✅ `kill` | 总线 `monster:killed` 订阅；`target` = 怪物 key，`map_id` 取**目标怪所在图** |
| `pick` | ✅ `pick` | 拾取成功 |
| `drop`（掉落生成） | **并入 `pick`** 的反面 —— 掉落是**世界**的产物不是玩家行为；玩家侧的对应事实就是「捡了什么」 | 要查「地上生成了什么」看 `map_monitor_events` / 掉落账本，不在这张表 |
| `bag_op`（穿脱 / 使用 / 丢弃 / 回收） | ✅ 拆进 `gain`（收入侧）/ `consume`（支出侧），`detail.reason` 区分 `sell` / `drug` / `discard` | 两类足够回答「钱与物从哪来、到哪去」，不必按操作名分家 |
| `mall`（购买 / 出售） | ✅ 买 → `gain`（`detail.source="mall"` + 价格）；卖 → `consume`（`detail.reason="sell"` + 单价） | 同上 |
| `quest`（接 / 交） | ✅ `quest` | 总线 `quest:claimed` 订阅；`detail.kind` 区分任务类型 |
| `death`（玩家死亡） | **暂时放置** | 重开条件：做死亡惩罚 / 复活统计 / 「反复送死刷某某」这类检测时 |
| `chat`（发言含被拒） | **暂时放置** | 重开条件：要做「广告号 / 辱骂」自动识别时（那时还需要被拒原因的埋点，现在拒因只回给客户端） |
| `trade` | **暂时放置**（字典占位，无发布者） | 重开条件：26 篇的交易模块落地 |
| `enhance` | **暂时放置**（字典占位，无发布者） | 重开条件：24 篇的强化模块落地 |
| （设计里没有）`mail` | ✅ **实做补上** | 「补发的奖励到底领没领」是运营最常问的问题，且领奖是明确的成功点 |

**两条不变的硬约束**（设计与落地一致）：只记服务端已确认的事实；写失败只 `warn`，绝不让埋点拖倒业务
（e2e 把 `event_logs` 改名后登录仍成功、一条也没写 —— 这是反证，不是缺陷）。

### 2.2 采集点（先接 12 个）

| `kind` | 采集点 | `target` | `value` |
|---|---|---|---|
| `login` | 登录成功 | 空 | 0 |
| `enter_map` | `world` 帧换图成功 | 地图 key | 0 |
| `kill` | 结算完成 | 怪物 key | 伤害总量 |
| `death` | 玩家死亡 | 凶手（怪物 key / 角色 id） | 0 |
| `pick` | 拾取成功 | 物品 id | 数量 |
| `drop` | 掉落生成 | 物品 id | 数量 |
| `bag_op` | 穿脱 / 使用 / 丢弃 / 回收 | 物品 id | 数量 |
| `enhance` | 24 篇强化结算 | 装备 id | 目标等级 |
| `trade` | 26 篇交易成交 | 对方角色 id | 金额 |
| `mall` | 商城购买 / 出售 | 商品 id | 金额 |
| `quest` | 接 / 交 | 任务 id | 0 |
| `chat` | 发言（含被拒原因） | 频道 | 0 |

**为什么是这 12 个**：它们覆盖了「成长、经济、社交、异常」四条线，
且**全部在服务端已有明确的成功点**（不需要新加判断，只是多一行 emit）。

### 2.3 聚合层

```sql
CREATE TABLE event_daily (
  day        INTEGER NOT NULL,       -- yyyyMMdd
  zone_id    INTEGER NOT NULL DEFAULT 1,
  role_id    TEXT NOT NULL DEFAULT '',  -- 空 = 全区汇总
  metric     TEXT NOT NULL,          -- kills / play_ms / gold_in / gold_out / drops / deaths
  value      INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (day, zone_id, role_id, metric)
);
```

每日 05:00（与 31 篇同一把尺子）跑一次 rollup，从 `event_log` 聚合。
**报表与看板只读 `event_daily`**，不扫明细表 —— 明细是给排查用的，不是给报表用的。

| 报表 | 口径 |
|---|---|
| 留存 | 当日新增角色中，D1 / D3 / D7 还在登录的比例 |
| 漏斗 | 建号 → 首次击杀 → 首次穿装备 → 首个任务 → 10 级，各步人数 |
| 在线时长 | `event_daily.play_ms`（登录到下线累计） |
| 经济净额 | `gold_in - gold_out`（与 26 篇 `economy_log` 对账，两处必须一致） |

## 三、反外挂：服务端能独立判定的八类信号

**原则**：只做「不依赖客户端自证」的判定。凡是需要客户端说自己没作弊的，一律不算。

| # | 信号 | 判据 | 误伤风险 |
|---|---|---|---|
| 1 | 移动异常 | 单位时间位移 > `speedRate × 1.2 × 上限` | 低（服务端权威坐标） |
| 2 | 攻击频率异常 | 同技能两次释放间隔 < 冷却 × 0.8（22 篇冷却上服务端后可判） | 低 |
| 3 | 击杀速率异常 | 连续 10 分钟 `kills/min` > 服务器 P99 × 3 | 中（可能是活动倍率） |
| 4 | 资源产出异常 | 单日 `gold_in` > 同级段 P99 × 5 | 中（可能是交易收入） |
| 5 | 物品复制嫌疑 | 同 `itemId` 总件数增加，但 `economy_log` 无对应 `in` 记录 | **极低**（对账即证据） |
| 6 | 拾取越界 | 拾取距离 > AOI 上限 / 拾取不属于自己的掉落（18 篇 `owner`） | 低 |
| 7 | 交易对刷 | 同一对角色 24 小时内互相交易 > N 次且净额趋 0 | 中（可能是朋友互助） |
| 8 | 心跳异常 | 心跳间隔方差极小（机器规律）或长时间零波动 | 中（可能是网络稳定） |

### 3.1 处置：只记录 + 告警（已定）

| 级 | 触发 | 动作 |
|---|---|---|
| 观察 | 单个信号命中一次 | 落 `anomaly_log`，**不告警** |
| 关注 | 24 小时内命中 ≥ 3 次 | 管理端看板亮灯 + 站内提示给运营 |
| 高危 | 信号 5（复制）或 6（越界）命中 | 立即告警（日志 error 级 + 管理端红点），**仍不自动处置** |

```sql
CREATE TABLE anomaly_log (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  ts         INTEGER NOT NULL,
  role_id    TEXT NOT NULL,
  signal     TEXT NOT NULL,      -- move / cast_rate / kill_rate / gold / dup / pick / trade / heartbeat
  score      INTEGER NOT NULL DEFAULT 0,  -- 0~100，越大越可疑
  evidence   TEXT NOT NULL DEFAULT '{}',  -- 触发时的原始数据（坐标/间隔/金额）
  handled_by TEXT,                        -- 处置人（人工）
  handled_at INTEGER,
  verdict    TEXT                         -- innocent / warned / banned
);
```

**为什么坚持不自动封**：与 26 篇「脚本风控不自动封号」同一条原则 ——
自动处置的误伤成本（一个付费玩家被封 7 天）远高于漏检成本（一个外挂多刷一晚）。
**但「不自动封」不等于「不管」**：高危信号必须能在一分钟内被人看到。

### 3.2 举报闭环

现有 `role_reports` 表只读列表。补一条链路：

```
玩家举报 → role_reports（已有）→ 管理端处置工作台（35 篇）
   ├─ 拉该角色的 anomaly_log + event_log 最近 2 小时
   ├─ 一键「观察 / 警告 / 封禁（选时长）」
   └─ 处置结果回写 role_reports.verdict + 给举报人一封 system 邮件（32 篇）
```

## 四、客户端完整性（先只做最省的一层）

| 层 | 做法 | 阶段 |
|---|---|---|
| L1 版本对齐 | 客户端启动上报 `clientVersion` + `resourcesVersion`（资源清单已有），服务端记进 `event_log(extra)` | **本篇做** |
| L2 关键字段自洽 | 客户端上报的移动帧带 `seq`，服务端判「间隔单调」，乱序/回退直接丢帧 | 28 篇已有雏形，本篇只加计数 |
| L3 包体哈希校验 | 服务端比对已知 web 产物哈希 | 暂时放置（Web 端可绕过，收益低） |
| L4 反调试 / 混淆加固 | 客户端构建期处理 | 暂时放置（Cocos Web 端加固成本高、可绕过） |

## 七、边界情况

| # | 情形 | 期望 |
|---|---|---|
| 1 | 事件队列满（flush 跟不上） | **丢弃低优先级事件**（`chat` / `enter_map`），保 `kill` / `trade` / `dup`；丢弃计数进 `/admin/system` |
| 2 | 埋点写库失败 | 只打日志，**不回滚业务**（一次击杀不因埋点挂掉而失败） |
| 3 | 玩家 24 小时在线，`play_ms` 计算 | 按 `login`/`logout` 事件配对；进程崩溃无 logout → 按最后心跳算 |
| 4 | 时钟回拨 | 事件 `ts` 只取服务端；回拨时按单调计数兜 |
| 5 | 活动倍率导致击杀率异常 | 信号 3 判定前**读 31 篇的活动倍率**，按倍率放宽阈值 |
| 6 | 交易对刷误判（朋友互助） | 只记「观察」级，不升级到「关注」；需要 N 次且净额趋 0 双条件 |
| 7 | 复制嫌疑但 `economy_log` 尚未建（26 篇未上） | 信号 5 **不上线**（没有对账基准就无法判定），等 26 篇 |
| 8 | 月度表归档失败 | 保留在线表不删（宁可撑大，不丢数据），告警 |
| 9 | 一个角色被多个人举报 | 合并成一条处置记录，`role_reports` 保留原始条数 |
| 10 | `extra` 超 200 字符 | 截断 + `truncated: true` |
| 11 | 管理端一次查 10 万条事件 | 强制分页 + 时间范围必填（默认最近 2 小时） |
| 12 | `SUPER` 跨区看异常 | 允许；`ADMIN` 只看本区（35 篇的 `ZoneScopeGuard`） |

## 九、验收

| 用例 | 断言 |
|---|---|
| `e2e-event-emit` | 杀一只怪 → `event_log` 有一条 `kind='kill'`，`value` 等于结算伤害 |
| `e2e-event-nonblocking` | 把 flush 打桩成抛错 → 击杀照常成功、经验照发 |
| `e2e-event-drop` | 队列塞满低优先级事件 → 被丢的是 `chat` 不是 `kill` |
| `e2e-rollup` | 造 100 条 `kill` → 跑 rollup → `event_daily.kills = 100` |
| `e2e-anomaly-move` | 注入一帧超速移动 → `anomaly_log` 一条 `signal='move'`，**角色未被踢** |
| `e2e-anomaly-dup` | 凭空给背包加一件（不走 `economy_log`）→ 信号 5 命中 |
| `e2e-anomaly-no-autoban` | 命中 100 次 → 角色仍在线（证明不自动处置） |
| `e2e-report-closure` | 举报 → 处置 `banned` → `role_reports.verdict` 回写 + 举报人收到 system 邮件 |

## 十、暂时放置（含重开条件）

| 项 | 现在的口径 | 重开条件 |
|---|---|---|
| 客户端包体哈希 / 反调试加固 | 只上报版本号（L1） | 出现成规模的「改包绕校验」案例时（Web 端加固收益有限，别提前投入） |
| 实时反作弊（在线判定 + 立即拦截） | 只记录，阈值判定离线跑 | 22 篇冷却上服务端后仍有明显的瞬时作弊时（届时信号 1/2 可做实时） |
| 自动封禁 | 坚持人工（已定） | 出现「人工处置完全跟不上」的量级（如日活过万且外挂泛滥）时 |
| 事件外送（Kafka / ClickHouse / 第三方 BI） | 只落 SQLite + 每日聚合 | 单日事件过 500 万，或需要多维即席分析时（现在四容器部署，加组件成本高） |
| 客户端埋点（点击 / 页面停留） | 只做服务端事件 | 需要做 UI 层体验优化时（客户端埋点要过审，且数据可信度低于服务端） |
| 设备指纹与多开检测 | 只记 IP + UA（33 篇） | 工作室多开成为主要问题时 |
| A/B 实验框架 | 无 | 有「两种数值方案要对比」的实际需求时（现在直接改配置看数据即可） |
