# 05 · 装备链路（样板篇）

> 一件装备从「一行配置」到「头顶一把刀」，中间要过六道手。
> 这一篇按顺序把每一道都拆开 —— 同样的读法适用于药品、材料、货币道具、升级卷轴。

## 全景

```
①配置          ②展开              ③掉落表            ④击杀抽取
equipments  →  equipment_variants → monster_drops  →  rollDrops()
(685 基础件)   (10275 变体)         drop_tables      (账本 + 绑定 + 溯源)
                                                        │
                                   ⑧展示 ← ⑦属性 ← ⑥穿戴 ← ⑤进背包 ← ④'拾取
                              外观/边框  战力/血量  bagOp    placeGoodsIntoBag
```

一句话记住各段的权威：**配置在库、抽取在服务端、入包在服务端、属性在服务端、只有「摆在哪一格」听客户端的**。

---

## 一、① 配置：一件装备是哪几行数据

| 表 | 行数 | 作用 |
|---|---|---|
| `equipments` | 685 | **基础件**：部位、等级、12 个属性列、售价、外观图与几何 |
| `equipment_variants` | 10275 | **变体**：5 前缀 × 3 后缀 = 15 个组合，每个组合一行**最终值** |
| `equipment_meta` | 1 | 前后缀倍率 / 文案 / 名字颜色 |
| `equipment_slots` | 13 | 部位表（`key / label / image_src / position / sort_order`） |
| `equip_aligns` | — | **地图上**的几何覆盖（`id = "cloth:cloth_10"`，角色本体是 `role:1`） |
| `equip_in_aligns` | — | **内观界面**的几何覆盖（`id = "weapon:weapon_1"`） |
| `equipment_appearance` | 1 | 按前后缀映射的品质**边框 / 底图**（15 组 + 自定义覆盖） |

`equipments` 的属性列是固定的 12 个 —— 六项「区间」（各 `_min` / `_max`）+ 两个单值：

```
max_hp | hp_recover
physical_attack_min/max | magic_attack_min/max | taoist_attack_min/max
physical_defense_min/max | magic_defense_min/max | taoist_defense_min/max
```

部位（`equipment_slots`，13 个，其中 3 个是 `other`）：

```
bottom: other1 / cloth / other2
left  : weapon / necklace / ring / accessories / shinguard
right : helmet / scapular / belt / wristband / shoes
```

`position` 决定内观面板里槽位摆哪一侧，`sort_order` 决定上下顺序。
**客户端 7 个主部位是既有约定**（#785 的边界）：`other1/other2` 是给运营留的空位，不参与穿戴校验之外的任何逻辑。

## 二、② 展开：15 个变体怎么来的

```ts
// game-config.service.ts → variantsOfBase(base, meta, now)
for (let prefix = 0; prefix < meta.prefixRates.length; prefix++)
  for (let suffix = 0; suffix < meta.suffixRates.length; suffix++) {
    const scale = (v: number) => Math.round(v * prefixRate * suffixRate);
    rows.push({
      id: prefix === 0 && suffix === 0 ? base.id : `${base.id}_p${prefix}s${suffix}`,
      sell_price: scale(10 * base.level),   // 售价公式，重建时保留运营逐条调过的价
      max_hp: scale(base.max_hp), /* …12 个属性同 scale… */
    });
  }
```

出厂倍率（`equipment_meta`）：

```json
prefix_rates: [1, 1.1, 1.2, 1.3, 1.4]     prefix_labels: ["普通的","强化的","精良的","极品的","超神的"]
suffix_rates: [1, 2, 3]                    suffix_labels: ["人级","天级","神级"]
```

四条必须记住的口径：

1. **`p0s0` 的 id 就是基础件 id**（不带后缀）—— 所以 `equipmentVariantRows` 里同时能查到 `belt_1` 与 `belt_1_p3s2`。
2. **变体存的是最终值，运行时零现算**。`equipmentAttributesOf(id)` 直接读那一行的属性包 ——
   这也是为什么「改了倍率必须点重建变体」：不重建，新倍率对已有装备毫无影响。
3. **倍率是相乘**：`p3s2` = 1.3 × 3 = 3.9 倍。所以「超神·神级」是「普通·人级」的 3.9 倍。
4. **重建保留售价**：`pricePreserved` 让运营逐条调过的 `sell_price` 不被公式冲掉，
   只有扩档后新出现的组合才按 `10 × 等级 × 倍率` 垫底。

**加一件装备时会自动展开**：`createEquipment` 里 `insert(row)` 之后立刻 `seedRow` 15 个变体，
返回 `{ equipment, variants: 15 }`。删除则连带清掉全部变体 + 两张几何表里指向它们的行；
**还在商城上架清单里 → 409**（先下架再删，否则客户端会陈列「名字退回 id、图标空」的幽灵商品）。
删装备**不碰玩家存档** —— 背包里那些 id 会变成认不出的路径，服务端与客户端都只是跳过。

## 三、③ 掉落怎么配：`monster_drops` 三态

每个怪物一行（`monster_key` 主键），`source` 决定用哪一种：

| `source` | 用哪份 | 说明 |
|---|---|---|
| `table` | `drop_tables` 里 `table_id` 那张 | 具名表，多只怪共享；行内 `picks` 可覆盖表里的件数 |
| `entries` | 行内 `entries` JSON | 内联条目池，单只怪独有（出厂 219 只怪用这种） |
| 空 / 缺行 | `drop_tables` 的 `default` | 兜底：没配掉落的怪也掉点药 |

一张表的结构：

```json
{
  "picks": 1,                 // 数字 = 固定件数；[min, max] = 区间随机
  "entries": [
    { "goodId": "drug_hp_1", "weight": 30, "chance": 1,   "count": [1, 3] },
    { "goodId": "material_gem","weight": 15, "chance": 0.6, "count": [1, 1] }
  ]
}
```

- `weight` 缺省 1、`<= 0` 视为不参与（不是「低概率」）。**权重是相对值**，总和多少都行。
- `chance` 缺省 1（必掉），写成 `0.6` 就是命中后还要再过一道 60%。
- `count` 缺省 `[1,1]`，两端含。
- 出厂 5 张表：`common`(1 抽) / `elite`(2 抽) / `boss`(3 抽) / `default`([1,2] 抽) / `elite_1_10`(10 抽，全掉 `cloth_1`，给 1~10 级精英的固定衣服)。

**装备进掉落表的写法**：直接写变体 id（`weapon_1_p0s1`）。出厂数据把 15 个变体都列进条目池，
且权重随倍率递减（`weapon_1` 6.29 → `_p0s1` 3.14 → … → `_p4s2` 0.17），
所以「越好的前缀越难掉」是**权重配出来的**，不是代码里的规则。

## 四、④ 击杀时抽什么：`rollDropTable`

`combat-settlement.service.settleKillReward` → `rollDrops(monsterKey)` → `rollDropTable(table)`：

```
1. picks = 数字 ? floor(picks) : randomInt(picks[0], picks[1])，下限 0
2. 过滤 weight > 0，算总权重 total
3. 循环 picks 次：Math.random()*total 按累计权重落点（**每次独立，可重复命中同一条目**）
4. 命中后过 chance（Math.random() > chance → 跳过）
5. count = randomInt(count[0], count[1])；<= 0 跳过
6. 同一 goodId 的多次命中**合并数量**（一次击杀不会出两条同名掉落）
```

### 绑定判定（#789）：三条规则，先硬后软

```ts
bound: monsterBind || bindOnDropOf(drop.goodId) || Math.random() * 100 < bindChance
```

| 顺序 | 规则 | 配置处 |
|---|---|---|
| 1（硬） | 物品侧强制绑定 | `equipments.bind_on_drop` / `drugs` / `items` / `money_items` / `level_scrolls` 各一列 |
| 2（硬） | 这只怪掉什么都绑 | `monster_drops.bind_drops` |
| 3（软） | 按百分比随机 | `runtime_params.drop_params.bindChance`（0~100，缺省 0） |

三个坑：

- **装备按基础件读绑定**：变体 id 先折回 `base_id`（`baseKeyOf` 剥 `_pXsY`）。绑定是这件装备的属性，
  不是某个前后缀组合的属性 —— 掉落表里写的也全是 `p0s0` 光板。
- **查不到的 id 返回 `false`**：认不出的东西不该被顺便锁死。
- **判定放在抽取侧，不放在拾取侧**：同一次击杀，掉落账本与客户端拿到的 `reward` 必须说同一件事。
  拾取时再算一次就可能「账本说绑、背包说没绑」。

`bindChance` 缺键 / 坏值 → **0**（不随机绑定）。配漏了该「不生效」而不是「所有掉落都被锁」。

## 五、④' 掉落账本：地面那堆东西存在哪

掉落**不落库**，存在实时进程内存（`dropLedgers`，按账号隔离）：

```ts
interface DropLedgerEntry {
  goodId; count; bound;
  from?: { role; monster; at };   // 只有装备有：谁杀的 / 哪个怪 / 什么时候
  picked: boolean;
}
```

四条口径：

- **按 `castId` 存**：同一次击杀的掉落是一组，客户端拾取时报 `{ castId, index }`。
- **容量与幂等账同上限**（`CAST_DEDUPE_CAPACITY`），超出挤掉最旧的一次击杀 —— 地面掉落物过期即消失。
- **`from` 只给装备**：一堆药记「谁掉的」没有意义，还让存档无谓变大。
- **幂等重发走 `recentSettles` 原样重放**，不重复入账、不重复广播。

**换图即清账**（#817）：账本按账号隔离，`worldJoin` 放行时服务端**自己**清掉（连同幂等账），
所以隔图拾取查不到条目（`unknown_drop`）。这一条早先只靠客户端发 `targetsReset` ——
那是客户端消息，改包不发就能把上一张图的地面掉落吸进包。

**距离暂不校验**：账本里没有记掉落点坐标，而角色坐标是客户端 4Hz 自报的（#811 才收口），
拿它当准入会大面积误伤。重开条件写在 `combat-settlement.service.ts` 的 `pickDrop` 注释里 ——
账本补 `mapId` + 掉落点坐标（18 篇的 `DropService` 会把坐标落库）之后再接拾取半径。

绑定**只拦交易**，卖店回收照常（见第十节）。这是本期的明确口径：只做标记与展示，不做交易禁令之外的联动。

## 六、⑤ 进背包：`pickDrop` → `placeGoodsIntoBag`

```
pick 帧 { castId, index }
  → 账本里找那条掉落（找不到 unknown_drop）
  → entry.picked ? 幂等应答（alreadyPicked: true + 当前 revision）
  → RolesService.pickDrop(accountId, goodId, count, { bound, from })
  → placeGoodsIntoBag: 两轮放格
  → 落库 revision + 1，返回 { revision, placed }
  → 成功之后才把账本标记 picked
```

**标记必须放在入包成功之后**：背包满被拒时地面掉落物还得在，玩家腾出格子后同一 `castId/index` 能再拾。

两轮放格（与客户端 `StorageManager.addGood` 同口径）：

| 轮 | 规则 |
|---|---|
| 1 | 可叠加物品先吃**已有的同 id 堆**，单格 `maxStack` 封顶（药品/材料读表，读不到按 99） |
| 2 | 再行优先占空格；可叠按 `maxStack` 分堆，**装备每件一格**（`maxStack = 1`） |

**#789 起多一条合并条件：绑定状态不同不并堆。** 否则「捡到一堆绑定的药」会并进未绑定的那堆，
绑定就从有变成没有（反过来的情况更糟：白送一堆可交易品）。于是同一种物品在背包里最多分两堆。

放不下 → `20012`（`MALL_BAG_FULL`）拒拾，**存档一个字节都不动**（`data` 被就地改过，但异常路径不落库）。
实时侧把这个码翻成 `bag_full` 的错误帧，连接不断、地面掉落物保留。

## 七、⑥ 穿戴：`POST /roles/:id/bag-op`

五个动作共用一条写路径（`action` 字段）：`equip` / `unequip` / `discard` / `move` / `tidy`。

### `equip`：服务端算，不是客户端搬

```ts
const cell = cellAt(grid, dto.row, dto.col);                   // 这一格有东西吗 → 20020
const equipmentSlot = equipmentSlotOf(cell.id);                // 是装备吗 → 20021
const required = equipmentLevelOf(cell.id);                    // 认得吗 / 等级够吗 → 20021
if (required > existing.level) throw ...;
equipAt(grid, worn, row, col, equipmentSlot);                  // 换上 + 旧的回原格
```

`equipAt` 的语义值得单独记：**旧装备放回刚腾出来的那一格**（`grid[row][col] = worn ? {id: worn, count: 1} : null`），
所以格数守恒、玩家不用自己挪位置。

⚠️ 服务端只判「部位 + 等级」。职业 / 性别在 `equipments` 表里有列（`occupation` / `sex`），
但**穿戴接口目前不判** —— 客户端 `getEquipmentRejectReason` 会预检并给提示。
要收严这条，改 `bagOp` 的 `equip` 分支，别指望客户端预检。

### `unequip`：找第一个空格

槽位名不在清单里（改包塞了个 `other99`）直接拒；槽位空 → 20020；背包满 → `20012`。
返回值带落点，客户端不必自己再找一遍空格。

### `move` / `tidy`：只验守恒，不重算排布

```
客户端给排布（稀疏格子）→ applyBagCells 铺进原网格
        ↓  #789
reconcileBagCells(旧网格, 新网格)：位置听客户端的，绑定与溯源听服务器的
        ↓
sameGridShape + sameBagContent 两条守恒判据
        ↓ 任一条不过 → 20022「背包内容与服务器不一致，请重新打开背包」
```

为什么必须有 `reconcileBagCells`（这是这条链路最容易踩的坑）：
上报的格子契约只有 `row/col/id/count`，**没有 `bound`**。拿原始排布去比守恒，
绑定的那一堆一挪位置就会被当成「凭空冒出几个可交易的」而拒 —— 玩家的整理动作直接失败。
所以先按 id 归堆、用旧网格的桶件数反推、深搜挑出「件数之和等于绑定桶」的那批（多解按
「旧绑定格原址 > 空格 > 旧未绑定格原址」择优），再比守恒：交叉合并（绑定 2 + 未绑定 4 报成一格 6 个）
会因另一桶归零被抓到。

### 收尾

```ts
data.bag = grid; data.equipments = worn;
if (action === "equip" || action === "unequip") {
  this.applyAuthoritativeAttributes(existing.level, data);  // 装备是属性输入，当场重算
  this.clampVitals(data);                                   // 血蓝上限跟着变
}
revision + 1
```

进 `bagOp` 之前还有一步 `sanitizeEquipments`：清掉「部位不符 / 同一件穿在多个槽」的脏数据。
**必须在属性重算之前** —— 重算遍历 `equipments` 的所有值、不看键，同一件算三遍就是三倍战力。
三条处置口径：认不出的 id 原样保留（多半是客户端配置比服务端快照新）、部位不符能挪就挪、同一件出现两次留第一个。

## 八、⑦ 属性怎么来

```ts
summarizeRoleAttributes({ level, equipments, soulOfWar, title, rank })
```

| 项 | 来源 |
|---|---|
| `maxHp` / `hpRecover` | 等级曲线**单值** + 每件装备的单值 |
| **`maxMp`** | **只跟等级走**（装备不影响魔法值，客户端既有口径） |
| 六项攻防 | 等级曲线区间 + 每件装备区间 + 战魂 + 称号 + 军衔，逐项**区间相加** |
| `combat` | 权重 ×（区间取**两端之和**；`maxHp` 取单值） |

- 装备这一侧的唯一入口是 `collectEquipmentBundles` → `equipmentAttributesOf(id)`：
  先查运营库覆盖层，没有再提出厂属性。**认不出的 id 跳过并记进 `notes.unknownEquipmentIds`**（不崩、不静默吞）。
- 属性包按**变体的那一行**读，所以「同一件基础件的 15 个变体属性不同」在这里自动成立。
- 战斗力权重从覆盖层读（管理端「战斗力权重」页可改）。两个反直觉但必须记住的口径：
  区间取**两端之和**（不是平均、也不是上限），`maxHp` 走另一条分支取单值。
- 算完由 `applyAuthoritativeAttributes` 盖回存档，然后 `settleVitalsAuthority` 补自然回复、`clampVitals` 夹区间。
  顺序见 [04](./04-角色与存档权威.md) 第四节。

**客户端不做这套算法**（#541 起）。它只把服务端给的八项属性 + 战力照搬进内存（`applyServerRoleUpdate` / `runBagOp` 的应答）。

## 九、⑧ 展示：三套外观，各自一份数据

| 场合 | 数据 | 覆盖表 |
|---|---|---|
| **地图上**（角色身上） | `out_atlas` + `out_positions`（按方向 8 个点）+ `out_scale` | `equip_aligns`（`id = "slot:equipmentId"`，角色本体 `role:1`） |
| **内观界面**（人物特写） | `in_atlas` + `in_pos_x/y` + `in_scale_x/y` + `in_rotate` | `equip_in_aligns` |
| **品质边框 / 底图** | `equipment_appearance.borders` / `backgrounds`，按 `{prefix, suffix}` 索引 | `border_items` / `background_items`（自定义序列） |

三条口径：

- 几何覆盖（`equip_aligns` / `equip_in_aligns`）是**工作台调出来的绝对位置**，`out_manual = 1` 表示人工调过、别再按公式算。
  出厂给每件装备都存了 8 个方向的点，是因为「写死一个位置只能对上一件身体」。
- 边框/底图按前后缀查 15 组（`resolveEquipmentBorder`），所以「极品·神级」自带更亮的框 —— 与属性倍率无关，纯展示。
- 换装收尾走 `applyEquipmentChange`：刷地图主角外观 + 内观 + 预载素材。**不做属性重算**（属性已由服务端应答带来）。

名字（`getEquipmentNameParts`）：前缀文案 + 基础名 + 后缀文案，颜色取 `equipment_meta` 的
`prefix_colors` / `suffix_colors`（空则用默认色）。这就是「超神的·屠龙·神级」这种红金字的来源。

## 十、回收：售价只认库，绑定不拦

`POST /roles/:id/sell`（背包「一键回收」）：

1. **计价读库**：`sellPriceOf(goodId)` —— 装备 = 变体行自带的 `sell_price`（已含前后缀倍率），
   药品/材料/货币/卷轴 = 各自表的价签。客户端报多少都无效，它只报「卖什么、卖几件」。
   `unitPrice <= 0` 一律 `20018`（不可出售）—— 任务物与关键道具靠这条拦住，白名单在数据里不在代码里。
2. **扣物**：同 id 多条先合并（一键回收会把同件装备的多个格子拆成多条报上来），
   先点数后扣，任何一条不够 → 整单拒绝（不存在「卖了一半」的存档）。
3. **入账**：进 `bindGold`（绑定元宝），与背包回收的展示口径一致。

**绑定不影响回收** —— 本期口径是「绑定只拦交易」，卖店照常给钱。

## 十一、加一件新装备（六步，顺序不能反）

1. **建基础件**：管理端「装备」→ 新建（`POST`），填部位 / 等级 / 12 个属性 / 图与几何。
   落库后**自动展开 15 个变体**（返回 `variants: 15`）。
2. **看倍率对不对**：`equipment_meta` 改了倍率 → 必须点「重建变体」，
   否则老装备仍是旧值，且新装备会按新倍率展开（两种倍率同时存在于库里，最难查）。
3. **补资源**：`in_atlas` / `out_atlas` 指向的图必须存在，`make audit` 的 `audit-resource-refs` 会点名断链。
4. **工作台调几何**：地图上的位置逐方向调（存进 `equip_aligns`），内观调 `equip_in_aligns`。
   不调就用基础件的出厂点，多半会飘。
5. **进掉落表**：把 15 个变体 id 按递减权重写进目标怪的 `monster_drops.entries`（或具名表里加一条）。
   漏写变体 = 这件装备只有光板会掉。
6. **要卖就上架**：`mall_goods.id` 就是**变体 id**，上架清单决定商城陈列。
   ⚠️ 上架了就不能直接删这件基础件（409，先下架）。

改完记得验：

```bash
make audit                 # 15 项审计，含资源引用与快照契约
cd server && npm run test:e2e:game-config   # 变体展开与装备 CRUD
```

## 十二、排障

| 症状 | 第一嫌疑 | 查法 |
|---|---|---|
| 怪不掉装备 | `monster_drops.source` 是 `entries` 但 `entries` 为空 → 落到 `default` 表 | 查那一行的 `source` / `entries` |
| 掉了但拾取说「找不到」 | 账本已过期（超出 `CAST_DEDUPE_CAPACITY`）或换了连接 | 看是不是重连后拾旧掉落 |
| 掉了但拣不起来 | 背包满（`20012`，翻成 `bag_full` 帧） | 腾格子后同一 `castId/index` 可重拾 |
| 穿戴没反应 | 走了本地改、没走 `bag-op` → 下次存档被回填 | 搜客户端是否直接改 `role.bag` / `role.equipments` |
| 穿不上但提示没说原因 | 服务端 20021（部位/等级），客户端预检可能先放行 | 看服务端返回的 message |
| 战力比预期高 | 同一件穿在多个槽（老存档脏数据） | 搜 warn `装备槽位有脏数据` |
| 改了倍率装备没变 | 没点「重建变体」 | 查 `equipment_variants` 里那件的值 |
| 整理背包被拒 20022 | 绑定堆被挪位且客户端上报丢了绑定信息 | 确认走的是 `bagOp`（`reconcileBagCells` 会认领） |
| 边框/底图不显示 | `equipment_appearance` 里没有该 `{prefix,suffix}` 组合 | 查 `borders` 数组的 15 项 |
| 名字颜色不对 | `prefix_colors` / `suffix_colors` 为空 → 用默认色 | 查 `equipment_meta` |
