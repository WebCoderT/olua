## 零、现状（实测）

### 0.1 两个都叫「邮件」，实际是两个东西

| | `role_mails`（游戏内收件箱） | `mail_queue`（站外邮件） |
|---|---|---|
| 用途 | 附件容器（奖励 / 好友申请 / BOSS 战报） | SMTP 外发（回归召回 / 封禁通知） |
| 通道 | 站内，玩家登录后看 | 玩家邮箱，可能根本没填 |
| 模块 | `modules/game-mail/*` | `modules/mail/*`（模板 + 队列 + 调度器 + 发信器） |
| 关联 | **代码上零关系**（`game-mail.service.ts` 注释明写「两者只是中文都叫邮件」） | 同左 |

本篇讨论的是**左边那个**；右边只在「账号要通知到站外」时才碰（33 篇）。

### 0.2 收件箱已实现的（比想象中完整）

| 项 | 现状 |
|---|---|
| 频道 | `MAIL_CHANNELS = ["system", "reward", "social", "combat"]`，**收敛在 `mail-channel.ts` 一处** |
| `kind` vs `channel` | `channel` = 玩家视角分类（4 个固定）；`kind` = 来源标签（自由扩展，只用于日志） |
| 领取 | `claim` 单封；`claimAll(channel?)` 按频道一键领 |
| 领取幂等 | **`markClaimed` 与发奖在同一事务里，且先标后发**（#868）：`WHERE claimed_at IS NULL` 命中 0 行即视为被别人领走（抛 50142 整体回滚），并发点两次只发一份，也挡得住另一进程的自动入包 |
| 背包满 | `claim` 抛 20012 且**邮件原样保留**；`claimAll` **跳过继续**（#870，不再 `break`）：背包满只挡「要放物品」的那几封，纯绑定元宝 / 纯经验照样到手；`stoppedByBag` = 至少有一封因背包满没领到 |
| 其余失败 | `claimAll` 每封独立事务 + 独立 `try/catch`（#870）：物品不存在 20003 / 乐观锁 409 / 已被人领走 50142 都只影响那一封，回执带 `failedCount` + `failures[]`（`mailId` / `code` / `reason`） |
| 已读 | `read_at` 只写第一次，重复标不动 |
| 奖励没领不能删 | 玩家自己删未领邮件 → `MAIL_UNCLAIMED`（50143）。「有奖励」= **绑定元宝 / 经验 / 附件任一**（#866），纯公告（三样都没有）可删 |
| 未领角标 | `unclaimed` 只数「有奖励且未领」（#869）：纯公告不贡献红点，也不让频道角标虚高 |
| 过期 | `expires_at` 由**投递方**给 TTL（BOSS 战报 7 天 / 运营补发永久）；读口一律滤掉过期行。写入侧三态（#867）：**不传 = 默认 30 天**（`MAIL_DEFAULT_TTL_MS`）、`ttlMs: 0` = 永久、`ttlMs > 0` = 指定 —— 「忘了给」与「故意永久」必须能分开 |
| 自动入包 | `GameMailAutoClaimService` 每小时扫「快到期的 + 主人离线 + 有奖励」的邮件，逐封事务进包，成功才 `auto_claimed_at`（#867，见 §2.2） |
| 清理 | `GameMailPurgeService` 每 60 秒分批（默认 500）删过期行；判据是「**已领** 或 **三样都没有**（`bind_gold <= 0 AND exp <= 0 AND attachments 空`）」，没领的有奖励行删不掉（#867） |
| 发信入口 | `send(roleId, SendMailInput)`（内部）+ `sendFromAdmin`（只能发 `system` / `reward`） |
| 数量 | `role_mails` 实测 **0 行**（新库） |

### 0.3 三处硬伤

| # | 问题 | 证据 |
|---|---|---|
| 1 | ~~**清理判据与删信判据不同源**~~ **→ 已修（#867）** | 原 `purgeExpired` 的 SQL 是 `AND (claimed_at IS NOT NULL OR attachments = '[]')` —— 判据与删信不同源，`attachments = '[]'` 的**纯绑定元宝 / 纯经验邮件未领就被物理删除**，奖励直接蒸发。注意「带未领附件的过期行永不删」**不是 bug 而是取舍**（宁可占磁盘也不替玩家扔奖励，方向对，见 §1.1）。已按 §2.2 成对落地：判据扩到「三样都没有」+ 过期前先自动入包。**别再单独把它改成「看 `bind_gold` / `exp`」** —— 那只是让这些行永远留着 |
| 2 | **没有容量上限，读口全量返回** | `listByRole` 是 `SELECT * ... ORDER BY created_at DESC`，**没有 LIMIT**。老玩家几百上千封 → 每次开背包面板都全量序列化 |
| 3 | **没有幂等键** | `send()` 每次插新行。调度器重跑 / 运营手抖点两次 → 玩家收到两封同样的补偿 |

## 一、四个结构性问题

### 1.1 过期≠可以扔奖励

现在的取舍是「宁可占磁盘也不删未领附件」，方向对，但没解决问题 ——
玩家 30 天没上线，回来发现邮件没了（读口滤掉），奖励也没进包。
**「过期」这件事本身不该发生在这种邮件上**：只要还有附件，它就该有一个归宿。

### 1.2 读口全量，迟早爆炸

`role_mails` 现在 0 行，所以没人发现问题。一个玩了半年的角色，光 BOSS 战报
一周 7 封 × 26 周 = 182 封，加上成就、好友、运营补发，轻松过千。全量返回 =
每次打开消息中心传几百 KB JSON。**必须先有上限，再谈分页**。

### 1.3 发奖入口还没统一

`game-mail.claim()` 直接调 `RolesService.grantQuestRewards()`，
与任务交付、成就领奖是同一个函数 —— 这点是好的。但 31 篇要引入 `RewardService` 之后，
`claim` 必须改走它，否则「背包满转邮件」会绕成环（邮件 → 背包满 → 建邮件）。
**环必须在 `RewardService` 里断掉**：邮件领取失败就是失败，不再转邮件。

### 1.4 离线发不了奖【关键实现前置 —— ✅ 已补（#867）】

`grantQuestRewards(accountId, roleId, ...)` 第一行是 `onlineRoleOrThrow(accountId, roleId)` ——
**要求角色在线**。于是：

- 排行赛结算（31 篇）：玩家多半离线 → 发不进去；
- 过期前自动入包（本篇 §2.2）：玩家离线正是主要场景 → 发不进去；
- 运营补偿给离线玩家：只能建一封空邮件。

已补一个**不依赖在线标记**的落库变体 `RolesService.grantByRoleId(roleId, rewards)`：
直接读 `roles` 行 → 改 `data` → 写回（revision +1），不碰 `accounts.online_role_id`。
实现上把发奖主体抽成私有 `applyRewards(existing, consume, rewards, source)`，
两条入口只差「怎么拿到那行角色」：在线走 `onlineRoleOrThrow`，离线走 `findById`。
**`accountId` 一律从角色行上取（`role.account_id`），不信入参** —— 离线调用方手里没有可信的账号 id。

## 二、目标形态

### 2.1 收件箱 = 奖励投递的最终落点

```
                ┌─ 在线且背包放得下 ─→ 直入背包（落 reward_log）
RewardService ──┼─ 离线 ─────────────→ role_mails（channel=reward，30 天）
                └─ 在线但背包满 ─────→ role_mails（同上）
```

| 规则 | 说明 |
|---|---|
| 落邮件必带 TTL | 默认 **30 天**（已定）；BOSS 战报 7 天这类特例仍由投递方给 |
| 领邮件失败不转邮件 | 背包满 → 20012，邮件留着（现状语义，保持）—— **否则会成环** |
| 系统邮件也能带附件 | 现状即可（`send()` 支持 bindGold / exp / items） |

### 2.2 过期 30 天 + 过期前 3 天自动入包（✅ 已落，#867）

```sql
ALTER TABLE role_mails ADD COLUMN auto_claimed_at INTEGER NOT NULL DEFAULT 0;  -- 系统代领成功的时刻
ALTER TABLE role_mails ADD COLUMN auto_attempts   INTEGER NOT NULL DEFAULT 0;  -- 硬失败次数（到上限就停手）
CREATE INDEX IF NOT EXISTS idx_role_mails_auto ON role_mails(expires_at) WHERE claimed_at IS NULL;
```

`GameMailAutoClaimService`（`modules/game-mail/` 下新建，`unref()` 定时器，每小时一轮）：

| 步 | 动作 |
|---|---|
| 1 | 仓储 `listAutoClaimCandidates(now + 3d, maxAttempts, batch)`：`claimed_at IS NULL` + `expires_at <= deadline` + `auto_claimed_at = 0` + `auto_attempts < 5` + **有奖励**（`bind_gold > 0 OR exp > 0 OR attachments 非空`）+ **主人离线**（`JOIN roles / LEFT JOIN accounts`，`online_role_id` 不是这个角色），按 `expires_at, id` 升序取前 200 |
| 2 | 逐封**独立事务**：`markClaimed`（命中 0 行 → 50142 回滚，闸门语义同 #868）→ `RolesService.grantByRoleId(...)` → `markAutoClaimed` → `markRead` → `appendBody` |
| 3 | 成功 → 正文**追加**一行「［系统］附件已于 YYYY-MM-DD 自动入包（无需再点）」，不改原文 |
| 4 | 失败（背包满 20012 / 乐观锁 409 / 物品已不存在）→ **事务外** `auto_attempts + 1`，下一轮再试 |

五条口径（每条都有反证兜着，见 `server/test/e2e-mail-auto-claim.cjs` 32 条断言）：

| 口径 | 为什么 |
|---|---|
| **只对离线角色做** | 在线角色的存档在客户端手里，它随时会全量覆盖；服务端改了库 = 静默丢东西 |
| **「有奖励」看三样任一** | 只认 `attachments` 就漏掉纯绑定元宝 / 纯经验那批 —— 而它们正是 #867 要救的（反证 A：5 红） |
| **每个角色一份事务、逐封处理** | 一封失败不拖累其他封，与一键领取同一个理由 |
| **失败计数写在事务外** | 事务已回滚，写在里面会被一起抹掉 → `auto_attempts` 永远 0 → 每轮都重试同一封 |
| **跨进程互斥靠 SQL 不靠内存锁** | `GameMailModule` 同时挂在 API 与实时两个进程上，两边都会起定时器；内存锁跨进程无效，`markClaimed` 的 `WHERE claimed_at IS NULL` 才是真闸门 |

**为什么 3 天**：玩家平均上线间隔远小于 3 天；提前太早会「偷走」玩家的领取动作
（他看不到奖励动画），提前太晚会来不及重试（背包满要时间清）。五个值都在
`configuration.ts` 里（`mailAutoClaimIntervalMs` / `LeadMs` / `Batch` / `MaxAttempts` / `mailDefaultTtlMs`），
`MAIL_AUTO_CLAIM_INTERVAL_MS <= 0` 即关闭这个任务。

**没做 `auto_claim_at`（计划列）**：判据是「还剩 3 天」，由 `expires_at - lead` 现算即可；
存一列反而要在 TTL 变更 / 续期时同步维护，多一个能写错的地方。

**到上限之后**：只停手、**不删**（沿用「宁可占一行，不能替玩家扔奖励」），行留在库里但对玩家不可见（读口滤过期）。
运营要一份「卡住的补偿清单」时再加标记位 —— 暂时放置，重开条件是「出现背包长期满导致批量卡死的实例」。


### 2.3 容量上限 200 + 读口分页

| 项 | 规则 |
|---|---|
| 上限 | 每角色 **200 封**（`mail_box_capacity` 可配） |
| 满时 | 先清「已领且无附件」的最老邮件（**静默回收，玩家无感**）；仍满 → 清「已读且无附件」的最老；仍满 → **拒收新邮件**并落告警日志（`mail_overflow`） |
| 系统奖励邮件 | **永不拒收**：优先走 2.1 的「在线直入 / 离线邮件」，容量满且在线 → 直入背包；离线且满 → 写 `mail_overflow` 表按天重试 |
| 读口 | `GET /game-mails?cursor=&limit=50`（默认 50，上限 100），`cursor` 用 `created_at|id` 复合游标；频道过滤仍在**客户端本地**（现状设计，不改） |
| 角标 | `unread` / `unclaimed` 仍由服务端算（`COUNT` 查询，不拉全量） |

### 2.4 幂等键

```sql
ALTER TABLE role_mails ADD COLUMN dedupe_key TEXT;
CREATE UNIQUE INDEX idx_role_mails_dedupe ON role_mails(role_id, dedupe_key) WHERE dedupe_key IS NOT NULL;
```

| 来源 | `dedupe_key` 形状 |
|---|---|
| 活动奖励 | `act:${activityId}:${roleId}:${resetDay}` |
| 赛季结算 | `season:${seasonNo}:${rank}` |
| 运营补发 | 管理端表单填的批次号 `${batchId}:${roleId}`（不填 = 不去重） |
| BOSS 战报 | `boss:${bossKey}:${killAt}` |
| 好友申请 | `friend:${fromRoleId}:${toRoleId}:${dayNo}` |

插入冲突 → **静默返回已有那封**（不报错）。`send()` 加可选 `dedupeKey` 参数。

### 2.5 邮件索要（接 26 篇）

26 篇定了「拍卖行 / 面对面之外，玩家之间可发带附件的邮件（付费）」：

| 项 | 规则 |
|---|---|
| 入口 | `POST /game-mails/send`（玩家侧，**新增**；现在的 `send` 是内部方法） |
| 收件人 | 按**角色名**精确匹配（服务端解析 `role_id`；同名不存在 → `MAIL_TARGET_NOT_FOUND`） |
| 附件 | 只能放**未绑定**物品；**不能放货币**（C2：绑定元宝不可流通，邮件不能成为转移通道） |
| 费用 | 每封 `mail_send_fee` 绑定元宝（默认 100），落 `economy_log`（26 篇） |
| 频道 | 强制 `channel='social'`，`kind='player'` |
| TTL | 30 天；附件 30 天未领 → 2.3 的自动入包**退回发件人**（不是收件人） |
| 上限 | 每人每天最多发 20 封（防刷） |
| 拒收 | 对方拉黑你 → `blocked` |

**退回语义**：`role_mails` 加 `returned_at`；退回时新建一条发给发件人的邮件，
`kind='return'`、`dedupe_key='return:'+原mailId`。原邮件删掉（此时已无附件归属争议）。

### 2.6 站外邮件通道的边界

`mail_queue` 保持独立，职责单一：**只在「玩家可能不上游戏也必须知道」时使用** ——
封号通知、账号删除冷静期提醒（33 篇）。它不进收件箱，也不发奖励。
两套共用一个 `MAIL_CHANNELS` 之外的东西都别共享（现在也没共享）。

## 五、边界情况

| # | 情形 | 期望 |
|---|---|---|
| 1 | 自动入包时背包满 | 不删、不标记已领，`auto_attempts+1`，次日再试；最多 5 次 |
| 2 | 自动入包成功但玩家正在领取 | `markClaimed` 单条 SQL 带 `claimed_at IS NULL`，谁先命中算谁的，另一方拿到 50142（已领） |
| 3 | 玩家把带附件邮件手动删了 | 拒（50143），现状保持 |
| 4 | 邮件过期瞬间玩家正在点领取 | 读口已滤 → 404；若已取到行，`markClaimed` 照常（先到先得） |
| 5 | 容量满且新邮件是系统奖励、玩家离线 | 落 `mail_overflow` 按天重试，不静默丢弃 |
| 6 | 容量满且新邮件是系统奖励、玩家在线 | 直入背包（绕过邮件），并在 `reward_log` 记 `via='bag_direct'` |
| 7 | 玩家间邮件附件里有绑定物品 | 拒（`mail_item_bound`） |
| 8 | 玩家间邮件 30 天未领 | 附件退回发件人（新建 `return` 邮件），原邮件删 |
| 9 | 退回时发件人角色已删（33 篇冷静期到期） | 附件**丢弃并记账**（`economy_log` 记 `sink='orphan_mail'`），不再重试 |
| 10 | 群发 5000 人 | 分批入库（每批 200，事务内），失败批次可重跑（幂等键保证不双发） |
| 11 | 同一 `dedupe_key` 但内容不同（运营改了文案重发） | 返回已有那封，**不改内容**（去重优先于覆盖） |
| 12 | `expires_at` 为 NULL（永久邮件） | 永不自动入包（没有截止压力），但受容量上限约束 |
| 13 | 玩家角色被冻结/封号（33 篇） | 自动入包跳过（不往冻结角色背包塞东西），解封后补跑一次 |
| 14 | 自动入包时角色已被删（软删冷静期） | 跳过，等冷静期结束一并处理 |
| 15 | 附件物品配置被删（`itemTypeOf` 返回 null） | 该封标 `expire_blocked=1` + 告警，不半途发一半 |

## 七、验收

| 用例 | 断言 |
|---|---|
| `e2e-mail-autoclaim` | 造一封 `expires_at = now+2d` 带附件邮件 → 跑一轮 → `claimed_at` 非空、背包多出物品、`auto_claimed_at` 非空 |
| `e2e-mail-autoclaim-fail` | 背包塞满 → 跑一轮 → `claimed_at` 仍空、`auto_attempts=1`；清包后再跑 → 成功 |
| `e2e-mail-capacity` | 造 201 封已领无附件 → 再发一封 → 总数仍 200，最老那封被回收 |
| `e2e-mail-dedupe` | 同一个 `dedupe_key` 发两次 → 只有一封，返回同一 `id` |
| `e2e-mail-page` | 造 120 封 → `limit=50` 返回 50 + `cursor`；翻三页取完且不重不漏 |
| `e2e-mail-player-send` | 发一封带未绑定物品 → 扣 `mail_send_fee`；带绑定物品 → 拒 |
| `e2e-mail-return` | 玩家间邮件过期未领 → 发件人收到 `kind='return'` 邮件，附件一致 |
| `e2e-mail-offline-grant` | 角色离线 → `grantByRoleId` 成功写库，`revision` +1，`online_role_id` 不变 |

## 八、暂时放置（含重开条件）

| 项 | 现在的口径 | 重开条件 |
|---|---|---|
| 按条件群发（按等级区间 / 最后登录时间） | 管理端只支持逐个角色发 + 手动粘贴角色 id 列表 | 运营需要「给 30 天未登录的人发回归礼」时（届时接 33 篇的 `last_login_at` 索引） |
| 邮件模板（游戏内） | 标题/正文由调用的服务硬写字符串 | 出现第三处「同一套文案要在多处发」时；现在每处文案都不一样，抽模板反而绕 |
| 邮件分类自定义（玩家自建文件夹） | 固定四频道 | 频道不够用（比如加了「交易」栏）时 |
| 已领附件的历史回执 | 只在 `role_mails` 留 `claimed_at` | 需要「我什么时候领的什么」玩家侧可查时（现由 `reward_log` 支撑后台查询） |
| 站外邮件与收件箱联动（站内未读时补发邮件） | 各自独立 | 出现「玩家长期不上线导致重要通知失效」的实际事故时 |
| 邮件附件预览概率箱 | 附件是确定的物品列表 | 引入随机箱时（与 31 篇概率公示同一条规则） |

## 九、已定参数

| 项 | 结论 |
|---|---|
| 保留期 | **30 天** |
| 过期前自动入包 | **提前 3 天**尝试，入包失败才保留（最多 5 次） |
| 容量上限 | 200 封/角色（满时先回收「已领无附件」的最老） |
| 读口 | 游标分页，默认 50 / 上限 100 |
| 幂等 | 每个来源一个 `dedupe_key`，冲突返回已有那封 |
| 玩家间邮件 | 做（接 26 篇），只允许未绑定物品，收费 `mail_send_fee` |
