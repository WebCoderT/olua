## 标准版（约 160 字，放「项目经历」首段）

**olua —— 2D 角色成长与战斗游戏（三端全栈）**
独立设计并实现的一款 MMORPG 风格游戏原型，覆盖登录选角、地图探索、帧动画战斗、装备与三条成长线（战魂 / 称号 / 军衔）、掉落与背包、商城等完整玩法。采用三端架构：Cocos Creator 3.8.7 + TypeScript 客户端、NestJS 12 + SQLite 服务端（46 个 REST 接口、JWT 双受众鉴权、Swagger 文档即契约）、React 19 管理后台（按权限渲染的角色运营台）。工程上以「配置与逻辑分离 + 接口契约代码生成 + 自动化守卫」为骨架，把回归成本压缩到一条命令。

## 要点版（直接作为「项目经历」的分条内容）

**项目定位**：一款 2D MMORPG 风格的角色成长与战斗游戏原型，含客户端、服务端、管理后台三端，可完整跑通「注册 → 建角 → 打怪升级 → 穿装养成 → 后台运营」闭环。

- **三端全栈架构**：三端在仓库里平级（`client/` · `server/` · `admin/`，各有独立 README 与 FAQ）——Cocos Creator 3.8.7 + TypeScript 客户端（164 个源文件 / 约 4.9 万行，其中 3 万行为纯数据配置表）、NestJS 12 + `node:sqlite` 服务端（75 文件 / 6.5 千行）、React 19 + Vite + Tailwind v4 管理后台（27 文件 / 4.7 千行）。
- **客户端玩法系统**：Tiled 地图渲染与对象组驱动刷怪、8 方向帧动画角色与装备外观、技能/冷却/魔法消耗/状态（Buff）系统、A\* 寻路 + 自动挂机 + 自动战斗、掉落光柱与品质边框动画、背包整理/回收/拖拽、商城、小地图寻路与传送、操作摇杆与屏幕自适应。
- **数值与成长体系**：设计并落地统一的成长曲线（等级 / 怪物 / 装备 / 药品共用一张分段档位表），支撑 **11 张地图、220 只怪物、555 件装备（37 基础件 × 15 品质变体）、12 个技能**，以及战魂 37 阶 / 称号 34 阶 / 军衔 100 阶三条同构成长线；用「角色普攻要几刀砍死同级怪」反推怪物血量，保证各系统数值同涨同落。
- **服务端与接口契约**：实现 46 个 REST 接口（公共 6 / 客户端 8 / 管理端 32）、37 条路径 / 60 个模型的 OpenAPI 契约，统一响应包裹与业务码分段，JWT 双受众（玩家 / 管理员）鉴权 + 每次请求回查库（封禁 / 改密即时生效）、15 个权限点 / 3 种管理员角色的双层守卫、角色数据的乐观锁（revision）冲突自愈；并在同一批里补齐运营底座——口令重置与**令牌主动作废**（`token_version`）、登录限流（用户名 + IP 双维度）、**操作审计日志**（写接口自动留痕、敏感字段打码、CSV 导出）、后台踢下线、封禁闭环、**公告发布与全服触达**（生效时间窗 + 客户端拉取接口）、系统信息页与生产加固（启动自检 + 脱敏配置快照 + 默认密钥告警）。
- **接口契约代码生成**：以服务端 Swagger 文档为唯一契约源，自研生成器产出客户端与管理端的路径表 / 接口方法 / 实体类型；三端签名不一致会**编译报错**而非线上故障，配套五个审计脚本（生成物一致性、地址与常量硬编码、配置外泄、UI 点击穿透、部署接线）反向验证过 8 类破坏全部被拦下。
- **管理后台**：角色运营台支持六维筛选检索、批量删除、改名与基础信息编辑、运行时数据（装备 / 技能 / 背包格子）可视化编辑、管理员与权限管理、**公告发布 / 编辑 / 删除与生效状态**、**操作日志查询**、玩家口令重置与踢下线、管理员自助改密；界面按权限点渲染，服务端仍是唯一权威。
- **质量保障**：**25 套单测 + 5 套审计脚本 + 服务端 629 条 e2e（248 + 77 + 279 + 25）**，覆盖数值曲线、背包/掉落规则、存档兼容、输入穿透、弹窗层级、接口契约、权限与运营底座、公告触达、备份恢复等；为「可静态验证」而把堆排序、背包搬运、伤害结算、寻路判定等全部写成纯函数并通过沙箱单测。
- **工程规范**：所有可调项（数值、文案、布局、配色、资源路径）零散落，统一收敛进 `client/assets/configs`（46 个配置文件）；由审计脚本自动拦截「配置写进逻辑」「接口地址硬编码」两类回退。

## 难点与解法（面试被追问时用，每条都是一个可展开的技术故事）

1. **数值体系不崩**：等级、怪物、装备、成长线四条曲线如果各自为政，改一个数就会全线失衡。解法是把它们收敛到同一张分段档位表（`configs/growth`），并把「怪物血量按角色普攻几刀砍死反推」定为标定方法；新增属性（如每秒回血）只需按同一比例派生，全套来源自动同涨同落。
2. **三端契约不漂移**：手写接口类型必然随迭代腐化。解法是让服务端 OpenAPI 文档成为唯一契约源，自研生成器产出两端代码，让「签名不一致」在编译期暴露；再用审计脚本守住「不许手改生成物 / 不许硬编码地址」。
3. **存档兼容不能靠迁移脚本**：反复迭代会不断新增字段。解法是读取路径宽容 + 缺字段自动补默认（`ensureRoleDefaults`），写入路径严格（解析失败必须报错，防止空对象把玩家背包清空）。
4. **在线存档与后台改动的冲突**：玩家在线时被后台改数据，回写会覆盖新值。解法是给角色加修订号做乐观锁，冲突时**不覆盖不重试**，静默拉取服务端最新数据并提示玩家，做到「后台改动优先」。
5. **引擎级坑的定位与固化**：如打包后 `[...Map.values()]` 被降级导致背包静默清空、鼠标事件被引擎模拟成触摸事件导致重复派发、Tiled 地图裁剪造成传送黑屏等。解法是每个坑定位后立刻**写成回归脚本**，而不是靠记忆防复发。

## 关于「由 AI 编写」这一点怎么写（重要，建议先决策再投递）

项目本身是 Vibe Coding 实践（人类只提需求与验收，代码由 AI 产出），这在不同岗位上是加分或减分项，**建议按目标岗位选择口径**：

- **投「AI 工程 / AI 提效 / 全栈」方向 → 主动写**，这是核心卖点。可在项目末尾加一行：
  > 该项目以 AI 原生方式开发：我负责需求拆解、架构与契约设计、验收标准定义，AI 负责编码实现。为此专门设计了「配置与逻辑分离 + 契约代码生成 + 自动化守卫」三件套，使 AI 的每次改动都能被机器验证 —— 项目内 27 个回归脚本即由此沉淀。
- **投传统后端 / 客户端岗位 → 弱化表述**，把重心放在架构决策与质量保障上，用上一条的替换写法：
  > 主导技术选型与架构设计，建立配置与逻辑分离、接口契约代码生成、自动化回归守卫三项工程机制，将改动回归成本压缩到一条命令。
- 无论哪种口径，**面试时如实说明开发方式**并重点讲「你做了哪些决策、如何验证正确性」（上文「难点与解法」五条就是最好的弹药）—— 这比声称每行手写更经得起追问。
