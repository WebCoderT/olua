# 35 · 管理端与运营工具设计

> **状态**：设计稿，未实现。[21 总表](./21-系统差距总表.md) 判定「扩写 · P2」。
> 依赖：[34 配置与热更新](./34-配置与热更新设计.md)（发布/回滚页）、[33 存档与账号](./33-存档与账号设计.md)（销号与登录记录）。
>
> **一句话**：管理端**功能不缺**（50 个页面 / 23 个权限点 / 823 条审计），
> 缺的是**组织方式**：导航平铺、没有分区权限、批量操作各写一套、
> 危险动作没有分级。本篇补的是「运营一天要用十次的东西」的形态。

## 零、现状（实测）

| 项 | 现状 |
|---|---|
| 页面 | `admin/src/pages/` **50 个 tsx** |
| 权限点 | **23 个**（`common/constants/permission.ts`，唯一来源） |
| 角色 | `SUPER` / `ADMIN` / `VIEWER` 三档（`ROLE_PERMISSIONS` 决定谁有什么） |
| 文档化 | `@ApiAdminDoc({ permissions })` 装饰器 → 文档自动反查角色，不会漂移 |
| 审计 | `audit_logs` 823 行（`actor` / `action` / `target` / `ip` / `method` / `path` / `status_code` / `detail`），有拦截器统一记 |
| 已有能力 | 账号封禁/解封/批量、角色改属性、踢下线、重置密码、公告、邮件（站外 + 游戏内）、排行赛?（否）、地图监控、怪物 AI 事件流、掉落表、装备/技能/任务/商城/音效/特效/引导… |
| 分区 | **无**（`zone_id` 只在 `accounts` 上，管理端不分） |

### 0.1 值得保留的三条纪律（别推翻）

1. **权限点唯一来源**在 `permission.ts`，不在业务里写角色判断；
2. **敏感权限必须单列**：`account:password`（接管账号）与 `account:email`（个人信息）都不并进读权限；
3. **文档由装饰器反查**，不手写「所需权限」。

## 一、五个问题

### 1.1 50 个页面平铺，找东西靠记忆

侧边栏没有分组的话，第 51 个页面加进来就彻底找不到。
新来的运营要花一周才能记住「掉落表在哪儿」「音效在哪儿」。

### 1.2 没有分区权限

`accounts.zone_id` 已经存在，但管理端**完全不看**。分片上线后（28 篇），
一个区的客服能看到并操作**所有区**的玩家 —— 这是权限模型的洞，不是体验问题。

### 1.3 批量操作各写一套

现在有的批量（账号批量封禁/解封）是一套；将来「批量发奖」「批量补发邮件」
「批量改配置」会各写一套。共同的问题每次都重新回答一遍：

- 怎么预览「这次会影响谁」？
- 部分失败怎么办（继续还是中止）？
- 操作完给谁看结果？

### 1.4 危险操作没有分级

「删角色」「重置密码」「回滚配置」「清空掉落」与「改个文案」在界面上长得一样 ——
都是按钮 + 可能一个 `confirm()`。误点的成本差了几个数量级。

### 1.5 审计只到 HTTP 层

`audit_logs` 记的是 `PUT /admin/roles/xxx` + `detail`（通常是一段 JSON 字符串）。
想回答「谁把这家伙的绑定元宝改成了 10 万」需要人肉读 detail。
**业务语义没有结构化**：改了哪个字段、从多少到多少。

## 二、目标形态

### 2.1 导航信息架构：五组

| 组 | 页面（现有 + 新增） |
|---|---|
| **玩家** | 账号、角色、登录记录（新）、封禁、注销申请（新） |
| **内容** | 装备、技能、状态、怪物、NPC、地图、任务链（新）、活动（新）、掉落、商城、音效、特效、引导 |
| **经济** | 货币道具、价格、流水（新）、对账（新）、交易订单（新） |
| **运营** | 公告、邮件、补偿（新）、批量任务（新）、排行榜、赛季（新） |
| **系统** | 管理员、权限、审计、配置历史（新）、系统信息、地图监控 |

**规则**：新增页面必须挂进这五组之一（导航配置里没挂 = 页面存在但入口缺失，
用一条前端单测断言「pages 目录下每个文件都在导航里出现过」）。

### 2.2 管理员绑区（已定）

```sql
CREATE TABLE admin_zones (
  admin_id TEXT NOT NULL,
  zone_id  INTEGER NOT NULL,
  PRIMARY KEY (admin_id, zone_id)
);
```

| 规则 | 说明 |
|---|---|
| 绑定 | 一个管理员可绑**多个**区；`SUPER` **不受限**（不需要绑，见全部） |
| 生效点 | **守卫层统一注入**：`ZoneScopeGuard` 从令牌拿 `admin.zones`，写进 `RequestContext`；所有列表查询与写操作自动 `WHERE zone_id IN (...)` |
| 越权 | 访问范围外的资源 → **404 而不是 403**（不泄露「这个 id 存在」） |
| 未绑 | `ADMIN` 角色未绑任何区 → 视为「未配置」，登录后提示且只看得到空列表（**fail-closed**） |
| 写入 | 新建账号/角色时 `zone_id` 强制取当前区上下文，不接受前端传 |
| 审计 | `audit_logs` 加 `zone_id` 列，便于「按区查谁干了什么」 |

**为什么在守卫层而不是每个 service**：50 个页面、几十个 service，
逐个加 `zone_id` 一定会漏；漏一个就是越权。守卫层是唯一收口点。

### 2.3 批量操作统一模型

```sql
CREATE TABLE batch_jobs (
  id          TEXT PRIMARY KEY,
  kind        TEXT NOT NULL,              -- account_ban / game_mail / reward / config_patch
  zone_id     INTEGER NOT NULL DEFAULT 1,
  selector    TEXT NOT NULL,              -- 选择条件 JSON（角色 id 列表 / 等级区间 / 最后登录…）
  payload     TEXT NOT NULL,              -- 要做什么
  total       INTEGER NOT NULL DEFAULT 0,
  done        INTEGER NOT NULL DEFAULT 0,
  failed      INTEGER NOT NULL DEFAULT 0,
  status      TEXT NOT NULL DEFAULT 'pending', -- pending / running / done / aborted
  preview     TEXT NOT NULL DEFAULT '{}',      -- 预览结果（影响多少行 + 前 20 个样本）
  created_by  TEXT NOT NULL DEFAULT '',
  created_at  INTEGER NOT NULL,
  finished_at INTEGER
);
```

| 阶段 | 规则 |
|---|---|
| ① 预览 | 必做。算出「将影响 N 个对象」+ 前 20 个样本，落 `preview`。**N 太大（> 5000）需要二次确认** |
| ② 执行 | 分批（每批 200，独立事务）；**部分失败不中止**，逐条记失败原因 |
| ③ 幂等 | 每批用 `dedupe_key`（32 篇）或 `reward_log`（31 篇）兜；重跑同一 job 不双发 |
| ④ 结果 | `done` / `failed` 明细可导出 CSV |
| ⑤ 中止 | `status='aborted'`，已做的**不回滚**（明确写进 UI：中止不是撤销） |

**四种 kind 共用一套**：`selector` 决定「选谁」，`payload` 决定「做什么」，
执行器按 kind 分派。这样「批量发奖」与「批量封号」的预览/分批/中止/导出是同一份代码。

### 2.4 运营要一天用十次的六个工具

| 工具 | 对应缺口 | 落点 |
|---|---|---|
| 补发（单发） | 已有（`sendFromAdmin`） | 玩家页 → 操作 |
| **补偿（按条件批量）** | 无 | 运营组 → 补偿（走 `batch_jobs`） |
| **踢下线 + 清冷却** | 踢有、清冷却无 | 玩家页 → 操作（22 篇冷却上服务端后必需） |
| **封号/解封（带原因模板）** | 有，无模板 | 玩家页 |
| **配置回滚** | 无 | 34 篇 |
| **活动/赛季开关** | 无 | 31 篇 |

「清冷却」看起来小，但它决定了一次误封/一次卡技能 **要不要重启进程**。

### 2.5 危险操作分级

| 级 | 判定 | 界面要求 | 例子 |
|---|---|---|---|
| L0 只读 | 不改状态 | 无需确认 | 查列表 / 看详情 |
| L1 可逆 | 改数值、可改回 | 无需确认，记审计 | 改等级 / 改价格 |
| L2 有损失 | 影响玩家资产或在线状态 | **二次确认 + 显示影响面** | 踢下线 / 删邮件 / 批量发奖 |
| L3 不可逆 | 删数据 / 接管账号 / 回滚全量配置 | **输入对象名确认 + 记 `audit_logs(kind='dangerous')`** | 删角色 / 重置密码 / 恢复配置层 |

**判定写在装饰器上**：`@AdminAction({ level: "L3", confirm: "role.name" })` ——
前端据此渲染确认框，**不靠每个页面自己实现**。L3 全部汇总进「危险操作」看板，便于事后复盘。

### 2.6 审计结构化

`audit_logs.detail` 现在是一段 JSON 字符串。加一列结构化变更：

```sql
ALTER TABLE audit_logs ADD COLUMN changes TEXT;  -- [{"field":"bindGold","from":100,"to":100000}]
```

| 来源 | 怎么填 |
|---|---|
| 角色属性改动 | 现有 `role:write` 路径已知改哪些字段 → 直接填 |
| 配置改动 | 34 篇的 diff 结果 |
| 批量任务 | `batch_jobs.preview` 的统计 |

**保留期**：现状可配（#176）。目标：`audit_logs` 留 **180 天**，`changes` 超 4KB 截断并标 `truncated=1`。

## 三、协议与接口

| 接口 | 说明 |
|---|---|
| `GET /admin/zones` | **新增**：当前管理员可见的区 |
| `POST /admin/admins/:id/zones` | **新增**：绑区（`SUPER` 专属） |
| `POST /admin/batch/preview` | **新增**：`{kind, selector, payload}` → 影响面 + 样本 |
| `POST /admin/batch` | **新增**：提交执行（要求带 `previewToken`，防「预览的和执行的不是一批」） |
| `GET /admin/batch/:id` | **新增**：进度与失败明细 |
| `POST /admin/batch/:id/abort` | **新增**：中止 |
| `POST /admin/roles/:id/clear-cooldown` | **新增**：清冷却（22 篇落地后） |
| `GET /admin/audit/dangerous` | **新增**：L3 操作汇总 |

**`previewToken`**：预览时生成一个短期令牌（5 分钟有效），执行时必须带。
没有它，「预览 3 个人、执行 3000 人」这种错配无法防。

## 五、边界情况

| # | 情形 | 期望 |
|---|---|---|
| 1 | 管理员绑了两个区，操作第三个区的角色 | 404（不泄露存在） |
| 2 | `SUPER` 未绑区 | 看全部（不受 `ZoneScopeGuard` 限制） |
| 3 | `ADMIN` 未绑区 | fail-closed：列表空 + 顶部提示「未配置分区」 |
| 4 | 绑区改小（从 2 个区改成 1 个） | 存量数据不动；新查询立刻只见剩下的区 |
| 5 | 批量任务跑到一半服务重启 | `status='running'` 残留 → 启动时扫一次标 `aborted`，**不自动续跑**（续跑语义含糊，交人工决定） |
| 6 | 批量任务里某个对象已被删 | 计入 `failed`，原因 `target_not_found`，不中止整批 |
| 7 | 预览后 10 分钟才点执行 | `previewToken` 过期 → 拒，要求重新预览 |
| 8 | L3 操作确认框输入的名字有空格/全角 | 服务端 `trim()` 后比较；不一致即拒（前端只管渲染） |
| 9 | 审计 `changes` 里含密码 | **必须脱敏**：`password` / `token` / `secret` 字段一律写 `***` |
| 10 | 同一管理员两个标签页同时提交批量 | 两个 job，各自执行（不做互斥）；重复发奖靠幂等键兜 |
| 11 | 批量发奖 5000 人、每人 100 件物品 | 分批 200 → 25 批；每批独立事务，失败批可单批重跑 |
| 12 | 分区后跨区转账/交易（26 篇） | 拒（`zone_mismatch`）；交易只允许同区 |
| 13 | 导航单测误伤（页面是子组件不是路由页） | 用 `pages/**/Page.tsx` 命名约定区分，只检查 `*Page.tsx` |

## 七、验收

| 用例 | 断言 |
|---|---|
| `e2e-admin-zone-scope` | 绑区 A 的管理员查区 B 的角色 → 404；列表里不含区 B 的行 |
| `e2e-admin-zone-failclosed` | `ADMIN` 未绑区 → 列表空 + `unbound` 标记 |
| `e2e-admin-zone-super` | `SUPER` 未绑区 → 能看到全部区 |
| `e2e-batch-preview-token` | 不带 `previewToken` 执行 → 拒；伪 token → 拒 |
| `e2e-batch-partial` | 100 个对象里 3 个不存在 → `done=97`/`failed=3`，job 仍 `done` |

## 八、暂时放置（含重开条件）

| 项 | 现在的口径 | 重开条件 |
|---|---|---|
| 双人审批（L3 需另一人确认） | 只有单人 + 输入确认 | 出现一次真实的误操作事故，或团队超过 3 人 |
| 管理端操作回放（按时间轴看法） | 只有列表与筛选 | 排查「某玩家数值为什么变成这样」成为经常性工作时 |
| 客服工单系统 | 无（靠群聊） | 付费玩家规模上来、工单量 > 20/天时 |
| 玩家侧举报的处置工作台 | 有 `role_reports` 表，管理端只读列表 | 30 篇的禁言上线后（届时需要「举报 → 处置」闭环） |
| 移动端管理界面 | 桌面 Web only | 运营需要随时封号时（先做「应急封号」单页） |
| 数据导出（角色/流水 CSV） | 部分页面支持 | 26 篇对账上线后（财务要月报时） |
