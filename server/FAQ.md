## 启动与运行

### 服务端怎么跑起来？接口文档在哪？

- **启动**：`cd server && npm install && cp .env.example .env && npm run dev`（`npm run start` 跑已构建产物）。默认监听 `3100`、路由前缀 `api`，客户端默认连的就是 `http://localhost:3100/api`
- **接口文档**：<http://localhost:3100/api-docs>（Swagger UI；JSON 在 `/api-docs-json`）。文档**不带路由前缀**，因为它不是业务接口。所有接口都是「统一响应包裹 + 统一错误出口」，所以文档里每个接口的响应都是 `code / message / data / timestamp` 五件套，`data` 才是业务数据
- **数据库**：SQLite（Node 22 内置 `node:sqlite`，**不需要任何原生模块**），默认 `server/data/olua.db`，首次启动自动建 `accounts / roles / admins / audit_logs` 四张表。删账号由外键 `ON DELETE CASCADE` 级联删掉它的全部角色
- **回归**：`cd server && npm run test:e2e` —— 真实起服务进程 + 真实 HTTP 请求，**187 条断言**（注册登录 / 角色 CRUD 与上限重名 / 保存与切换在线 / 越权与令牌受众隔离 / 管理端全流程 / **文档三组分类与每个接口的权限标注** / **只读观察员越权被拒** / **超管保护**）。角色相关改动另跑 `npm run test:e2e:roles`（77 条）；口令 / 审计 / 限流 / 踢下线相关改动另跑 `npm run test:e2e:guard`（91 条）。一条命令全验：`npm run verify`
- **新增接口的规矩**：只改服务端（控制器 + DTO + `operationId`），然后 `npm run gen:api` 重新生成两端的接口文件 —— 见 [../FAQ.md](../FAQ.md#接口文件路径--类型--方法为什么是生成的想加一个接口改哪)。路径、方法名、类型都不允许在两端手写

### 跑测试时一直「等待服务启动超时」，也不打日志，为什么？

**某些终端 / IDE 会注入 `NODE_OPTIONS`（通常塞一个 `--require` 垫片）**。服务端是以子进程方式启动的，继承到这个环境变量后会**不打印任何日志、也不监听端口**地静默起不来，e2e 就停在「等待服务启动超时」上 —— 看起来像端口占用或代码问题，其实都不是。

```bash
env -u NODE_OPTIONS npm run dev
env -u NODE_OPTIONS npm run verify
```

同类环境坑：本机 `curl 127.0.0.1` 可能被代理环境变量打成 502（假故障），加 `--noproxy '*'` 即可。

## 接口与文档

### 接口文档是怎么分组的？为什么每个管理端接口都写着「所需权限」？

- **三个分组 = 三种调用者**，顺序就是权限层级：
  1. **公共接口** —— 无需令牌：`/health`、玩家注册登录、管理员登录注册（共 5 个）
  2. **客户端** —— 需要 `player` 令牌，只能操作自己账号的数据（共 8 个）
  3. **管理端** —— 需要 `admin` 令牌，且每个接口还要求权限点（共 22 个）
- **分组是按「单个接口」标的，不是按控制器**：认证控制器里 `register/login` 属于「公共接口」、`me` 属于「客户端」，一个类里两种分组都有。所以控制器类上不写 `@ApiTags`，统一用 `common/decorators/api-doc.decorator` 里的组合装饰器（`ApiPublicDoc / ApiPlayerDoc / ApiAdminDoc`）—— 分组、令牌锁图标、权限说明一次到位
- **踩过的坑**：Nest 的 Swagger 有一个「没有类级 tag 就自动拿控制器类名当分组」的默认行为（`autoTagControllers`，默认开），于是文档里每个接口除了自己的分组还会多挂一个 `Health` / `Auth` / `AdminRoles` 之类的类名分组。已在 `main.ts` 的 `createDocument(..., { autoTagControllers: false })` 关掉；e2e 里钉了「每个接口恰好属于一个分组」的断言
- **「所需权限」不是手写的**：`ApiAdminDoc({ permissions })` 里传的权限点会①变成运行时校验（守卫真读这份元数据）②由 `ROLE_PERMISSIONS` 反查「哪些角色拥有」写进文档说明 ③以 `x-olua-permissions` 扩展挂在操作上（给机器读）。三者同源，不会出现「文档写了但没拦」或「拦了但文档没写」
- 新增接口时顺手做的事：加权限点 → 在控制器上 `@ApiAdminDoc({ permissions: [Permission.XXX] })` → 决定哪些角色拥有（只改 `ROLE_PERMISSIONS`）→ 跑 e2e

### 管理员有几种角色？权限点在哪加？权限不够会怎样？

- **三级角色**（`server/src/common/constants/permission.ts` 是唯一来源）：

| 角色 | 权限 |
| --- | --- |
| 超级管理员 `super_admin` | 全部权限（含「管理管理员」与「重置管理员密码」） |
| 管理员 `admin` | 除「管理管理员」外全部 —— 管理员之间不能互相提权 |
| 只读观察员 `viewer` | 只能看：概览 / 账号列表与详情 / 角色列表与详情（**看不到操作日志**） |

- **权限点**（12 个）：`stats:read`、`account:read`、`account:status`、`account:password`、`account:delete`、`role:read`、`role:write`、`role:select`、`role:delete`、`admin:read`、`admin:manage`、`audit:read`。**加权限点只改 `ROLE_PERMISSIONS` 那张表**，不要在业务代码里写 `if (role === "admin")`
- `account:password`（重置玩家口令）单独成点、不并进 `account:status`：这是能**接管他人账号**的操作，敏感度高于封禁，值得让「谁能做」单独可调
- **注册时怎么定角色**：**第一个**注册的管理员自动是超级管理员（否则没人能管管理员），之后一律普通管理员，提权由超管在管理端的「管理员」页改。存量库由 `ensureSuperAdmin()` 兜底
- **权限不够会怎样**：`403` + 业务码 **30006**，提示会直接写出缺哪个权限（如「当前角色没有该操作权限：封禁 / 解封账号」）。管理端界面会**按权限点隐藏菜单与禁用按钮**，但那只是体验 —— 服务端每次请求都重新判一次，改地址栏硬闯也只有 403
- **改完立即生效**：守卫每次请求都从库里取管理员的角色（和账号封禁同一套逻辑），降权后旧的令牌下一次请求就受限，不用等令牌过期
- **两道保护（业务码 30007）**：不能把**最后一个启用中的超级管理员**降级 / 停用 / 删除 —— 否则后台就没人能管了。有第二个超管时自降是允许的（可以用来轮值）
- 回归：`cd server && npm run test:e2e` 的第七段（只读观察员四处写操作被拒、降权即时生效、超管保护、管理员列表与筛选）；角色相关改动另跑 `npm run test:e2e:roles`（77 条）；口令 / 审计 / 限流 / 踢下线相关改动另跑 `npm run test:e2e:guard`（91 条）

## 数据模型

### 服务端为什么不校验角色数据的内容？

- **角色数据是「不透明文档」**：背包 / 装备 / 技能 / 快捷键 / 新手物品全部由客户端 `configs/role` 这套配置驱动生成，服务端**不复制**游戏配置（复制必然漂移：改了配置忘了改服务端，就会出现「客户端有的东西服务端说非法」）。所以服务端只校验结构、归属、数量上限与重名，内容原样存
- **代价与代价的兜底**：服务端只把索引字段（id / name / occupation / sex / level）另存成独立列 —— 列表查询因此不用解析 JSON。改客户端配置**不需要**同步改服务端
- **改存档格式时注意**：`roles.data` 存的是 JSON **字符串**。读取路径用容错解析（坏数据当空对象），**编辑路径必须严格解析且解析失败直接报错** —— 绝不能用「空对象」兜底去写，那会把玩家的背包/装备清空（这是踩过的坑，e2e 里钉了断言）
- **上限在哪调**：见下一条

### 角色数量上限想改，改哪边？

- **权威在服务端**：`server/.env` 的 `ROLE_MAX_PER_ACCOUNT`（默认 3），创建时由服务端拒绝超限请求
- **客户端也有一份**：`client/assets/configs/role.maxRoleCount` —— 它做两件事：创建前先拦一道省一次往返、以及和选角界面的站位数量对齐（`configs/layout/scenes.roleSelectorLayout.rolePositions` 只有几个站位，超出的角色界面上没地方放）
- **两边要一起改**，否则会出现「服务端说有 5 个位置但界面只画 3 个」

## 口令与安全

### 玩家忘记密码怎么办？重置之后他为什么被踢出去了？

- 客户端**没有找回流程**（没有邮箱 / 短信），只能客服在后台重置：「账号管理 → 进某个账号 → 重置密码」；「管理员」页里也能重置其他管理员的（`admin:manage`，超级管理员专属）
- 口令由**前端生成**（10 位，刻意去掉了 `0/O`、`1/l/I` 这类念给玩家容易听错的字符）、**只显示一次**：服务端只存 scrypt 哈希，关掉弹窗就再也查不到，忘了只能再重置一次
- 重置后**此前签发的令牌全部作废**。做法是两表各加一列 `token_version`：签发令牌时把它写进载荷（`ver`），`AuthGuard` 每次请求回查库比对，对不上就返回 `401` + 业务码 **40103** —— 无状态 JWT 光改口令是踢不掉旧令牌的，这就是补上的那一环
- **改自己的密码走管理端的「我的账号」页**，不走上面的「重置密码」：那边要验证原密码，成功后服务端**下发新令牌**（旧令牌已作废），前端把它覆盖到本地会话 —— 否则管理员改完自己的密码会立刻被自己踢回登录页。同理，管理员列表里的「重置密码」对自己那一行是禁用的
- 改密与版本号自增写在**同一条 SQL** 里（避免「口令改了但版本号没加」的半截状态，并发下也不会丢自增）；存量库由启动时的 `ensureColumn` 补列、默认 `0`，旧令牌没有 `ver` 字段按 `0` 处理 —— 向后兼容，不需要清库
- 管理端的两个入口怎么分，见 [../admin/FAQ.md](../admin/FAQ.md)

### 一直被锁在登录页？登录限流是怎么算的？

- 两个维度分别计数，任一超限即锁：**用户名**（`LOGIN_MAX_FAILURES` / `LOGIN_LOCK_MS`，默认 5 次 / 10 分钟）与**来源 IP**（`LOGIN_IP_MAX_FAILURES` / `LOGIN_IP_LOCK_MS`，默认 20 次 / 10 分钟）。玩家端与管理端共用同一套
- 达阈值时**计数归零**（锁定期满从 0 重新计）—— 把一个「误锁之后一错再错」的体验问题，换成「爆破速率上限 = 阈值 ÷ 锁定时间」
- 判定是**纯函数**（`common/utils/rate-limit.util.ts`：`afterFailure` / `lockedForMs` / `remainingAttempts` / `describeWait`…），计数只放内存（这是短命速率状态，落库只会带来写放大和垃圾；代价是进程重启归零，单实例 SQLite 可接受，将来换 Redis 接口形状不变）。`maxFailures <= 0` = 关闭该维度 —— e2e 正是靠它把 IP 维度放宽到 1000，才能单独验用户名维度
- **用户名去空格 + 转小写后再计数**，换个大小写绕不开限流
- **反代的坑**：`TRUST_PROXY=false`（默认，直连）时 `request.ip` 是真实来源；放在 Nginx / 云负载均衡后面**必须**设 `true`，否则所有玩家共用一个代理 IP、会被一起锁死。反过来，直接暴露时开着它，就允许伪造 `X-Forwarded-For` 绕过限流。两种场景已在 `server/.env.example` 注释里写明。注：`app.set('trust proxy', ...)` 只有 Express 适配器有，所以 `NestFactory.create<NestExpressApplication>` 是必需的
- **客户端被锁了会看到什么**：业务码 `10005`（玩家）/ `30009`（管理员），提示里带还要等多久。客户端的 `ApiCodes` 里有对应文案 key

### 后台「踢下线」到底做了什么？为什么玩家非得重选角色？

- 后台只做一件事：清掉账号的 `online_role_id`。但**光清标记是拦不住人的** —— 玩家本地还在跑，1.5 秒后照样把存档推上来
- 所以服务端在存档写入路径上补了一道：**推上来的角色必须仍是账号当前的在线角色**，否则 `409` + 业务码 **20007**（`ROLE_KICKED`）。这个判定放在乐观锁**之前** —— 被踢的玩家该看到「回选角」，而不是反复重试「版本冲突」
- 客户端收到 20007 后：飘字「你的角色已被管理员下线，请重新选择角色进入游戏」→ **只清本地的在线标记**（`StorageManager.clearOnlineRole`）→ 回选角场景。**绝不能像 20002（角色已删除）那样删本地角色**：角色还在，删了就真没了 —— `client/tools/test-client-net.cjs` 特意钉了「这段处理里不许出现 `deleteRole`」
- 重选一次即可继续：选角会调 `POST /roles/:id/select` 把 `online_role_id` 重新写上，顺便拿到服务端最新数据
- 副作用（可接受）：玩家手动切过角色后，旧角色的存档就推不回来了。游戏里一个账号同时只跑一个角色，所以没做多角色并发
- 管理端那一侧的入口与限制见 [../admin/FAQ.md](../admin/FAQ.md#后台踢下线到底做了什么为什么玩家非得重选角色)

### 后台点了按钮，去哪儿看「谁改了什么」？

- **管理端写接口自动留痕**（`common/interceptors/audit.interceptor`）：只看 `POST/PUT/PATCH/DELETE`，跳过 `@Public()` 与玩家令牌。**读接口不记** —— 否则翻一页列表就能把日志刷满
- **动作就是接口标识**：`@ApiAdminDoc({ operationId })` 里顺带 `SetMetadata(AUDIT_ACTION_KEY, operationId)`，于是「文档里的接口标识」与「日志里的 action」永远是同一个字符串，**新增接口零额外工作**。中文名只是管理端 `api/types.ts` 里的一张展示字典（没登记的原样显示标识符），筛选下拉的动作清单从 `/admin/audit-logs/actions` 拉，界面不写死
- **登录成功与失败都记**（`AuditService.recordLoginAttempt`）：那时还没有「已认证的操作人」，所以操作人留空、把尝试的账号名放进 `detail` —— 这恰恰是最需要留痕的事件（谁在什么时候从哪里猛试哪个号）
- **敏感字段递归打码**：字段名命中 `/pass(word)?|secret|token|registercode|credential/i` 就把值换成 `***`。宁可多打 —— 审计日志是事后必看的东西，口令泄漏一次就是明文躺在库里
- **绝不影响主流程**：`record()` 内部吞掉一切异常（日志表写不进去，也不该让一次封号操作失败）；超过 `AUDIT_LOG_MAX_ROWS`（默认 2 万行）时每写 200 条顺手清一次最旧的
- 目标的**当前**名字用相关子查询取（一张表打三种目标，JOIN 要写三段 UNION），目标已删就显示「（已删除）」+ id（日志行里存的是 id，不会因为改名而失真）
- 查询的 `keyword` 模糊匹配**操作人账号名 / 动作 / 目标 id / 请求路径**四项，`%` 与 `_` 都按字面量处理（否则玩家名里的下划线会变成单字符通配符，静默多查出东西）
- 只读观察员看不到这一页：`audit:read` 不在它的三个读权限里 —— 它的定位是看数据，不是查人
- 管理端的查询界面（筛选项 / 展开详情）见 [../admin/README.md](../admin/README.md)
